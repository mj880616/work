# /게시반영

입력:

$ARGUMENTS

규칙은 `AGENTS.md`(보안·작업 흐름·보고)와 `docs/sec-publication-auto-merge.md`(허용 목록·관문·자동 merge)를 따른다. 여기에는 이 명령의 순서만 적는다.

## 0. 모드와 세션

- 입력에 "연습"이 있으면 **연습 모드**다. 브랜치·커밋·push·PR을 만들지 않는다. 1~3단계만 하고 아래 "연습 모드 끝내기"로 간다.
- 실제 게시는 `gh`가 동작하는 세션에서만 한다(`gh auth status`). 안 되면 파일만 만들어 보여 주고 중단·보고한다.

## 1. 입력 분류

- 새 성명·보도자료·취재요청 → **press/ 새 글**. 종류는 `statement`(성명)·`release`(보도자료)·`request`(취재요청) 중 하나다.
- 기존 Web1 페이지의 내용 추가·수정(예: 민자철도 사업현황에 영상 추가) → **기존 페이지 갱신**. 대상 파일을 찾아 사용자에게 경로를 보여 준다.
- 어느 쪽인지, 또는 어떤 페이지인지 판단이 안 되면 **한 번** 묻는다.

## 2. 원문 불변과 빠진 정보

- 사용자가 준 제목·본문·날짜·발신 기관·담당자 정보는 글자 그대로 쓴다. 문장·띄어쓰기·문장부호를 고치지 않는다. 문단 나눔만 `<p>`로 옮긴다.
- 오탈자로 보이는 곳은 바꾸지 않고 보고의 "원문 확인 필요"에 적는다.
- 날짜·제목·종류가 없으면 지어내지 않는다. 슬러그(영문 소문자·숫자·하이픈)는 주제에서 제안할 수 있지만, 사용자가 주지 않았으면 빠진 정보와 함께 **한 번에** 확인받는다. 연습 모드에서는 제안값으로 진행하고 보고에 적는다.

## 3. 파일 작성

### press/ 새 글

가장 최근 같은 종류의 `press/YYYY-MM-DD-slug/index.html`과 `press/archive.json`·`press/index.html`을 먼저 읽고 그 구조를 그대로 따른다.

- 디렉터리: `press/YYYY-MM-DD-slug/` (`scripts/publication-pr-policy.mjs`의 경로 규칙과 같아야 한다).
- `index.html`: 최근 글과 같은 `<head>` 구성(title·description·canonical `https://work.bokdoong.com/work/press/<디렉터리>/`·og 메타·favicon·`press-archive.css?v=1`·인라인 style), `body.press-archive-detail`, 뒤로가기 nav, `header.head`(tag·h1·meta `YYYY. M. D. · 발신`), `article.article`. 업로드 입력(`type="file"`)은 넣지 않는다.
- 첨부: 사용자가 PC 경로를 주면 `.hwp`·`.hwpx`·`.pdf`만 같은 디렉터리에 원래 파일 이름으로 복사하고, 최근 글처럼 `.attachment` 안에 `download` 링크를 둔다. 다른 확장자는 넣지 않고 묻는다.
- `press/archive.json`: `items` 맨 앞(날짜 내림차순 위치)에 `year`·`date`·`display_date`(`MM.DD`)·`type`·`type_label`·`title`·`publisher`·`href`(`./<디렉터리>/`) 항목을 추가한다.
- `press/index.html`: 해당 연도 `.list`의 날짜 순서 위치에 `<a class="item" data-type="…" href="./<디렉터리>/">` 한 줄을 기존 줄과 같은 모양(`date`·`tag <종류>`·`h3` 제목·`org`)으로 넣는다. 제목은 archive.json과 같게 한다.
- 테스트·CSS·문서·원장(`docs/roadmap.md`)은 고치지 않는다. 게시 내용 PR은 원장 갱신 예외다. 테스트를 고쳐야 통과한다면 멈추고 보고한다.

### 기존 페이지 갱신

- 요청한 부분만 바꾼다. 페이지의 기존 구조·스타일을 따르고 다른 곳은 손대지 않는다.
- 그 페이지를 `?v=`로 불러오는 로더가 있으면 `AGENTS.md`의 캐시 버전 규칙을 따른다.

### 로컬 확인 (두 경우 모두)

- `node --test scripts/publication-content.test.mjs`
- 링크한 첨부 파일이 디렉터리에 실제로 있는지 확인한다(위 테스트는 첨부 존재를 보지 않는다). 복사가 안 됐으면 게시하지 않고 묻는다.
- 변경 경로 분류: `git -c core.quotepath=false status --porcelain`(연습) 또는 `git -c core.quotepath=false diff --name-only origin/main...HEAD`(실제)의 경로를 `scripts/publication-pr-policy.mjs`의 `classifyPublicationPaths`로 판정해 `publication`과 `outside`를 보고에 쓴다.

## 연습 모드 끝내기

- 만든 파일 목록과 diff 요약, 테스트 결과, 분류 결과를 보여 준다.
- 커밋하지 않는다. 보여 준 뒤 만든 디렉터리를 지우고 고친 파일을 `git restore`로 되돌린다. 사용자가 남기라고 하면 남긴다.

## 4. 브랜치·PR (실제 게시)

1. `git fetch origin` 후 원격 `main` 최신에서 새 브랜치 `publish/YYYY-MM-DD-slug`(갱신은 `publish/<페이지>-<날짜>`)를 만든다. 사용자의 미커밋 변경은 건드리지 않는다.
2. 이 게시에 필요한 파일만 커밋한다(`git add <경로>`; `git add -A` 금지). push하고 `gh pr create --base main`으로 PR을 연다. draft로 만들지 않는다.
3. `gh pr checks <번호> --watch`로 모든 검사가 끝날 때까지 본다.
4. 실패하면 로그를 읽고 **형식 문제만** 고쳐 새 커밋으로 다시 올린다. 원문은 고치지 않는다. 원문을 바꿔야만 통과한다면 멈추고 보고한다.

## 5. 허용 목록 파일만 바뀐 경우 (자동 게시)

`classifyPublicationPaths`가 `publication=true`일 때.

1. `Publication auto merge`의 `reserve`가 성공하고 PR에 auto-merge가 예약됐는지 본다(`gh pr view <번호> --json autoMergeRequest,state,mergedBy`).
2. 검사 통과 뒤 PR이 `MERGED`(merge 주체 `github-actions`)가 될 때까지 본다. 예약이 안 되거나 merge되지 않으면 이유(로그)를 보고하고 멈춘다.
3. 같은 실행의 `build-pages`가 성공했는지, `gh api repos/mj880616/work/pages/builds/latest`의 commit이 merge commit이고 `built`인지 확인한다.
4. 공개 주소 `https://work.bokdoong.com/work/press/<디렉터리>/`가 200이고 제목이 들어 있는지, `https://work.bokdoong.com/work/press/`에 새 `href`가 있는지 확인한다. 반영이 늦으면 몇 분 간격으로 다시 본다. 이 PC는 Git Bash `curl`이 막혀 있으므로 PowerShell `Invoke-WebRequest -UseBasicParsing`을 쓴다.

## 6. 허용 목록 밖 파일이 바뀐 경우

PR 생성과 검사 통과까지만 한다. "커맨드센터 확인 후 merge 필요"라고 보고하고 멈춘다. 같은 내용을 PR 댓글로도 남긴다.
