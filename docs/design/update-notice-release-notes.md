## 9. 누적 목록 설계 (2026-10-27 추가)

### 9.1 저장 위치: 저장소 파일, 배포와 함께 나감. DB·Edge·Worker 변경 없음

- 4장의 "PR 본문을 배포 때 API로 읽어 최근 20건만 만든다"는 **누적**에 맞지 않는다(최근 PR만 조회 가능, GitHub 장애 때 과거가 사라짐). 그래서 목록 자체를 **저장소 파일**로 두고 빌드가 그대로 배포물에 싣는다. 기기 저장소·DB는 쓰지 않는다(모든 사용자가 같은 목록을 서버 배포물에서 읽음).
- 형식: PR마다 **새 파일 1개** `app/release-notes/<날짜>-<작업이름>.json`(= 3.3 안 B′의 저장 방식). 한 파일을 모두가 고치면 PR끼리 충돌하므로(2026-10-17 결정) 파일을 나눈다. 파일 하나 = 위 4.1 절과 같은 내용 `{ "date":"2026-10-27", "pr":1314, "changes":["…"], "checks":["…"] }`.
- 빌드(`build-pages.mjs` 확장 또는 새 스크립트)가 파일들을 모아 **번호 붙여** `app/release-notes.json` 하나로 만들어 배포물에만 둔다. 앱은 이 파일 하나만 읽는다.
- 4.2의 추출·금지 모양 거르기 규칙은 PR 본문 대신 **CI가 이 파일을 검사**하는 데 그대로 쓴다. 장점: merge **전에** 형식·비밀값 모양을 막을 수 있고(안 A의 약점 해소), GitHub API·`pull-requests: read` 권한이 필요 없어 **workflow 권한 변경이 사라진다**(5장 3단계 대부분 삭제).
- 파일이 없거나 깨져도 알림·배포는 지금처럼 동작(4.4 원칙 유지). 오래된 기록은 지우지 않고 계속 쌓음(글자만이라 작음. 화면은 20건씩 끊어 보임).

### 9.2 버전명

- 앱의 실제 번호(해시 `?v=`)는 사람이 못 읽는다. 목록의 **버전명 = 날짜-그날 순번**(예: `10/27-2` = 10월 27일 두 번째). 파일 안의 날짜와 파일 이름 순서로 빌드가 계산한다. 같은 날 순서는 파일 이름의 시각(`20261027-1432-…`)으로 정한다.
- 알림의 "새 버전"과 목록의 "지금(현재 버전)" 표시는 빌드가 현재 해시 ↔ 마지막 버전명을 같이 기록해 맞춘다(`release-notes.json`에 `current` 한 줄).

### 9.3 새 버전 알림 한 줄

- 지금 줄(아이콘 + "새 버전이 있어요" + [새로고침] + ✕)을 유지. 바뀐 것이 있으면 문구만 `새 버전: <바뀐 점 첫 줄>`(한 줄 말줄임), 여러 건이면 `새 버전 · 바뀐 것 N건`.
- 눌러 펼치지 않는다(큰 카드·접힘 금지). 자세한 것은 누적 목록에서 본다. 알림 높이·위치 규칙(`--kptu-version-notice-height`)은 그대로라 CSS 변경이 거의 없다.
- 6장(알림 안에 목록·접힘·baseline)은 **불필요**해져 삭제 대상: baseline 계산 없이 "알림이 뜬 시점에 배포물의 `current`보다 새 건수"만 세면 된다.

### 9.4 누적 목록 화면

- 시안 ②. 한 줄 = 버전명 · 날짜 · 바뀐 점 첫 줄 말줄임, 누르면 펼쳐 **바뀐 점 전체 + 폰에서 볼 것**. 현재 버전 줄은 처음부터 펼침 + "지금" 꼬리표. 20건씩 [이전 기록 더 보기].
- 쓰는 기존 부품: 프로필 화면의 `.ps-*` 줄 모양, `<details>`/`summary`(접힘 규칙 AGENTS §5), 올리브 토큰. 새 색·큰 버튼·카드 없음. 글자는 `textContent`로만.

### 9.5 메뉴 위치와 쓰는 사람

- **위치**: 메뉴(폰 하단 [메뉴]) → 계정 → 내 프로필 → 맨 아래 한 줄 `업데이트 기록  10/27-2 ›`. PC는 같은 프로필 화면 맨 아래 같은 줄. 홈·하단 탭에는 두지 않음(가끔 찾는 용도).
- **쓰는 사람**: **작업 세션이 PR마다 파일 1개를 추가**한다(앱에 보이는 변화가 있는 PR만. 문서·원장·내부 정리는 안 씀). CC는 PR 검토 때 파일이 있는지·일상어인지·업무 내용이 없는지만 확인한다. CC가 merge 때 대신 쓰는 방식은 채택하지 않음: merge 뒤 main에 직접 올리는 커밋이 늘고 CC 한 곳에 병목이 생기며, 변경 내용을 가장 잘 아는 작업 세션이 쓰는 편이 정확하다.
- 규칙은 `AGENTS.md` §10(D4)에 "앱 화면이 바뀌면 `app/release-notes/`에 일상어 파일 1개, 개발 용어·이름·업무 내용 금지"로 한 줄.

## 1. 일상어 요약

- **지금**: 앱은 열 때·화면 복귀 때·10분마다 배포된 첫 화면 파일(`index.html`)의 앱 스크립트 번호(내용 해시)를 지금 실행 중인 것과 비교해, 다르면 하단에 "새 버전이 있습니다 [새로고침] [×]"만 띄운다. **무엇이 바뀌었는지는 모른다.**
- **원하는 것**: 같은 알림에 "이번에 바뀐 점"과 "폰에서 확인할 것"이 같이 보이기.
- **방법(안 A)**: 일 마친 작업자가 PR 본문 끝쪽에 정해진 절 하나를 쓴다. merge 뒤 Pages 배포 때 빌드가 최근 merge된 PR 본문에서 **그 절만** 골라 짧은 목록 파일(`release-notes.json`)을 배포물에만 만든다. 앱은 열릴 때 그 목록을 한 번 읽어 "내 화면이 아는 변경"을 기억해 두고, 새 버전 알림이 뜰 때 다시 읽어 **새로 생긴 것만** 보여 준다.
- **조심할 점 3가지**: ① 공개 저장소·공개 Pages라 목록 파일은 누구나 읽을 수 있음 → 허용한 절만, 길이 제한, 이메일·키 모양 거르기 ② 목록을 못 만들거나 못 읽어도 **배포도 알림도 그대로 동작**해야 함 ③ 글자는 `textContent`로만 넣어 화면 깨짐·악성 코드 삽입을 막음.
- **한계(솔직하게)**: 알림이 뜬 시점에 이미 merge가 여러 번 쌓였으면 여러 건이 한꺼번에 보인다. 설명을 안 쓴 PR은 안 보인다. 탭을 오래 켜 둔 상태에서 열 때 목록 읽기가 실패했으면 "최근 N건"을 보인다(오래된 것이 섞일 수 있음).

## 3. 후보 비교 (상세)

### 3.1 안 A: 배포 때 PR 본문의 지정 절 → `release-notes.json`

흐름: `main`에 push → build job이 `gh api`로 최근 닫힌 PR 목록(본문 포함)을 **1회** 조회 → 순수 함수로 지정 절만 추출·정리 → 출력 폴더에 `app/release-notes.json` 기록 → 업로드. 저장소에는 두지 않는다(AGENTS §4 캐시 버전 절이 `asset-manifest.json`을 빌드 결과물에만 두는 것과 같은 방식).

- 장점: 충돌 파일 0개, 작성은 PR 본문에 이미 쓰는 완료보고 흐름 안에서 끝남, 모든 도구(Claude Code 로컬·웹, Codex)가 같은 방식으로 씀, 목록이 저장소에 쌓이지 않음.
- 단점/위험: ① merge 전에 자동 검사 불가(→ 4장 방어 + 3단계 단위 시험으로 추출 규칙 고정) ② API 한도·권한(→ 4.4) ③ merge 뒤에 PR 본문을 고치면 다음 배포부터 반영(이미 나간 목록은 그대로) ④ 빌드가 PR 본문 형식에 의존 → 형식이 틀리면 그 PR은 조용히 "설명 없음" 처리.

### 3.2 안 B: 저장소의 설명 파일을 작업마다 수정

모든 PR이 같은 파일의 맨 위 줄을 고친다 = `docs/roadmap.md`를 PR이 못 고치게 한 2026-10-17 결정과 같은 이유로 충돌한다. 비추천.

### 3.3 안 B′: PR마다 새 파일 추가

`release-notes/2026-10-19-UI-쓰기창PC탭유지.md`처럼 파일을 추가하고, 빌드가 가장 최근 N개를 모아 JSON으로 만든다. 충돌은 없고 PR 단계에서 CI(단위 시험)가 형식·금지 모양을 검사할 수 있어 공개 노출 관점에서는 안 A보다 안전하다. 대신 ① 파일이 하루 몇 개씩 쌓임(정리 규칙·정리 PR 필요) ② 문서 전용 PR 규칙(§9)과 "관련 없는 변경 섞지 않기"에 새 파일 한 개가 늘 끼어듦 ③ 작업 이름 중복 시 파일명 충돌 가능. 안 A가 마음에 안 들 때의 차선.

### 3.4 안 C: 제목만

`docs: 원장 — …`, `[UI-하단바색] manifest background_color를 앱 바탕색으로` 같은 제목이 그대로 나오게 된다. 일상어·폰 확인 항목이 없고 내부 행 이름이 공개 목록에 섞인다. 비추천.

### 3.5 추가 후보

- **안 D: 설명을 `index.html` 안에 넣기**(빌드가 첫 화면 파일에 `<script type="application/json">` 삽입). 알림이 이미 받아 오는 `index.html` 한 번으로 번호와 설명을 같이 얻어 요청이 늘지 않고 Worker가 `.html`에 이미 보관 우회를 걸어 줌. 단점: 빌드가 HTML 해시 대상 파일을 가공해야 해 `build-pages.mjs`의 해시·`check-pages-build` 계산을 건드림(첫 화면 파일 내용이 PR 본문에 따라 바뀌어 해시 안정성이 흔들림). 위험 대비 이득이 작아 비추천.
- **안 E: 설명을 커밋 메시지 꼬리말로**. 코드 변경 없이 쓸 수 있으나 squash merge 때 메시지가 바뀌고, 도구마다 쓰는 방식이 달라 일관성이 떨어짐. 비추천.

## 4. 안 A 상세 설계

### 4.1 PR 본문 형식 (작업자가 쓰는 것)

PR 본문에 아래 절을 **정확히 이 제목**으로 한 번 쓴다(앱에 보이는 변화가 있는 PR만. 문서·원장·내부 정리·테스트만이면 쓰지 않음).

```
## 앱 업데이트 안내
- 바뀐 점: (일상어 한 줄, 최대 100자)
- 폰에서 확인: (폰에서 무엇을 눌러 보면 되는지 한 줄, 최대 100자)
```

- `바뀐 점`은 1~3줄, `폰에서 확인`은 0~3줄까지 허용(줄마다 같은 머리말 반복).
- 개발 용어(RLS, Edge, `?v=` 등)·내부 작업 이름·사람 이름·업무 내용은 쓰지 않는다는 지침을 `AGENTS.md` §10에 한 줄로 추가(D4).

### 4.2 추출 규칙 (순수 함수 `extractReleaseNote(body)`)

1. 본문 줄바꿈을 `\n`으로 통일. 제목 줄이 `## 앱 업데이트 안내`와 **정확히 같은** 첫 절만 사용(코드 펜스 안은 무시). 다음 `## ` 또는 `---` 또는 끝까지가 절 범위.
2. 절 범위에서 `- 바뀐 점:`·`- 폰에서 확인:`으로 **시작하는 줄만** 취함. 그 밖의 줄(문단, 표, 링크, 이미지, HTML)은 버림.
3. 값 정리: 마크다운 기호·링크 문법·HTML 태그·제어문자 제거, 공백 정리, 줄당 최대 100자(넘으면 잘라 `…`), 항목당 최대 3줄, PR당 최대 400자.
4. 금지 모양이 하나라도 있으면 **그 줄을 버림**(전체 PR이 아니라 줄): 이메일 모양, `http(s)://` 주소, 32자 이상 연속 영숫자·16진, `eyJ…`·`sk-`·`ghp_`·`sb_` 같은 키 머리, IPv4, 파일 경로(`/home/…`, `C:\…`), `Bearer`/`Authorization` 낱말.
5. `바뀐 점`이 하나도 안 남으면 그 PR은 목록에서 **제외**(D3).
6. 결과: `{ pr, title?:없음, mergedAt, changes:[…], checks:[…] }`. 제목·작성자·본문 원문·커밋 SHA는 **싣지 않는다**(PR 번호만 식별자).

### 4.3 `release-notes.json` 모양

```
{"schema":1,"generatedAt":"2026-10-19T07:00:00Z","commit":"<짧은 SHA>",
 "notes":[{"pr":703,"mergedAt":"…","changes":["…"],"checks":["…"]}, …최신 먼저, 최대 20개]}
```

- 위치: 빌드 출력의 `app/release-notes.json`. 저장소에는 두지 않고(`.gitignore` 불필요: 저장소 소스에 없음) 소스 트리에서 만들지 않는다.
- 해시 `?v=` 대상이 아니다(`build-pages.mjs`는 스크립트가 읽는 JSON을 버전 안 붙임: `versionable`의 `.json` 예외). 따라서 앱 코드에서 이 파일 이름 문자열이 `graph()` 참조로 잡혀도(출력에 없던 파일이면 `Object.hasOwn` 거름) 빌드가 건드리지 않음. 3단계에서 `check-loader-cache`가 "저장소에 없는 파일 참조"를 허용하는지 확인한다.
- PR 선택: `repos/{owner}/{repo}/pulls?state=closed&base=main&sort=updated&direction=desc&per_page=40` 1회 호출, `merged_at`이 있고 **이번 push 커밋 시각 이전**인 것을 `merged_at` 최신 순 20개까지. 같은 push에 여러 PR이 들어가도 포함됨. 수동 실행(`workflow_dispatch`)도 같은 로직(PR 없이 돌려도 안전).
- 조회는 `GH_TOKEN`(환경 변수, `github.token`)으로만 `gh api` 실행(AGENTS §3 토큰 취급: 값을 명령 인자에 넣지 않음).

### 4.4 빌드 실패 방지·실패 시 동작

- 새 스크립트 `scripts/build-release-notes.mjs`는 **어떤 오류에도 종료 코드 0**으로 끝나고, 실패하면 `notes: []`인 파일을 쓰거나 파일을 만들지 않는다(앱은 "파일 없음/빈 목록 = 기존 알림 그대로"). 오류는 `GITHUB_STEP_SUMMARY`에 한 줄 기록.
- 기존 `tests/security/pages-deploy-workflow.test.mjs`는 build job에 `continue-on-error`·`|| true`를 금지하므로, 이를 쓰지 않고 **스크립트 자체가 예외를 삼키는 방식**으로 한다(검사 의미를 유지).
- 단계 위치: `cloudflare-check-urls.mjs` 뒤, 업로드 앞. 해시·manifest 검사가 끝난 뒤라 서로 영향 없음. 같은 파일을 쓰는 `check-pages-build`에는 "파일이 있으면 모양 검사(스키마·길이·금지 모양)"만 추가(없으면 통과).
- 입력 크기 상한: PR당 본문 읽기 20KB까지만 파싱, API 응답 오류·타임아웃(30초)이면 포기.
- 권한: build job에 `pull-requests: read` 한 줄 추가(`contents: read`·`pages: read`는 그대로). **workflow 변경이므로 사용자 승인 필요**(5장 3단계).

### 4.5 공개 저장소·공개 배포 관점

- Web2 앱 화면은 로그인해야 열리지만, 배포 파일(`app/…`)은 GitHub Pages 공개 주소에 그대로 놓인다(익명 접속 차단은 앱 스크립트가 하는 일이라 파일 자체를 막지 못함). `release-notes.json`도 **누구나 읽는 파일**이라고 전제한다.
- PR 본문은 이미 공개 저장소에 공개돼 있지만, 본문 전체(조사 내용·운영 상황·내부 행 이름)를 배포물에 실을 이유가 없다 → **허용 절의 허용 줄만**, 제목·작성자·SHA·링크 제외.
- 실제 업무 내용(조직·인물·교섭 내용)이 설명에 섞이지 않게: 작성 지침("앱 기능 변경만, 업무 내용·이름 금지")을 AGENTS에 두고, 추출기는 4.2의 금지 모양과 길이 제한만 기계적으로 거른다(의미 판단은 못 함 → 남는 위험 7장).
- 앱의 표시는 **`textContent`·`createElement`만** 쓴다. `innerHTML`로 목록 글자를 넣지 않는다(현재 알림이 정적 문자열에 `innerHTML`을 쓰는 것과 별개로, 새 코드는 목록 글자에 절대 쓰지 않음).
- 응답 검증: `schema===1`, `notes`는 배열 최대 20개, 각 글자는 문자열·길이 상한, PR 번호는 양의 정수. 하나라도 어긋나면 그 항목(또는 전체)을 버리고 기존 알림만 보임.

## 6. 알림 UI 설계

### 6.1 보이는 모양 (D2 추천안)

```
┌────────────────────────────────────────────┐
│ 새 버전이 있습니다            [새로고침] [×] │
│ 이번에 바뀐 점                              │
│  · 쓰기 창이 PC에서 메뉴를 덮지 않아요        │
│  폰에서 확인: 메뉴 → 쓰기를 열어 보기         │
│ ▸ 이전 변경 2건 더 보기                      │
└────────────────────────────────────────────┘
```

- 최신 1건은 **항상 보임**(바뀐 점 + 폰에서 확인), 나머지는 `<details><summary>이전 변경 N건 더 보기</summary>…</details>`. 최대 표시 6건, 넘는 것은 "그 밖의 변경은 …" 문장 한 줄(링크 없음).
- 목록이 없거나 비면 지금 알림 그대로(문구도 동일).
- `role="status"` 문장은 짧게 유지("새 버전이 있습니다"). 목록 전체를 라이브 영역으로 읽히지 않게 별도 요소로 둔다(스크린리더 소음 방지).
- 높이: 이미 `ResizeObserver`가 `--kptu-version-notice-height`를 갱신하므로 토스트·[+] 버튼 위치는 따라온다. 추가 규칙: 목록 영역은 `max-height: min(40vh, 280px)` + 세로 스크롤, 줄바꿈 `overflow-wrap:anywhere`, 폭은 지금과 같은 `min(560px, 100% - 24px)`.
- 터치: `summary`는 높이 44px 이상(현재 버튼 `min-height:44px`와 맞춤), 글자 14px 이상. 색은 기존 `--kptu-*` 변수 그대로(다크/라이트 자동 대응). 새 디자인 요소·애니메이션 없음, 기존 `<details>` 패턴(AGENTS §5의 접힘 규칙)과 같게.

### 6.2 "무엇을 새 변경으로 볼 것인가" (이미 본 설명 처리)

- 번호 대조는 어렵다: 실행 중인 앱은 자기 파일 해시만 알고 어느 PR까지 포함하는지 모른다. 그래서 **baseline 방식**을 쓴다.
  1. 앱이 열린 뒤 한가할 때 `release-notes.json`을 한 번 받아 PR 번호 집합을 `known`으로 메모리에 보관(실패하면 `known=null`).
  2. 새 버전 알림이 처음 뜰 때 목록을 다시 받아, `known`에 없는 PR만 표시. `known===null`이면 최신 3건만 표시하고 "최근 변경"이라고 문구를 바꿈.
  3. 같은 배포 번호에서 한 번 받은 목록은 재사용(알림을 닫았다 다시 켜는 경우 포함).
- [×]로 닫은 배포는 지금처럼 이 탭 메모리에서 다시 안 뜸. 새로고침하면 새 앱이 새 `known`을 만들어 **같은 설명이 다시 뜨지 않음**. 그래서 브라우저 영구 저장소(`localStorage`)는 필수 아님. (AGENTS §5 "원문·작성 중 글은 영구 저장소에 두지 않음"과도 충돌 없음.) 탭을 닫았다 열어도 새 앱 로드 시 baseline이 새로 만들어지므로 동일.
- 요청 주소: `…/app/release-notes.json?d=<알림이 비교한 배포 해시>`, `fetch(…,{cache:'no-store'})`. **이유**: Worker의 보관 우회(15초 값)는 `.html`·`/`에만 붙고 `.json`은 대상이 아니어서 Pages 10분 보관본을 받을 수 있다. 배포마다 다른 값을 쿼리에 붙이면 새 배포 때 새 주소가 된다. 쿼리 이름은 `v`가 아닌 `d` 등을 쓴다(`v`는 Worker의 자산 보관 규칙과 CI의 손 쓴 `?v=` 금지 검사에 걸림; JS 소스에 `?v=` 글자를 직접 쓰지 않음). 시작 때 baseline 조회는 값 없이 `no-store`만 쓴다(조금 낡아도 baseline 용도로는 안전: 낡으면 이미 나간 변경이 "새 것"으로 한 번 더 보일 뿐).

### 6.3 접근성·모바일 점검 항목

- 키보드: `summary`는 기본으로 Enter/Space 동작. 대화상자가 열려 있을 때 Tab 순환(`accessibility-dialog.js:7`)에 `#versionNotice summary`가 빠져 있으므로 포함시켜야 한다(4단계).
- 이름: 알림 `aria-label="새 버전 안내"` 유지, 목록은 `<ul>`·`<li>`, "폰에서 확인:"은 굵은 글자 낱말이 아니라 일반 텍스트 머리말.
- 큰 글자·좁은 폭(360px)에서 가로 스크롤 없음, 세로로 길어지면 목록 영역만 스크롤.
- 입력창 포커스 중(자판이 열림) 알림이 자판 위로 커지지 않게 기존 하단 오프셋 규칙(`ui-standard.css`)을 재사용하고, 높이 상한을 둠.
