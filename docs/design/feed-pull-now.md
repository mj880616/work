## 0. 명진이 정할 것 (먼저 읽기)

**무엇이 바뀌나**: 통화·텔레그램 화면에 [최신화]를 두고, 누르면 1시간마다 도는 '보내기'(앱 스크립트)를 기다리지 않고 바로 한 번 돌려 1~3분 안에 새 줄을 보여 준다.
**잘못되면**: 앱 스크립트 하루 사용 한도를 넘겨 그날 남은 시간 동안 자동 수집 전체(매시 실행 포함)가 멈출 수 있다(가안), 또는 새로 여는 입구 주소·비밀값이 새면 남이 '수집 한 번 더'를 누를 수 있다(나안, 내용은 못 봄·못 바꿈).
**되돌리기**: 화면 버튼을 빼는 커밋 하나 + 앱 스크립트에서 새 트리거(가) 또는 웹 앱 배포(나)를 지우면 지금 그대로(매시 수집)로 돌아간다. 기존 자료는 건드리지 않는다.

## 2. 안 비교

### (가) 요청 줄 + 앱 스크립트가 짧게 확인 (끌어오기)

```
[최신화] → Web2 DB 함수(로그인 본인 + 운영자 허용 표 확인, 하루 횟수·3분 간격)
         → 요청 줄 1개(작업공간·출처·요청 시각) 표 app_feed_pull_requests
앱 스크립트 새 트리거 feedPull_check (5분마다, 한국 7~24시만 일함)
         → collector-feed ?action=pull_poll (기존 비밀값, 몸통 없음) → {telegram: true/false, call: true/false}
         → 참이면 tgFeed_runCore_ / callFeed_runCore_ 를 그 자리에서 한 번 (기존 잠금·상태 그대로)
         → 끝나면 ?action=pull_done 으로 요청 줄 닫음 + 기존 멈춤 알림
화면 → 15초마다 자기 표를 다시 읽다가(최대 6분) 새 줄이 오거나 요청 줄이 닫히면 멈춤
```

- 얼마나 빨리: 누르고 평균 2.5분·최대 5분 + 실행 시간(텔레그램 보통 1분 안쪽 [추정]). 1분마다로 하면 최대 1분이지만 아래 한도 문제가 커진다.
- 할당량 [공개 문서]: 앱 스크립트 트리거 하루 총 실행 시간 — 개인(gmail) 계정 90분, 업무용(Workspace) 6시간. URL 호출 하루 20,000번(개인)·100,000번(업무용). 실행 한 번 6분.
  - 5분 확인: 하루 17시간 × 12번 = 204번. 한 번 1초 안팎이면 하루 약 3~4분, URL 호출 204번. 저장소 기본값 `TG_FEED_FETCH_BUDGET` 15,000은 개인 계정 기준이라 [사실: setup 265행] 계정이 개인 계정일 가능성이 높다 [추정].
  - 1분 확인: 1,020번 → 하루 약 17분 + 1,020번 호출. 매시 보내기가 밀린 날(4.5분 × 이어 하기 5번)과 겹치면 90분을 넘을 수 있고, 넘으면 **그날 남은 시간 모든 트리거가 멈춘다** [공개 문서]. 그래서 (가)는 5분으로만 권한다.
- 보안: 사람 쪽 입구는 DB 함수(로그인·운영자 허용 표, 기존 규칙 그대로), 앱 스크립트 쪽은 기존 비밀값·기존 `collector-feed` 비밀 입구에 action 둘을 더하는 것(인증 경계 변화 없음). 새 비밀값·새 공개 주소 없음.
- 바꿀 것: DB migration 1개(표 1·함수 2, 짝 파일 5개, ★DB 적용 정지★) + `collector-feed` action 둘(★Edge 배포★) + 앱 스크립트 함수 1개·트리거 1개(★앱 스크립트 반영★) + 화면 두 곳.
- 실패 때 화면: 6분 안에 요청 줄이 안 닫히면 "수집 요청은 들어갔지만 아직 응답이 없어요 · 다음 매시 수집에 반영돼요" 한 줄. 요청 거절(횟수·간격)은 "n분 뒤에 다시 누를 수 있어요".

### (나) Web2가 앱 스크립트 웹 앱을 깨움 (밀어 넣기) — 권함

```
[최신화] → Edge(사용자 로그인 확인 + 서버 운영자 허용 표 확인 + 하루 횟수·3분 간격, 서버 표에 기록)
         → 앱 스크립트 웹 앱 doPost (주소·비밀값은 Supabase 비밀값에만, 몸통에 {secret, source})
         → doPost는 비밀값 고정 길이 비교 → 3분 안 중복이면 그냥 OK
         → 1회용 트리거 feedPull_run 을 '지금 바로'(after 1초)로 하나만 만들고 즉시 응답(일은 하지 않음)
feedPull_run → tgFeed_runCore_ / callFeed_runCore_ 한 번(기존 잠금·상태·멈춤 알림 그대로) → 1회용 트리거 지움
화면 → (가)와 같이 다시 읽기, 끝은 멈춤 알림(heartbeat) 받은 시각이 요청 뒤로 바뀌면
```

- 얼마나 빨리: 1회용 트리거는 보통 1분 안팎에 돈다 [추정, 앱 스크립트는 정확한 시각을 약속하지 않음] → 누르고 1~2분 + 실행 시간.
- 할당량: 누를 때만 쓴다. 하루 20번 상한이면 URL 호출 20번 + 실행 시간은 원래 매시 실행이 할 일을 앞당긴 것이라 거의 늘지 않는다(앞당긴 만큼 다음 매시 실행이 짧아짐) [추정]. 웹 앱 동시 실행 상한 30 [공개 문서] — 상관없는 크기.
- 보안:
  - 웹 앱은 '나로 실행·누구나 접근'으로 배포해야 서버가 부를 수 있다 [공개 문서]. 웹 앱은 **요청 머리글을 읽지 못하므로** 비밀값은 몸통에 넣는다 [공개 문서: doPost 이벤트에 머리글 없음]. 주소와 비밀값은 Supabase 비밀값(`COLLECTOR_PULL_URL`·`COLLECTOR_PULL_SECRET`, 이름은 제안)과 앱 스크립트 속성에만 둔다. 저장소·로그·화면에 쓰지 않는다.
  - doPost는 자료를 돌려주지 않고(늘 같은 짧은 응답) 할 수 있는 일은 '이미 정해진 수집 한 번 앞당기기'뿐이다. 주소·비밀값이 새도 내용은 못 보고 못 바꾼다. 최악은 한도 소모 → 앱 스크립트 캐시에 '마지막으로 깨운 시각'을 두고 3분 안 두 번째는 무시, 하루 30번 넘으면 무시.
  - 사람 쪽 입구: `collector-feed`는 사용자 로그인 머리글을 401로 막는 것이 경계라 [사실] 여기에 사람 입구를 더하지 않는다. 이미 소유자 로그인 입구가 있는 `drive-summary`에 action 하나(`collector_pull`)를 더하고, 서버가 service_role로 `app_operator_feature_workspace('telegram'|'calls')`가 로그인 본인 작업공간과 같을 때만 부른다(화면 숨김으로 막지 않음). 하루 횟수·간격은 서버 표(예: 기존 `app_feed_days`에 칸 추가, 또는 작은 새 표)로 센다.
- 바꿀 것: `drive-summary` action 1개(★Edge 배포★) + 횟수 세는 칸(DB migration, ★DB 적용 정지★) + 앱 스크립트 `doPost`·`feedPull_run`(★앱 스크립트 반영★, 웹 앱 배포는 손으로 한 번) + 새 비밀값 2개(대시보드) + 화면 두 곳.
- 실패 때 화면: Edge가 웹 앱 응답을 못 받으면 "수집기를 깨우지 못했어요 · 다음 매시 수집을 기다려 주세요"(바로 알 수 있음 — (가)보다 낫다). 깨웠는데 6분 안에 멈춤 알림이 안 바뀌면 (가)와 같은 한 줄.

## 3. 즉시가 안 되는 한계

## 4. 고른 뒤 차례 (줄 세우기)

(나)일 때:

1. DB PR — 하루 횟수·간격 칸(짝 파일 5개, 권한은 service_role만, anon·PUBLIC 없음, 실제 PostgreSQL 시험). ★DB 적용 정지★ → CC 승인형 workflow(시험 적용 먼저).
2. Edge PR(1 위) — `drive-summary ?action=collector_pull`: 로그인 owner + `app_operator_feature_workspace` 일치 + 횟수·간격 + 웹 앱 부르기(10초 제한, 응답 내용은 버리고 상태 코드만). 시험: 비로그인 401·다른 작업공간 403·허용 표에 없음 403·횟수 초과 429·웹 앱 실패 502·비밀값 없음 503. ★Edge 배포: drive-summary★(되돌리기 ref 기록).
3. 앱 스크립트 PR(같은 PR 가능) — `collector-feed.gs`에 `doPost`·`feedPull_run`·`feedPull_setup`(웹 앱 비밀값 속성 만들기, 값은 로그에 안 찍음). 시험은 node로 순수 함수(비밀값 비교·중복 무시·하루 상한). ★앱 스크립트 반영★ + 웹 앱 배포 안내(`collector-feed-setup.md`에 단계 추가).
4. 화면 PR(2 위) — `telegram-feed.js`·`call-feed.js` 머리 줄 ⋯ 메뉴 또는 머리 줄 작은 [최신화](운영자 작업공간만 서버 응답으로 보임), 진행·실패 한 줄, 다시 읽기는 각 화면의 기존 읽기 함수(새 그리기 주인 없음, AGENTS §5). E2E: 누름 → 요청 → 가짜 새 줄 → 화면에 보임 / 실패 한 줄. 업데이트 기록 json 1개.

(가)일 때: 1 DB(요청 표 + 사람 함수 + 서버 함수) → 2 Edge(`collector-feed` `pull_poll`·`pull_done`, 기존 비밀 입구) → 3 앱 스크립트(`feedPull_check` + 5분 트리거, 한국 7~24시만) → 4 화면(같음).

## 6. 남은 위험

- 앱 스크립트 계정 종류(개인/업무용)를 저장소에서 확인할 수 없다 [추정: 개인]. (가)를 고르면 첫 주에 실행 기록에서 하루 총 실행 시간을 CC가 확인한다.
- 1회용 트리거(`after`)가 도는 시각은 앱 스크립트가 약속하지 않는다 [공개 문서]. 늦으면 (나)도 몇 분 걸릴 수 있다 — 화면 문구는 "1~3분"으로 넉넉히.
- 잦은 [최신화]는 텔레그램 묶음을 잘게 나눠 서버 AI 부르기 횟수를 늘린다(묶음마다 한 번). 하루 20번 상한이면 기존 `collector-feed` 한 달 AI 상한(6,000원) 안이라고 본다 [추정] — 구현 PR에서 하루 사용량 칸으로 확인.
