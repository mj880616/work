## 0. 명진용 요약

**하려는 것.** 통화 메뉴는 지금처럼 업무 통화만 보여 준다. 맨 위에 작은 '개인 통화함 n'을 두고, 누르면 같은 목록·같은 상세 화면으로 개인 통화가 나온다(메뉴를 새로 만들지 않는다). 개인 통화도 요약과 전문까지 Web2에 남기고, 업무↔개인을 양쪽에서 옮길 수 있다. 개인 통화는 주간보고·원장·챙길 것·업무일지에 쓰이지 않고, 업무로 옮긴 것만 쓰인다.

**추천: 통화의 구분을 '출처 값' 자체에 둔다.** 지금 통화 줄의 출처는 `call`이다. 여기에 `call_personal`(개인), `call_unsure`(애매)를 더한다. 업무 기록을 만드는 쪽(원장 자동 기록 등)은 전부 "출처가 `call`인 것"만 읽기 때문에 **코드를 하나도 안 고쳐도 개인·애매는 자동으로 빠진다.** 앞으로 새 읽는 곳이 생겨도 같은 방식이면 섞일 수 없다. "개인인지 표시하는 칸"을 따로 두는 방식은 읽는 쪽이 필터를 하나라도 잊으면 섞이는데, 이 방식은 반대로 잊어도 안 섞인다.

**오늘 merge된 #1194(원장 자동 기록이 통화를 재료로 씀)와의 관계.** 문제없이 맞는다. #1194는 `source=call`이고 지우지 않은 것만 읽는다(`supabase/functions/ai-assist/handler.ts` 1245행, 1351행). 다만 두 가지를 발견했다(5절): ① 이미 원장에 쓰인 통화를 개인으로 옮겨도 원장 기록은 지워지지 않는다(원장은 더하기만 하는 규칙). ② 개인→업무로 옮긴 통화는 만들어진 시각이 오래돼서 원장이 읽는 기간 밖일 수 있다. 업무로 옮긴 것이 원장에 들어가게 하려면 `ai-assist`를 한 번 더 고쳐야 한다(4단계).

**기존 결정과 달라지는 곳(명진 요청으로 바뀜).** 통화 설계 Q2("개인 통화는 개수만, 살리기 없음")와 3.2절 "애매하면 옮기지 않는다"를 이번 요청이 대체한다. 개인·애매 통화도 내용을 저장하고 옮길 수 있게 된다. 대신 개인 통화에는 안전장치를 더 둔다(고정·조직·프로젝트 연결 금지, 업무 경로 읽기 금지).

**단계.** ① DB(이 PR 옆의 DB PR) → ② Edge `collector-feed`·보내기 스크립트 → ③ 화면 → ④ 옮길 때 AI 다시 채우기 + 원장 읽기 보정 → ⑤ 10/24 이후 개인 통화 다시 채우기. 맨 앞에 명진 쪽 선행 작업(분석 스크립트가 개인도 요약·전문을 남기게 하는 일, 커맨드센터 담당)이 있다. ①②④는 각각 멈춤 지점(DB 적용, Edge 배포)이라 승인을 받는다.

**결정이 필요한 것은 12절의 질문 8개.** 모두 추천을 붙였다.

## 2. 요구와 설계 원칙

1. 업무 통화가 기본이고 개인은 한 번 눌러야 보인다. 목록·상세 화면은 같은 것을 쓴다.
2. 개인은 업무 기록 어디에도 쓰이지 않는다. **막는 장치는 읽는 쪽 필터가 아니라 저장 방식 자체여야 한다**(필터를 잊어도 안전한 쪽, "fail-closed").
3. 옮기기는 데이터를 지우지 않는다. 옮기면 구분만 바뀐다.
4. 권한을 넓히지 않는다. 옮기기·다시 채우기는 로그인한 본인(소유자 확인)만, 표·칸 권한은 그대로다.
5. 새 AI 판정을 늘리지 않는다. 구분은 기존 통화 분석(Gemini)이 정한다. 새 AI 호출은 "업무로 옮길 때 업무 기준 정보 다시 채우기" 하나뿐이다(7절).

## 3. 저장 방식 비교와 추천

| | A. 같은 `call`에 구분 칸 추가 | B. 별도 표 `app_call_personal` | **C. 출처 값을 나눔(추천)** |
| --- | --- | --- | --- |
| 모양 | `source='call'` + `kind in ('work','personal','unsure')` | 개인 전용 새 표(같은 모양) | `source in ('call','call_personal','call_unsure','telegram')` |
| 업무 경로에 안 섞이는 이유 | 읽는 쪽이 `kind='work'`를 **잊지 않아야** 한다. #1194 등 이미 배포된 읽기도 고쳐야 한다 | 새 표라서 구조적으로 안 섞임 | 읽는 쪽이 이미 `source=call`로 읽으니 **고치지 않아도** 안 섞임. 새 읽기도 같은 규칙 |
| 옮기기 | 칸 하나 바꾸기 | 표 사이에서 복사+삭제. 로그인 본인에게 넣기·지우기 권한이 없으므로 새 권한 또는 대형 함수가 필요하고, "지우지 않고 옮기기"를 어김 | 구분 값 하나 바꾸기(함수 하나) |
| 화면 | 한 표를 `kind`로 거름 | 두 표를 읽어 같은 화면에 붙임. 중복·정렬 코드가 는다 | 한 표를 `source`로 거름(지금 방식 그대로) |
| 중복 방지 | 기존 unique 그대로 | 표마다 따로(같은 통화가 양쪽에 들어갈 수 있음) | 통화 세 값을 합쳐 한 번만(부분 unique index) |
| 단점 | 필터 누락 위험(가장 큼) | 옮기기 복잡, 권한 늘어남 | `source` 값이 "출처"와 "구분"을 겸함(이름이 조금 어색) |

- 추천은 **C**다. `tg-personal.md`가 같은 이유로 별도 표를 골랐던 것과 같은 목적(업무 경로 구조적 차단)을 달성하면서, 옮기기를 한 줄 고치기로 둘 수 있다. 어색한 이름은 문서(이 절)와 DB 주석으로 풀고, 화면·서버는 `callClass(row)` 같은 한 함수로만 구분을 다룬다.
- C의 보강 장치(DB에서, 모든 역할 공통): 개인·애매 줄은 고정(`pinned_at`)·조직·프로젝트·추천 프로젝트 칸이 항상 비어 있다(CHECK `app_feed_items_call_class_check`). 그래서 주간보고의 "고정한 소식" 재료, 조직 기록 연결, 프로젝트 연결이 개인 통화를 가리킬 수 없다. 옮길 때 트리거가 이 칸들을 비운다(줄 자체는 지우지 않음).

### 3.1 개인 표시 방식과 #1194의 조건 확인

- #1194의 조건: `source=eq.call`, `hidden_at is null`(지우지 않은 것), 생성 시각이 읽는 기간 안(`handler.ts` 1245행). C안에서 개인·애매 통화의 `source`는 `call`이 아니므로 **조건이 그대로 맞다.** 시험: 이 DB PR의 시험이 "ai-assist의 `app_feed_items` 읽기는 모두 `source=eq.call`"을 소스에서 고정한다.
- 개인으로 옮긴 통화의 `hidden_at`은 건드리지 않는다. 즉 "지우기(숨김)"와 "개인" 두 가지는 따로다(개인으로 옮겨도 개인 통화함에 보이고, 지우면 어디에도 안 보인다).

- 개인 통화 AI 처리: 분석은 기존 Gemini가 이미 했다. Web2 서버는 개인 통화 내용을 OpenAI로 보내지 않는다(저장·표시만). 예외는 사용자가 [업무 통화로 옮기기]를 누른 한 건(7절, 결정 Q5).

## 5. 이미 원장에 쓰인 통화와 옮기기

- **업무→개인**: 그 통화에서 이미 만들어진 원장 기록은 그대로 남는다(원장은 더하기만, 기존 기록을 고치거나 폐기하지 않는다. AGENTS.md 원장 절). 조직 기록에 더한 요약도 남는다. 그래서 개인으로 옮길 때 "이미 원장에 기록된 내용이 있으면" 확인 문구를 보여 준다(시안 라). 원장 기록 쪽 정리는 기존 '원장 수정 요청'으로 명진이 한다. 이 문구가 이미 쓰였는지 아는 방법은 원장 처리 표(`app_ledger_auto_sources`)에 그 통화의 처리 흔적이 있는지 조회하는 것이다(화면 단계에서 확인).
- **개인→업무**: 원장 자동 기록은 `created_at`이 읽는 기간 안인 통화만 읽고, 처리 표에도 `created_at`을 적는다(`handler.ts` 1245행, `ledger-sources.md` 6절 Q3). 옮긴 통화는 만들어진 시각이 옛날이라 **원장에 영영 안 들어갈 수 있다.** 해결(④단계): 읽기 조건을 "만든 시각 또는 옮긴 시각(`moved_at`)이 기간 안"으로 넓히고 처리 표에 적는 "본 시각"을 둘 중 늦은 것으로 한다. 이번 DB PR이 그 재료인 `moved_at` 칸을 만든다.

## 6. 옮기기의 서버 경로 (소유자 RLS 안, 권한 확대 없음)

- **로그인한 본인은 `source`·`title`·`counterpart`·`moved_at` 칸을 직접 고칠 권한이 없다(그대로 유지).** 옮기기는 새 함수 `public.app_feed_call_move(p_id uuid, p_to text)` 하나로만 한다. `p_to`는 `work`/`personal`/`unsure`.
  - SECURITY DEFINER, 빈 search_path, PUBLIC·anon·service_role 실행권 회수, **authenticated만 실행**. 함수 안에서 `private.app_is_workspace_owner(workspace_id)`로 소유자를 확인한다(기존 휴지통 함수들과 같은 방식). 없는 줄과 남의 줄은 같은 오류(`FEED_NOT_FOUND`)로 답해 존재 여부를 알리지 않는다.
  - 통화(`call*`)가 아니면(`telegram`) 거절한다. 같은 값으로 옮기면 아무것도 안 하고(`changed:false`) 옮긴 시각도 올리지 않는다.
  - 줄 자체는 `update`만 한다. 지우기·복사 없음. 전문·요약·제목은 그대로다.
- 트리거(모든 역할 공통)가 옮길 때: 통화끼리만 허용, `moved_at`을 서버 시각으로 기록, `refilled_at`을 비움, 개인·애매로 옮기면 고정·조직·프로젝트 연결을 비운다.
- 화면은 REST `POST /rest/v1/rpc/app_feed_call_move`를 쓴다(기존 `rt.api`). 실패하면 목록을 그대로 두고 한 줄 오류를 보인다. 되돌리기는 같은 함수로 반대 방향이다.
- 폰 길게 누르기·PC 오른쪽 클릭·⋯ 메뉴(시안 다·마): 텔레그램 소식의 고정·지우기 메뉴와 같은 컴포넌트를 쓴다.

## 7. 업무로 옮길 때 AI 다시 채우기

- 채울 것은 요청대로 네 가지: 통화 제목, 관련 조직, 상대 이름, 직함(상대 표기 `counterpart` 한 칸에 이름·직함). 핵심내용·전문은 건드리지 않는다.
- 경로: 화면이 `app_feed_call_move(..., 'work')`를 부른 뒤 응답의 `needs_refill:true`를 보고 `ai-assist`의 새 동작(`call_refill`, ④단계)을 로그인 토큰으로 부른다. `ai-assist`가 그 줄(전문 포함)과 담당조직 목록을 사용자 토큰 권한으로 읽고, 업무 기준 지시문으로 네 가지를 정한 뒤 `app_feed_call_work_info(p_id, p_title, p_counterpart, p_organization_id)`로 저장한다.
- `app_feed_call_work_info`: 소유자 확인, **업무 통화이고 옮긴 적이 있고 아직 안 채운 줄에만 한 번** 저장(`FEED_REFILL_NOT_PENDING`), 조직은 같은 작업공간 것만, 제목이 비면 기존 제목 유지, 상대·조직이 비면 비운 채로 "채움 끝"만 기록(`refilled_at`). 그래서 이 함수로 임의의 통화 제목을 고칠 수 없다.
- AI가 실패하면 줄은 업무 통화로 옮겨졌지만 제목·조직은 옛 값이다. 화면은 "정보 채우기 실패 [다시 시도]" 한 줄을 보이고 `refilled_at`이 비어 있는 동안 다시 시도할 수 있다. 사람이 모르게 덮어쓰지 않는다.
- AI 입력은 전문이므로 기존 규칙대로 전화번호를 지우고(`stripPhones`) 외부 입력을 자료로만 읽도록 지시한다(통화 내용 안의 지시를 따르지 않음). 비용은 건당 수 원 수준(추정), 기존 AI 한 달 상한 안에서 센다.
- 대안(채택 안 함): 보내기 스크립트가 Gemini로 업무 기준 분석을 다시 돌려 보내는 방식. Web2가 스크립트를 부를 길이 없어 스크립트가 "다시 하기 요청" 표를 주기적으로 읽어야 하고 길이 하나 더 생긴다.

## 10. 애매 통화의 자리 (시안 가·마)

- **추천**: 애매 통화는 통화 메뉴(업무) 맨 위에 "확인할 통화 n" 그룹으로 보이고, 줄마다 `애매` 표시와 [업무][개인] 작은 버튼이 있다. 정하기 전까지는 `call_unsure`라서 원장·주간보고에 쓰이지 않는다("애매하면 업무 기록에 쓰지 않는다"가 기존 원칙과 같다). 정하면 그룹에서 빠진다.
- 대안: 개인 통화함 안에 "애매" 탭을 두는 방식. 눈에 덜 띄어 쌓일 수 있어서 추천하지 않는다.
- 숨기기·지우기는 지금처럼 `hidden_at`이다.

## 12. 명진 결정 질문 (모두 추천 포함, 일상어)

1. **개인 통화를 어디에 두나요?** 추천: 같은 통화 목록 저장소에 두되 "개인" 이름표를 출처 값으로 붙입니다(3절 C). 그러면 주간보고·원장 같은 업무 기록은 손대지 않아도 개인을 못 봅니다. 다른 안(별도 저장소, 표시 칸)은 3절 표.
2. **애매 통화를 어디에 보일까요?** 추천: 통화 메뉴 맨 위에 "확인할 통화 n"으로 모아 [업무][개인]을 바로 누르게 합니다. 정하기 전엔 업무 기록에 쓰지 않습니다.
3. **업무 통화를 개인으로 옮길 때**, 이미 원장에 기록된 내용이 있으면 "원장 기록은 지워지지 않습니다"라고 알려 주기만 해도 될까요? 추천: 예(원장은 더하기만 하는 규칙이라 자동으로 지우지 않음. 필요하면 원장 수정 요청으로 따로 정리).
4. **개인 번호·이름 목록에 든 통화도 내용까지 개인 통화함으로 가져올까요?** 지금은 목록에 든 통화는 분석을 읽지 않고 개수만 셉니다. 추천: 예. 가져와도 개인 통화함에만 보이고 업무에는 안 쓰입니다. 아니오로 하면 그 통화들은 개수만 남습니다.
5. **업무로 옮길 때 통화 전문을 AI(OpenAI)에 보내도 될까요?** 제목·조직·상대·직함을 다시 채우려면 전문을 읽어야 합니다(옮긴 그 한 건만, 전화번호는 지움). 지금 회의 전사본과 같은 길입니다. 추천: 예. 아니오면 옮기기만 하고 정보는 사람이 직접 채웁니다.
6. **업무로 옮길 때 핵심내용도 업무 기준으로 다시 써 줄까요?** 개인으로 분석된 통화는 핵심내용에 개인 이야기가 섞여 있을 수 있고, 업무로 옮기면 그 글이 원장 재료로 쓰입니다. 추천: 우선 요청하신 네 가지(제목·조직·상대·직함)만 채우고, 옮긴 뒤 핵심내용을 직접 확인하게 합니다. 필요하면 다시 쓰기를 나중에 추가합니다(함수 보강 migration 한 번).
7. **개인 통화함을 검색에 넣을까요?** 추천: 넣지 않습니다(검색 결과에서 개인 통화가 업무 결과와 섞이지 않게).
8. **예전 "개인 통화 n건 걸러짐" 화면은?** 추천: 개인 통화함 안의 한 줄 안내("목록 도입 전 걸러진 n건은 개수만")로 줄이고 따로 화면은 두지 않습니다.

## 13. 범위 밖 발견 (고치지 않음)

- 보내기 스크립트의 "구분 없음"(옛 3.1 파일)은 서버가 애매로 센다(`call-analysis.ts` `workKind`의 기본값). 개인 통화함 도입 뒤에도 요약이 없는 옛 파일은 애매 줄을 만들 재료가 없어 개수만 남는다. ②단계에서 처리 방식을 정한다(Q12 "옛 분석은 가져오지 않는다" 결정 유지가 기본).
- 통화 하루 상한(50)이 업무·개인 합산이라 위 11절 위험이 있다. 상한 변경은 Edge 변경이라 ②단계에서 다룬다.
- 분석 스크립트가 개인 통화에 요약을 안 남기는 부분(저장소 밖)은 선행 작업이다.
