## 0. 한 줄 요약

자료를 **올릴 때 이미 한 번 부르는 자료실 AI 채우기(`library_fill`)에 "한두 줄 요약" 칸 하나를 더해** 같은 호출로 만들고, 이미 있는 "자료별 AI 요약 표"(`app_document_ai_index`, 자료마다 1행)에 저장한다. [주간 정리]는 그 주 자료를 읽을 때 요약을 같이 읽어 조직 칸·프로젝트 줄에 "(자료) 제목 — 요약"으로 넣고, 그 주 기록과 같은 내용이면 접어 둔다. [빼기]·고치기는 WEEKLY-임시저장의 그 주 행(`draft`)에 같이 저장한다. 새 표·새 AI 호출 경로·새 반복 실행 없음.

### 1.2 자료실 AI 채우기 (`ai-assist` `kind=library_fill`)

- 파일: `supabase/functions/ai-assist/library-fill.ts`(순수 함수), `handler.ts` `runLibraryFill`.
- 재료: 글자 앞부분(한 번에 합계 12,000자, 한 파일 최대 8,000자·최소 1,000자), 파일 이름·형식, 분류 목록, (빈 연결이 있을 때만) 프로젝트·조직 이름과 짧은 참조. `store:false`, strict JSON schema.
- 답 칸: 제목·자료 날짜·작성 주체·유형 + 프로젝트·담당조직(빈 연결만). 사람 칸(`field_origin` `'user'`)은 안 씀.
- 할 일이 없는 자료(모든 칸이 사람 칸이고 연결도 있음)는 **AI를 부르지 않는다**.
- 비용 한도: 하루 `library_fill` 50회, 전체 하루 50회, 월 추정 15,000원(`handler.ts` `DAILY_LIMITS`·`MONTHLY_LIMIT_KRW`). 기본 단가 입력 350원·출력 2,800원 / 100만 토큰.

### 1.3 자료별 AI 요약 표 — 이미 있음

- `app_documents` 말고 **`app_document_ai_index`**가 있다(자료마다 1행, `document_id` 기준 upsert). 알려진 칸: `document_id`, `workspace_id`, `content_hash`, `summary`, `keywords`, `chunk_count`, `summary_model`, `indexed_at`, `updated_at`(사실: `supabase/functions/document-ai-index/index.ts`의 upsert, `supabase/tests/authz_sole_owner.sql`의 insert).
- 정책: `task12a_owner_all`(for all, authenticated, `private.app_is_owner_document(document_id)`) — 자료 주인만(사실: `20260925084844_task12a_sole_owner_db.sql`).
- 이 표를 만든 migration은 저장소에 없다(migration 기록 이전 운영 표). 칸 종류·제약·grant·행 수는 **확인하지 않았다**(추정: 2026-09 이전 `document-ai-index`가 쓴 행이 조금 있거나 0).
- 이 표에 쓰는 Edge `document-ai-index`는 앱 호출이 없고 삭제 후보다(`docs/roadmap.md` 2026-09-26 메모). 읽는 Edge `page-ai-draft`도 앱 호출이 없다. `docs/design/global-search.md` 215행은 "삭제 후보 정리 때 행 수·사용처를 함께 확인"이라 적었다 — **이 설계가 표를 다시 쓰면 그 정리에서 표를 지우면 안 된다**(9절 위험 1, Q1).

### 1.5 기록 요약 규칙과 중복 판단 (지금)

- **바구니 중복 판단**(사실: `app/basket-ai-handoff.js` `existingBlock`, `app/basket-classification.js` `judgeVerdict`, `app/basket-classification-ui.js`):
  - 같은 목적지(조직·프로젝트)의 최근 28일 기존 기록을 AI에 같이 준다.
  - `duplicate`(같음): 사실상 같음 → 체크가 풀린 채 "이미 같은 내용이 기록돼 있어요. 체크하면 다시 기록해요."(지우지 않음).

## 2. 요약 생성 시점 — 올릴 때 한 번, 같은 AI 호출에 묶음 (추천)

### 2.1 묶는 곳

`library_fill` 답 형식에 칸 하나를 더한다: `brief`(한두 줄 요약, 없으면 빈 글). 재료·지침·형식 검사·한도는 지금 그대로 쓴다.

| 때 | 지금 | 바뀜 |
| --- | --- | --- |
| 올릴 때(`mode fill`) | 글 칸 4개 + 빈 연결 | + `brief`. 다른 칸이 모두 사람 칸이라 지금은 AI를 안 부르는 자료도, **요약이 없고 글자가 있으면** 부른다(요약만) |
| 자료실을 열 때(`mode tidy`) | 정리 안 된 칸, 글자가 나중에 들어온 자료 한 번 더 | + **최근 14일 안에 올린 자료** 중 글자가 있고 요약이 없거나, 글자가 바뀐 자료(5.1의 글자 지문이 다름)의 요약 |
| 밤 글자 읽기 | AI 없음 | 그대로(AI 없음). 밤에 글자가 들어온 자료는 다음에 자료실을 열 때 tidy가 요약 |
| 주간 정리를 열 때 | — | **AI·파일 읽기 없음**. 저장된 요약만 읽음 |

- 따로 부르지 않는 이유: 요약에 필요한 재료(글자 앞부분)는 채우기 호출이 이미 보낸다. 묶으면 입력이 거의 늘지 않고 출력만 자료당 100~150토큰 는다(7절).
- 14일로 자르는 이유: 주간 정리는 그 주 올린 자료만 쓴다. 예전 자료 전체를 요약하면 쓰지 않을 요약에 돈을 쓴다(Q4).
- 같은 글자 지문(5.1)의 요약이 다른 자료에 이미 있으면 AI 없이 그 요약을 복사한다(같은 파일을 두 번 올린 경우).

### 2.2 대상과 한도

| 자료 | 요약 |
| --- | --- |
| HWP·HWPX·PDF·DOC·DOCX·RTF·ODT·txt·md·csv, 글자 `ready` | 만든다 |
| 스캔 PDF(글자 `empty`), 사진, 못 읽은 파일(`error`) | 만들지 않음 → 제목만 |
| 글자 읽기가 아직(`pending`·없음) | 기다리지 않음. 글자가 들어오면 tidy가 나중에 |

- 재료: 지금처럼 글자 **앞 8,000자**(한 번에 여러 자료면 1,000~8,000자로 나눔). 표지·첫 쪽·머리말에 사안이 몰려 있어 앞부분이면 충분하다. 12,000자 저장 상한 밖은 원래 없다.
- 요약 상한: 1~2줄, 줄마다 120자, 합계 200자. 줄바꿈 말고 제어 문자·HTML·꺾쇠 없음. 넘으면 버림(자르지 않음 — 자른 문장이 뜻을 바꿀 수 있음).

### 2.3 요약 규칙 (지침에 더할 문장)

- **바구니 기록 요약 규칙을 같은 문장으로** 쓴다: 날짜·요일·시간·장소·주체·대상·숫자와 진행 상태(예정·검토·확정·취소)를 그대로 보존, **예정이나 검토를 확정으로 바꾸지 않음**, 원문에 없는 사실·추측 금지, "내용 공유"처럼 빈 말 금지.
  - 한 곳에 두기: 서버 상수 `RECORD_SUMMARY_RULE`(`ai-assist`)로 두고, 시험이 `app/basket-classification.js`의 같은 문장과 글자 그대로 같은지 비교한다(화면 JS와 Edge가 파일을 공유하지 못하므로 시험으로 묶음).
- 주간보고 문체: 명사형으로 맺음(조직 요약 지침 `ORG_SUMMARY_INSTRUCTIONS`와 같은 문장). 사람 이름·연락처는 쓰지 않고 직책·조직으로(조직 요약과 같은 기준, 연락처는 서버가 한 번 더 지움 — `cleanOrgText` 규칙 재사용).
- 자료 안의 지시문은 따르지 않음(지금 지침 그대로).
- 무엇을 요약하나: "이 자료가 무엇인지 + 핵심 사실 하나". 예(가상): `A 지부 임금교섭 요구안. 기본급 5% 인상·인력 충원 요구, 10.28.(화) 1차 교섭 예정.`

## 3. 저장 위치 — 기존 "자료별 AI 요약 표" 재사용 (추천)

### 3.1 추천 A: `app_document_ai_index`에 저장

| 칸(기존) | 쓰는 값 |
| --- | --- |
| `document_id` | 자료 ID(1행) |
| `workspace_id` | 자료의 업무공간 |
| `summary` | 한두 줄 요약(빈 글 = 요약할 것 없음, 다시 시도하지 않음) |
| `content_hash` | `b1:` + 글자 지문(5.1). **`b1:`로 시작하는 행만 이 기능의 행**으로 본다 |
| `summary_model` | 쓴 모델 이름 |
| `indexed_at`·`updated_at` | 만든 시각 |
| `keywords`·`chunk_count` | `{}`·0(쓰지 않음) |

- 이유: 같은 목적("자료 하나의 AI 요약")의 표가 이미 있고, 자료 주인 전용 정책도 걸려 있다. `app_documents`에 칸을 더하면 같은 일을 하는 자리가 둘이 된다(중복).
- 쓰기: `ai-assist`가 **내 로그인 토큰**으로(지금 `library_fill`이 `app_documents`를 쓰는 길과 같음, 관리자 키 없음) upsert. 서버가 쓰기 전에 형식·글자 수를 다시 검사(AI 답은 믿지 않는 입력).
- 옛 행(`b1:`로 시작하지 않는 행, `document-ai-index`가 쓴 긴 인덱싱 요약): **덮어쓰지 않는다**. 그 자료는 요약을 만들지 않고 제목만(데이터 보존). 사전 확인에서 옛 행 수를 세어 0이 아니면 Q1에서 정한다.
- 화면 읽기: `readWeekDocuments`가 `app_documents?...&select=...,app_document_ai_index(summary,content_hash)`로 같이 읽는다(외래키가 있을 때. 없으면 자료 ID 목록으로 한 번 더 읽음 — 사전 확인에서 정함).

### 3.2 다른 길 B: `app_documents`에 칸 3개(`brief`·`brief_hash`·`brief_at`)

- 깔끔하지만 같은 목적 표가 이미 있는데 칸을 또 만드는 것이 된다. 자료 목록 화면 여러 곳이 `select=*`라 칸이 늘면 목록 읽기도 조금 무거워진다(library-ai-fill.md 3절과 같은 이유). 옛 표가 삭제 후보라 헷갈림이 없다는 점은 낫다.
- A가 사전 확인에서 막히면(표 모양이 다르거나, 권한이 없거나, 옛 행 처리를 못 정하면) B로 간다.

### 3.3 저장하지 않는 것

- 파일 본문·글자는 요약 표에 옮기지 않는다(글자는 이미 `extracted_text`에).
- 그 주 "같음/비슷함" 판단 결과는 저장하지 않는다(화면이 매번 규칙으로 계산, 5절).

## 5. 중복 판단

### 5.1 같은 파일 두 번 → 한 줄

- **글자 지문**: 자료 글자(`extracted_text`)를 띄어쓰기·줄바꿈을 하나로 맞추고 NFKC로 바꾼 뒤 SHA-256 앞 32자. 요약 표 `content_hash`에 `b1:`과 함께 저장(3.1).
- 같은 주에 지문이 같은 자료가 둘 이상이면 **먼저 올린 하나만** 줄로, 나머지는 그 줄 끝에 "같은 파일 2번" 작게.
- 지난 주에 이미 올린 자료와 지문이 같으면(다시 올림) "기록과 같아 뺀 자료"(5.3)로 접는다(보고는 이미 지난주에 됨). 지문 비교는 화면이 그 주 요약 행의 지문으로 `app_document_ai_index?content_hash=in.(…)&select=document_id`를 한 번 읽어 확인.
- 글자 없는 자료(스캔·사진)는 지문이 없어 합치지 않는다. 같은 바구니 첨부는 이미 한 행(`exists`)이라 걱정 없음.

### 5.2 그 주 기록과 비교 — 바구니와 같은 세 갈래, 규칙으로 (추천)

바구니 분류와 **같은 기준**(같음 → 기본으로 빼되 되살릴 수 있음, 바뀜 → 새 사실만, 근거 없으면 새 내용)을 쓰되, 주간 정리를 열 때마다 AI를 부르지 않도록 **화면 규칙**으로 판단한다. 비교 대상은 같은 칸(그 조직 칸 / 그 프로젝트 줄)의 그 주 기록 줄: 조직 기록, 확정 연결 요약, 바구니 업데이트 첫 줄, 프로젝트 기록, 사업 보고(회의·활동 결과 중 같은 조직·프로젝트에 연결된 것).

| 판단 | 규칙(둘 다 띄어쓰기·문장부호를 뺀 글로) | 화면 |
| --- | --- | --- |
| **같음** | 요약이 기록 안에 통째로 있거나 기록이 요약 안에 통째로 있음(기록 10자 이상), 또는 낱말 겹침 80% 이상이면서 요약의 숫자·날짜가 모두 기록에 있음 | 줄을 넣지 않고 칸 맨 아래 접힌 "기록과 같아 뺀 자료 N"에 [넣기](바구니 "체크하면 다시 기록"과 같은 뜻) |
| **같은 업데이트의 첨부** | 이 자료가 그 칸에 이미 보이는 바구니 업데이트의 첨부(`file_id`가 그 업데이트 `attachments`에 있음) | 줄은 넣되 '비슷한 기록 있음' |
| **비슷함(애매)** | 낱말 겹침 40% 이상, 또는 같은 날짜(M.D.)가 있고 두 글자 이상 낱말 2개 이상 겹침 | 줄을 넣고 작게 '비슷한 기록 있음'(빼지 않음) |
| **새 내용** | 위에 안 걸림 | 줄을 그대로 |

- "새 사실만 더하기"(바구니의 '바뀜·후속')는 규칙만으로 새 사실을 골라낼 수 없다. 그래서 비슷한 줄은 **빼지 않고 표시만** 하고, 합치기는 ① 명진이 [고치기]로 하거나 ② 그 조직에 [요약 만들기]를 누르면 AI가 기록과 자료 요약을 한 사안 한 줄로 합친다(4.3 끝). 프로젝트 줄은 AI 요약이 없어 ①만.
- 숫자 조건을 둔 이유: "1차 교섭 예정"과 "2차 교섭 진행"처럼 낱말은 비슷해도 숫자·상태가 다르면 같음이 아니다. 상태 낱말(예정·검토·확정·취소·진행·완료)이 다르면 같음으로 보지 않는다(비슷함까지만).
- 규칙·기준값은 `weekly-file-lines.mjs` 한 곳에 두고 시험으로 고정. 써 보고 너무 많이/적게 접히면 기준값만 바꾼다.
- 다른 길(채택 안 함): 주간 정리를 처음 열 때 AI가 자료 요약 ↔ 기록을 비교해 바구니처럼 `duplicate/changed`를 내고 그 주 행에 저장. 정확도는 낫지만 주마다 AI 호출이 하나 늘고, 그 뒤에 들어온 기록과는 다시 비교해야 하며, 결과를 둘 자리가 필요하다(Q6).

## 6. [빼기]·고치기 저장 — WEEKLY-환류와 같은 그 주 행

### 6.1 저장 자리

WEEKLY-임시저장의 그 주 행 `app_weekly_exec_requests.draft`(주마다 1행, migration `20261024001000_weekly_draft`)에 키 하나를 더한다. 서버 검사는 `v:1` 객체·200KB뿐이라 **DB 변경이 없다**(안쪽 모양은 화면이 검사).

```
draft = {
  v: 1, …(임시저장 칸 그대로)…,
  dropped: [event],                          // 5. 주요 일정 [빼기] (환류 설계 3.4)
  docs: [{ id: "<자료 id>", drop?: true,      // 자료 줄 [빼기]
           text?: "고친 줄",                  // 자료 줄 [고치기] (200자, 한 줄)
           keep?: true }]                     // "기록과 같아 뺀 자료"에서 [넣기]
}
```

- 쓰기는 임시저장과 같은 `draft_saved_at` 조건 PATCH, 두 기기 충돌은 같은 칸 단위 3자 비교(칸 열쇠 = `doc:<자료 id>`). 쓰는 모듈도 임시저장의 `app/weekly-draft-store.js`(임시저장 화면 PR에서 생김) 하나.
- [빼기]는 [주간 정리] 화면·[복사]·한글 파일 후보에 모두 적용. 뺀 줄은 칸 맨 아래 "뺀 자료 N [다시 넣기]"(회의 종류 빼기·일정 빼기와 같은 모양).
- [고치기]는 그 주 보고 글만 바꾼다. 자료의 요약(요약 표)은 그대로(자료실에서 보이는 요약을 바꾸고 싶으면 따로, Q7).

### 6.2 환류(다음 주 기억)와의 관계

- 자료 줄은 **올린 주에만** 나온다. 그래서 일정처럼 "다음 주에도 같은 이름 → 같은 처리"를 기억할 일이 거의 없다. 이번엔 그 주 행에만 저장하고 프로필 기억(`weekly_schedule_memory`)에는 넣지 않는다(Q8).
- 같은 파일을 다음 주에 다시 올린 경우는 5.1이 "기록과 같아 뺀 자료"로 접는다.
- [확정] 뒤 "다음 주에도 쓸까요?" 목록에는 자료 줄이 나오지 않는다.

### 6.3 DB 적용 전

- `draft` 칸이 없으면(#1081 DB 미적용) [빼기]·[고치기]를 그리지 않는다. 줄 보이기·같음 접기는 그대로 된다(저장할 것이 없음). 요청 표의 `missing`과 같은 방식.

## 9. 위험

1. **옛 표 재사용**: `app_document_ai_index`는 저장소에 만든 기록이 없고 삭제 후보 Edge와 엮여 있다. 정리 때 표째 지우면 요약이 사라진다 → 원장 메모(8.1 ④), 사전 확인에서 모양이 다르면 B로.
2. **요약이 사실을 바꿈**: AI가 "예정"을 "진행"으로 쓰는 등 → 바구니와 같은 상태 보존 문장 + 서버 시험(예정·검토가 든 가상 자료에서 상태 낱말이 그대로인지), 주간 정리에서 [고치기]. 요약은 "재료"이고 보고서에는 명진이 확인한 뒤 들어간다.
3. **같음 규칙이 잘못 접음**: 실제로 다른 사안을 접으면 보고에서 빠질 수 있다 → 접힌 묶음을 칸 안에 늘 보이게("기록과 같아 뺀 자료 N"), 숫자·상태가 다르면 같음 아님, 기준을 보수적으로.
4. **조직·프로젝트 연결이 AI가 붙인 것**: LIB-AI분류보완이 빈 연결을 AI로 채운다. 잘못 붙으면 엉뚱한 조직 칸에 자료 줄이 생긴다 → 줄을 누르면 자료가 열려 연결을 고칠 수 있음, [빼기].
5. **개인정보**: 요약에 사람 이름·연락처가 섞일 수 있다 → 지침(직책·조직으로) + 서버가 연락처 지움. 요약은 owner 전용 표에만, 로그·PR·오류 보고에 내용 없음.
6. **자료 안 지시문**: 지금 채우기 지침·시험 그대로(지시 무시).
7. **비용 증가**: "요약만" 부르는 경우가 늘면 자료당 5~6원 → 하루 50회 한도 안. 한 주 건수를 7절보다 훨씬 많이 올리면 하루 한도에 먼저 닿아 채우기도 같이 멈춘다 → 요약 생성은 최근 14일만.
8. **스캔 PDF**: 글자가 없으면 제목만. 의미 있는 자료가 빠질 수 있다 → 10절 검토.
9. **읽기 부담**: 주간 정리 자료 읽기에 요약 200자 × 최대 300건이 붙는다(≈60KB 이하). 지문 확인 읽기 한 번 추가.
10. **임시저장 PR과 엮임**: [빼기]·고치기는 WEEKLY-임시저장 화면 PR이 먼저 있어야 한다 → 화면 ①·②로 나눔.

## 10. 스캔 PDF·사진 — 바구니 사진 글자 읽기(OCR) 검토만

- 지금(사실): 바구니 사진(JPEG·PNG)은 `basket-files`의 사진 글자 읽기(`_shared/drive-ocr.ts`, Drive에 한국어 OCR로 임시 문서를 만들어 글을 읽고 지움)가 있다. 자료실 글자 읽기(`document-text.ts`)는 사진을 읽지 않고, PDF는 Drive 변환을 쓰되 OCR 언어를 따로 주지 않는다.
- 쓸 수 있는 길 두 가지(둘 다 Edge 변경 = 배포 정지 지점, AI 비용 없음 — Drive가 함):
  1. **스캔 PDF**: `document-text.ts`의 PDF 변환 요청에 한국어 OCR 언어를 주기. 한 곳만 고치면 올리기·자료실·밤 읽기·검색이 모두 덕을 본다. 시간이 더 걸릴 수 있다(한 파일 최악 ~90초 제한 안).
  2. **자료실 사진**: `document-text.ts`가 JPEG·PNG면 `drive-ocr.ts`의 같은 OCR을 부르기(크기 상한·임시 문서 지우기 규칙 재사용).
- 위험: OCR 글자는 틀린 글자가 많아 요약이 틀릴 수 있다(숫자·날짜). 사진은 업무 자료가 아닌 것(현장 사진)이 많아 요약할 게 없다.
- 추천: 이번 범위에서는 하지 않음. 써 보고 "제목만 나오는 스캔 자료가 많다"면 ①만 따로 원장 행으로(Q9).

## 12. 범위 밖 발견 (고치지 않음)

- `app_document_ai_index`·`app_document_chunks`를 만든 migration이 저장소에 없다. 저장소 기준 표 정의가 없어 `docs/migration-history.md`로 추적되지 않는다(Task 12A 전 운영 표).
