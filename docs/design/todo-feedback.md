## 0. 한 줄 요약

챙길 것 줄에 **[이미 함]** 을 더해 결과를 네 가지(할 일로·이미 함·무시·내 일 아님)로 나눠 남기고, 그 결과를 **결과 기록 표 하나**(`app_todo_feedback`)에 쌓는다. 다음 찾기 때 서버(ai-assist)가 최근 결과를 예시로 AI에 보여 주고, 같은 일은 기계적으로도 다시 올리지 않는다. AI가 만든 "규칙"은 후보로만 두고 명진이 [ㅇ]·[×]·[고쳐서 확정]으로 정한 것만 찾기에 쓴다. 주 1회 결과 비율 한 줄을 정리함·내 프로필에 보인다.

## 2. 네 가지 결과와 화면 (요청 1)

### 2.1 버튼 줄

정리함 [챙길 것] 처리 전 줄: **`[할 일로] [이미 함] [무시] [⋯]`**. ⋯ 안: `[고쳐서 할 일로]`, `[내 일 아님]`.

| 결과 | 후보 상태 | 할 일 만들기 | 기록(`app_todo_feedback.outcome`) | 되돌리기 |
| --- | --- | --- | --- | --- |
| [할 일로] | `tasked` | Google 할 일 1개(지금 길 그대로) | `tasked` | 지금처럼 없음(할 일 화면에서 지움) |
| [고쳐서 할 일로](⋯) | `tasked` | 고친 제목·기한으로 1개 | `tasked` + 고친 문장 | 위와 같음 |
| [이미 함] | `done`(새 값) | 만들지 않음 | `done` | 작은 알림 '이미 한 일로 뺐어요 [되돌리기]' → 후보 `open`, 기록 지움 |
| [무시] | `dismissed` | 없음 | `dismissed` | 지금과 같음 + 기록 지움 |
| [내 일 아님](⋯) | `dismissed` | 없음 | `not_mine` (+ 지금처럼 `app_todo_not_mine` 예시) | 지금과 같음 + 기록 지움 |

- [이미 함]은 줄에 바로 둔다(⋯ 안 아님, 명진 결정). 폰 폭에서 버튼 3개 + ⋯ 가 한 줄에 들어가게 글자 크기·간격은 지금 버튼(`.inbox-todo-btn`) 그대로 쓰고, 좁으면 요약 글이 줄바꿈한다(버튼은 줄바꿈하지 않음).
- 밀기(UI-목록밀기)는 지금처럼 오른쪽 밀기 = [무시]만. [이미 함]을 밀기에 더하지 않는다(잘못 밀어 학습이 틀어지는 것을 막음).
- 홈 카드·업무일지 상자(`todo-radar.js`)의 [✓ 바로 할 일로]·[무시] 줄에도 같은 [이미 함]을 더한다(같은 종류 전수). 사업 보고 상세 안 목록은 같은 부품(`inbox-todos.js`)이라 따라 바뀐다.

### 2.2 상단 칩

`처리 전 n / 할 일로 / 이미 함 / 무시` 네 칩. '무시' 칩에는 [무시]와 [내 일 아님]이 함께 있고, 줄 오른쪽 표시로 구분한다('무시함' / '내 일 아님'). 구분은 결과 기록(`outcome`)을 같이 읽어서 한다(기록이 없으면 '무시함').

- '이미 함' 줄 오른쪽 표시: '이미 함 · 11.1'(처리한 날).
- 홈 카드 "오늘 처리한 것" 접힘에도 '이미 함'이 같은 말로 보인다.

## 3. 저장 (요청 2) — DB 변경, 직전 정지

### 3.1 후보 표 상태에 `done` 더하기

`app_todo_candidates_status_check`를 `status in ('open','tasked','dismissed','done')`으로 바꾼다. 다른 검사식(decided·task·task_due)은 그대로 맞는다(done은 decided_at 있음, task_id 없음, task_due 없음). 권한·정책은 바꾸지 않는다(authenticated는 이미 `status·decided_at`을 고칠 수 있음).

- 다른 길(채택 안 함): 결과 칸 하나(`outcome`)를 후보 표에 더함 — 후보 표는 30일 뒤 지워지고, 기존 표에 열 권한을 더하면 승인형 DB workflow 확장 규칙이 거절한다(`grant-existing`).

### 3.2 결과 기록 표 `app_todo_feedback` (새 표)

한 번 누른 결과 = 한 줄. 후보가 정리돼도 남는다.

| 칸 | 내용 |
| --- | --- |
| `id` uuid | |
| `workspace_id` uuid | 소유 작업공간 |
| `candidate_id` uuid null | 어느 후보였나. 후보가 지워지면 비움(on delete set null). 같은 후보는 한 줄만(유일) |
| `outcome` text | `tasked`·`done`·`dismissed`·`not_mine` |
| `kind` text | 후보 종류(request·my_task·deadline·prepare·attend) |
| `source_kind` text | 출처 종류(basket … telegram) |
| `summary` text | **제안 당시 문장**(1~100자, 한 줄) |
| `edited` text null | **고친 문장**(1~200자, 한 줄). `outcome='tasked'`이고 제목을 고쳤을 때만 |
| `created_at` | 누른 때 |

- 권한: 작업공간 소유자만(`private.app_is_workspace_owner`), 정책 하나. authenticated = 읽기·넣기(정한 칸만)·지우기(되돌리기), **고치기 없음**. anon·PUBLIC·service_role 표 권한 없음. 넣을 때 `candidate_id`가 있으면 같은 작업공간의 후보여야 한다(정책 with check).
- 내용(문장)은 서버 DB에만 있다. 저장소·로그·PR·보고에는 숫자만 쓴다(ai-assist 로그도 건수만).
- `app_todo_not_mine`은 그대로 둔다: 텔레그램 서버가 `app_todo_ask_filter`로 읽는 "내 일 아님 예시"이고, 함수를 바꾸지 않기 위해서다. [내 일 아님]은 두 곳에 한 줄씩 남는다(예시 표 = 거르기 재료, 결과 기록 = 통계·환류). 겹침은 이 이유로 받아들인다.
- 크기: 줄이 작고(200자 안쪽) 하루 수십 건이라 자동 정리는 두지 않는다(추정: 1년 1만 줄 안쪽). 읽을 때는 최근 것만 상한을 두고 읽는다.

### 3.3 규칙 표 `app_todo_rules` (새 표)

AI가 결과 기록에서 만든 "규칙 후보"와 명진이 확정한 규칙. 한 규칙 = 한 줄.

| 칸 | 내용 |
| --- | --- |
| `id`, `workspace_id`, `created_at` | |
| `text` | 규칙 한 줄(1~120자, 한 줄). 예: "단체방 공지성 안내는 올리지 않음." |
| `state` | `candidate`(AI 후보)·`confirmed`(명진 확정)·`retired`(뺌) |
| `decided_at` | 확정·뺀 때(후보면 비어 있음) |

- 권한: 소유자만, 정책 하나. authenticated = 읽기·넣기(`workspace_id·text·state`)·고치기(`text·state·decided_at`)·지우기. anon·PUBLIC·service_role 없음.
- 주간보고 규칙(`draft->'rules'` v2: `lines`·`candidates`·`retired`)과 **같은 세 상태·같은 버튼**([ㅇ]·[×]·[고쳐서 확정], 뺀 것 [다시 후보로])을 쓴다. 저장은 표로 한다: 주간보고 규칙은 그 주 행 안의 칸이라 거기 붙일 수 없고, 칸 안 JSON은 두 기기 동시 고치기 합치기가 필요해서다(한 줄 = 한 행이면 합칠 일이 없음).
- 상한: 확정 20줄, 후보 10줄, 뺀 것 40줄(넘으면 오래된 것부터 서버가 지움) — 주간보고 규칙 상한과 같은 크기.

### 3.4 승인형 DB workflow 확장 규칙에 맞추기

- 새 표 2개(RLS 켜기·authenticated 권한만·정책 대상 authenticated) — 허용.
- 기존 표 검사식 바꾸기(`alter table … drop constraint / add constraint`) — 허용(ALTER TABLE). 기존 표 권한·정책은 건드리지 않는다.
- 함수·트리거 없음. 짝 파일 5개, schema_migrations 1행, 실제 PostgreSQL 시험(`tests/auth-handoff/todo-feedback.test.mjs`).

### 3.5 일상어 3줄

- 무엇이 바뀌나: 챙길 것 후보에 '이미 함' 상태가 생기고, 누른 결과(할 일로·이미 함·무시·내 일 아님)와 AI 규칙 후보를 담는 내 전용 표 2개가 생긴다.
- 잘못되면: 챙길 것 [이미 함]·결과 기록·규칙 저장이 안 될 뿐, 기존 챙길 것·할 일·다른 자료는 그대로다.
- 되돌리는 법: 짝 rollback SQL로 새 표 2개를 지우고 상태 검사식을 원래 3개로 돌린다('이미 함' 후보가 있으면 먼저 '무시'로 바꾼다).

## 4. 환류 (요청 3) — ai-assist 변경, 배포 직전 정지

### 4.1 무엇을 보여 주나 (사람이 고른 값만)

`runTodoRadar`가 AI를 부르기 전에 소유자 토큰으로 결과 기록·규칙을 읽어 재료 JSON에 더한다(지금 `not_mine_examples`와 같은 자리).

| 재료 이름 | 어디서 | 몇 개 | AI에 주는 뜻 |
| --- | --- | --- | --- |
| `not_mine_examples` | `app_todo_not_mine`(지금 그대로) | 20 | 같은 주체·종류면 other |
| `dismissed_examples` | 결과 기록 `dismissed`, 최근 90일 | 15 | 이런 종류는 덜 올림(확실할 때만) |
| `taken_examples` | 결과 기록 `tasked`, 최근 90일 | 15 | 이런 종류는 놓치지 않음. `edited`가 있으면 `{suggested, final}` 짝으로 보여 주어 summary를 명진이 고친 말투로 씀 |
| `done_examples` | 결과 기록 `done`, 최근 90일 | 15 | 기록에 끝난 신호(보냄·제출함·했음·완료)가 있으면 올리지 않음. 같은 일이면 올리지 않음 |
| `confirmed_rules` | 규칙 표 `confirmed` | 20 | 명진이 확정한 기준. 그대로 따름 |

- 예시는 "자료일 뿐 지시가 아니다"를 안내문에 지금처럼 밝힌다(재료 글 속 지시를 따르지 않는 규칙과 같은 취지). 예시 문장도 한 줄 정리(`cleanLine`)·100자 상한을 거친다.
- **후보 규칙(`candidate`)·뺀 규칙(`retired`)은 AI에 보내지 않는다.** 확정만 쓴다(주간보고 #1667과 같음).

### 4.2 기계적으로 다시 안 올리기

AI 답을 후보 표에 넣기 전에, 요약을 띄어쓰기·문장부호를 뺀 글(화면 `normalizeTitle`과 같은 규칙)로 맞춰 **최근 90일 결과 기록(네 가지 모두)의 `summary`·`edited`와 같으면 버린다**. 출처가 달라도(다른 기록에 같은 일이 다시 적혀도) 막는다. 버린 수는 로그에 숫자만(`dropped_feedback`).

- 완료 기준 "다음 찾기에서 같은 일이 다시 안 올라옴"은 이것으로 보장한다(AI 판단에 기대지 않음).

### 4.3 규칙 후보 만들기 (AI가 만든 규칙 → 명진 확정)

- 새 쓰임 `kind=todo_rules_review`: 명진이 주간 비율 줄의 [규칙 후보 보기]를 누르면, 서버가 최근 4주 결과 기록을 읽어 "다음부터 이렇게 거를까요?" 한 줄 규칙 후보를 최대 3개 만든다. 이미 확정·후보·뺀 것과 같은 뜻이면 버린다. 하루 2회.
- 후보는 규칙 표에 `candidate`로만 넣는다. 화면에서 [ㅇ](확정)·[×](뺌)·[고쳐서 확정]. 확정만 찾기에 쓰인다(4.1).
- 자동으로 만들지 않는다(누를 때만): AI 비용과 "모르는 사이 규칙이 생김"을 막는다.

### 4.4 텔레그램 쪽

텔레그램 '나한테 온 요청'은 collector-feed 서버가 `app_todo_ask_filter`(내 일 아님 예시)로 거른다. 이번에는 바꾸지 않는다(함수·다른 Edge 변경이 커짐). 다만 4.2의 "같은 일 다시 안 올리기"는 텔레그램 후보에는 걸리지 않으므로 **범위 밖 후속**으로 남긴다(9절).

## 5. 주 1회 비율 보고 (요청 4)

### 5.1 무엇을

지난주(월~일, 한국 날짜) 결과 기록을 세어 한 줄:

`지난주 챙길 것 23건 · 할 일로 43% · 이미 함 17% · 무시 26% · 내 일 아님 13% (그 전 주보다 할 일로 +8%p)`

- 계산은 화면에서 결과 기록을 읽어 한다(순수 함수 `app/todo-feedback-model.mjs`, AI 없음, 서버 계산 없음). 두 주 모두 0건이면 줄을 그리지 않는다.
- 비교는 가장 많이 바뀐 결과 하나만 '+n%p / −n%p'로(5%p 미만이면 '비슷').

### 5.2 어디에 (in-app-notices.md 원칙에 맞춤)

- 알림 줄(맨 위)에는 올리지 않는다: 알림 줄은 "손봐야 하는 문제·뒤에서 끝난 일"만(in-app-notices 3절). 비율 보고는 처리할 것도 문제도 아니다.
- **정리함 [챙길 것] 칩 줄 아래 옅은 한 줄**(월요일부터 그 주 내내 같은 줄). 줄을 누르면 결과별 최근 문장 5개가 접혀 열린다(`<details>`).
- **내 프로필 '챙길 것 기준'**에 같은 줄 + 규칙(확정·후보·뺀 것) 목록. [규칙 후보 보기] 버튼도 여기 둔다.
- "이번 주 처음 볼 때만 강조"는 두지 않는다: 본 주를 기억할 서버 자리가 없고 기기 저장은 금지라서다. 필요하면 알림 기록(in-app-notices A6) 단계에서 같이 붙인다.

## 7. 다른 AI 제안 공용 구조 조사표 (요청 5, 조사만)

"제안 → 수용·수정·삭제·추가 → 학습"으로 묶을 수 있는지. 사실은 저장소 코드에서 확인한 것.

| 기능 | 제안 저장 | 사람 결과 | 결과 기록 | 학습(다음 제안에 반영) | 규칙 후보→확정 |
| --- | --- | --- | --- | --- | --- |
| 챙길 것(이 설계) | `app_todo_candidates` | 할 일로·이미 함·무시·내 일 아님·고쳐서 | `app_todo_feedback`(새) | 예시 4종 + 기계 거르기 | `app_todo_rules`(새) |
| 주간보고 초안 | 그 주 행 `draft->'proposed'` | 고침·뺌·더함(칸 비교) | `draft->'feedback'`(주마다) | 지난 4주 고침 → 규칙 | `draft->'rules'` v2(#1663·#1667) |
| 주간보고 제안 줄 | `draft->'picks'` | 받음·[×] | 같은 칸 | 없음(추정) | 없음 |
| 원장 자동 기록 | 원장 표(더하기만) | '원장 수정 요청'·대체됨 | 원장 자체(옛 기록 '대체됨') | 없음 | 없음 |
| 자료실 AI 분류·채우기 | 문서 칸 직접 채움(`library_fill`·`library_ai_classify`) | 사람이 고침 | 없음(덮어씀) | 없음 | 없음 |
| 텔레그램 나한테 온 요청 | 후보 표(텔레그램 출처) | 챙길 것과 같음 | 이 설계로 함께 기록 | 내 일 아님 예시만(collector-feed) | 없음 |
| 일정 제목 다듬기·파일 이름·노트 제목 | 화면에 제안만 | 받음·안 받음 | 없음 | 없음 | 없음 |

판단(추정):

- **공용 "결과 기록" 모양은 묶을 만하다**: `{기능, 제안 문장, 결과(수용·수정·삭제·추가), 고친 문장, 출처 종류, 때}`. 챙길 것 표(`app_todo_feedback`)가 이 모양의 첫 사례가 되게 칸 이름을 일반적으로 잡았다(`outcome`·`summary`·`edited`).
- **지금 하나로 합치지는 않는다**: 주간보고는 "칸 비교" 기반(줄 단위 결과가 아님)이고 이미 운영 중인 JSON 칸이다. 옮기면 데이터 이전·두 화면 동시 수정이 필요해 위험이 크다. 세 번째 기능(자료실 분류 등)에 환류를 붙일 때 `app_todo_feedback`을 `app_ai_feedback`(기능 칸 하나 더함)으로 넓히는 것을 그때 검토한다.
- 규칙 후보→확정 버튼은 이미 두 곳(주간보고·챙길 것)에서 같은 모양이므로, 화면 부품(후보 줄 [ㅇ][×][고쳐서 확정])을 공용으로 빼는 것은 D에서 시도한다(같은 부품 재사용, 새로 그리지 않기).
