## 1. 휴대폰 본인인증 연동 방법 조사

### 1.1 직접 계약 vs 통합 연동

| | 본인확인기관 직접 계약(NICE평가정보·코리아크레딧뷰로(KCB)·통신사 PASS 등) | 포트원 같은 통합 연동 |
| --- | --- | --- |
| 계약 상대 | 기관마다 따로(심사·서류·가입비) | 포트원 1곳 + 포트원이 중개하는 인증사(다날·KG이니시스) |
| 연동 | 기관마다 다른 모듈·암복호화 | 브라우저 SDK + 서버 REST 조회 하나 |
| 비용 | **[확인 필요]** 기관별 견적 | 다날 직계약 가입비 10만 원이 포트원 경유 시 무료라고 안내 [확인], 건당·월정액은 1.3절 |
| 판단 | 1인 운영·투표 단위 소량 사용에 맞지 않음 | **추천** — 서버 검증 구조가 단순하고 인증사를 바꿔도 코드가 거의 같음 |

- 본인확인기관은 "주민등록번호 외의 대체수단(인터넷개인식별번호, 휴대폰, 신용카드, 인증서 등)을 통해 본인확인을 해주는 기관"이고 정보통신망법 제23조의3에 따라 지정된다 [확인, 법무법인 세종 2026-05 뉴스레터]. 우리 서비스는 기관이 아니라 **이용자(이용기관)** 이므로 지정을 받을 일은 없다.
- 토스 인증도 '본인확인' 상품(CI/DI 제공, 서버 간 결과조회)을 직접 제공한다 [확인]. 결과조회가 성공 기준 최대 2회·완료 후 60분 안이고, 개인정보가 암호화되어 와서 복호화 절차가 따로 필요하다 [확인]. 비용·계약 조건은 문서에 없음 [확인 필요]. 포트원이 막히면 두 번째 후보로 둔다.

### 1.2 포트원 V2 본인인증 흐름 [확인]

1. 브라우저(앱 화면)가 포트원 브라우저 SDK로 본인인증 창을 띄운다. 인증 ID(`identityVerificationId`)는 **서버가 먼저 만들어** 화면에 준다(우리 쪽 투표·명부 행과 묶기 위해).
2. 사용자가 PASS 앱 또는 문자(SMS)로 인증한다.
3. 화면은 "끝났다"고만 서버에 알린다. 서버(Edge 함수)가 `GET /identity-verifications/{id}`로 포트원에 직접 조회한다. 서버 SDK 기준 클라이언트는 `secret`(포트원 API Secret), `base_url`(기본 `https://api.portone.io`)을 받는다.
4. 응답이 `VerifiedIdentityVerification`이면 `verified_customer`에 `name`, `phone_number`(숫자만), `birth_date`(yyyy-MM-dd), `gender`, `is_foreigner`, `ci`, `di`, `operator`가 온다. 실패는 `FailedIdentityVerification`, 진행 중은 `ReadyIdentityVerification`. 시각은 `requested_at`·`verified_at`(RFC 3339).
   - **인증사마다 주는 칸이 다르다**: 다날은 `ci`를 늘 준다, KG이니시스는 `di`를 주지 않는다, 다날의 `operator`·`phone_number`·`is_foreigner`는 **별도 계약**이 필요하다 [확인, 서버 SDK 설명]. → 명부 대조에 전화번호를 쓰려면 다날 계약 때 '휴대폰 번호 제공'을 함께 신청해야 한다(8절 사용자 할 일).
5. 다건 조회 API는 포트원 기술지원에 목적·기간을 보내야 쓸 수 있다고 적혀 있다 [확인]. 우리는 단건 조회만 쓴다.
6. 인증 정보 삭제: V1(아임포트)에는 `DELETE /certifications/{imp_uid}`(영구 삭제)가 있다 [확인]. **V2 삭제 API는 확인하지 못했다** [확인 필요]. 포트원 쪽 보관 기간·삭제 요청 방법을 계약 때 묻는다.
- 인증 헤더 형식·V2 브라우저 SDK 인자 이름(`redirectUrl` 등)은 V2 가이드 페이지를 이번에 읽지 못했다 [확인 필요 — 구현 PR 첫 단계에서 공식 문서로 고정].

### 1.4 안드로이드 앱(WebView)·PC 웹에서 동작

- **PC 웹**: SDK가 팝업(또는 화면 안 창)으로 인증창을 띄운다. 팝업 차단을 피하려면 버튼 누름과 같은 흐름에서 창을 열어야 한다(토스 문서도 같은 주의, `preparePopup()` 먼저) [확인 — 토스 문서]. 포트원 V2 PC 기본 방식은 [확인 필요].
- **폰 앱(우리 안드로이드 앱)**: 지금 앱은 앱 안 주소가 아닌 https 주소를 **Custom Tab(크롬 탭)** 으로 열고(`ShellRules.opensOutside` → `openTab`), `intent://`는 `openIntentUri`로 처리하며, 새 창은 막혀 있다(`setSupportMultipleWindows(false)`) — 저장소 `android-app/.../MainActivity.kt` 확인.
  - 그래서 앱에서는 **리디렉션 방식**으로 연다: 인증창 주소가 Custom Tab에서 열리고, PASS 앱 호출(`intent://`)은 크롬 탭이 처리한다. 일반 WebView에서 PASS 앱을 부르려면 `shouldOverrideUrlLoading`에서 `intent` 스킴을 `Intent.parseUri(..., URI_INTENT_SCHEME)`로 실행하고 앱이 없으면 `market://`으로 보내야 한다는 것이 토스 문서·개발자 글의 공통 안내다 [확인]. 우리 앱은 이 처리가 이미 있다.
  - 인증이 끝나면 리디렉션 주소(우리 https 페이지)가 Custom Tab에 뜬다. 그 페이지는 결과를 판정하지 않고 "앱으로 돌아가기"(`kptuwork://` 돌아오기 — `ShellRules.isAppReturn`)만 한다. 앱 화면은 돌아오면 **서버에 인증 ID 상태를 물어** 다음 단계로 간다. 판정은 늘 서버이므로 어느 창에서 끝나도 결과가 같다.
  - 돌아오기 경로 허용 목록에 투표 경로를 더하는 것은 앱 변경 → 폰 앱 릴리스가 필요할 수 있다 [확인 필요, 구현 때 `ShellRules` 시험으로 확인].
- 삼성 인터넷·크롬(폰 웹)은 SDK의 모바일 리디렉션 방식 그대로 동작한다 [추정].

## 2. 서버 흐름 (Supabase Edge)

새 함수 2개(이름은 제안). 둘 다 `docs/web2-env6b-edge-source.md` 5절 표에 먼저 올리고 `first_deploy=true`로 하나씩 배포한다(AGENTS.md 8절).

| 함수 | verify_jwt | 하는 일 |
| --- | --- | --- |
| `union-vote-auth` | `true` | ① 인증 시작: 로그인 사용자·투표·명부 확인 → 인증 ID 발급 ② 인증 확인: 포트원 조회 → 명부 대조 → 인증 표시 → 블라인드 서명 투표권 발급 |
| `union-vote-cast` | `false`(코드에서 투표권 서명 검사) | 표 넣기. **로그인 토큰을 받지 않는다**(받으면 사람과 표가 이어질 길이 생김). 투표권 서명·사용 여부만 본다 |

### 2.1 인증 시작 `POST union-vote-auth {op:'start', vote_id}`

1. `auth.uid()` 확인(비로그인 401).
2. DB 함수 `app_union_vote_auth_start(vote_id)`(security definer)가 확인: 투표가 `open` 상태, 부른 사람이 그 노조 묶음 현재 멤버, 이 투표에서 아직 투표권을 받지 않음, 결제 확인됨(6절), 하루·투표별 시도 횟수 제한(예: 투표당 5회).
3. 서버가 추측 불가 인증 ID(`uv_` + 128비트 무작위)를 만들고 `app_union_vote_auth_attempts`에 (vote_id, user_id, 인증 ID 해시, 만든 시각, 상태 `ready`)를 남긴다. 화면에는 인증 ID와 포트원 공개값(storeId·channelKey — 비밀 아님)만 준다.

### 2.2 인증 확인 `POST union-vote-auth {op:'confirm', vote_id, identity_verification_id, blinded_token}`

1. 인증 ID가 **이 사용자·이 투표로 2.1에서 만든 것**인지 DB에서 확인(남의 인증 ID 재사용 막기). 한 번 확인한 ID는 다시 못 씀.
2. 포트원 서버에 `GET /identity-verifications/{id}` (API Secret은 Edge 비밀값에서만 읽음, 로그에 찍지 않음).
3. 다음을 모두 만족해야 통과:
   - 결과가 `VERIFIED`이고 `verified_at`이 2.1 시각 이후 30분 안
   - 응답의 인증 ID·storeId가 우리가 만든 값과 같음
   - 명부 대조(3.2절)에서 **정확히 1행**과 일치하고 그 행이 아직 인증 안 됨
   - 같은 투표에서 같은 사람(CI 지문, 3.1절)이 다른 명부 행·다른 로그인 계정으로 이미 인증하지 않음
4. 통과하면 한 트랜잭션에서: 명부 행 `verified=true`, 사람 표시 `app_union_vote_voters`(vote_id, user_id, roll_row_id, ci_mark, verified_at_hour) 1행, 시도 상태 `verified`. 그리고 화면이 보낸 **가린 투표권(blinded_token)에 투표별 키로 서명**해 돌려준다(4.2절). 서명은 한 사람 한 번만.
5. 포트원 응답 원문(`pg_raw_response` 포함)은 함수 메모리에서만 쓰고 버린다. DB·로그·오류 메시지에 이름·전화·생년월일·CI·DI를 넣지 않는다. 오류 응답은 이유를 뭉뚱그린다("인증을 확인하지 못했습니다" / "명부와 맞지 않습니다 — 투표관리자에게 문의").
6. 화면이 보낸 값 중 믿는 것은 vote_id·인증 ID·가린 투표권뿐이고, 셋 다 서버가 다시 확인한다(AGENTS.md 3절 3). 사용자 ID·명부 행·노조는 받지 않는다.

## 3. 무엇을 저장하나 — 최소 보관

### 3.1 원칙

- 노동조합 가입·탈퇴 정보는 개인정보 보호법 제23조의 **민감정보**다 [확인, 법 조문]. 명부(누가 조합원인가) 자체가 민감정보이고, 인증 기록도 "이 사람이 이 노조 투표에 참여했다"는 사실이라 민감정보다.
- 그래서 남기는 것은 **"이 투표에서 이 명부 행이 인증됨"** 뿐이다.

| 값 | 저장 | 방식 |
| --- | --- | --- |
| 이름·생년월일·전화(인증 결과) | **안 함** | 대조에만 쓰고 버림 |
| CI | 원값 안 함 | `ci_mark = HMAC-SHA256(서버 비밀 pepper, 투표별 salt ‖ CI)` — 같은 투표 안 이중 인증 막기용. 투표별 salt라 **다른 투표끼리 같은 사람인지 이을 수 없음** |
| DI | 안 함 | 쓰지 않음 |
| 인증 시각 | 시(hour) 단위로 내림 | 4.4절 시각 맞추기 공격 줄이기 |
| 투표권과 사람 연결 | **아예 생기지 않음** | 4.2절 블라인드 서명 |
| 투표 salt | 투표 행에 | 마감 + 보관 기간 뒤 salt를 지우면 `ci_mark`는 아무것과도 대조할 수 없게 됨(7.4절) |

- pepper는 DB에 두지 않고 Edge 비밀값에만 둔다(DB만 새도 대조표를 못 만들게). pepper·salt는 HMAC 키이므로 원값과 지문이 같은 곳에 있지 않다.
- 포트원·다날도 인증 정보를 자기 쪽에 보관한다. 보관 기간·삭제 방법은 계약 때 확인 [확인 필요].

### 3.2 명부 대조

- 명부는 투표관리자가 투표마다 올린다(CSV: 이름·생년월일·휴대폰). 명부는 노조의 자료이고, 우리는 그 처리를 맡는 쪽이다(7.4절 위탁).
- 저장: 행마다 `roll_key = HMAC(pepper, 투표 salt ‖ 정규화(이름)|생년월일|전화)` + 투표관리자에게만 보이는 표시용 `label`(이름 + 전화 끝 4자리). 전체 전화번호·생년월일 원문은 올린 뒤 저장하지 않는다.
- 대조: 인증 결과로 같은 방식의 키를 만들어 `roll_key`와 비교. 정규화는 이름 앞뒤 공백·가운데 공백 제거, 전화는 숫자만(`010…`).
- 맞지 않을 때(번호 변경·개명): 투표관리자가 그 행을 고쳐 올린다(고친 사람·시각만 기록). "명부에 없음" 사유를 서버가 사람에게 자세히 알려 주지 않는다(누가 조합원인지 떠보기 막기).
- 다날이 전화번호를 주지 않는 계약이면 이름+생년월일만으로 대조해야 하는데 동명이인·같은 날 생일이 겹칠 수 있다 → 일치 2행 이상이면 거절하고 관리자 확인으로 보낸다. **전화번호 제공 계약을 추천**(8절).

## 4. 비밀투표 — 인증과 표의 분리

### 4.1 목표

1. 한 명부 행 = 한 표(이중 투표 없음)
2. 누가 무엇을 찍었는지 **서버·운영자·투표관리자·간부 누구도 이을 수 없음**
3. 결과를 나중에 다시 셀 수 있음(재검표)

### 4.2 블라인드 서명 투표권 (추천)

"표에 사람 칸이 없다"만으로는 부족하다. 서버가 투표권을 만들어 주면 서버는 그 투표권이 누구 것인지 안다. 그래서 **서버가 내용을 보지 못한 채 서명하는 방식**(RSA 블라인드 서명, RFC 9474)을 쓴다.

1. 투표를 열 때 서버가 투표별 RSA 키쌍을 만든다. 공개키는 투표 행에 공개, 비밀키는 Edge 쪽에서만 쓰는 저장소(Vault 등)에 두고 마감 때 지운다 [구현 방식 확인 필요].
2. 인증 전에 화면(사용자 기기)이 무작위 투표권 `t`를 만들고 가려서(blind) `blinded_token`만 서버에 보낸다.
3. 인증 통과 시 서버는 가린 값에 서명해 돌려준다(2.2-4). 서버는 `t`를 본 적이 없다.
4. 화면이 가림을 벗겨 `(t, 서명)`을 얻는다. 이 쌍은 서버가 서명한 것으로 검증되지만, 서버는 어느 서명 요청에서 나온 것인지 알 수 없다.
5. 표 넣기 `union-vote-cast {vote_id, t, 서명, choice}` — 로그인 없이 보낸다. 서버는 서명 검증 → `spent_tokens`에 `hash(t)`가 없으면 넣고(고유 제약) → `ballots`에 (무작위 id, vote_id, choice)만 넣는다. 한 트랜잭션.
- 이중 투표: 서명은 사람당 한 번(2.2), `t`는 한 번만 쓰임(고유 제약). 둘 다 서버 DB 제약으로 지킨다.
- Deno에서 쓸 수 있는 RFC 9474 라이브러리(예: Cloudflare `blindrsa-ts`)는 구현 PR에서 고정 버전·검토 후 확정 [확인 필요].
- 투표권은 기기 메모리에만 둔다(서버에 저장하지 않음 — 서버에 두면 사람과 이어짐). 이것은 '기록 저장'이 아니라 몇 분짜리 1회용 열쇠라 "웹 저장은 서버" 원칙의 예외로 문서에 적는다(7.3절 개정안). 앱이 꺼져 표를 못 넣었으면 **다시 받을 수 없다**(다시 주면 이중 투표 길이 생김). 대신 인증 직후 바로 같은 화면에서 표를 넣게 하고, 결과 확인서에 '투표권 발급 수 − 투표 수'를 그대로 적는다.

### 4.3 대안 (블라인드 서명이 늦어질 때)

- 서버가 투표권을 만들어 주고 그 해시만 `tokens`에 사람 칸 없이 저장. 표 구조는 같다. 단 서버가 발급 순간에 사람과 투표권을 함께 본다 → "운영자도 연결 못 함"을 **구조가 아니라 운영 약속으로만** 지키게 된다. 효력 있는 투표(규약 개정·쟁의 찬반)에는 쓰지 않고 일반 의견 투표에만 쓴다.

### 4.4 남은 연결 경로와 막기

| 경로 | 막기 |
| --- | --- |
| 표 표에 시각 칸 | `ballots`에 시각을 두지 않음. 마감 여부는 투표 상태로만 판정 |
| 행 순서·연속 id로 인증 순서와 맞추기 | 표 id는 무작위 uuid, 집계·내려받기는 id 순 정렬 |
| Edge·API 접속 기록의 시각·IP | 표 넣기는 로그인 토큰 없이 보냄. 그래도 Supabase 플랫폼 로그에 시각·IP가 남는다 → 함수 코드는 투표 내용·투표권을 로그에 쓰지 않음, 화면은 인증 직후 바로 보내지 않고 '표 넣기' 버튼을 사람이 누를 때 보냄. 플랫폼 로그 보관 기간·접근자는 [확인 필요]. 이것이 남은 위험의 핵심이고 결과 확인서·안내문에 적는다 |
| 투표 중간 집계로 '방금 넣은 표' 알아내기 | 마감 전에는 누구에게도 집계를 주지 않음(투표 수만) |
| 투표 수가 아주 적은 투표 | 명부 3명 미만이면 비밀 보장 투표로 열 수 없음(서버 거절) [추정 — 숫자는 결정] |
| 운영자가 DB 주인 권한으로 표 열기 | 3절 '남의 기록 안 보기' — 운영 확인은 개수만. 표 내용은 결과 확인서로만 |

### 4.5 결과 확인서 (자동 발급)

마감 시각이 되면 서버(예약 작업 `pg_cron` 또는 첫 조회 때)가 투표를 `closed`로 바꾸고 한 번만 만든다.

- 담는 값: 투표 제목·종류(규약 개정/쟁의 찬반/일반), 의결 기준(예: 재적 과반 투표·과반 찬성), 개시·마감 시각(연장 기록 포함), 명부 수, 인증 수, 투표권 발급 수, 투표 수, 선택지별 집계, 기준 충족 여부, `ballots_hash`(표를 정해진 순서로 이어 SHA-256), 공개키 지문, 확인서 자체 해시, 발급 시각.
- 투표 수 = 사용된 투표권 수 = 표 수가 서로 맞는지 서버가 검사하고 확인서에 '일치'를 적는다. 안 맞으면 발급하지 않고 투표관리자에게 알린다.
- 노조 묶음 멤버 누구나 확인서를 본다. PDF 내려받기는 화면 기능으로.
- 재검표: 참관인·투표관리자는 표 목록(무작위 id·선택만)을 내려받아 다시 세고 `ballots_hash`와 맞춘다.
- 내 표가 들어갔나: 표를 넣을 때 화면에 '접수 번호'(표 id 앞 8자리)를 보여 주고, 마감 뒤 "이 번호가 집계에 들어 있음"만 확인해 준다. 공개 표 목록에 접수 번호와 선택을 함께 싣지 않는다(표를 증명해 팔거나 강요받는 일을 막기 위해).

### 4.6 개표 참관

- 투표를 만들 때 참관인(노조 멤버 중 1~3명)을 지정. 참관인은 마감 즉시 같은 시각에 집계·표 목록·확인서를 본다. 마감 전에는 참관인도 투표 수만 본다.
- 참관인·투표관리자 지정·변경은 `app_union_vote_staff_log`에 남는다.

### 4.7 장애 때 연장 규칙

- 투표 공고에 미리 적는 기본 규칙(투표를 만들 때 화면에서 함께 정함):
  - 인증사·서버 장애가 마감 전 2시간 안에 30분 이상 이어졌으면 투표관리자가 **한 번, 최대 24시간** 연장할 수 있다 [추정 — 숫자 결정 필요].
  - 연장은 마감 전에만, 투표관리자 2명(또는 관리자 1명 + 참관인 1명) 확인으로, 사유를 적어야 한다. 마감 뒤 연장·재개는 불가 — 새 투표로.
  - 연장 기록(누가·언제·사유·새 마감)은 확인서에 그대로 실린다.
- 장애 판단 근거: 서버가 인증 시도 실패율(개수만)을 시간별로 남겨 관리자 화면에 보여 준다.

## 5. 법·규약 쪽 확인

- 노동조합 및 노동관계조정법: 규약 변경은 총회(대의원회)에서 재적 조합원 과반수 출석과 출석 조합원 3분의 2 이상 찬성(제16조 제2항), 규약 제정·변경 등은 직접·비밀·무기명 투표(제16조 제4항), 쟁의행위는 조합원의 직접·비밀·무기명 투표로 과반수 찬성(제41조 제1항) [법 조문 기준, 최신 조문은 법제처에서 재확인 필요].
- 전자투표가 '직접·비밀·무기명'을 채운다고 인정받는지에 대한 고용노동부 해석·판례는 이번에 확인하지 못했다 [확인 필요 — 노무사·변호사 자문 권장]. 이 문서의 4절 구조(사람-표 연결 불가, 이중 투표 불가, 재검표 가능, 결과 확인서)는 그 판단에 낼 근거 자료가 되도록 짰다.
- 투표 종류별 의결 기준은 노조마다 규약이 다르므로 투표를 만들 때 기준을 고르게 하고(서버는 계산만), 법 기준을 서버가 대신 판정하지 않는다.

## 6. 과금 연결 지점

결제 수단은 사용자가 정한다. 여기서는 **붙일 자리와 서버 차단**만 정한다.

- 투표 행 칸: `identity_required`(본인인증 사용), `expected_voters`(명부 수로 자동), `unit_price_won`(개설 시점 단가를 복사해 고정), `estimate_won`, `billing_status`(`not_needed`·`pending`·`paid`·`waived`), `billing_ref`(결제 기록 id — 결제 내용 아님).
- 예상 비용 = 명부 수 × (1 + 재시도 여유율, 예 20%) × 단가 [추정]. 실제 청구용 사용 건수는 `app_union_vote_auth_attempts`의 포트원 조회 횟수(개수만).
- `app_union_vote_open(vote_id)`(서버)는 `identity_required = true`이고 `billing_status`가 `paid`·`waived`가 아니면 **거절**한다. 화면에서 버튼을 숨기는 것으로 막지 않는다.
- `billing_status`를 `paid`로 바꾸는 길은 둘만: ① 결제사 웹훅을 받는 Edge 함수(결제사 서명 검증 후, 나중 단계) ② 운영자 SQL(지금 단계, 입금 확인 뒤). 화면·API로 노조가 스스로 바꿀 수 없다. 운영자는 투표 제목이 아니라 투표 id·노조 묶음 id·예상 금액만 보고 처리한다.
- 명부 수가 결제 뒤 늘면(예상의 110% 초과) 추가 결제 전까지 그 투표의 인증 시작을 멈춘다 [추정].
- 단가 표(`app_union_vote_prices`)는 SQL로만 쓴다(`app_operator_features`와 같은 방식).

## 7. 기존 구조 재사용과 규칙 개정안

### 7.1 표 (모두 RLS 켬, 정책 없음, API 역할 표 권한 없음, `security definer` 함수로만)

| 표 | 주요 칸 | 사람 연결 |
| --- | --- | --- |
| `app_union_votes` | id, group_id(노조 묶음), title, kind, rule, options, opens_at, closes_at, status(`draft`·`open`·`closed`·`void`), salt, public_key, identity_required, billing 칸(6절) | — |
| `app_union_vote_staff` | vote_id, user_id, role(`manager`·`observer`) | 간부 역할만 |
| `app_union_vote_roll` | id, vote_id, roll_key, label, verified | 명부(민감) — 관리자만 label 봄 |
| `app_union_vote_auth_attempts` | vote_id, user_id, verification_id_hash, status, created_hour | 있음(누가 인증 시도) — 표와 연결 없음 |
| `app_union_vote_voters` | vote_id, user_id, roll_row_id, ci_mark, verified_hour | 있음(누가 인증됨) — 표와 연결 없음 |
| `app_union_vote_spent` | vote_id, token_hash | **없음** |
| `app_union_vote_ballots` | id(무작위), vote_id, choice | **없음** |
| `app_union_vote_receipts` | vote_id, 4.5절 값, hash | 없음 |
| `app_union_vote_staff_log` | vote_id, actor, event, at | 간부 행동만 |

- 사람 쪽 표(attempts·voters)와 표 쪽 표(spent·ballots)는 **서로 참조 키가 없다**. 정적 시험으로 "ballots·spent를 읽거나 쓰는 함수는 cast·집계·확인서 함수뿐, 그 함수들은 user_id·auth.uid()를 읽지 않는다"를 지킨다.
- 노조 묶음은 `app_collab_groups`(kind `union`)·`app_collab_members`를 그대로 쓴다(`docs/design/collab-sharing.md` 3절). 투표 만들기는 묶음 `admin`만, 투표관리자·참관인 지정은 투표 만든 사람·묶음 관리자. 다른 묶음의 투표는 존재 여부조차 돌려주지 않는다.
- 투표·명부·표는 어느 개인 작업공간에도 속하지 않는 **묶음 소유 자료**다. 개인 작업공간의 owner 정책은 한 줄도 바꾸지 않는다.
- 올인원 다이어리 얼굴(`docs/design/allinone-diary-plan.md`)에서는 투표 메뉴·경로를 빼고, 서버도 그쪽 Supabase 프로젝트에 이 함수를 배포하지 않는다.

### 7.2 위협 모델과 거절 시험 (구현 단계에서 추가)

| 위협 | 막는 곳 | 시험 |
| --- | --- | --- |
| 화면이 "인증 성공"을 꾸며 보냄 | 서버가 포트원에 직접 조회 | 포트원 응답 `FAILED`·`READY`·다른 storeId 모의 → 거절 |

### 7.3 AGENTS.md 개정안 (구현 1단계 PR에서 반영, 3절 보안 규칙은 바꾸지 않음)

1. **5절 첫 문단 공유 경로 목록에 (c) 추가**:
   > (c) group-owned union-space records (notices, boards, votes, library — UNION-노조공간), which belong to a union group rather than to any personal workspace and are read and written only through `app_union_*` SECURITY DEFINER functions that check current membership and role from `auth.uid()`. Votes keep identity (who was verified) and ballots (what was chosen) in separate tables with no link between them (`docs/design/union-vote-identity.md`).
   - 지금 D1 문단의 "공유 종류는 캘린더·사업 영역·담당조직·자료실 폴더 네 가지뿐"과 겉으로 부딪힌다. 노조 공간 자료는 '내 것을 켜서 나누는 공유'가 아니라 처음부터 묶음 소유라서 다른 길로 적고, 네 가지 제한(텔레그램·통화·가족은 어떤 길로도 안 열림)은 그대로 둔다.
2. **3절 '남의 기록 안 보기'에 한 줄**: "투표 명부·인증 기록·표는 운영자도 내용을 보지 않는다. 운영 확인과 과금은 투표 id·개수·금액만."
3. **1절 운영 토큰 줄 보완**: 지금은 운영 비밀값을 GitHub `production-edge` environment에만 두고 workflow는 비밀값을 바꾸지 않는다. 이 기능은 Edge 실행용 비밀값(`PORTONE_API_SECRET`, `UNION_VOTE_PEPPER`)이 Supabase 함수 비밀값에 있어야 한다. 두 안:
   - (가·추천) 원본은 GitHub `production-edge` environment 비밀값에 두고, 새 승인형 workflow `edge-secret-set.yml`이 이름이 정해진 비밀값만 Supabase 함수 비밀값으로 옮긴다(값은 출력하지 않음, 이름 허용 목록, `production-edge` 승인). AGENTS.md 1절 표의 "비밀값 변경 금지" 줄에 "허용 목록 이름만, 이 workflow로만" 예외를 적는다.
   - (나) 사용자가 Supabase 대시보드 Edge Functions → Secrets에 직접 넣는다(지금 규칙 그대로, 1절 "비밀값 변경은 대시보드").
4. **개발 원칙 '로컬 저장 금지' 예외 한 줄**(프로젝트 지침·문서): "투표권(블라인드 서명 1회용 열쇠)은 비밀투표를 위해 기기 메모리에만 둔다."

### 7.4 개인정보 처리 구조

- 명부·투표의 개인정보처리자는 **노조**, 서비스(사용자)는 처리를 맡는 **수탁자**다(개인정보 보호법 제26조) [추정 — 자문 권장]. 노조와 위탁 계약(목적·항목·보관 기간·파기·재위탁(포트원·다날) 명시)이 필요하다.
- 노조 가입 정보(민감정보)는 정보주체 별도 동의 또는 법령 근거가 있어야 처리한다(제23조). 노조 공간 가입 때 '투표 명부 대조에 이름·생년월일·휴대폰을 쓰는 것'에 대한 동의 문구를 둔다(문구는 화면 단계).
- 보관: 명부 `roll_key`·`label`, `voters`, `attempts`는 마감 + 이의 제기 기간(예: 30일 [결정 필요]) 뒤 지우고, salt도 지운다. 표·확인서는 노조 보관 기간(규약)까지 남긴다. 표에는 사람이 없으므로 남겨도 민감정보가 아니게 된다.

### 8.2 사용자 할 일 (순서대로)

1. 사업자 등록(이미 하기로 함).
2. 포트원 가입 → 상점 만들기 → '본인인증' 신청에서 **다날 휴대폰 본인인증** 고르기. 신청할 때 **휴대폰 번호·통신사·내외국인 정보 제공**도 함께 요청(다날은 별도 계약이라고 적혀 있음).
3. 계약할 때 포트원에 물어볼 것(답을 CC에 전달):
   - 월 정액 요금제가 지금도 같은지, 남는 건수 이월, 실패·중단 건 과금, 초과 단가
   - V2에서 인증 정보 삭제 방법·포트원/다날 보관 기간
   - 웹뷰 앱(크롬 탭으로 여는 방식)에서 문제 없는지
4. 테스트용 키를 받으면 **채팅에 붙이지 말고** GitHub 저장소 → Settings → Environments → `production-edge` → Secrets에 `PORTONE_API_SECRET` 이름으로 넣기(7.3-3 (가)안일 때). storeId·channelKey는 비밀이 아니므로 CC에 알려 줘도 됨.
5. 노무사·변호사에게 한 번 확인: "이 구조(5절·4절)의 전자투표가 규약 개정·쟁의 찬반 투표로 효력이 있는가", "노조와 맺을 개인정보 위탁 계약서 양식".
6. 결정할 것(일상어): ① 비밀값 넣는 방법 (가) GitHub에 넣고 자동으로 옮기기 / (나) Supabase 화면에 직접 ② 노조에 받을 1인당 인증비 ③ 장애 연장 규칙 숫자(30분·24시간) ④ 명부 보관 기간(마감 뒤 30일) ⑤ 비밀투표로 열 수 있는 최소 인원(3명).
