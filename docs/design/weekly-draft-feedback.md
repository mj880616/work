## 0. 한 줄 요약

- **임시저장**: 한글 파일 상자에서 고치던 것(줄 글·일정 제목·이름·일시)을 그 주 "요청 표" 행(이미 주마다 1행인 서버 표)에 칸 하나 더해 저장한다. 새 표를 만들지 않는다.
- **환류**: [확정] 때 달력 제목과 다르게 고친 일정 이름·뺀 일정을 **원래 제목**을 열쇠로 내 프로필 칸 하나에 기억하고, 다음 주 초안을 만들 때 먼저 적용한다. Google Calendar 원본은 건드리지 않는다. 회의 종류 빼기(이미 프로필에 있음)와 같은 방식이다.

## 1. 현재 구조 (사실)

### 1.1 초안이 만들어지고 고쳐지는 곳

업무일지 [주간 정리] 탭(`app/journal.js` + `app/journal-weekly.js`)이 그 주 기록을 양식 순서로 모아 보여 주고, 맨 위 [주간보고 한글 파일 만들기] 상자(`app/journal-hwpx.js`)에서 명진이 고쳐 파일을 만든다.

1. 바탕: 지난주 팀 확정본(자료실 분류 "주간보고 확정본" 최신 또는 기기 파일)을 기기 안에서 읽어 **내 줄**만 남긴다(`weekly-hwpx/draft.mjs` `startDraft`).
2. 고치기: 요약 내 줄·투쟁 사업장·산하조직 칸(글 칸), 담당 팀원 칸 이름, ■ 일시, 5. 주요 일정 제목·장소(제목 확인 목록, [AI로 다듬기]는 제안만).
3. 받기·확정: .hwpx / HWP로 받기, [확정]은 `library-files`로 자료실(Drive)에 "주간보고 개인본"으로 1회 저장(`app/hwp-drive.js` `saveWeeklyReport`).

### 1.2 지금 서버에 저장·기억하는 것

| 무엇 | 어디(서버) | 언제 쓰임 | 환류 성격 |
| --- | --- | --- | --- |
| 회의 종류 빼기 | `app_profiles.weekly_hidden_meeting_kinds` text[] (migration `20261022090000`, `app/journal-meeting-kinds.js`) | [주간 정리] 회의·활동 결과에서 [주간보고에서 빼기]/[다시 올리기]. 열쇠 = 회의 이름(띄어쓰기 없음·소문자) | **있음** — 다음 주에도 빠짐 |
| 임원 요청 표 줄 | `app_weekly_exec_requests` 주마다 1행(`items` jsonb, `carried_at`) (migration `20261023140000`, `app/weekly-exec-requests.js`) | [주간 정리] 1. 요청사항 › 1). 쓰기는 `updated_at=eq.<읽은 값>` 조건 PATCH(다른 기기가 먼저 썼으면 다시 읽고 한 번 더) | 지난주 확정본 줄을 그 주 한 번만 가져옴 |
| 조직 현황 요약 | `app_weekly_org_summaries` 주×조직 1행, `edited` 표시 (migration `20261022140000`) | 고친 요약은 AI 다시 만들기가 덮지 않음 | 그 주 안에서만 |
| 확정본 파일 | 자료실(`app_documents` + Drive) "주간보고 개인본" | 다음 주 바탕은 팀 확정본("주간보고 확정본") | **본문 글은 이미 환류됨** — 내가 고친 줄은 팀 확정본에 들어가고, 다음 주 바탕이 그 확정본이라 그대로 이어짐 |

### 1.3 지금 저장하지 않는 것 (상자 메모리에만, 브라우저 저장소도 없음)

`app/journal-hwpx.js`의 `state`(파일 첫머리 주석: "브라우저 저장소에 아무것도 두지 않는다"):

| 값 | 내용 | 사라지는 때 |
| --- | --- | --- |
| `state.edits` | 칸별(요약·산하조직·투쟁 사업장) 줄 글. 열쇠는 바탕 줄 번호(`row.index`) | 상자를 닫거나, 주를 바꾸거나(`setWeek`), [처음부터], 새로고침, 다른 기기 |
| `state.titles` | 5. 주요 일정 제목·장소 고친 값. 열쇠 = 일정 키 `달력id:일정id`(`journal-weekly.js` `upcomingSchedule`) | 위와 같음 |
| `state.me`, `state.date` | 담당 팀원 칸 이름, ■ 일시 | 위와 같음 |
| [붙이기] 짝 | "줄을 찾지 못한 기록"을 붙일 줄 | 기억하지 않음(weekly-hwpx-draft.md 13.4) |

- 5. 주요 일정에는 지금 **[빼기]가 없다**(사실). 빼려면 달력에서 지우거나 파일을 받은 뒤 한글에서 지워야 한다. 그래서 환류의 "[빼기]로 뺀 항목"은 이 설계에서 새로 생기는 버튼이다(3.4).
- 달력 일정은 매주 새로 읽고, 반복 일정은 회차마다 일정 id가 다르다. Edge `google-calendar`는 `recurring`(참/거짓)만 내주고 반복 묶음 id(`recurringEventId`)는 내주지 않는다(`supabase/functions/google-calendar/index.ts` `normEvent`).
- 5. 주요 일정은 "보고 주 + 그다음 주" 2주라, **이번 주 초안의 둘째 주 = 다음 주 초안의 첫째 주**다. 같은 일정이 두 번 나온다.

## 2. 임시저장 (WEEKLY-임시저장)

### 2.1 무엇을 저장하나

상자의 고친 값만 저장한다. 확정본 파일·바탕 표 전체·이번 주 기록 원문은 저장하지 않는다(바탕은 다시 열고, 기록은 다시 읽는다).

```
draft = {
  v: 1,
  base: {from: "library" | "file", document_id?, file_name, digest},  // digest = 바탕 내 줄 글의 SHA-256 앞 16자
  me, me_from, date,
  rows: [{section: "summary"|"orgs"|"sites", key, n, lines: [..]}],   // 고친 칸만
  titles: [{event, title, place}],                                    // event = 달력id:일정id
  dropped: [event],                                                   // 이번 주만 뺀 일정(3.4)
  confirmed?: {document_id, at}                                       // [확정] 성공 뒤
}
```

- **칸 열쇠**: 지금의 줄 번호(`row.index`)는 바탕이 바뀌면 어긋난다. 저장은 칸 이름으로 한다 — 요약은 `사업영역›세부 과제`, 산하조직·투쟁 사업장은 조직 이름. 같은 이름이 두 번이면 `n`(몇 번째)으로 구분.
- 바탕과 같은 칸은 저장하지 않는다(고친 칸만). 크기 상한 200KB(서버 검사).

### 2.2 어디에 저장하나 — 기존 주 행 재사용 (추천)

주마다 1행 표 `app_weekly_exec_requests`(주간보고 1. 요청사항 표)에 칸 2개를 더한다: `draft jsonb`(비어 있음 = 임시저장 없음), `draft_saved_at timestamptz`.

- 이유: 이미 "작업공간 × 주(월요일)" 1행, owner 정책, 다른 기기 동시 쓰기 처리(조건부 PATCH)가 있다. 같은 주 단위 상태를 두 번째 표로 나누면 "주마다 1행" 표가 둘이 된다(중복 표).
- 서로 방해하지 않게: 요청 표 저장은 지금처럼 `updated_at` 조건, 임시저장은 `draft_saved_at` 조건을 쓴다. 임시저장은 `updated_at`을 바꾸지 않으므로 요청 표를 고치는 다른 기기가 헛 충돌을 겪지 않는다.
- 행이 아직 없으면 임시저장이 `items=[]`로 행을 만든다(지금 요청 표 POST와 같은 길, 409면 다시 읽고 PATCH). `carried_at`은 비운 채라 지난주 줄 가져오기는 그대로 한 번 일어난다.
- 다른 길(채택 안 함): 새 표 `app_weekly_drafts` — 깔끔하지만 같은 모양의 주 행이 하나 더 생긴다. 표 이름("exec_requests")이 내용보다 좁아지는 점은 migration 주석과 이 문서로 밝힌다.

### 2.3 언제 저장하나

- 칸을 고치고 2초 멈추면 자동 저장, 상자를 닫거나 화면이 숨을 때(`visibilitychange`) 한 번 더. 상자 머리에 "임시저장 14:32" / "저장 중…" / "저장 못 함 — [다시]" 한 줄(명진 질문 Q1).
- 확정 전까지 몇 번이든 덮어쓴다(그 주 1행). [확정] 성공 뒤 `confirmed`를 적는다. [처음부터]는 묻고 `draft`를 비운다.
- 기기에만 남는 저장은 쓰지 않는다(로컬 스토리지·IndexedDB 금지, CI `browser-storage-audit` 그대로).

### 2.4 다시 열기·다른 기기에서 이어 고치기

1. 상자를 열면 그 주 행의 `draft`를 읽는다. 있으면 "이 주 임시저장본(10/24 14:32)이 있어요. [이어서 고치기] [처음부터]".
2. [이어서 고치기]: 바탕이 자료실이면 같은 `document_id`를 자동으로 다시 연다. 기기 파일이었으면 "같은 파일을 골라 주세요"(폰에 그 파일이 없을 수 있음 — 위험 7).
3. 바탕을 읽은 뒤 `digest`가 같으면 저장한 칸을 그대로 덮어 놓는다. 다르면(다른 확정본) 이름이 맞는 칸만 넣고, 못 넣은 칸은 "넣지 못한 임시저장 칸 N개"로 접어 글을 보여 준다(복사해 붙일 수 있게, 버리지 않음).
4. 일정 제목(`titles`)·뺀 일정(`dropped`)은 일정 키로 다시 맞춘다. 달력에서 그 일정이 없어졌으면 조용히 버린다.

### 2.5 두 기기에서 동시에 고칠 때

- 쓰기는 `draft_saved_at=eq.<마지막으로 읽은/쓴 값>`(처음이면 `is.null`) 조건 PATCH. 0행이면 그사이 다른 기기가 저장한 것이다.
- 그때 서버 것을 다시 읽어 **칸 단위 3자 비교**: 마지막으로 같았던 판(이 기기가 마지막에 읽은 서버 판) ↔ 이 기기 ↔ 서버.
  - 한쪽만 고친 칸은 자동으로 합친다(합친 결과로 다시 저장).
  - 같은 칸을 양쪽이 다르게 고쳤으면 그 칸만 "다른 기기에서도 고쳤어요: [이 기기 것] [다른 기기 것]"(Q2). 고를 때까지 그 칸은 자동 저장하지 않는다.
- 상자를 다시 열 때·화면이 다시 보일 때 서버 `draft_saved_at`이 더 새로우면 같은 비교를 한다(폰에서 고친 뒤 PC로 돌아온 경우).
- 화면에 "열려 있음" 표시나 잠금은 두지 않는다(혼자 쓰는 앱, 잠금이 풀리지 않는 위험이 더 큼).

## 3. 환류 (WEEKLY-환류)

### 3.1 무엇을 되먹이나 — 범위

| 고친 것 | 지금 다음 주로 가나 | 이 설계 |
| --- | --- | --- |
| 요약·산하조직·투쟁 사업장 줄 글 | **간다**(팀 확정본 → 다음 주 바탕, 1.2) | 손대지 않음 |
| 회의 종류 빼기 | **간다**(프로필 칸) | 그대로, 기억 목록에 같이 보이기만 |
| 5. 주요 일정 제목·장소 고친 것 | 안 감(메모리) | **기억**: 같은 원래 제목 → 고친 이름 |
| 5. 주요 일정 [빼기](새 버튼) | 버튼 없음 | **기억**: 같은 원래 제목 → 빼기 |
| [붙이기] 짝(기록 → 줄) | 안 감 | 2차(Q7 추천: 나중에 따로) |

### 3.2 열쇠 — 원래 제목 (추천)

- 열쇠 = 달력의 **원래 제목**을 띄어쓰기 없이·소문자로 맞춘 글(회의 종류 열쇠 `meetingKindKey`와 같은 규칙). 원래 제목은 Google Calendar에 있는 그대로이며 바꾸지 않는다.
- 일정 id를 열쇠로 쓰지 않는 이유: 반복 일정은 회차마다 id가 다르고, 반복 묶음 id는 지금 Edge가 내주지 않는다(1.3). 제목 열쇠는 반복 일정·다음 주에 겹치는 둘째 주 일정을 모두 덮는다. id만 쓰면 Edge 변경(배포 정지 지점)이 필요하고 얻는 것이 적다.
- 이번 주에만 고친 것(이 회차만 다른 이름)은 임시저장(`titles`, 일정 id 열쇠)에 남고 기억으로 가지 않게 [확정] 때 고를 수 있다(3.3).

### 3.3 언제 기억하나 — [확정] 때 (추천, Q3)

- [확정]이 성공하면 "다음 주에도 쓸까요?" 접힌 목록에 이번 주 달력 제목과 다르게 확정한 일정·뺀 일정이 체크된 채 나온다. [기억하기]를 누르면 체크된 것만 프로필에 쓴다. 체크를 풀면 이번 주만.
- [확정]하지 않고 파일만 받은 주는 기억하지 않는다(확정본이 기준).
- AI가 다듬은 제목도 명진이 그대로 확정하면 고친 것과 같이 기억 후보가 된다(사람이 확정한 값만).

### 3.4 [빼기] 버튼 (새로)

- 한글 파일 상자 "5. 주요 일정 — 제목 확인" 줄마다 작은 [빼기]. 누르면 그 줄은 흐려지고 파일 표에 들어가지 않는다(임시저장 `dropped`). [다시 넣기]로 되돌림.
- 그 주 [확정] 때 3.3의 기억 후보에 "빼기"로 나온다. 같은 제목 일정이 다음 주에도 빠진다(Q4).
- 달력 원본은 지우지 않는다. [주간 정리] 5번 묶음 화면에도 같은 기억을 적용한다(Q6 아래 3.6).

### 3.5 저장 구조 — 내 프로필 칸 하나

`app_profiles.weekly_schedule_memory jsonb not null default '[]'` (회의 종류 `weekly_hidden_meeting_kinds`, 보기 설정 `view_prefs`와 같은 "내 프로필 칸" 방식. 새 표·새 함수 없음).

```
[{ key: "가상결의대회",          // 원래 제목 열쇠(1~200자)
   origin: "가상 결의대회",       // 목록에 보일 원래 제목(200자)
   title?: "OO 결의대회",         // 고친 이름(빼기면 없음, 200자)
   place?: "가상 광장",           // 고친 장소(있을 때만, 100자)
   drop?: true,                   // 빼기
   saved: "2026-10-26",           // 기억한 날(보고일)
   used?: "2026-11-02" }]         // 마지막으로 초안에 적용된 날
```

- 200개까지, 같은 열쇠 한 번. 쓰기는 회의 종류처럼 **쓰기 직전에 다시 읽고 한 항목만 바꿔** 이 칸만 PATCH(다른 기기 변경 보존).
- 만료(Q5 추천): 자동으로 지우지 않는다. 목록에 "N주 안 쓰임"(마지막 적용일 기준)만 보인다. 200개가 차면 가장 오래 안 쓰인 것부터 지운다고 미리 알린다.
- `used`는 [확정] 때(그 주에 실제 적용된 항목만) 한 번에 갱신한다. 초안을 열 때마다 쓰지 않는다.

## 4. DB 변경안 (PR 1, 적용 직전 정지)

두 migration을 한 PR에 둔다. 둘 다 **기존 표에 칸만 더함**, 새 표·새 정책·새 함수 없음, RLS·정책은 그대로(기존 owner 정책이 새 칸도 덮음). 권한 확대 없음.

### 4.1 `<ver>_weekly_draft` — 요청 표 행에 임시저장 칸

- `alter table public.app_weekly_exec_requests add column draft jsonb, add column draft_saved_at timestamptz;`
- CHECK: `draft is null or (jsonb_typeof(draft)='object' and draft->>'v'='1' and octet_length(draft::text) <= 204800)`. 칸 안 모양 검사는 화면이 하고 서버는 크기·형태만(글이 길고 칸이 많아 jsonpath 전수 검사는 과함 — 요청 표보다 느슨한 이유를 migration 주석에 적음).
- 권한: `grant insert (draft, draft_saved_at)`, `grant update (draft, draft_saved_at) on ... to authenticated`(지금 열 권한 방식 그대로, 지우기 권한 없음 그대로). 정책 `weekly_exec_requests_owner_all` 그대로.
- 사전 확인: 이 version 기록 없음, 칸 없음, 표·정책 1개·RLS 켜짐·anon/service_role 권한 없음이 지금 모양일 때만. 사후 확인: 같은 경계 + 새 칸 열 권한이 authenticated에만.
- 되돌리기: `drop column draft_saved_at, drop column draft`(workflow rollback 허용 범위) + 기록 1행 삭제. 임시저장본만 사라지고 요청 표 줄은 그대로.

### 4.2 `<ver>_profile_weekly_schedule_memory` — 프로필 기억 칸

- `alter table public.app_profiles add column weekly_schedule_memory jsonb not null default '[]'::jsonb;`
- CHECK(요청 표 `items` 검사 방식): 배열, 200개 이하, 64KB 이하, 항목은 객체, 키는 `key·origin·title·place·drop·saved·used`만, `key·origin·saved` 필수, 글은 한 줄(제어문자 없음)·길이 상한, `drop`은 참/거짓, `saved·used`는 YYYY-MM-DD, `title` 또는 `drop` 중 하나는 있어야 함. 열쇠 중복은 화면이 막음(CHECK 안 하위 질의 불가 — 회의 종류처럼 이어 붙여 검사는 jsonb라 어려움, 위험 5).
- 권한: grant·정책·RLS 변경 없음. 기존 `task12a_owner_all`(내 행만) 그대로 — `20261023180000_profile_view_prefs`와 같은 사전 확인(표 UPDATE 권한·정책 2개 모양).
- 되돌리기: `drop constraint`, `drop column`. 기억만 사라지고 초안은 달력 제목으로 돌아감.

### 4.3 짝 파일·시험·적용

- 각 migration마다 `docs/<version>_<name>.precheck.sql`·`.snapshot.sql`·`.postcheck.sql`·`.rollback.sql`·`.summary.md`(5개, `docs/ops-db-workflow.md` 확장 규칙). summary 첫머리에 일상어 3줄(무엇이 바뀌나 / 잘못되면 / 되돌리는 법).
- 시험: `tests/auth-handoff/weekly-draft.test.mjs`·`profile-weekly-schedule-memory.test.mjs`(embedded Postgres, 가짜 자료): owner 읽기·쓰기, 다른 사람·anon 거절, 지우기 권한 없음, CHECK 경계(크기·키·한 줄), 조건부 PATCH(`draft_saved_at` 조건 0행), 임시저장 쓰기가 `updated_at`을 안 바꿈, rollback 뒤 원래 모양. CI `authz-security-check`가 돈다.
- 적용: PR 1 merge 뒤 커맨드센터가 승인형 DB workflow로 시작 → 명진 승인. 4.1은 열 grant가 있어 확장 규칙 대상(요청 표 migration과 같은 길 — 그때 "로컬 plan 통과"로 workflow 적용됨, `20261023140000` 주석). workflow가 거절하면 SQL Editor(폰 경로 C).

## 6. 위험

1. **바탕이 바뀌면 칸이 안 맞음**: 같은 주에 다른 확정본을 바탕으로 열면 칸 이름이 달라질 수 있다 → 못 넣은 칸을 접어 보여 주고 버리지 않음(2.4).
2. **제목 열쇠가 너무 넓음**: "회의"처럼 짧고 흔한 제목을 [빼기]로 기억하면 다른 회의도 빠진다 → 기억 후보에서 2자 이하 제목은 체크를 풀어 두고, [주간 정리]에 "기억으로 뺀 일정 N개"를 늘 보이게.
3. **달력 제목을 바꾸면 기억이 안 맞음**: 원본 제목이 바뀌면 열쇠가 달라져 기억이 적용되지 않는다(새 제목이 그대로 보임) → 조용히 틀리지 않고 "N주 안 쓰임"으로 드러남.
4. **두 기기 합치기 실수**: 3자 비교의 "마지막으로 같았던 판"을 메모리에만 두므로 새로고침 뒤에는 서버 판을 기준으로 다시 시작한다(그 사이 이 기기에서 저장 못 한 글은 화면에 "저장 못 함"으로 남아 있어야 함 — 새로고침 전 경고).
5. **기억 열쇠 중복**: DB CHECK로 jsonb 배열 안 중복을 막기 어렵다 → 화면이 다시 읽고 고쳐 쓰며 중복을 합침. 중복이 생겨도 첫 항목만 쓰므로 해는 작다.
6. **요청 표 이름과 내용 불일치**: `app_weekly_exec_requests`가 임시저장도 품는다 → migration·문서 주석. 표 이름 바꾸기는 하지 않음(운영 표 이름 변경은 위험이 더 큼).
7. **기기 파일 바탕**: 폰에서 이어 고치려면 같은 파일이 폰에도 있어야 한다 → 자료실 "주간보고 확정본" 바탕을 권하는 안내.
8. **임시저장 내용은 업무 글**: 서버 DB(owner 전용)에 남는다. 요청 표·조직 요약과 같은 수준. 로그·PR·오류 보고에 내용을 쓰지 않는다.
9. **E2E**: 자동 저장 타이머가 있는 화면은 시험이 흔들리기 쉽다 → 타이머를 바깥에서 넣을 수 있게 만들고 저장 함수는 순수 함수 시험으로.
