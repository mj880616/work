## 1. AI 초안 실패 원인 (11:34 "ai초안 만들기 눌렀는데 못만든다고 했거든")

- **사실(코드):** 화면 `meeting-transcript-draft.js`가 `rt.api('/functions/v1/meeting-ai-draft', …)`를 `timeoutMs` 없이 불렀다.
  - 공용 요청(`app/runtime-client.js`)의 기본 기다림은 **15초**(`config.timeoutMs:15000`)다.
  - 50분 전사본(약 6~7만 자)을 생각 모델로 요약하면 15초를 넘는다. 그래서 화면이 먼저 끊고 '초안을 만들지 못했어요'를 띄웠다.
  - 화면 안내 글은 "1분쯤 걸릴 수 있어요"였는데 실제로는 15초에 끊었다.
  - 짧은 전사본은 15초 안에 끝나서 됐다.
  - 서버는 화면이 끊은 뒤에도 끝까지 돌아 AI 사용량을 썼을 수 있다(낭비).
- **추정(덧붙는 위험):** 7만 자 입력이면 생각 토큰이 출력 상한(설정 최대 3500 + 여유 1500)을 넘어 답이 'incomplete'로 끊길 수 있다. 운영 로그는 이 세션(웹)에서 볼 수 없다. CC가 `meeting-ai-draft` 로그에서 11/03 오전 실패가 화면 끊김(서버는 200)인지, 서버 400('AI 응답이 중단되었습니다')인지 한 줄로 확인한다.
- **고침(PR 1):**
  1. 요약 한 번의 기다림을 240초로 늘린다(`DRAFT_TIMEOUT_MS`).
  2. 3만 자가 넘는 전사본은 2만 4천 자 안팎으로 줄 경계에서 나눈다.
     - 조각마다 요약한다(`stage:'part'`).
     - 조각 요약들을 한 번 더 합쳐 요약한다(`stage:'merge'`).
     - 조각은 최대 12개(28만 8천 자, 2시간 넘는 녹음도 됨)다.
     - 한 번 호출이 짧아져 Edge 시간 한도·생각 토큰 넘침을 함께 피한다.
  3. 실패 문구를 이유별로 나눈다: 시간 초과 / 연결 끊김 / 로그인 / 서버 한 줄(한도 등) / 그 밖.
- **비용:** 50분 녹음은 조각 3개와 합치기 1번이라 AI 요청 4번이다(전에는 1번, 그런데 실패). 하루 요청 한도(`daily_request_limit`)에 4번으로 센다. 입력 토큰 합은 거의 같고, 합치기 입력은 작다.

## 4. 공통 서버 작업 길 (PR 2·3, B·C)

녹음 정리(C)와 그 자리 전사(B)는 같은 일을 한다. 서버가 Drive의 소리를 전사하고, 요약하고, 결과를 회의 초안으로 남긴다. 그래서 길을 하나만 만든다.

```
[멈추고 정리]·[이어서 정리]·회의자료 ⋯ [전사해서 결과에 넣기]
  └► Edge meeting-transcribe ?action=job_start {kind:'recording'|'attached', session_id | document_id, meeting_id?}
        └► 작업 표 한 행(새 표 app_meeting_jobs: owner 전용 RLS, 상태·단계·진행·결과 글·오류 코드)
예약 실행(pg_cron, 1분마다 Edge meeting-transcribe ?action=job_tick, 서버 비밀값 인증)
  └► 한 번에 한 단계(합치기 조각 n개 / 구간 하나 전사 / 조각 요약 하나 / 합치기)만 하고 다음 단계로 표를 넘김
        ─ 한 번 호출 시간 한도를 넘지 않음(지금 화면이 30번 부르는 rec_finish를 서버가 이어 받음)
  └► 끝: 결과 = {전사 전문, 요약 초안, 후속 할 일}을 작업 행에 저장, Drive '… 전사.txt' 만들기
        → phone-push '회의 요약이 준비됐어요' + Web2 알림 줄(뒤에서 끝난 일)
화면(어느 기기든): 작업 행을 읽어 진행 띠만 그림. 누르면 사업 보고 입력 창(새 회의) 또는 그 회의 [수정] 창에
  초안·전문을 채운 채 열림. 저장은 명진이 [저장](자동 저장 없음).
```

- **B(그 자리 전사):** 회의자료 소리 파일(m4a·mp3·ogg·wav 등) ⋯ 메뉴에 [전사해서 결과에 넣기]를 둔다.
  - 서버는 Drive 파일 id로 바로 전사한다. 내려받아 다시 올리지 않는다.
  - 1시간이 넘는 파일은 서버가 시간 구간으로 나눠 전사한다. Gemini Files 하나에 1시간 상한이 있다.
  - 같은 파일(Drive id·수정 시각이 같음)을 다시 누르면 앞 결과를 다시 쓴다(비용 0).
  - 끝나면 그 회의 [수정] 창에 '결과 원문에 요약 더하기'와 '회의록 전문 채우기'가 채워져 열린다.
- **C(서버 정리):** 지금 화면 정리 순서(`rec_finish` → `transcribe` → 합치기 → 요약)를 서버 단계로 옮긴다.
  - 화면을 닫거나 다른 앱으로 가도 계속된다. 폰 녹음(`phone-recorder-core.mjs`)도 같은 `job_start`를 부른다.
  - 실패 문구는 띠에서 두 줄로 보이거나 눌러 펼친다.
- **보안:**
  - 작업 표는 owner 전용이다(`private.app_is_workspace_owner`). 예약 실행은 서버 비밀값으로만 들어온다. anon·PUBLIC 권한은 없다.
  - 전사·요약은 명진이 누를 때만 시작한다. 외부 발송·공유와 자동으로 잇지 않는다.
- **DB:** 새 표·예약 실행 migration과 짝 파일 5개가 필요하다. 적용은 CC가 시험 적용부터 한다.
- **Edge:** `meeting-transcribe`(job_start·job_tick·job_read)와 `meeting-ai-draft`(서버 안에서 부를 수 있게 요약 부분을 `_shared`로 빼기)가 바뀐다.

## 6. `<>` 버튼 (11:42 "이거 뭔 기능?")

- `<>`는 '서식 보기 ↔ 원문(기호 그대로) 보기' 전환이다(MTG-결과마크다운 #1584).
  - 사업 보고(`record-text-view.js`)와 정리함 업데이트·노트(`basket.js`)가 같은 아이콘을 썼다.
  - 이제 두 곳 모두 작은 글자 버튼이다. 지금 서식 보기면 [원문], 원문 보기면 [서식].
  - 읽기 프로그램용 이름(aria-label)은 그대로다.
- 서식 기호가 그대로 보인 까닭(사실, 코드): `markdownSource`는 **2만 자가 넘는 글을 서식 없이 글자 그대로** 보여 준다(`MD_RAW_MAX=20000`, 성능 보호). 50분 전사 전문은 2만 자를 넘으므로 `###`·`**`가 그대로 보인다.
  - 이때는 전환 버튼이 숨는다. 캡처에 `<>`가 보였다면 그 글은 2만 자 아래였고, 명진이 한 번 눌러 원문 보기 상태였을 가능성이 크다(추정).
  - 기본은 서식 보기가 맞다. 2만 자 상한은 이 PR에서 바꾸지 않는다. 회의록 전문은 접혀 있어 펼칠 때만 그린다.

## 8. S49-2 구현 결정 (A 서버 정리 · B 그 자리 전사)

CC 지시(11/03 S49-2): A(서버 길·DB)를 먼저, B(회의자료 ⋯ [전사해서 결과에 넣기] 화면)는 A 브랜치 위에서. 5절 표의 순서(2 → 3)를 바꿨다.

- **작업 표:** 새 표 `app_meeting_server_jobs` 하나. 기존 두 표는 구간(`app_meeting_recordings`)·파일(`app_meeting_transcribe_jobs`) 단위라서, 녹음 한 건(또는 붙은 파일 하나)의 단계·진행·결과(전문·요약 초안)를 둘 칸이 없다.
  - 권한: authenticated는 읽기만(owner RLS `private.app_is_workspace_owner`). 쓰기는 Edge `meeting-transcribe`(service_role, 정한 칸만, 지우기 없음). anon·PUBLIC 없음.
  - 구간 합치기·파일 전사 기록은 기존 두 표를 그대로 쓴다(`rec_finish`·`transcribe`와 같은 함수 본문을 서버 단계가 부른다).
- **예약 실행 대신 '이어 부르기':** pg_cron·새 비밀값을 만들지 않는다.
  - `job_start`가 행을 만들고 첫 단계를 뒤에서(`EdgeRuntime.waitUntil`) 돌린다. 한 단계가 끝날 때마다 같은 함수의 `job_tick`을 다시 부른다.
  - 한 단계 = 구간 합치기 하나 / 구간(파일) 전사 하나 / 요약 한 번. 한 번 호출 시간 한도를 넘지 않는다.
  - `job_tick` 열쇠: 서버 안에서만 아는 HMAC(service role 키로 서명, 작업 id·10분 기한에 묶임). 화면·남은 받지 못한다. 게이트(verify_jwt=true)는 `SUPABASE_ANON_KEY`로 지나고, 함수 코드가 HMAC을 확인한다.
  - 겹침 방지: 단계를 잡을 때 `lease_until`(9분)을 조건부로 바꾼다. 동시에 두 번 와도 한 번만 돈다.
  - 끊김 회복: 화면이 열려 있으면 `job_read`(5초마다)가 기한이 지난 작업을 다시 깨운다. 앱을 다시 열 때(`job_list`)도 같다.
- **요약:** 서버가 `meeting-ai-draft`와 같은 지시문(`_shared/meeting-draft-prompt.mjs`로 뺐다)으로 '새 회의' 요약을 만든다. 3만 자가 넘으면 나눠 요약한 뒤 합친다(1절과 같은 규칙). 하루 한도·사용량 기록도 같다.
- **끝:** 전문·초안을 작업 행에 저장 → 폰 알림 `meeting_done`('회의 요약이 준비됐어요', FCM 비밀값이 있을 때) + `app_push_log` 기록(알림 줄과 같은 열쇠).
  - 누르면 `?view=reports&rec_job=<id>` → 사업 보고 회의 입력 창에 날짜·결과 원문·후속 할 일·회의록 전문이 채워져 열린다. 저장은 명진 [사업 보고 저장]. 저장하면 녹음을 그 회의에 붙이고(기존 `attach`) 작업 행에 '열었음'.
- **B:** 같은 `job_start`에 `{kind:'attached', document_id}`. 서버가 회의자료 행(owner RLS로 읽음)의 Drive 파일을 바로 전사한다. 같은 파일(Drive id·md5가 같음)의 끝난 작업이 있으면 그 결과를 다시 쓴다(AI 비용 0). 끝나면 그 회의 [수정] 창에 회의록 전문·결과 원문 요약이 채워져 열린다.
- **이번에 하지 않는 것:** Drive '… 전사.txt' 파일 만들기(전문은 명진 지시로 회의 기록 DB에 남는다). 폰 앱 자체 녹음(`phone-recorder-core.mjs`)을 서버 정리로 돌리는 것은 같은 `job_start`를 부르면 되지만 앱 판 올리기가 필요해 뒤 PR(REC-새로고침계속과 한 설계).
