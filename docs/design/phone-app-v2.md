## 0. 명진용 요약

**무엇을 만드나.** 갤럭시 폰에 까는 "웹2" 앱을 새로 만든다. 화면은 지금 desk.bokdoong.com 웹 화면을 그대로 띄운다. 웹으로는 할 수 없는 세 가지만 앱이 직접 맡는다.

1. 다른 앱의 [공유] 메뉴에 "웹2 바구니"가 나온다. 글·링크·사진·파일을 바로 바구니에 넣는다.
2. 홈 화면 위젯에 오늘 일정과 할 일을 보여 주고, 바구니 빠른 넣기 버튼을 둔다.
3. 하단 시스템 바 색, 뒤로가기, 로그인 뒤 앱으로 돌아오기를 제대로 처리한다.

**핵심 장점.** 웹에 새 기능이 들어오면 앱을 다시 깔지 않아도 앱을 다시 열 때 바로 보인다. 앱 업데이트는 공유·위젯·시스템 바처럼 앱 껍데기를 고칠 때만 필요하다.

**서버.** 새 서버나 새 저장소를 만들지 않는다. 공유로 받은 것은 웹 바구니가 이미 쓰는 길(`basket-files`, `app_notes`)로 올린다. 권한도 넓히지 않는다.

**단계.** ① 웹 감싸기 + 시스템 바·뒤로가기·로그인 복귀 → ② 공유로 바구니 넣기 → ③ 위젯 → ④ 알림(지금은 만들지 않는 것을 추천).

**옛 앱.** 같은 이름·같은 앱 ID로 대체한다. 옛 앱은 한 번 지우고 새 앱을 깐다. 데이터는 서버에 있으므로 다시 로그인만 하면 된다.

원장 `APP-Android`(보류)의 발견 3가지는 코드와 일치한다.

- 하단 바 아이콘이 안 보인다. targetSdk 35부터 앱이 화면 끝까지 그려지고(edge-to-edge) `setNavigationBarColor`가 무시된다. 그래서 흰 바탕 위에 흰 아이콘이 남는다(추정, 원인 일치).
- 바탕은 흰색으로 고정돼 있다. 웹 바탕 `#f3f1ea`, 다크 `#161613`과 맞지 않는다.

**추정.** CI는 매번 새 debug 키로 서명한다(러너마다 `~/.android/debug.keystore`를 새로 만든다). 그래서 업데이트할 때마다 서명이 달라 지웠다 다시 깔아야 했을 가능성이 높다.

### 1.3 웹2 쪽 사실

- 주소: `https://desk.bokdoong.com/` → Worker가 `/work/app/`로 보낸다. HTML은 매번 새로 받고, 파일은 해시 버전으로 받는다(`cloudflare/bokdoong-router.mjs`의 `deskDocument`, `versionedAsset`). **그래서 웹을 고치면 앱 안의 화면도 다시 열 때 바로 바뀐다.**
- 로그인 세션: 웹은 `localStorage`의 `kptu_collab_session_v1`에 로그인 세션을 둔다(`runtime-client.js`). 업무 데이터가 아니라 기기별 로그인 상태다. "로컬 저장 금지" 원칙은 업무 데이터에 대한 것이다.
- `auth-handoff` 허용 Origin: `desk.bokdoong.com`, `work.bokdoong.com`, `mj880616.github.io`.
- 바구니 저장 길: 파일·사진은 `POST /functions/v1/basket-files`(multipart, 파일당 100MB, 메모당 20개, 서버가 owner workspace 확인, Drive "Web2 바구니" 폴더)를 쓴다. 글만 있는 메모는 `POST /rest/v1/app_notes`(RLS owner)를 쓴다. 사진 글자 읽기는 업로드 뒤 `basket-ocr-runtime.js`가 한다. PC 드롭(`basket-pc/…/BasketApi.cs`)도 이 두 길만 쓴다.
- 알림: `push-notifications` Edge는 410 "retired"만 돌려준다. 지금 웹2에는 알림 경로가 없다.
- 화면: `viewport-fit=cover`, `interactive-widget=resizes-content`, `env(safe-area-inset-*)` 사용 37곳. `theme-color`는 라이트 `#f3f1ea`, 다크 `#161613`.

### 2.2 추천: C. 웹 화면을 감싼 앱 + 공유 받기·위젯·시스템 바만 네이티브

이유는 세 가지다.

1. **재설치 없는 반영.** 앱 화면 전체가 desk.bokdoong.com을 그대로 띄우고, Worker가 HTML을 매번 새로 준다. 그래서 일정·바구니·노트 같은 새 기능은 웹에 merge·배포되는 순간 앱에도 들어온다. 앱을 다시 깔아야 하는 경우는 공유 받기, 위젯, 시스템 바, 로그인 복귀처럼 앱 껍데기 자체를 바꿀 때뿐이다. 이런 변경은 드물게 몰아서 한다.
2. **요청 기능 중 둘(공유 받기의 파일, 위젯)은 웹만으로 안 된다.** B(TWA)를 고르면 결국 위젯과 공유를 네이티브로 덧붙여야 하고, 시스템 바·뒤로가기 제어는 오히려 더 약하다. TWA는 Cloudflare에 파일을 하나 더 올려야 하는 정지 지점도 생긴다.
3. **기존 자산을 그대로 쓴다.** 로그인 복귀(handoff, 앱 ID 지정 intent), 웹의 뒤로가기 장치, `KPTUAndroid` 판정이 이미 C 방식에 맞춰 웹에 들어 있다. 공유 받기도 웹 바구니 업로드 코드를 그대로 쓰게 설계한다(4절). 앱 쪽 코드는 작게 유지한다.

D(전부 네이티브)는 "새 기능 재설치 없이 반영"과 정면으로 어긋나므로 제외한다.

### 2.3 앱 껍데기의 원칙

- **화면은 모두 웹이다.** 공유 확인창도 웹 바구니 화면의 한 상태로 만든다(4절). 네이티브 화면은 위젯 하나뿐이다.
- **업무 데이터를 폰에 저장하지 않는다.** 공유로 받은 파일은 올릴 때까지 메모리와 안드로이드가 준 임시 권한(content URI)으로만 다룬다. 위젯이 보여 줄 오늘 목록은 위젯 표시용으로만 잠깐 둔다(6.3).
- **언어·도구.** Kotlin, AndroidX WebKit, 위젯은 Jetpack Glance. minSdk 29(갤럭시 전용이므로 안드로이드 10 이상), targetSdk 36. 빌드는 기존처럼 GitHub Actions에서 한다.

## 3. 기능 목록과 단계

| 단계 | 내용 | 크기 | 서버·설정 변경 | 정지 지점 |
| --- | --- | --- | --- | --- |
| **① 웹 감싸기** | 새 껍데기(Kotlin)로 옛 앱 교체. 기본 주소 `https://desk.bokdoong.com/work/app/`(github.io·work.bokdoong.com의 `/work/app/`도 내부로 인정). 시스템 바: 화면 끝까지 그리고, 상태·하단 바 자리에 웹 바탕색을 칠하고, 라이트·다크에 따라 아이콘 색을 바꾼다(웹 `theme-color`를 따라감). 자판이 열리면 자판 높이만큼 비킨다. 뒤로가기: 기존 `KPTUNativeBack` 연결. 첫 화면에서는 앱을 종료하지 않고 뒤로 보낸다. 로그인: Custom Tab으로 구글 로그인 → 기존 handoff로 복귀. 외부 링크: Custom Tab. 파일 선택·카메라: 유지. 서명된 release APK와 승인형 릴리스 workflow | 중(PR 2개: 껍데기, 릴리스 workflow) | 없음. 단 "desk 주소의 `native-callback.html`이 Supabase 허용 주소에 들어 있는가"는 확인 필요(5.1) | 서명 키 만들기·GitHub 비밀값 등록(💻 PC 또는 명진), 허용 주소가 없을 때만 추가(명진 승인) |

| **③ 홈 화면 위젯** | 1차 후보: "오늘" 위젯 하나(오늘 일정 + 오늘·지난 할 일 몇 줄 + [바구니에 넣기] 버튼). 줄을 누르면 앱의 해당 화면이 열린다. 할 일 체크는 1차에서 빼고 보기만 한다. 갱신: 30분마다 + 앱을 닫을 때 + 위젯의 새로고침 버튼 | 중~대(PR 2개: 위젯 로그인 + 위젯 화면) | 기존 `google-tasks?action=overview`, `google-calendar?action=events`를 읽기만 함. 위젯 전용 로그인 세션 필요(5.3) | 위젯 로그인 방식은 보안 설계라 Opus 제안 + 명진 승인 |

**크기 기준.** 소 = 세션 1개·PR 1개, 반나절 이하. 중 = 세션 1~2개·PR 1~2개. 대 = 세션 3개 이상 또는 서버 변경 포함.

**순서·의존.** ① → ②(①의 껍데기 위) → ③(①의 로그인 위). ②와 ③은 서로 독립이라 ① 뒤에 나란히 돌릴 수 있다. ④는 별도 결정 전까지 착수하지 않는다.

**①의 세부 확인 목록(갤럭시 폴드 실기기).** 접은 화면·편 화면 전환 때 바 색과 여백이 맞는가. 라이트↔다크 전환 때 아이콘이 보이는가. 자판이 열릴 때 빠른 입력칸이 자판 위로 오는가. 뒤로가기로 메뉴·시트·탭이 차례로 닫히는가. 로그인 → 앱 복귀가 되는가. 파일 선택과 카메라가 되는가.

## 4. 공유로 바구니 넣기 설계 (② 상세)

### 4.1 받는 것

| 다른 앱이 보내는 것 | 안드로이드 형식 | 바구니에 저장되는 모양 |
| --- | --- | --- |
| 글·링크 | `ACTION_SEND`, `text/plain`(`EXTRA_TEXT`, 제목 `EXTRA_SUBJECT`) | 글만 있는 바구니 메모(`app_notes`, `raw_text`). 제목이 있으면 첫 줄로 붙인다. 링크는 글 그대로 저장하고, 바구니의 링크 처리는 웹 기존 동작을 따른다 |
| 사진 1장·여러 장 | `ACTION_SEND` / `ACTION_SEND_MULTIPLE`, `image/*` | 메모 1개 + 첨부(`basket-files`), 사진 글자 읽기 |
| 파일(PDF·한글·엑셀 등) | 같은 방식, `*/*` | 메모 1개 + 첨부 |
| 글 + 파일 함께 | `EXTRA_TEXT` + `EXTRA_STREAM` | 메모 원문 = 글, 첨부 = 파일(`raw_text` + `file`) |

**한도.** 서버와 같다(파일당 100MB, 메모당 20개, 글 20,000자). 넘으면 확인 줄에서 미리 알려 주고 넘는 것만 뺀다. 빈 파일은 거절한다.

### 4.2 흐름 (토큰을 앱 쪽으로 꺼내지 않는 방식)

1. 앱이 공유를 받는다. 받은 파일은 안드로이드가 준 content URI 목록으로만 메모리에 들고 있는다. 폰 저장소에 복사하지 않는다.
2. 앱이 WebView에서 `…/work/app/?view=basket&share=<일회용 번호>`를 연다. 앱이 이미 열려 있으면 그 화면 위에서 연다.
3. 웹 바구니가 `share` 값을 보고, 앱이 넣어 준 좁은 다리(JavaScript 인터페이스)로 "받은 항목 목록(이름·종류·크기·글)"만 묻는다.
4. 파일 내용은 웹이 `https://desk.bokdoong.com/work/app/__share/<일회용 번호>/<순번>`을 fetch해서 받는다. 이 주소는 실제 서버로 나가지 않는다. 앱이 WebView 안에서 가로채(`shouldInterceptRequest`) content URI를 그대로 흘려준다. 그래서 100MB 파일도 문자열로 바꾸지 않고 Blob으로 받는다.
5. 웹은 그 Blob과 메모 한 줄로 **기존 `basket-upload.js`의 업로드(= `basket-files`)와 기존 글 메모 저장(= `app_notes`)**을 그대로 부른다. 토큰은 웹 세션 그대로이고 앱 코드는 토큰을 보지 않는다.
6. 끝나면 앱이 일회용 번호와 URI 권한을 버린다. 실패하면 확인 줄에 [다시 보내기]가 남는다. 앱을 닫으면 버려진다(폰에 보관하지 않는다, D6).

**다리 제한.** 다리 객체와 `__share` 가로채기는 최상위 화면이 `desk.bokdoong.com/work/app/`(또는 허용한 두 주소)일 때만 응답한다. 일회용 번호는 추측할 수 없는 값으로 하고, 한 번 다 읽으면 닫는다. 다른 사이트(iframe·외부 링크)에서는 다리가 보이지 않게 한다.

### 4.3 화면 (웹 쪽)

- 바구니 탭 위에 얇은 확인 줄이 뜬다: `사진 3 · 파일 1 (12.4MB)` + 메모 한 줄 입력칸 + [넣기] [취소]. 큰 카드나 큰 버튼은 쓰지 않는다. 하단 탭 바에 가리지 않게 한다.
- 넣은 뒤에는 바구니 목록 맨 위에 새 메모가 보이고, 작은 알림 "바구니에 넣었어요 · [돌아가기]"가 뜬다. [돌아가기]는 공유를 시작한 앱으로 돌아간다.
- 로그인이 안 된 상태면 로그인부터 하고, 받은 항목은 메모리에 그대로 둔 채 이어서 확인 줄을 보여 준다.

## 5. 로그인·보안

### 5.1 WebView 로그인 (①)

- 구글은 WebView 안 로그인을 막는다(`disallowed_useragent`). 그래서 지금처럼 브라우저에서 로그인하고 돌아온다. 다만 외부 브라우저 대신 **Custom Tab**(앱 위에 뜨는 브라우저 탭, 기본 브라우저인 삼성 인터넷이나 크롬)을 쓴다. 로그인이 끝나면 탭이 닫히고 앱으로 돌아온다.
- 돌아오는 길은 **기존 handoff를 그대로 재사용**한다. 기존 `native-callback.html` → `auth-handoff` seal(새로고침 토큰을 서버 키로 봉인, 5분, 일회용) → 앱 ID 지정 intent → 앱이 `?handoff=`로 웹을 엶 → `auth-handoff-client.js` consume. 새 서버, 새 허용 주소, 새 비밀값이 없다.
- **앱 ID를 `kr.or.kptu.work` 그대로 유지**하는 것이 전제다. `native-auth-bridge.js`의 intent가 이 ID를 지정하므로, 다른 앱이 로그인 결과를 가로챌 수 없다. ID를 바꾸면 웹 다리도 같이 고쳐야 한다.
- **확인 필요(정지 지점 후보).** desk 주소에서 로그인을 시작하면 돌아올 주소가 `https://desk.bokdoong.com/work/app/native-callback.html?native=android`가 된다. `docs/bokdoong-domain.md`에 따르면 desk 허용 주소는 `/work/app/`와 `confirmed.html`을 "경로 단위"로 등록했다. 그래서 `native-callback.html`이 허용 목록에 있는지 이 세션은 확인할 수 없다. ① 구현 세션 첫 단계에서 실제 로그인을 시험하고, 허용 목록에 없으면 거기서 멈춘다. 그다음 명진이 대시보드에서 한 줄을 추가한다(읽생기와 공유하는 설정이므로 지우거나 바꾸지 않고 추가만 한다).
- 웹 세션은 지금 웹과 같이 WebView의 브라우저 저장소(앱 전용 공간)에 있다. 앱 백업은 끈다(`allowBackup=false` 유지). 그래서 로그인 상태가 다른 폰으로 복사되지 않는다.

### 5.2 공유 받기 (②)의 보안

- 앱 코드는 토큰을 만지지 않는다(4.2). 저장 권한 판정은 지금과 같이 서버(`basket-files`의 owner 확인, `app_notes` RLS)가 한다. 권한 확대 없음.
- 앱이 받는 안드로이드 권한은 인터넷 하나다. 사진·저장소 전체 읽기 권한은 요청하지 않는다. 공유된 항목은 그 항목에 대한 임시 읽기 권한만 받는다.
- 범위 밖 사이트에서는 다리와 `__share` 가로채기가 동작하지 않는다(4.2 다리 제한).

### 5.3 위젯 로그인 (③, Opus 제안 대상)

위젯은 앱이 닫혀 있을 때도 서버를 읽어야 한다. 그래서 웹 세션과 **별도의 로그인 세션**이 필요하다. 같은 새로고침 토큰을 웹과 위젯이 나눠 쓰면, 한쪽이 갱신할 때 다른 쪽 토큰이 무효가 되어 로그아웃된다(Supabase 새로고침 토큰 교체 방식, 추정).

| 후보 | 내용 | 서버·설정 변경 | 평가 |
| --- | --- | --- | --- |
| W1 (추천) | 위젯 첫 사용 때 Custom Tab으로 구글 로그인을 한 번 더 한다. 기존 handoff를 "위젯용"으로 받아 앱이 직접 consume한다 | 웹 `native-auth-bridge.js`에 "위젯용" 표시 추가(소), 앱이 `auth-handoff`에 요청할 때 Origin 처리 확인 필요(현재 허용 Origin만 받음 → 앱 요청은 Origin이 없어 403. 서버를 고칠지, 앱이 정해진 Origin을 보낼지 보안 검토) | 새 허용 주소 없음. 세션이 따로라 웹 로그아웃과 독립 |
| W2 | PKCE + 앱 링크(https 돌아오기)로 위젯 전용 로그인 | Supabase 허용 주소 추가 + desk에 `assetlinks.json`(Cloudflare 변경) | 정석이지만 정지 지점 2개 |
| W3 | 위젯 전용 읽기 토큰을 새로 발급하는 서버 | 새 Edge + DB | 새 권한 체계라 비추천 |

- **토큰 보관:** 위젯 세션의 새로고침 토큰 하나만 안드로이드 키 저장소(Android Keystore)의 키로 암호화해 앱 전용 공간에 둔다. 접근 토큰은 메모리에만 둔다. 앱 백업에서 뺀다.
- **위젯이 읽는 것:** 기존 `google-tasks?action=overview`, `google-calendar?action=events`(오늘 범위)만 쓴다. 웹과 같은 사용자 권한이고 새 권한이 없다. 쓰기(할 일 체크)는 1차에서 뺀다.
- **위젯 로그아웃:** 앱 설정(웹 화면의 프로필 메뉴에서 앱 다리로 호출)에 [위젯 로그아웃]을 둔다. 서버 세션 폐기(`/auth/v1/logout`)와 폰의 토큰 삭제를 같이 한다.
- **잠금 화면:** 위젯 내용(일정 제목, 할 일 제목)은 홈 화면에 보인다. 잠금 화면 위젯은 만들지 않는다.

### 5.4 하지 않는 것

인증 우회, RLS 약화, 서비스 키를 앱에 넣기, 저장소에 서명 키·비밀값 넣기, 사진·저장소 전체 권한 요청, 앱 안 디버깅 켜기(`setWebContentsDebuggingEnabled`는 release에서 끔).

## 6. 배포·설치·업데이트

### 6.1 서명 키

- release 서명 키(keystore)는 **저장소에 넣지 않는다.** GitHub의 승인형 environment(예: `phone-app-release`, 승인자 명진, 관리자 우회 끔)의 비밀값으로만 둔다(키 파일 base64, 비밀번호 2개). BASKET-PC드롭의 `basket-pc-release`와 같은 방식이다.
- 키는 💻 PC 로컬 Claude Code 세션이 만들어 `gh secret set`으로 바로 등록한다. 화면이나 로그에 출력하지 않는다. 예비 사본 1개는 명진이 오프라인 보관 장소(예: USB)에 둔다. 위치는 어디에도 기록하지 않는다.
- 키를 잃어도 업무 데이터는 서버에 있으므로 잃는 것이 없다. 앱을 한 번 지우고 새 키로 만든 앱을 깔고 다시 로그인하면 된다.

### 6.2 처음 설치 (명진이 할 일, 한 번)

1. 갤럭시 [설정] → [보안 및 개인정보 보호] → [자동 차단기]가 켜져 있으면 잠시 끈다(켜져 있으면 인터넷에서 받은 앱 설치를 막는다).
2. 폰의 삼성 인터넷에서 GitHub 릴리스 페이지(문서에 링크)를 열고 `web2-phone-x.y.z.apk`를 누른다.
3. "이 출처의 앱 설치 허용"을 묻면 [설정] → 허용을 켠다.
4. [설치] → [열기] → [구글로 로그인].
5. 설치가 끝나면 1에서 끈 자동 차단기를 다시 켠다(이미 깔린 앱은 그대로 동작한다).

### 6.3 업데이트

- **화면·기능(대부분):** 웹 배포만 하면 앱을 다시 열 때 반영된다. 할 일 없음.
- **앱 껍데기(공유·위젯·바 색 등):** 태그 `phone-app-v*` → 승인형 workflow가 서명된 APK를 GitHub 릴리스에 올린다(명진은 승인 버튼만). 앱은 열 때 공개 릴리스 목록에서 최신 버전을 확인한다. 새 버전이 있으면 웹 화면 위에 작은 줄 "앱 새 버전 0.2.0 · [받기]"를 띄운다. [받기]를 누르면 브라우저로 APK를 받고 설치 화면이 뜬다. 같은 키로 서명했으므로 지우지 않고 덮어 깔린다.
- 앱이 직접 내려받아 설치하는 방식(`REQUEST_INSTALL_PACKAGES` 권한)은 쓰지 않는다. 권한이 늘고 이득이 작다.
- **Play 스토어는 쓰지 않는다**(개발자 계정 비용·본인 인증·심사, 1인용 앱에 과함). 단 구글이 2026년부터 나라별로 "인증된 개발자 앱만 설치" 정책을 넓히고 있다. 한국 적용 시점은 확인 필요다. 적용되면 무료 개인 개발자 등록이 필요할 수 있다(위험 목록).

### 6.4 빌드 workflow

- 기존 `build-android-app.yml`(debug APK)을 새 껍데기에 맞게 교체한다. PR에서는 서명 없는 빌드와 테스트만 돌리고 비밀값을 쓰지 않는다. 릴리스 workflow는 태그·승인 environment에서만 서명한다.
- 테스트: 껍데기 단위 테스트(내부 주소 판정, 공유 항목 해석·한도, 다리 Origin 제한, 버전 비교)와 웹 쪽 E2E(공유 확인 줄을 가짜 다리로 띄워 `basket-files` 가짜 서버에 업로드).

## 7. 옛 앱 처리

**추천: 대체.** 같은 이름 "웹2", 같은 앱 ID `kr.or.kptu.work`, 같은 아이콘(`app/app-icon.svg`)을 쓰고 `android-app/` 내용을 새 껍데기로 바꾼다. 옛 코드는 git 기록에 남으므로 따로 보관 폴더를 두지 않는다.

- 폰: 옛 앱은 debug 키로 서명돼 있어 새 앱이 덮어 깔리지 않는다. **옛 앱을 한 번 지우고** 새 앱을 깐다. 데이터는 서버에 있어 잃는 것이 없고 다시 로그인만 한다.
- 홈 화면에 웹 바로가기("홈 화면에 추가"한 웹2)가 있으면, 새 앱을 확인한 뒤 지우는 것을 추천한다. 아이콘 두 개가 같은 이름이면 헷갈린다. 이때 UI-하단바색 행은 "앱으로 대체"로 닫는다.
- `windows-app/`(보관용)은 이번 범위가 아니다.

## 10. 범위 밖 발견사항 (고치지 않고 기록만)

1. `app/calendar-return-bridge.js`는 구글 캘린더 연결 뒤 앱으로 돌아갈 때 앱 ID를 지정하지 않은 `kptuwork://auth?google=…`를 쓴다. 로그인 쪽(`native-auth-bridge.js`)은 앱 ID를 지정한다. 실어 나르는 값이 연결 결과(connected/error)뿐이라 위험은 낮다. ①에서 같이 맞출지는 별도 판단이다.
2. `app/login/native-google-return.js`는 사용자 에이전트에 `wv`가 있으면 모두 안드로이드 앱으로 본다. 그래서 카카오톡 같은 앱 안 브라우저에서 웹2 구글 로그인을 하면 `native-callback.html?native=android`로 가서 `kr.or.kptu.work` 앱을 열려고 한다. 앱이 없으면 "전달하지 못했습니다"로 끝날 가능성이 있다(추정, 시험 안 함).
3. `app/windows-manifest.json`의 `name`·`short_name`이 "9-6"이다. 홈 화면에 추가한 웹 앱 이름이 이것으로 보일 수 있다(확인 필요).
4. `docs/basket-design.md` 8절의 "Android 앱 중단" 문장과 원장 후보-1 행은 이 설계가 채택되면 갱신이 필요하다(원장 반영 절).
