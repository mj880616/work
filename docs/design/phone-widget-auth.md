📱 이 문서는 설계만 한다. 앱·웹 코드, DB, Edge, Supabase Auth 설정, workflow는 바꾸지 않는다. **명진 승인(9절)이 있어야 구현한다.**

- 원장 행: APP-폰앱새로 단계 ③(위젯). 상위 설계 [phone-app-v2.md](phone-app-v2.md) 5.3·D7·D8. 단계 ①(#1414)·②(#1421) merge 뒤 기준.
- 관련: [로그인 handoff](../web2-sec1-auth-handoff.md), `supabase/functions/auth-handoff/index.ts`, `app/native-auth-bridge.js`, `app/login/native-google-return.js`, `android-app/README.md`.

## 0. 명진용 요약

- **무엇.** 홈 화면 위젯은 앱이 닫혀 있어도 오늘 일정·할 일을 읽어야 한다. 그래서 위젯을 처음 켤 때 **구글 로그인을 한 번 더** 한다. 이 로그인은 앱 화면(웹)의 로그인과 따로 산다. 그래서 둘이 서로를 로그아웃시키지 않는다.
- **서버·웹은 고치지 않는다.** 지금 앱 로그인이 쓰는 길(브라우저 탭 로그인 → 봉인 → 앱으로 복귀)을 그대로 쓴다. 다른 점은 돌아온 로그인을 웹 화면에 넘기지 않고 **앱이 위젯용으로 직접 받는다**는 것 하나다. 새 서버, 새 표, 새 비밀값, 새 허용 주소가 없다.
- **폰에 남는 것.** 위젯용 "다시 로그인 열쇠"(새로고침 토큰) 하나만 폰의 잠금 금고(Android Keystore) 키로 암호화해 앱 전용 공간에 둔다. 일정·할 일 내용은 폰에 따로 저장하지 않는다(추천).
- **위젯이 하는 일.** 읽기 두 가지(오늘 일정, 할 일)뿐이다. [바구니에 넣기] 버튼은 앱을 여는 버튼이라 위젯 로그인을 쓰지 않는다.
- **끊기.** 앱 프로필 메뉴의 [위젯 로그아웃], 앱 지우기, 또는 PC 웹2 로그아웃(모든 기기 로그아웃, 확인 필요)으로 끊긴다.

## 1. 지금 상태 (사실)

| 항목 | 내용 |
| --- | --- |
| 앱 로그인 길 | 앱이 Supabase `…/auth/v1/authorize?provider=google&redirect_to=…/work/app/native-callback.html?native=android`를 브라우저 탭(Custom Tab)으로 연다(`native-google-return.js`가 바꾼 주소) → 콜백 화면이 주소의 토큰을 즉시 지우고 `auth-handoff` `seal`로 새로고침 토큰을 봉인 → `intent://auth?handoff=…;package=kr.or.kptu.work` → 앱 → 웹 `auth-handoff-client.js`가 `consume` |
| 봉인(seal) | AES-GCM, 키는 서버 비밀값에서 만든다. 안에 `version:2`, `nonce`, `sub`(사용자 id), `rt`(새로고침 토큰), 5분 만료 |
| 받기(consume) | 서버가 봉인을 열고 `app_consume_auth_handoff` RPC로 nonce를 **한 번만** 쓴다(재사용 거절). 그 뒤 새로고침 토큰으로 새 세션을 받아 `sub`와 사용자가 같은지 확인하고 세션을 돌려준다 |
| Origin 검사 | `auth-handoff`는 `Origin`이 허용 4곳(`desk`·`work`·`mj880616.github.io`·`bokdoong.com`)이 아니면 403. 앱의 직접 요청(브라우저가 아님)에는 Origin이 없어 지금 그대로는 403이다 |
| 위젯이 읽을 곳 | `google-tasks` `action=overview`, `google-calendar` `GET action=events&timeMin&timeMax`. 둘 다 `verify_jwt=false`이고 코드에서 로그인(JWT)을 확인한다. CORS는 `*`, Origin 검사 없음 |
| 웹 로그아웃 | `app/team.js`가 `POST /auth/v1/logout`을 범위 지정 없이 부른다. Supabase 기본값은 "모든 세션"(global)이다(추정, 확인 필요) |
| 앱 저장 | 백업·기기 옮기기에서 앱 저장 공간 전체 제외(`allowBackup=false` + `data_extraction_rules.xml`). 앱은 지금 토큰을 따로 저장하지 않는다 |

## 2. 왜 세션을 따로 두나

- 웹 화면의 세션은 WebView 저장 공간(`localStorage` `kptu_collab_session_v1`)에 있고 웹이 알아서 갱신한다.
- 위젯이 같은 새로고침 토큰을 쓰면, 한쪽이 갱신하는 순간 다른 쪽이 가진 토큰은 버려진 토큰이 된다. Supabase는 버려진 토큰이 다시 오면(재사용 유예 시간 뒤) 그 세션 전체를 끊는다(추정, Supabase 새로고침 토큰 교체 규칙). 그러면 앱 화면과 위젯이 번갈아 로그아웃된다.
- 그래서 위젯은 **같은 사용자의 두 번째 세션**을 갖는다. 다른 브라우저에서 한 번 더 로그인한 것과 같다.

## 3. 흐름 (W1)

1. 위젯을 홈 화면에 처음 놓으면 위젯에 "로그인" 줄 하나만 보인다. 누르면 앱이 열리고 "위젯용 로그인" 표시를 **메모리에** 세운 뒤(일회용 번호 + 시각, 10분 유효) 단계 ①과 **똑같은 로그인 주소**를 브라우저 탭으로 연다. 돌아올 주소가 같으므로 Supabase 허용 주소를 늘리지 않는다.
2. 구글 로그인 → `native-callback.html`이 봉인 → `kptuwork://auth?handoff=…`로 앱 복귀(지금과 같다).
3. 앱이 복귀를 받을 때 "위젯용 로그인" 표시가 살아 있으면, handoff를 웹 화면에 넘기지 않고 **앱이 직접** `auth-handoff`에 `consume`을 보낸다. 표시는 그 자리에서 지운다(한 번만). 표시가 없으면 지금처럼 웹 화면으로 넘긴다.
   - 앱이 로그인 도중 꺼졌다 살아나면(메모리 부족) 표시가 사라진다. 이때 handoff는 웹 화면으로 가서 앱 화면이 로그인될 뿐이다(해가 없음). 위젯에는 여전히 "로그인" 줄이 남아 다시 누르면 된다. 표시를 폰에 저장하지 않는 대신 화면 상태 저장(`savedInstanceState`)에는 둘 수 있다(구현 때 판단).
4. `consume` 요청에 앱은 `Origin: https://desk.bokdoong.com`을 붙인다(4절 근거). 응답의 세션에서
   - 새로고침 토큰 → 암호화해 저장(5절),
   - 접근 토큰 → 메모리에만,
   - `user.id` → 저장(위젯 화면 확인용, 비밀 아님).
5. 위젯 갱신(30분마다·앱을 닫을 때·위젯 새로고침 버튼): 메모리에 유효한 접근 토큰이 없으면 저장된 새로고침 토큰으로 `POST /auth/v1/token?grant_type=refresh_token` → **새 새로고침 토큰을 먼저 저장한 뒤** 접근 토큰을 쓴다 → `google-calendar`(오늘 0시~24시, 서울)·`google-tasks overview`를 읽어 위젯을 그린다.
6. 갱신이 401·`invalid_grant` 등으로 실패하면 저장된 토큰과 키를 지우고 위젯을 "로그인" 줄로 되돌린다. 네트워크 오류면 토큰을 지우지 않고 다음 갱신을 기다린다.

**동시 갱신 막기.** 위젯 갱신은 WorkManager 고유 작업 하나로만 돌리고(같은 이름은 `KEEP`), 토큰 갱신은 앱 안 잠금(mutex) 하나로 묶는다. 두 갱신이 같은 토큰을 동시에 쓰면 2절의 "세션 전체 끊김"이 날 수 있기 때문이다.

## 4. Origin 처리 — 서버를 고치지 않는 근거

| 안 | 내용 | 서버 변경 | 판단 |
| --- | --- | --- | --- |
| **A (추천)** | 앱이 `consume` 요청에 `Origin: https://desk.bokdoong.com`을 붙인다 | 없음 | 아래 근거 |
| B | `auth-handoff`가 Origin 없는 `consume`도 받게 고친다 | Edge 수정·배포(정지 지점) | A와 보안상 같은데 서버만 흔든다 |
| C | 앱 전용 새 Origin(`android-app://…`)을 허용 목록에 더한다 | Edge 수정·배포 | 브라우저가 보내는 값이 아니라 의미가 없다 |

근거:

- `auth-handoff`의 Origin 검사는 **다른 웹사이트의 스크립트가 브라우저에서 이 함수를 부르지 못하게** 하는 장치다(브라우저는 Origin을 속일 수 없다). 브라우저가 아닌 프로그램(앱, `curl`)은 원래 Origin을 마음대로 붙일 수 있다. 그래서 이 검사는 "누가 보냈나"를 증명하는 로그인 수단이 아니고, 서버도 그렇게 쓰지 않는다.
- `consume`의 실제 보안은 **봉인 자체**다. 서버 키 없이는 만들 수 없고, 5분 뒤 만료되며, nonce가 한 번 쓰이면 다시 못 쓴다. 봉인은 앱 ID를 지정한 intent로만 이 앱에 전달된다(다른 앱이 가로채지 못함, 상위 설계 5.1).
- 따라서 A는 **권한을 넓히지 않는다.** 서버 규칙·허용 목록·인증 경계가 그대로이고, 앱은 "desk 화면의 일부로서" 그 Origin을 밝힐 뿐이다. 웹 화면이 지금 같은 봉인을 `desk` Origin으로 consume하는 것과 결과가 같다.
- 확인 필요: 안드로이드 `HttpsURLConnection`이 `Origin` 머리글을 그대로 보내는지(자바 표준의 "제한 머리글" 목록에 걸리지 않는지). 구현 첫 단계 단위·실기기 시험으로 확인하고, 막히면 앱이 쓰는 HTTP 도구만 바꾼다(서버 변경 없음).
- **확인 결과(③ 구현, 2026-10-29).** 자바 표준 `HttpURLConnection`은 JVM에서 `Origin`을 소리 없이 버린다(단위 시험 `WidgetHttpTest`). 안드로이드판은 내부가 달라 보낼 수 있지만 JVM 시험으로 증명할 수 없어, 위젯은 **OkHttp**로 바꿨다(JVM·안드로이드 같은 코드, 같은 시험이 `Origin: https://desk.bokdoong.com` 도착을 확인). 서버 변경 없음.

## 5. 토큰 보관·만료·폐기

| 대상 | 어디에 | 얼마나 |
| --- | --- | --- |
| 새로고침 토큰(위젯 세션) | Android Keystore에 만든 AES-GCM 키(밖으로 꺼낼 수 없음, 이 앱만 사용)로 암호화한 값을 앱 전용 공간 파일 하나에. 백업·기기 옮기기 제외(이미 설정됨) | 위젯 로그아웃·갱신 실패·앱 삭제까지 |
| 접근 토큰 | 메모리에만 | 약 1시간(Supabase 기본, 확인 필요). 다음 갱신 때 새로 받음 |
| 위젯 로그인 표시(3절 1) | 메모리에만 | 10분 또는 한 번 쓰면 끝 |
| 사용자 id | 앱 전용 공간(평문) | 토큰과 함께 지움 |
| 일정·할 일 내용 | **폰에 따로 저장하지 않음(추천, 결정 W-D2).** 그린 위젯 그림은 홈 화면(런처)이 들고 있을 뿐이다 | 다음 갱신 때 덮어씀 |

- `EncryptedSharedPreferences`(androidx security-crypto)는 쓰지 않는다. 구글이 사용 중단을 예고한 라이브러리라 Keystore를 직접 쓴다(추정, 구현 때 버전 확인).
- Keystore 키는 "화면 잠금 해제 때만" 조건을 걸지 않는다. 위젯은 폰이 잠긴 동안에도 30분마다 갱신해야 하기 때문이다. 대신 키는 이 앱 밖으로 나가지 않고, 파일을 복사해 가도 다른 폰에서는 풀 수 없다.
- **유지 기간.** Supabase 새로고침 토큰은 기본으로 만료가 없고(세션 시간 제한·비활동 제한 설정은 확인 필요, 대시보드 읽기만), 30분마다 갱신하므로 위젯 세션은 계속 산다. 앱 쪽에서 따로 끊지 않는 것을 추천한다(결정 W-D3).
- **폐기 방법 3가지.**
  1. **[위젯 로그아웃]**(앱 프로필 메뉴, 앱 안에서만 보임): 앱이 위젯 세션의 접근 토큰으로 `POST /auth/v1/logout?scope=local`(이 세션만) → 성공·실패와 관계없이 폰의 파일·Keystore 키 삭제 → 위젯은 "로그인" 줄. 이 메뉴는 웹 화면의 작은 줄 하나와 앱 다리 명령 하나(`widget:logout`, 기존 `KPTUAppShell` 허용 Origin 최상위 화면만)를 더한다. 웹 화면 변경은 이것뿐이다.
  2. **앱 지우기**: 앱 전용 공간과 Keystore 키가 같이 지워진다. 서버 세션은 남지만 열쇠가 사라져 쓸 수 없다.
  3. **폰을 잃어버렸을 때**: PC에서 웹2 로그아웃 한 번. 웹 로그아웃이 범위를 지정하지 않으므로 Supabase 기본값(모든 세션)이면 위젯 세션도 끊긴다(추정, ③ 구현 때 실기기로 확인하고 결과를 이 문서에 적는다). 아니라면 Supabase 대시보드 사용자 화면에서 로그아웃(명진 직접)으로 안내한다.

## 6. 위젯이 읽는 범위 (D7)

| 위젯 줄 | 서버 요청 | 쓰는 토큰 |
| --- | --- | --- |
| 오늘 일정 | `GET /functions/v1/google-calendar?action=events&timeMin=<오늘 0시>&timeMax=<내일 0시>` | 위젯 세션 |
| 할 일(오늘·지난 기한 몇 줄) | `GET /functions/v1/google-tasks?action=overview` | 위젯 세션 |
| [바구니에 넣기] 버튼 | 서버 요청 없음. 앱을 `?view=basket`으로 연다 | 앱 화면(웹) 세션 |
| 줄 누르기 | 서버 요청 없음. 앱의 그 화면(할 일·일정)을 연다 | 앱 화면(웹) 세션 |

- 위젯 코드가 부르는 서버 주소는 위 두 개와 Auth 두 개(`token`, `logout`)뿐이다. 앱 단위 시험으로 "위젯이 만드는 요청 주소 목록"을 고정한다.
- **솔직한 한계.** 위젯 세션은 일반 로그인 세션이라 서버 입장에서는 웹 화면과 **같은 힘**을 갖는다(쓰기도 가능). "읽기만"은 앱 코드의 약속이고 서버가 강제하는 것은 아니다. 서버가 강제하려면 위젯 전용 읽기 토큰 서버(상위 설계 W3, 새 Edge·새 표·새 권한 체계)가 필요해 추천하지 않는다. 그래서 보호는 "토큰을 안전하게 두기"(5절)로 한다.
- **사실.** `google-tasks overview`는 응답 뒤 서버가 끝낸 할 일 사본을 Web2 표에 맞추는 일(`syncCompleted`)을 백그라운드로 한다. 웹 화면이 같은 요청을 할 때도 똑같이 하는 일이고 사용자 본인 데이터라 권한 변화는 없다. 30분마다 한 번 더 돌 뿐이다.
- 할 일 체크 같은 쓰기는 1차에서 뺀다(D7). 나중에 넣으면 이 표와 시험을 같이 고친다.

## 7. 권한을 넓히지 않는 근거

- 새 서버 함수·새 표·새 RLS·새 권한(grant)·새 비밀값·새 Supabase 허용 주소·Cloudflare 변경이 **모두 없다.**
- 위젯 세션은 같은 사용자(단독 소유자)의 두 번째 로그인이다. 서버의 소유자 확인(`private.app_is_workspace_owner`, 각 Edge의 JWT 확인)을 그대로 거친다.
- 서비스 키·Google 토큰은 앱에 들어오지 않는다. Google 토큰은 지금처럼 서버(`app_google_calendar_connections` 등)에만 있다.
- 안드로이드 권한은 그대로 인터넷 하나다. 위젯은 권한이 필요 없다.
- 위젯은 홈 화면 전용(`widgetCategory="home_screen"`). 잠금 화면에는 놓지 않는다.

## 12. 앱 로그인으로 위젯 로그인 자동 마침 (2026-10-30, 요청함 [10/30 09:15])

명진 결정: 앱(웹 화면)이 로그인돼 있으면 위젯 줄을 누르는 순간 앱이 위젯 세션을 대신 만든다(구글 화면 없음). 앱도 로그아웃이면 지금의 구글 로그인 길(3절)로 간다. 위젯 세션이 따로 사는 구조(2절)·암호화 저장(5절)·consume·읽는 범위(6절)는 그대로다.

### 12.1 흐름

1. 위젯 [로그인] 줄 → `WidgetLoginActivity`가 메모리 표시(10분·한 번)를 세움 → `MainActivity` `ACTION_WIDGET_LOGIN`(지금과 같음).
2. 로그인된 웹2 화면은 뜰 때마다 앱 다리(`KPTUAppShell`, 허용 Origin 최상위 화면만)로 `widget:ready`를 보낸다(`app/phone-widget-auth.js`, `loader-v2.js`가 로그인 확인 뒤 폰 앱에서만 불러옴). 로그아웃이면 웹이 로그인 화면(`/work/app/login/`)으로 보내므로 이 글은 오지 않는다.
3. 앱은 표시가 살아 있고 `widget:ready`를 받았으면 그 화면에 `widget:mint`를 보낸다. 웹은 **자기 접근 토큰으로** `auth-handoff` `widget_seal`을 부른다(새로고침 토큰은 보내지 않음).
4. 서버(`widget_seal`): ① `/auth/v1/user`로 접근 토큰의 사용자를 확인(익명·메일 없음 거절) ② 서비스 키로 `/auth/v1/admin/generate_link`(`magiclink`, 메일을 보내지 않음) ③ `/auth/v1/verify`(`token_hash`)로 **같은 사용자의 새 세션**을 받음 ④ 링크·세션 사용자 id가 ①과 같은지 확인 ⑤ 새 세션의 새로고침 토큰을 seal과 **같은 봉인**(version 2, nonce, 5분)으로만 돌려줌. 원문 토큰·링크·메일 주소는 응답에 없다.
5. 웹은 봉인을 `widget:handoff:<봉인>`으로 앱에 넘긴다. 앱은 `widget:mint`를 보낸 단계(MINTING)이고 표시가 살아 있을 때만 받아(`takeLogin`) 지금의 `consume`(Origin `https://bokdoong.com`)으로 위젯 세션을 만든다 → "위젯 로그인 완료".
6. 대체 길(구글 탭): 웹 화면이 로그인 화면이거나, `widget:ready`가 12초·봉인이 10초 안에 안 오거나, 웹·서버가 `widget:mint:fail`을 보내거나, 자동 봉인의 consume이 실패하면 표시를 살린 채 구글 로그인 탭을 연다. 탭은 **화면이 앞에 나온 뒤(onResume)** 연다. 단계 판단은 `WidgetLoginFlow`(단위 시험 `WidgetLoginFlowTest`).
7. 앱 화면이 로그인 탭 뒤에서 다시 만들어지면(메모리 부족) 표시 시각(비밀 아님)을 화면 상태 저장(`savedInstanceState`)으로 잇는다(3절 3의 "구현 때 판단"). 폰 저장소에는 쓰지 않는다.

### 12.2 왜 웹 세션을 넘기지 않나

웹 화면의 새로고침 토큰을 그대로 봉인하면 위젯과 웹이 같은 토큰 줄기를 쓰게 되어 2절의 "번갈아 로그아웃"이 난다. 그래서 서버가 같은 사용자의 **새 세션**을 만든다. Supabase Auth에는 "새 세션 만들기" 관리자 API가 없어, 메일을 보내지 않는 관리자 링크 만들기 + 확인을 쓴다(일반적인 방법, 추정 — 배포 뒤 실기기 확인 항목).

### 12.3 권한을 넓히지 않는 근거와 한계

- 새 표·RLS·grant·비밀값·Supabase 허용 주소·Cloudflare 변경 없음. `auth-handoff` verify_jwt·허용 Origin 4곳·consume 규칙 그대로. 서비스 키는 서버 안에서만 쓴다.
- 위젯 세션은 같은 사용자(단독 소유자)의 두 번째 로그인이다(7절과 같음). 사용자 id는 Auth가 확인한 값만 쓰고 요청 본문의 id·메일은 무시한다(시험 고정).
- 한계(솔직히): `widget_seal`은 "유효한 접근 토큰(약 1시간)"을 "새 장기 세션"으로 바꿀 수 있다. 다만 같은 화면의 저장소에는 이미 새로고침 토큰이 있어, 화면을 장악한 공격자가 새로 얻는 힘은 없다. 브라우저 밖에서 훔친 접근 토큰만으로 부르는 경우가 새로 생기는 길이며, 막는 것은 Origin 검사(브라우저 한정)와 접근 토큰 수명뿐이다. 더 줄이려면 호출 횟수 제한이나 위젯 전용 읽기 토큰(W3)이 필요하다(추천하지 않음, 필요 시 별도 결정).
- 확인 필요(배포 뒤): Supabase 메일 로그인이 꺼져 있으면 `verify`가 거절될 수 있다. 그러면 웹이 `widget:mint:fail`을 받고 앱이 구글 탭(대체 길)으로 가므로 위젯 로그인은 여전히 된다.

### 12.4 대체 길이 끊긴 곳 (조사)

- 저장소 코드만으로는 끊긴 곳을 확정하지 못했다(실기기 로그 없음). 0.3.1(#1533)의 주소 변경은 로그인 주소(`…/work/app/native-callback.html?native=android`)·consume Origin(`https://bokdoong.com`, 서버 허용 4곳에 있음)·복귀 intent를 바꾸지 않아 **직접 원인은 아닌 것으로 본다**(추정).
- 가장 유력한 추정: 위젯 줄 → 보이지 않는 화면 → 앱 화면이 아직 앞에 나오기 전(`onNewIntent`/`onCreate`)에 구글 탭을 열었다. 안드로이드 14·15(앱 targetSdk 35)는 화면이 보이지 않는 앱의 화면 열기를 막을 수 있어, 앱만 앞에 나오고 탭은 열리지 않는다. 0.3.2는 탭을 `onResume` 뒤에 연다.
- 그 밖에: 구글이 계정 하나·이전 동의로 창 없이 바로 돌아오는 경우(그때는 "위젯 로그인 완료/못했어요" 알림이 떠야 함), 탭 뒤에서 앱이 다시 만들어져 표시가 사라지는 경우(12.1의 7로 막음).

## 13. 위젯 빠른 쓰기 — '새 글 넣기' 세 가지 (2026-10-31, 요청함 [10/31 12:23], APP-위젯빠른쓰기)

명진 결정 A안: 위젯 [업데이트]·[할 일]·[노트] 칸을 누르면 웹2 전체를 띄우지 않고 **앱 자체 작은 입력 창**이 바로 뜬다. 저장하면 위젯 세션으로 서버에 바로 보내고 창이 닫힌다. 이 절은 6절의 "위젯은 읽기만" 약속을 **새 글 넣기 세 가지만** 좁게 넓히는 설계다.

### 13.1 명진용 요약 (일상어 3줄)

- **무엇이 바뀌나.** 위젯 로그인으로 할 수 있는 일에 "새 업데이트 넣기(정리함)·새 할 일 만들기·새 노트 만들기" 세 가지만 더한다. 지우기·고치기·다른 표는 여전히 못 한다.
- **서버는 그대로.** 새 서버 함수·새 표·RLS·권한(grant)·비밀값 변경이 **없다.** 지금 웹2 화면이 쓰는 저장 길 세 개를 앱이 그대로 부를 뿐이고, 서버의 "본인 작업공간만" 검사도 그대로 거친다.
- **잘못되면·되돌리기.** 저장이 실패하면 글은 창에 남고 이유가 작게 뜬다(폰에 오래 저장하지 않음). 위젯 로그인이 풀렸으면 지금처럼 웹2 쓰기 창으로 넘어간다. 되돌리기는 앱 이전 판 설치(서버 변경이 없어 서버 되돌리기 없음).

### 13.2 허용 동작 목록 (앱 `WidgetRules.allowed`에 더하는 것 전부)

| 동작 | 방식·주소 | 보내는 내용 | 웹2에서 같은 길 |
| --- | --- | --- | --- |
| 작업공간 확인(읽기) | `GET /rest/v1/app_workspace_members?user_id=eq.<위젯 세션 사용자 id>&select=workspace_id&limit=1` | 없음 | `loader-v2.js`·`profile-settings.js`의 같은 읽기 |
| 업데이트(정리함) | `POST /rest/v1/app_notes` (`Prefer: return=minimal`) | `{workspace_id, raw_text}` 두 칸만 | `basket-data.js` `createNote`(곳을 고르지 않은 업데이트 = 정리함) |
| 노트 | `POST /rest/v1/app_notes` (`Prefer: return=minimal`) | `{workspace_id, kind:"note", title, raw_text}` 네 칸만 | `basket-data.js` `createNoteDoc` |
| 할 일 | `POST /functions/v1/google-tasks?action=create` | `{action:"create", title, notes:"", due:null}` (연결 없음) | `business-area-fields.js`·`calendar-plus.js`의 `google-tasks create` |

- 위 넷 말고는 더하지 않는다. `PATCH`·`DELETE`·`upsert`(`Prefer: resolution=…`)·다른 표·다른 `action`(update·toggle·delete·link·attach 등)은 앱 허용 목록에 없어 앱이 보내지 않는다(`WidgetAuthTest`가 주소·방식·머리글을 고정).
- `app_notes` 쓰기 주소는 **물음표 없는 정확한 주소 하나**만 허용한다(필터를 붙인 일괄 요청을 만들 수 없음). 본문은 앱이 정해진 칸만 넣어 만든다(사용자 글은 JSON 문자열로만 들어감).
- `workspace_id`는 앱이 고르지 않는다. 위젯 세션 사용자 id(Auth가 준 값, 3절 4)로 서버에서 읽은 값만 쓰고 메모리에만 둔다.
- 글 길이: 업데이트 20,000자(표 검사와 같음), 노트 제목 200자·본문 100,000자, 할 일 제목 1,024자 안쪽으로 앱이 먼저 자른다·막는다. 빈 글은 보내지 않는다.

### 13.3 본인 것만 (소유자 확인)

- `app_notes`는 RLS `notes_owner_all`(`private.app_is_workspace_owner(workspace_id)`, using·with check 둘 다)과 휴지통 제한 정책 그대로다. 다른 작업공간 id를 넣으면 DB가 거절한다(앱이 넣을 수도 없음).
- `google-tasks`는 코드에서 JWT 사용자 확인 + `requireOwner` 뒤 **그 사용자의** 구글 연결로만 만든다(지금과 같음).
- 위젯 세션은 같은 사용자의 두 번째 로그인이다(7절). 서버가 보기에는 웹 화면의 저장과 구별되지 않는다.

### 13.4 서버를 고치지 않는 근거와 한계 (솔직히)

- 6절의 "솔직한 한계" 그대로다: 위젯 세션은 원래 서버에서 웹 화면과 **같은 힘**을 가진다. 그래서 이 변경은 **서버 권한을 넓히지 않는다.** 넓어지는 것은 "앱 코드가 스스로 보내기로 한 요청 목록"뿐이고, 그 목록을 위 넷으로 묶는다.
- RLS·anon·PUBLIC 권한·grant·Edge 인증 경계·verify_jwt·Supabase 허용 주소·Cloudflare: **변경 없음.** 그래서 이 일에는 DB·Edge 정지 지점이 없다. 서버 강제(위젯 전용 쓰기 토큰, 상위 설계 W3)는 새 Edge·새 표가 필요해 추천하지 않는다(필요해지면 별도 설계·★정지★).
- 새로 생기는 위험: 홈 화면에서 바로 글을 넣을 수 있다 → 잠금이 풀린 폰을 남이 만지면 정리함·할 일·노트에 글이 들어갈 수 있다. 다만 같은 폰의 앱 화면(웹 세션)으로도 이미 같은 일을 할 수 있어 새 위험은 작다(8절 첫 줄과 같은 판단). 지우기·고치기는 여전히 못 한다.

### 13.5 토큰 수명·폐기

- 5절 그대로다. 접근 토큰은 메모리, 새로고침 토큰은 Keystore 암호화 파일. 쓰기도 `readList`와 같은 잠금 하나·같은 "401이면 한 번만 새로 받기"를 쓴다.
- 폐기도 5절 세 가지(위젯 로그아웃·앱 지우기·PC 웹2 로그아웃) 그대로다. 쓰기만 따로 끊는 스위치는 두지 않는다.

### 13.6 실패와 넘김

| 상황 | 창이 하는 일 |
| --- | --- |
| 위젯 로그인이 없거나 풀림(새로고침 실패 400·401·403) | 창을 열지 않거나 닫고 **지금처럼 웹2 쓰기 창**(`?write=종류`)으로 넘긴다. 쓰던 글이 있으면 그 글을 넘기지 않고(웹 주소에 글을 싣지 않음) 창에 남긴 채 "위젯 로그인이 풀렸어요 · [크게 열기]로 저장"을 작게 띄운다 |
| 네트워크 오류·서버 5xx·할 일 연결 없음 | 창을 닫지 않고 글을 그대로 둔다. 이유 한 줄(예: "인터넷 연결을 확인해 주세요", "할 일 연결이 필요해요")을 작게 표시. 다시 [저장] 가능 |
| 창을 닫음·앱이 꺼짐 | 글은 메모리에만 있었으므로 사라진다(폰 저장 금지 원칙). 화면 회전처럼 창이 다시 만들어질 때만 화면 상태 저장(`savedInstanceState`)으로 잇는다 |
| [크게 열기] | 웹2 쓰기 창(조직·사업 고르기, 긴 글, 첨부). 쓰던 글은 넘기지 않는다(같은 이유) |

- 로그에는 종류·걸린 시간(ms)·HTTP 상태 숫자만 남긴다. 글·토큰·응답 본문은 남기지 않는다.

### 13.7 [사진] 칸

- (0.4.3, APP-위젯빠른쓰기 남은 일 1) 고르기·카메라 창(`PhotoPickActivity`)에서 사진을 고르면 **창이 바로 닫히고 뒤에서 올린다.** 위젯 로그인이 없거나 복사가 실패하면 지금처럼 공유 받기 길(웹2 정리함 올리기)로 간다.
- 서버 길은 웹 `basket-upload.js` `uploadBatch`와 같은 정리함 첨부 올리기(`POST /functions/v1/basket-files`, multipart) 하나다. 첫 장이 정리함 글을 만들고(`raw_text` 없음), 다음 장은 그 `note_id`에 이어 붙인다. 앱 허용 목록에는 **물음표 없는 정확한 주소 + 'file' 파일 칸 하나 + 선택 'note_id'(uuid)** 모양만 더한다(`WidgetRules.allowedParts`). 같은 주소의 JSON(글자 읽기)·`action`(지우기·사진 보기·정리)은 보내지 않는다(`QuickPhotoTest`).
- 서버·DB·Edge·RLS·grant·verify_jwt 변경 없음. 작업공간·소유자는 서버가 로그인 사용자로 정한다(요청에 작업공간 id 없음). 사진 글자 읽기(웹 공유 길의 선택 단계)는 하지 않는다.
- 고른 사진의 임시 읽기 권한은 창이 살아 있을 때만 있으므로, 창을 닫기 전에 앱 전용·백업 제외 폴더(`noBackupFilesDir/quick-photo/<묶음>`)로 복사한다. 올린 장은 바로 지우고 다 올리면 폴더째 지운다. 실패 알림을 밀어 버리면 지우고, 3일 지난 묶음도 다음 [사진] 때 지운다. 20장·100MB(서버 한도)를 넘는 사진은 빼고 토스트로 알린다.
- 올리기는 WorkManager 작업(인터넷 연결 조건, 안드로이드 12+는 급한 작업)으로 한다. 접근 토큰은 위젯 세션 잠금 안에서 받고 올리기는 잠금 밖(위젯 갱신을 막지 않음), 401이면 한 번만 새로 받는다.
- 결과: 다 되면 토스트 '정리함에 사진 n장을 넣었어요'. 실패하면 토스트 + 알림 한 줄(새 권한 없음, 녹음 때의 알림 권한을 쓰고 없으면 토스트만). 인터넷·서버 일시 오류·로그인 풀림은 [다시 시도](남은 장만, 같은 정리함 글에 이어). 결과 모름(`note_save_result_unknown`)·너무 큼·권한 거절은 겹쳐 올리지 않게 묶음을 지우고 '정리함을 확인해 주세요'.
- 한계: 응답을 받기 전에 연결이 끊기면(서버는 저장) [다시 시도]가 같은 사진을 한 번 더 올릴 수 있다.

## 14. 위젯 다시 기획 — 이번 주 '가장 큰 일' 고르는 기준 (2026-10-31, 요청함 [10/31 12:31], APP-위젯다시)

명진 확인용. 이번 주 위젯(4×2) 아래 첫 줄 '가장 큰 일 D-n'은 아래 순서로 **한 개**를 고른다. 새 서버 읽기 없이 이미 허용된 `google-calendar action=events`(보이는 주 월~일)만 쓴다.

1. 보이는 주에서 **오늘 이후**(지난 일정 제외) 일정만 본다. 주말(토·일)에는 다음 주 월~일을 보인다.
2. 제목에 **큰 일 낱말**이 있는 일정을 먼저 고른다: 파업·집회·기자회견·결의대회·선포·총회·대의원·대표자회의·교섭·투쟁·출범·토론회·공청회·간담회·면담·대회.
3. 그런 일정이 없으면 **시간이 정해진 일정 중 가장 긴 것**(2시간 이상만). 종일 일정은 개인 메모(약 복용 등)가 섞여 2·3에서 고르지 않는다(2의 낱말이 있으면 고름).
4. 같은 조건이면 **더 이른 것**.
5. 고를 것이 없으면 줄을 그리지 않는다.

- 표시: `D-n`(오늘이면 `오늘`) + `요일 시각 제목`. 누르면 그날 달력.
- 둘째 줄 '상집 보고일': 보이는 주의 월요일(주간보고 기준일 규칙 `journal-data.js` reportDay와 같은 '다음 월요일' 정의 — 보이는 주 월요일은 지난주 보고일). 주간보고 확정 여부는 위젯이 읽지 않는다(새 읽기 없음).
- 셋째 줄 '일정 몰린 날': 오늘 이후 일정이 **3개 이상**인 첫 날. `요일 · 일정 n개 몰림 · 첫 일정 시각부터`.
- 요일 칸 색: 3개 이상 몰린 날·가장 큰 일이 있는 날을 옅은 색으로. 나머지는 바탕 그대로.
- 낱말 목록·기준이 맞지 않으면 명진이 고칠 낱말만 알려 주면 된다(앱 새 판에 반영).
