## 1. 원본 분석 (구조만)

분석 방법: HWP 5 원본을 저장소의 rhwp 엔진(`@rhwp/core` 0.8.7, `scripts/hwp-lab/rhwp-pin.json` 고정본)으로 .hwpx로 바꾼 뒤 시제품 읽기 도구(`scripts/weekly-hwpx/report.mjs`)로 표를 읽었다. 같은 결과를 HWP 5 레코드(DocInfo 스타일 표, BodyText 문단·표·칸 레코드)를 직접 읽어 대조했다. 원본·변환본·중간 결과는 비공개 작업 폴더에만 두었다.

### 1.1 쪽·글꼴·스타일 (사실, 7개 파일 모두 같음)

- 쪽: A4 세로, 왼쪽·오른쪽 여백 20mm, 위·아래 15mm, 머리말·꼬리말 10mm, 쪽 테두리 있음.
- 글꼴 5종: 함초롬돋움·함초롬바탕·휴먼고딕·HY견고딕·HY견명조.
- 스타일 이름과 글자 크기는 `hwp-style-map.md` 2절 표와 같다(바탕글 13pt, 안건제목 36pt, 큰 제목 18pt, 중간 제목 16pt, 작은 제목 14.5pt 굵게, 최하위 제목[강조] 13.5pt, 세부 참고사항 11pt·왼쪽 20pt, 표내부 10pt, (기타)의결주문 13pt, 중간대제목 28pt 굵게, 문서표지제목 44pt, 쪽 번호 14pt, 각주 9.5pt). 줄간격: 바탕글·제목 180%, 안건제목·세부 참고사항 160%, 표내부 150%.
- 스타일 수: 팀 전체본 14개(양식 13 + 사본 1), **개인본 46개**(양식 13 + 다른 문서에서 붙여 넣을 때 딸려 온 스타일 33개 — 엑셀 칸 스타일·"사본" 스타일 등). 팀 전체본에서 서식을 뽑으면 이 군더더기가 없어진다.
- 표 안 글: '표내부' 스타일(휴먼고딕 10pt). 표 머리 줄은 옅은 색 칠 + 가운데 맞춤, 테두리 0.12mm 실선. 요약 표는 쪽이 넘어가면 머리 줄을 되풀이한다.
- 색 관례: 팀 전체본은 이번 주에 새로 들어오거나 바뀐 글을 **파란 글씨**(표내부와 같은 크기·글꼴, 색만 다름), 참석 요청 표의 바뀐 일정을 **빨간 글씨**로 쓴다(글자 수 기준 파란 글씨가 본문의 약 12%). 이 글자 모양들은 양식 파일 안에 이미 있다.

### 1.2 팀 전체본(상집보고) 차례 (사실)

| 차례 | 스타일 | 내용 칸 |
| --- | --- | --- |
| 문서 제목 | 안건제목 | 팀 이름 한 줄 |
| ■ 일시 : YYYY년 M월 D일(요일) | 바탕글 | 보고일 |
| **1. 요청사항** | 큰 제목 | |
| 1) 집회/행사 참가 요청 | 작은 제목 | 표 A(아래) |
| 2) 주요 일정 | 작은 제목 | 팀본에서는 비어 있음 |
| **2. 기본․영역․의제 사업** | 큰 제목 | |
| 1) 요약 | 작은 제목 | 표 B(아래) |
| 2) 세부 내용 | 작은 제목 | (1)~(11) 회의·면담 결과. 항목마다 '작은 제목' 한 줄 + 2열 상자 표 |
| **3. 투쟁 사업** | 큰 제목 | 1) 집회·농성 등(3열 표), 2) 투쟁 사업장 현황(2열 표) — 여기서는 "1)"이 '중간 제목' |
| **4. 산하조직 현황** | 큰 제목 | 1) 요약(조직별 2열 표, 90여 줄), 2) 참고자료 — "1)"이 '중간 제목' |
| **5. 주요 일정** | 큰 제목 | 3열 표(일 \| 시간/내용/장소 \| 참석자) + "※" 휴가 등 참고 줄(표내부) |

- **번호 단계와 스타일이 절마다 다르다(사실).** 1·2절은 "1)"과 "(1)"에 모두 '작은 제목', 3·4절은 "1)"에 '중간 제목'. 2절 2) 안의 한 항목은 "(3)"에 '중간 제목'을 썼다(한 번). 기준표(`hwp-style-map.md` 3절: 1. 큰 제목 / 1) 중간 제목 / (1) 작은 제목)와 다르다 → 결정 W4.
- 번호는 자동 번호가 아니라 글자로 쳐 넣었다("1.", "1)", "(1)"). 시제품도 글자로 넣는다.

**표 A — 집회/행사 참가 요청**(사실)

| 칸 | 구성 |
| --- | --- |
| 열 | 머리 3칸: **일 \| 시간/내용/장소 \| 참석 요청**. 실제 격자는 4열(날짜 칸 옆에 폭 0.4mm쯤의 숨은 열이 있고, 머리의 "시간/내용/장소"가 두 열을 합침) |
| 병합 | 같은 날 행사가 둘 이상이면 날짜 칸을 세로로 합침 |
| 글 | 날짜 "M.D.(요일)" / "HH:MM / 행사 이름 / 장소" 한 줄 / 참석 요청은 한 사람에 한 문단 |
| 개인본과 차이 | 개인본은 진짜 3열(숨은 열 없음). 시제품은 머리 칸 기준 3열로 정리해서 쓴다 |

**표 B — 요약**(사실)

| 칸 | 구성 |
| --- | --- |
| 열 | **사업영역 \| 세부 과제 \| 진행 상황 및 이후 계획 \| 담당 팀원**(폭 약 11% / 18% / 61% / 10%) |
| 줄 | 머리 1줄 + 34줄. 사업영역 6개(세로 병합 13·4·3·4·9·1줄) |
| 병합 | 사업영역 칸은 늘 세로 병합. 세부 과제도 한 과제 아래 여러 줄이 있으면 세로 병합(한 과제 아래 8줄이 최대 — 줄마다 다른 연구 주제·다른 담당). 담당 칸도 가끔 세로 병합(3줄) |
| 진행 칸 글 | 한 칸에 여러 문단. 줄머리 기호: "◦ "(묶음 제목) → "- "(사실) → "  · "(들여 쓴 하위 줄), 가끔 "∘ ", "<…>"(제목), "※"(참고), "*"(참고). 날짜는 "10.7.", "10.7.(수)", "[3차] 11.5.(목) 14시" 꼴 |
| 담당 칸 | 사람 이름 한 문단씩, 공동 담당은 "갑 / 을" 또는 "갑, 을" 또는 문단 두 개 |
| 문체 | 압축형이 다수("…예정", "…완료", "…진행", "…추진"), "…함/…임/…됨"이 아직 남아 있음(개인본 6주와 팀본의 내 줄 203문단 중 17문단) |

**상자 표 — 2) 세부 내용**(사실): 2열, 왼쪽 칸 이름이 "제목 \| 일시/장소 \| 참석자 \| 회의 내용"(4줄) 또는 "회의제목 \| 일시/장소 \| 참석자 \| 내용 \| 차기일정"(5줄) 또는 "회의제목 \| 일시/장소 \| 참석자 \| 보고 \| 논의결과 \| *차기회의"(6줄) — 같은 문서 안에서 세 가지가 섞여 있다. 성명·기획안 같은 긴 글은 1×1 상자 표에 넣는다.

### 1.3 개인본 차례와 팀본과의 차이 (사실)

| | 개인본(6주 모두) | 팀 전체본 |
| --- | --- | --- |
| 1. 요청사항 | 1) 참가 요청 표(3열). 어떤 주는 2) 논의 요청 + 기획안 상자·할 일 표(할 일 \| 담당 \| 기한) | 1) 표(4열 격자) + 2) 주요 일정 |
| 2. 기본·영역·의제 사업 | 1) 요약 표(4열, **머리 + 29줄 고정**, 내 줄 말고는 빈칸) + 회의 결과 상자 (1)(2)… | 1) 요약 표(머리 + 34줄, 팀원 전부) + 2) 세부 내용 |
| 3. | 없음(번호를 건너뜀) | 투쟁 사업 |
| 4. 산하 조직 현황 | 1) 요약(2열, 머리 + 내 담당 조직 13줄), 2) 참고자료(상자), 3) 가입상담 | 4. 산하조직 현황(팀 전체 조직) |
| 5. 주요 일정 | 3열 표(7~16줄) + "※ 휴가" 줄 | 같은 모양, 팀 전체 |

- **요약 표 틀이 다르다.** 개인본은 옛 틀(29줄)을 6주 내내 그대로 썼다. 팀본에만 있는 세부 과제가 6개(새 사업영역 1개 포함, 모두 다른 팀원 담당이거나 담당 없음), 이름이 다른 세부 과제가 2개(낱말 하나 차이 1개, 띄어쓰기 차이 1개), 개인본에만 있는 빈 세부 과제 1개, 개인본 끝의 이름 없는 빈 줄 4개. → 개인본을 팀본 틀에 맞추면 팀장이 줄을 옮겨 붙일 일이 없어진다(이번 요청의 핵심).
- 내 담당 줄 수: 개인본 5→5→5→5→6→7줄. 팀본(10/19)에서는 6줄(개인본에서 끝난 항목 1줄이 팀본에서 빠짐).
- 팀장이 내 줄을 고친 정도(10/19 개인본 → 10/19 팀본): 내 줄 35문단 중 30문단 그대로, 2문단 문구 다듬음(기호 바꿈·낱말 빼기), 1줄(3문단) 정리해서 뺌.

| 10/6 → 10/19 | 6 | 4 | 25 | 15 |

  "고친 줄"은 뺀 줄 가운데 글자 두 개씩 묶음 기준 50% 넘게 비슷한 것과 짝지은 수(추정 기준). 매주 줄의 절반 안팎이 새로 들어오고 지난 일은 빠진다. **그대로 두는 줄이 매주 있으므로 "바탕 + 바뀐 것만"이 맞고, 새 줄이 많으므로 "더하기"가 일의 대부분이다.**

### 1.5 정리 — 초안이 지켜야 할 규칙

1. 틀은 지난주 팀 최종본의 요약 표(줄 순서·사업영역 병합·세부 과제 이름)를 그대로 쓴다.
2. 내 이름이 담당 칸에 있는 줄만 채우고, 나머지 줄의 진행·담당 칸은 비운다(세부 과제·사업영역 이름은 남김 — 팀장이 합칠 때 줄이 맞도록).
3. 팀장이 다듬은 내 줄 문구가 바탕이다. 이번 주에 바뀐 사실이 없는 줄은 손대지 않는다.
4. 새로 더한 줄·고친 줄은 파란 글씨(W5). 끝난 일은 빼는 제안만 하고 사람이 정한다.
5. 날짜("■ 일시")는 보고 주 월요일로 자동. 제목 줄도 자동.
6. 스타일·글자 모양·표 테두리는 확정본에서 뽑은 것만 쓴다(새로 만들지 않음).

## 3. 지난주 확정본 받기

### 3.1 추천: 자료실 "주간보고 확정본" 분류 (W1 ①)

| 단계 | 하는 일 | 어디서 | 바뀌는 것 |

| 올리기 | 팀장이 보낸 최종 .hwp를 [자료실 올리기]로 분류 "주간보고 확정본"에 올림 | 기존 `library-files` | 없음(분류는 자유 입력 칸) |

| 읽기 | [주간보고 한글 초안]을 누르면 가장 최근 "주간보고 확정본" 자료를 기존 `document-actions` `hwp-open`으로 받아 **브라우저 메모리에서** 연다 | 서버는 owner 확인 뒤 파일을 전달만 함(`supabase/functions/_shared/hwp-edit.ts`) | 없음 |

- 파일 내용은 공개 저장소·서버 로그·DB에 남지 않는다. 서버는 이미 있는 HWP 열기 경로(owner 확인, 30MB 상한)를 그대로 쓰고 새로 기록하지 않는다. AI로 가는 글은 4절의 "내 칸 글"뿐이다.
- 권한을 넓히지 않는다(`hwp-union-template-investigation.md` 4.2: Web2 Drive 권한은 `drive.file` — 앱이 올린 파일만 읽음. 자료실로 올린 파일은 앱이 만든 파일이라 읽힌다).
- 빈 서식은 따로 보관하지 않고 **매주 확정본에서 새로 뽑는다**. 팀 양식이 바뀌면 다음 주부터 저절로 따라간다. 뽑은 빈 서식은 매번 "원본 글이 한 글자도 안 남았는지" 검사한다(7절).

### 3.2 다른 길

- ② 기기에서 고르기: [HWP 편집] → [파일 선택]과 같은 방식. 보관이 없고 서버를 전혀 거치지 않는다. 폰은 파일 앱에 파일이 있어야 한다. **2단계는 이 길도 같이 둔다**(자료실에 아직 안 올렸을 때).
- ③ Drive 지정 폴더 직접 읽기: `drive.readonly` 이상으로 권한을 넓혀야 함(경고 화면·재연결·Edge 배포, `AGENTS.md` §6). 파일 한 개를 위해 넓히기엔 크다.
- 바구니 첨부로 받기도 같은 `hwp-open` 경로로 가능하지만, 확정본은 매주 쌓아 두는 자료라 자료실이 맞다.

## 4. 이번 주 바뀐 것만 고치기

### 4.1 흐름

1. 확정본 → 내 칸 바탕(`personalFromTeam`): 요약 표 틀 그대로, 내 줄만 남김.
2. 이번 주 재료(2절)를 모음.
3. AI에 **내 줄 글 + 이번 주 재료**를 주고 "고칠 목록"만 받음:
   - `add` — 어느 줄(사업영역·세부 과제, 같은 과제 여러 줄이면 몇 번째) 어디 뒤에 새 문단
   - `replace` — 바꿀 문단 **원문 그대로** + 새 문장(예: 지난주 "…예정"이 이번 주 일이 되어 "…완료")
   - `remove` — 뺄 문단 원문(끝난 일)
4. 화면이 목록을 검사(`applyPatch`): 내 줄이 아니면 거절, 바꿀 원문이 바탕에 정확히 없으면 거절, 이번 주에 이미 고친 줄을 또 고치면 거절. 거절된 항목은 버리지 않고 "확인 필요"로 보여 준다.
5. 줄마다 [받아들이기]/[버리기]. 받아들인 줄만 파란 글씨로 들어간다.
6. .hwpx(또는 HWP) 내려받기.

문단·표 줄 단위 대조는 시제품 `diffLines`(문단 단위 최장 공통 순서)와 `diffRows`(줄 짝짓기)를 쓴다. 비교 화면에서 "지난주 그대로 / 고침 / 새 줄 / 뺌"을 보여 줄 때도 같은 함수를 쓴다.

### 4.2 AI가 맡을 것 / 사람이 확정할 것

| AI(ChatGPT, 서버 `ai-assist`) | 사람(명진) |
| --- | --- |
| 이번 주 기록을 어느 내 줄에 붙일지 제안 | 줄마다 받아들이기·버리기 |
| 기록을 양식 문체로 압축("…함/…임" → 명사형, "예정임→예정", 날짜 "M.D.(요일)") | 참석 요청 대상(임원) |
| 지난 "예정"이 이번 주 일어난 일이면 바꾸기 제안 | 새 세부 과제 줄 만들기 |
| 끝난 일 빼기 제안 | 담당 칸, 다른 팀원 칸(손대지 않음) |
| 요청 표 칸 꼴 맞추기 | 최종 파일을 팀장에게 보내기 |

- AI가 지켜야 할 것(서버 검사, `ai-server.md` 4.4·5.4와 같은 방식): 엄격한 JSON 형식, 줄 위치는 넘겨준 목록 안의 것만, 원문에 없는 숫자·날짜·이름이 새로 생기면 그 항목은 "확인 필요", 한 번에 고칠 항목 수·문단 길이 상한.
- 보내는 것(W7): 내 줄 글(확정본 중 내 칸, 화면이 보냄 — 서버가 HWP를 읽지 않으므로 `ai-server.md` 4.3의 "쓰임 4 예외"에 해당, 길이 상한) + 이번 주 재료(서버가 내 로그인으로 DB에서 직접 읽음). 다른 팀원 칸·조직 현황·파일은 보내지 않는다. 사용 기록에는 횟수·토큰 수만 남긴다(지금 `app_ai_daily_usage`와 같음).
- 지금 `ai-assist`는 요청 2KB·답 800토큰 상한이라(`supabase/functions/ai-assist/handler.ts` `MAX_BODY_BYTES`, `MAX_OUTPUT_TOKENS`) 이 쓰임에는 작다 → 새 kind와 상한은 3단계에서 Edge 재배포(정지 지점).

## 5. .hwpx를 어디서 만들까 — 브라우저(추천, W6)

| | 브라우저(내 기기) | 서버(Edge) |
| --- | --- | --- |
| 파일 내용이 가는 곳 | 기기 안에만. 서버는 기존 열기 경로로 전달만 | 파일 전체가 서버로 감(로그·오류 보고에 섞일 위험) |
| HWP 5 → .hwpx | 편집기와 같은 rhwp 엔진(WASM) — 이미 반입본에 있음. 접착 JS(`rhwp.js`)만 더하면 됨(`hwp-union-template-investigation.md` 5절 F1과 같은 일) | Deno에서 같은 WASM을 돌려야 함(용량·실행 시간 한도, 새 배포) |
| zip 만들기 | 시제품 `zip.mjs`(외부 라이브러리 없음) + 브라우저 기본 `CompressionStream('deflate-raw')` | node:zlib 대신 Deno 압축 |
| 결과 받기 | 내려받기 단추 / 바로 HWP 편집기로 열기 | 다시 브라우저로 보내야 함 |
| 운영 변경 | 반입본 해시·고정 검사 갱신(`tests/hwp-lab-pin.test.mjs`) | 새 Edge 함수 배포(§6·§8) |

- 시제품 모듈(`scripts/weekly-hwpx/*.mjs`)은 Node 전용 기능을 쓰지 않게 만들었다. 압축 함수만 부르는 쪽이 넘긴다. 브라우저의 압축은 비동기라 2단계에서 "파일마다 먼저 압축 → zip 묶기" 순서로 감싸는 작은 손질이 필요하다(추정, 착수 때 확인).
- 엔진·파일 처리는 지금 편집기처럼 **로그인 정보가 없는 칸막이(sandbox iframe 또는 worker)** 안에서 돌린다. Web2 창은 바이트만 넘기고 결과 바이트만 받는다.

## 6. .hwpx가 안 열릴 때 (W8)

1. **[HWP로 받기]**: 같은 엔진으로 .hwpx → HWP 5 저장(`exportHwp`). 시제품 CI가 만든 파일마다 이 저장이 되는지 확인한다.
2. **Web2 HWP 편집기로 열기**: 만든 바이트를 편집기 `loadFile`로 열어 화면에서 보고 고친 뒤 저장(이미 있는 기능).
3. **글로 복사**: 칸별 글을 [한글용 복사](MD-내보내기)처럼 기호·줄바꿈만 맞춰 복사 → 지난주 파일에 붙여 넣기. 스타일은 한글에서 단축키로.
4. 어느 길이든 실패하면 오류 이름만 보여 주고 파일 내용은 화면·로그에 찍지 않는다.

## 10. 남은 위험

- **한글 실기 미확인**: 규격 검사와 rhwp 다시 열기는 통과했지만 한컴오피스가 받아 주는지는 실기로만 안다. 시제품 문단에는 줄 배치 정보(`linesegarray`)를 넣지 않았고 표·칸 높이를 다시 계산하지 않는다(한글이 다시 계산한다고 봄, 추정). 안 열리면 6절 1번(HWP로 받기)으로 간다.

- 확정본 틀이 크게 바뀌면(열 이름 변경 등) 표 찾기가 실패한다 → 그때는 "요약 표를 찾지 못함"으로 멈추고 아무것도 만들지 않는다.
- 이름 짝짓기: 세부 과제 이름이 프로젝트 이름과 다르면 사람이 한 번 짝지어야 한다.
- 압축 비동기 손질·엔진 접착 파일 반입은 2단계 일(추정 규모 작음).
