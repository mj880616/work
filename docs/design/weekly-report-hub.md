# 업무일지 = 주간보고 허브 기획 (JOURNAL-주간보고허브)

📱 폰 가능 — 이 문서는 기획·조사만 한다. 앱 코드·DB·Edge·권한 변경 없음.

- 작성: 2026-10-20, Claude Code 웹. 기준 main `fbf0eaa`.
- 원장 행: `docs/roadmap.md`의 JOURNAL-주간보고허브(대기, 기획 먼저). 이어지는 행: WEEKLY-자동화, JOURNAL-끝낸할일범위, PRJ-기록입력, MEET-기록보내기, BASKET-수집연동.
- 앞 설계: [journal-memo-diary-design.md](journal-memo-diary-design.md)(업무일지 2단계까지), [meet-record-send-investigation.md](meet-record-send-investigation.md)(회의 → 조직·프로젝트 기록).
- 표기: **사실**은 저장소 코드·문서에서 확인한 것(파일 위치를 붙임). **추정**은 그렇게 표시했다. 운영 DB는 이 세션에서 볼 수 없어(AGENTS.md §1, 웹 세션) 표의 실제 칸·행 수는 확인하지 않았다.
- 공개 저장소라 예시는 "A 사업장", "B 프로젝트"처럼 일반 이름만 쓴다.

## 명진이 정할 것

### 결정 1. 업무일지에 무엇을 더 모을까

| 선택지 | 내용 |
| --- | --- |
| ① 지금 앱에 이미 쌓이는 기록만 먼저 (**추천**) | 프로젝트 기록, 담당조직 기록, 회의(날짜·이름), 자료실 새 자료, 공유 페이지 고친 것, 할 일 예정을 더함. 서버·DB를 안 건드려서 바로 만들 수 있음 |
| ② ①에 텔레그램·통화까지 | 텔레그램·통화 기록은 아직 앱에 안 들어옴. 바구니로 가져오는 일(BASKET-수집연동)이 먼저 끝나야 함 |

추천 이유: ①만으로도 주간보고 재료 대부분이 한 화면에 모임. 텔레그램·통화는 바구니로 들어오기 시작하면 "바구니 업데이트" 칸에 저절로 같이 보임(따로 만들 일 없음).

### 결정 2. 하루씩 볼까, 한 주를 묶어 볼까

| 선택지 | 내용 |
| --- | --- |
| ① 지금처럼 하루 카드에만 붙이기 | 날짜를 누르면 그날 것만. 만들기는 쉽지만 주간보고 쓸 때 7일을 하나씩 눌러야 함 |
| ② 한 주 묶음 화면만 | 사업영역·조직별로 한 주를 정리. 보고서 쓰기엔 좋지만 "오늘 뭐 했지"를 보기 불편 |
| ③ 둘 다: 하루 카드 + [주간 정리] 탭 (**추천**) | 평소엔 하루 카드, 금요일엔 [주간 정리]로 바꿔 사업영역·조직별 묶음을 보고 복사 |

추천 이유: 평일엔 하루 기록, 금요일엔 주간보고라는 지금 쓰는 흐름과 같음. 둘이 같은 재료를 다르게 보여 줄 뿐이라 저장할 것이 늘지 않음.

### 결정 3. 프로젝트 정리를 먼저 할까

| 선택지 | 내용 |
| --- | --- |
| ① 주간 정리 탭은 프로젝트 정리 뒤에 (**추천**) | 하루 카드에 붙이는 1단계는 지금 바로. 사업영역별 묶음(2단계)은 명진이 큰 프로젝트를 주간보고 사업영역에 맞춰 정리한 뒤 |
| ② 정리 전에 지금 프로젝트 이름 그대로 묶기 | 바로 볼 수는 있지만 보고서 칸과 안 맞아 다시 고쳐야 함 |

추천 이유: 앱은 "큰 프로젝트 → 하위 프로젝트" 순서를 이미 알고 있음. 큰 프로젝트를 사업영역으로 맞춰 두기만 하면 새 칸 없이 그대로 묶을 수 있음. 정리 전에 만들면 묶는 기준을 두 번 만들게 됨.

### 결정 4. "담당자" 칸은 어떻게 채울까

| 선택지 | 내용 |
| --- | --- |
| ① 초안에서는 비워 두고 명진이 채움 (**추천**) | 앱에는 프로젝트마다 담당자를 적는 칸이 없음. 지금은 혼자 쓰는 앱이라 담당자는 대부분 명진 |
| ② 프로젝트마다 담당자 칸을 새로 만듦 | DB 변경이 필요함(서버 승인 단계). 같이 일하는 사람 이름을 앱에 남기게 됨 |

추천 이유: 담당자 칸 때문에 DB를 바꾸기엔 얻는 게 적음. 써 보고 매주 손으로 고치는 게 번거로우면 그때 ②로.

### 결정 5. 끝낸 할 일이 3일치만 보이는 문제

이미 원장에 있는 JOURNAL-끝낸할일범위(서버 고치기, 승인 단계 있음)를 **2단계 전에** 하자는 것이 추천. 한 주 전체의 끝낸 할 일이 안 모이면 주간 정리 탭이 반쪽이 됨.

## 1. 무엇이 모이고 무엇이 안 모이나

### 1.1 지금 업무일지에 모이는 것 (사실, `app/journal-data.js`)

이 표는 기획 당시(`fbf0eaa`)가 아니라 #822(JOURNAL-일지카드정리, merge `ddad13c`)와 이 문서 4절 1단계(JOURNAL-주간보고허브 1단계) 뒤의 모습이다. 기획 당시 있던 '바구니 업데이트'·'고친 노트'(`readChangedNotes`, kind=note) 칸은 #822에서 없어졌다. 바구니 업데이트는 조직 소식·프로젝트 소식 안으로 들어갔고, 노트는 더 읽지 않는다.

| 묶음(화면 순서) | 읽는 곳 | 그날로 보는 기준 | 비고 |
| --- | --- | --- | --- |
| 오늘 한 줄(여러 줄) | `app_notes` kind=work, `readWorkWeek` | `journal_day` | 유일하게 저장하는 것. 하루 50줄·줄마다 300자 |
| 일정 | Edge `google-calendar` action=events, `readWeekEvents` | 일정 시작 시각(서울), 종일 일정은 기간 | 주 단위로 읽음 |
| 끝낸 할 일 | Edge `google-tasks` action=tasks, `readDoneTasksWindow` | 완료 시각 | 최대 8일 요청. 옛 서버는 3일만 줌 → JOURNAL-끝낸할일범위(Edge 배포는 그 행) |
| 조직 소식 | `readBasket`(조직으로 확정 연결·[자료로 넣기]한 바구니 업데이트, 아무 데도 안 보낸 것은 '미분류') + `app_suborganization_updates`(`readOrgUpdates`) | `occurred_at` | 조직 이름별. 업데이트 하나는 첫 줄 한 항목 |
| 회의·행사 결과 | `app_meetings`(`readWeekMeetings`, 이름·회차·날짜만) | `meeting_at` | 회의 결과 글은 읽지 않음 |
| 프로젝트 소식(1단계) | `app_project_progress_updates`(`readProjectUpdates`) + 프로젝트로만 보낸 바구니 업데이트 | `effective_on`, 바구니는 `occurred_at` | 프로젝트 이름별. #822에서는 조직 소식 '미분류'에 "프로젝트명 · 내용"으로 있었음 |
| 할 일 예정(1단계) | 끝낸 할 일과 같은 Edge 응답의 미완료 할 일 | 마감일(`due`) | 서버 기본 범위 그대로: 지난 마감 + 오늘부터 7일 안. 마감 없는 할 일은 안 옴 |
| 자료실 새 자료(1단계) | `app_documents`(`readWeekDocuments`, 제목·파일 이름·분류·회의 연결만) | `created_at`(올린 날) | 분류는 자료실 분류 이름으로 표시, 회의에 붙은 자료는 "회의자료" |
| 공유 페이지(1단계) | `app_share_pages`(`readWeekSharePages`, 제목·상태만) | `updated_at`(고친 날) | 블록 본문은 읽지 않음 |

읽기 부담: 모두 서울 시간 월~일 한 주로 자르고, 필요한 칸만 고르며, 자료실·공유 페이지는 한 주 300개까지(넘으면 그 묶음과 초안에 안내). 빈 묶음은 상자 대신 맨 아래 "기록 없는 묶음: …" 한 줄로 접고, 못 읽은 묶음은 그 상자에서 따로 [다시 시도]한다.

[주간보고 초안 복사](`weeklyDraft`)는 날짜별(월~일)로 그날 한 줄 → 위 묶음을 화면 순서대로 글로 복사한다. 사업영역·조직 구분 정리는 2단계([주간 정리] 탭) 몫이다.

### 1.3 날짜 기준 원칙(제안)

- "그 일이 있었던 날"을 우선한다: 기록한 날짜(`effective_on`, `occurred_at`), 회의 날짜, 일정 날짜.
- 그런 날짜가 없는 것만 "앱에서 만들거나 고친 날"(`created_at`, `updated_at`)을 쓴다: 자료실, 공유 페이지, 노트.
- 모두 서울 시간 월~일 주(`weekStart`, `app/journal-data.js`)로 자른다. 홈 화면 주 계산(`ranges`, `app/home-read-model.js`)과 같다.

## 2. 보여 주는 단위 비교

| | ① 하루 카드에 붙이기 | ② 주 단위 묶음 화면 | ③ 둘 다 (하루 카드 + [주간 정리] 탭) |
| --- | --- | --- | --- |
| 모양 | 날짜를 누르면 지금 묶음 아래에 프로젝트·조직·회의·자료… 묶음이 더 붙음 | 한 주를 사업영역(큰 프로젝트) › 하위 프로젝트, 조직별로 묶은 표 | 일지 위쪽에 [하루 | 주간 정리] 전환. 하루는 ①, 주간 정리는 ② |
| 좋은 점 | 지금 구조(`dayMaterials`·`GROUPS`)에 묶음만 더함. 단순 | 주간보고 양식(사업 요약 표·조직 현황)과 거의 같은 순서 | 평일 기록·금요일 보고 흐름과 맞음. 같은 재료를 한 번 읽어 두 모양으로 |
| 나쁜 점 | 묶음이 10개 넘게 늘어 하루 화면이 길어짐(빈 묶음은 접어야 함). 보고서 쓸 땐 여전히 7일을 넘겨 봐야 함 | 하루 기록 보기가 사라짐. 프로젝트 정리 전엔 묶음이 어긋남 | 화면이 하나 늘어남. 주간 정리는 프로젝트 정리가 선행 |
| 작업 규모(추정) | PR 1개, 중간(읽기 함수 5~6개 + 묶음 표시 + 시험) | PR 1~2개, 중간~큼(묶음 규칙·사업영역 순서·복사 양식) | ①의 PR + ②의 PR. 합계는 ②와 비슷(재료 읽기를 같이 씀) |
| DB·Edge | 없음 | 없음(담당자 칸을 새로 만들면 DB) | 없음 |

추천: ③. 순서는 ① 먼저(1단계) → ② 탭(2단계). 1단계에서 만든 재료 읽기를 2단계가 그대로 쓴다.

하루 카드 정리 원칙(1단계 제안):
- 빈 묶음은 "없어요" 대신 숨긴다. (JOURNAL-다듬기 2026-10-22: 하루 화면의 맨 아래 "기록 없는 묶음: …" 줄은 없앴다.)
- 묶음 순서: 오늘 한 줄 → 프로젝트 → 담당조직 → 회의 → 일정 → 할 일(끝낸·예정) → 자료실·공유 페이지 → 바구니 → 노트.
- 줄을 누르면 원래 화면(프로젝트 상세, 조직 상세, 회의 상세 등)으로 간다. 회의는 "바로 열기 주소가 없다"(`meet-record-send-investigation.md` 2.1)는 점을 착수 때 먼저 확인.

## 3. 주간보고 양식과의 관계

### 3.1 양식(사실, 원장 WEEKLY-자동화 행)

① 요청사항(지도부 참석 요청) ② 사업 요약 표(사업영역 › 세부 과제 › 진행·이후 계획 › 담당) ③ 회의·면담 결과 ④ 산하 조직 현황.

### 3.2 앱에 이미 있는 것(사실)

| 양식 칸 | 앱의 짝 | 근거 |
| --- | --- | --- |
| 사업영역 › 세부 과제 | 큰 프로젝트 › 하위 프로젝트(`app_spaces.parent_id`), 화면 순서 `tree`(`app/project-catalog-model.mjs`) | 같은 모델을 Edge `drive-summary`도 사용 |
| 진행 | 프로젝트 기록(`app_project_progress_updates.summary`) + 🧺 연결 기록 | PRJ-기록입력 행 2026-10-17: "이 목록이 WEEKLY ② 재료" |
| 이후 계획 | 옛 기록의 `next_step`, 주요 일정(`app_project_milestones`) | 새 기록은 입력칸 하나라 `next_step`을 안 채움(`app/quick-save.js`: `next_step:null`) |
| 담당 | **프로젝트에 담당자 칸 없음**(`app_spaces`를 쓰는 화면 코드에서 찾지 못함) | 앞 표 확인. 운영 칸은 못 봄 |
| 회의·면담 결과 | `app_meetings` | — |
| 산하 조직 현황 | `app_suborganization_updates` + 🧺 연결, 내 담당 조직 `app_suborganization_assignees` | — |
| 요청사항 | 바구니 메모에 [요청] 표시(제안 단계, WEEKLY 행) | 표시 규칙은 아직 없음 |

참고(사실): 프로필 화면의 "맡은 프로젝트"(`app_profile_report_projects`, `app/profile-settings.js`)는 "주간보고의 사업요약표에 보고되는 개인 프로젝트"라고 적혀 있지만 **앱 프로젝트(`app_spaces`)와 따로 관리**되는 이름·설명 목록이다. 기록이 붙지 않으므로 허브의 묶음 기준으로는 큰 프로젝트를 쓰는 편이 맞다(추천). 두 목록을 합칠지는 WEEKLY-자동화에서 정한다.

### 3.3 프로젝트 정리가 먼저 필요한가

- **1단계(하루 카드)는 필요 없다.** 프로젝트 이름을 그대로 보여 줘도 하루 카드는 쓸모가 있다.
- **2단계(사업영역별 주간 정리)는 필요하다(추정 아님, 구조상 사실).** 묶는 기준이 큰 프로젝트이므로 큰 프로젝트가 사업영역과 1:1이어야 표가 양식과 맞는다. 원장에도 "귀국 뒤 사용자가 프로젝트를 주간보고 사업영역·담당자에 맞춰 직접 정리"가 WEEKLY 선행으로 적혀 있다.
- 정리 방법 제안(코드 변경 없음): 사업영역마다 큰 프로젝트 1개, 그 아래 세부 과제를 하위 프로젝트로. 예: "A 사업영역" › "B 과제", "C 과제". 사업영역에 안 맞는 개인 프로젝트는 보관하거나 "기타" 큰 프로젝트 아래로.
- 사업영역 표시 순서: 지금은 `sort_order` → 만든 날짜(`app/project-catalog.js`). 양식 순서와 다르면 정리할 때 순서를 맞추면 된다(추정: 순서를 바꾸는 화면이 이미 있는지 착수 때 확인).

## 4. 단계 제안

### 1단계 — 하루 카드에 지금 있는 재료 붙이기 (DB·Edge 없음)

- 더할 묶음: 프로젝트(기록 + 🧺), 담당조직(기록 + 🧺, 내 담당 조직만), 회의(이름·회차·연결 프로젝트), 자료실 새 자료(회의자료 포함, 카테고리 표시), 할 일 예정(마감일 기준, 지금 서버 범위 그대로), 공유 페이지 고친 것.
- 방식: `app/journal-data.js`에 주 범위 읽기 함수를 더하고 `GROUPS`·`dayMaterials`·`weeklyDraft`를 넓힌다. 묶음마다 따로 실패하는 지금 구조 유지. 저장하는 것은 계속 "오늘 한 줄"뿐. 새 저장소·브라우저 저장 없음.
- 읽기 부담: 주 범위·`select` 칸 제한·`limit`을 두고, 회의 결과 글 같은 긴 본문은 읽지 않는다.
- [주간보고 초안 복사]: 날짜별 → (선택) 묶음별 순서. 2단계 전까지는 날짜별 유지.
- PR 규모(추정): 1개, 중간. 단위 시험(주 경계·날짜 기준별 거르기·실패 묶음) + 브라우저 E2E(묶음 표시·빈 묶음 접기·복사 글).
- 정지 지점: 없음.

### 2단계 — [주간 정리] 탭 (DB·Edge 없음, 선행 조건 있음)

- 선행: 명진의 프로젝트 정리(3.3), JOURNAL-끝낸할일범위(Edge 배포, §6 정지 — 그 행에서 진행).
- 화면: 일지 위 [하루 | 주간 정리]. 주간 정리 = ② 사업 요약(큰 프로젝트 › 하위, 그 주 기록·🧺·끝낸 할 일·다음 주요 일정) → ③ 회의 → ④ 담당조직(기록 있는 조직만) → 그 주 한 줄 모음. 각 줄 누르면 원래 화면.
- [주간 정리 복사]: 위 순서 그대로, 양식 번호에 맞춘 글(ChatGPT에 붙여 넣어 정리하는 용도, WEEKLY 흐름).
- PR 규모(추정): 1~2개(화면 + 복사 양식), 중간~큼.
- 정지 지점: 이 단계 자체는 없음. 담당자 칸을 새로 만들기로 하면(결정 4 ②) 그 DB 변경 PR이 따로 생기고 §6·§7 정지.

### 3단계 — 외부 재료와 자동 초안 (WEEKLY-자동화와 합류)

- 회의 🗒 기록: MEET-기록보내기 DB 단계 뒤 프로젝트·조직 묶음에 자동으로 들어옴(같은 연결 표).
- 텔레그램·통화: BASKET-수집연동(새 정기 실행 서버 함수 + Drive 읽기 권한, §6 정지) 뒤 바구니로 들어와 1단계 "바구니" 묶음에 보임.
- 금요일 자동 초안: WEEKLY-자동화에서 방식 결정(ChatGPT 쪽 / 서버 AI). 서버 AI면 OpenAI 키·새 Edge 함수(§6, §8 신규 배포 절차).
- 지난주 보고서 비교·요청사항 [요청] 표시: WEEKLY-자동화 범위.
- 이 단계는 각 원장 행이 진행하고, 허브는 화면에 표시만 더한다.

### 단계별 정지 지점 요약

## 5. 추천안

**③ 하루 카드 + [주간 정리] 탭, 1단계(하루 카드에 지금 재료 붙이기)부터 바로.**

이유:
1. 1단계는 DB·서버를 건드리지 않고 이미 쓰는 표를 같은 권한으로 읽기만 해서 위험이 작다. 주간보고 재료 8묶음이 한 화면에 모인다.
2. 2단계(사업영역별 묶음)는 프로젝트 정리 없이는 양식과 맞지 않으므로, 정리를 기다리는 동안 1단계를 쓰면서 무엇이 빠졌는지 확인할 수 있다.
3. 막힌 재료(끝낸 할 일 범위, 회의 🗒, 텔레그램·통화, 성명)는 이미 원장의 다른 행이 맡고 있어 허브가 같은 일을 중복으로 만들지 않는다(AGENTS.md §4 중복 금지).
4. 저장하는 것은 계속 "오늘 한 줄"뿐이라 업무일지 설계 원칙("별도 저장 없이 날짜로 보는 화면", 2026-10-15 결정)을 지킨다.

## 6. 남은 확인(착수 때)

- 회의 상세를 밖에서 바로 여는 길(지금은 목록 카드 누르기만 — `meet-record-send-investigation.md` 2.1).
- 자료실 `created_at`이 Drive에서 옮겨 온 옛 자료에도 실제 올린 날인지(LIB-자료실정돈과 겹침, 추정: 옮긴 날로 찍혔을 수 있음).

## 7. 결정(2026-10-20 명진)

"명진이 정할 것" 5건 모두 추천안대로.

1. 앱에 쌓이는 기록부터 모은다(프로젝트·담당조직·회의·자료실·할 일 예정·공유 페이지 — DB 없이).
2. 평소 하루 카드 + 금요일 [주간 정리] 탭.

1단계는 JOURNAL-일지카드정리(같은 `app/journal-data.js`·`app/journal.js`, 하루 카드 칸 구성 변경) merge 뒤 착수한다. 그 작업으로 하루 카드 아래 칸이 일정 / 끝낸 할 일 / 조직 소식 / 회의·행사 결과로 바뀌므로, 1단계의 묶음 추가는 바뀐 칸 구성 위에 얹는다.
