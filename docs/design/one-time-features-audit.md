## 4. CC가 직접 할 수 있는 것과 없는 것

명진 말처럼 명진 데이터 한 번 정리는 화면 버튼 대신 CC가 직접 하는 게 맞다. 다만 길이 정해져 있다.

- **DB**: 승인형 DB workflow(`docs/ops-db-workflow.md`, 사전 확인 → 시험 적용 → 백업 → 적용 → 사후 확인)로만. production 데이터 변경은 6절 정지 지점이고 CC 상시 허락으로 진행하되 되돌리기 SQL을 먼저 둔다. `apply_migration`·`db push` 직접 쓰기는 계속 금지.
- **구글 드라이브**: claude.ai 구글 드라이브 커넥터가 **명진의 Web2 드라이브 계정과 같은 계정**일 때만 폴더 옮기기·이름 바꾸기·휴지통이 된다(영구 삭제 없음). 계정이 다르면 못 한다 — 처음 한 번 확인.
- **못 하는 것**: AI가 만들어야 하는 값(사진 설명·브리핑)은 SQL로 못 만든다 → 그런 정리는 명진이 화면에서 한 번 누르거나 서버 자동 일로 만든다. **다른 사용자 데이터**는 CC가 열지도 고치지도 않는다(3절) → 다른 사용자에게도 생기는 한 번 정리는 화면 버튼이 아니라 **서버가 쓸 때 저절로** 하게 만든다(7·8번이 이 경우).

## 5. 앞으로 규칙 제안 (이 PR에서는 제안만)

AGENTS.md 고치기는 명진 확인 뒤 CC가 따로 한다.

**AGENTS.md 4절 '조사와 수정'**, "기존 기능 수정 요청에 새 기능을 옆에 만들어 우회하지 않는다." 다음 줄에 더한다:

> - 명진 데이터 한 번 정리(옮기기·이름 맞추기·가져오기·중복 치우기·옛 형식 바꾸기)는 화면 버튼·메뉴로 만들지 않는다. CC가 승인형 DB workflow(7절)나 명진 계정 커넥터로 직접 하고 결과 숫자를 보고한다(2026-11-24 명진 요청). 다른 사용자에게도 생기는 정리는 버튼 대신 서버·앱이 쓸 때 저절로 하게 만든다. AI가 만들어야 해서 CC가 대신 못 하는 정리만 예외로 화면에 두고, 만들 때 PR 본문에 '지울 때'(끝나는 조건)를 적는다.

**docs/command-center-ops.md 1절 '작업 세션'**, "세션 지시 공통" 줄 아래에 더한다:

> - 지시서를 쓰기 전에 그 일이 '한 번 정리'인지 본다. 그렇다면 작업 세션에 화면 기능을 맡기지 않고 CC가 직접 한다(AGENTS.md 4절). 세션이 정리 버튼을 만들어 오면 merge 전에 되돌려 보낸다. 예외로 둔 정리 버튼은 원장에 '지울 때'와 함께 올리고, 그때가 되면 지우는 작업을 띄운다.
