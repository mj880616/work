# 브리핑 룸 설계 (BRIEF-브리핑룸)

- 시안: `docs/design/mockups/brief-room.html` (#2542)
- 요청: 수십~백 쪽 자료를 넣으면 담당자로서 알아야 할 최소한을 브리핑해 준다(명진 11/13 18:01).
- 작업 세션: S61-45 (CC V61 지시서)

## 1. 정한 것

명진 결정(11/13 18:07):

1. 자료를 넣은 뒤 [브리핑 받기]를 눌러야 만든다(넣기만 해서는 AI를 부르지 않는다).
2. 다섯 칸으로 정리한다: 한 줄 요지 / 내 담당 조직·사업에 닿는 것 / 해야 할 일·기한·숫자 / 우리 쪽 주장과 부딪히는 대목 / 꼭 직접 읽을 대목. 다섯째는 원문을 그대로 옮겨 쪽 번호와 함께 보인다.
3. 자료 맨 위(접힌 브리핑)와 폴더 목록 한 줄(한 줄 요지)에 보이고, 메뉴에 '브리핑 룸'을 둔다.

요청함 방 추천(명진 확정 아님, 지시서에서 채택 권장 → 이 설계는 채택):

- 옮긴 원문 문장은 서버가 원문과 대조해, 원문에 없는 문장은 뺀다(AI가 지어낸 인용 막기).
- 쪽 번호를 누르면 원문 그 쪽으로 간다(Drive 미리 보기의 쪽 주소. 쪽을 모르면 원문 맨 앞).
- 글자가 없는 스캔 PDF는 "글자를 읽을 수 없는 파일이에요" 한 줄.
- 만드는 중에는 다른 화면에 가도 서버가 조각씩 이어서 만든다.

## 2. 지금 구조에서 바뀌는 점

- 자료실 AI 채우기는 파일 글자를 앞 12,000자만 저장·사용한다(`supabase/functions/_shared/document-text.ts` `DOCUMENT_TEXT_CHARS`, `supabase/functions/ai-assist/library-fill.ts` 25~29줄). 100쪽 자료는 20만 자 안팎이라 이 값으로는 끝까지 못 읽는다.
- 그래서 **끝까지 읽는 새 서버 길**을 둔다. 저장 상한 12,000자와 자료 목록 select는 그대로 두고(다른 화면 영향 없음), 브리핑 길만 같은 읽기 함수(`createDocumentText`)를 "자르지 않음" 모드로 한 번 더 부른다.
- 쪽 번호: PDF를 Google 문서로 바꿔 글로 내보낼 때 쪽 나눔이 폼 피드(`\f`)로 남는 경우 그 자리로 쪽을 센다. 쪽 나눔이 없는 형식(HWP·DOCX 등 일부)은 쪽을 모른다 → '꼭 읽을 대목'에 쪽 대신 "원문 앞쪽/중간/뒤쪽" 같은 거짓 쪽 번호를 만들지 않고, 쪽 칸을 비우고 [원문 열기]만 둔다. [추정] Drive 내보내기가 PDF 쪽 나눔을 남기는지는 실제 파일로 확인해야 한다(9절 위험).

## 3. 저장 (DB 짝 파일, PR ①)

새 표 1개 `public.app_document_briefs` — 자료 하나의 브리핑 작업 = 한 행. 모양·권한은 `app_meeting_server_jobs`(20261103170000)와 같다.

| 칸 | 뜻 |
| --- | --- |
| `workspace_id`·`created_by`·`document_id` | 누구의 어느 자료(자료가 지워지면 행도 지움) |
| `source_file_id`·`source_md5` | 읽은 Drive 파일과 판(파일이 바뀌면 다시 받기) |
| `status` | `queued`·`running`·`done`·`failed` |
| `stage` | `read`(글 읽기) → `chunk`(조각 정리) → `merge`(합치기) → `done` |
| `step_no`·`step_total` | 화면의 "만드는 중 7/12" |
| `page_count` | 쪽 수(모르면 비움) |
| `source_text` | 끝까지 읽은 글(쪽 나눔 표시 포함). 조각 정리·인용 대조에만 쓰고 끝나면 비운다 |
| `parts` | 조각마다 AI가 뽑은 메모(배열) |
| `brief` | 다섯 칸 결과(객체) |
| `error_code`·`lease_until`·`attempts`·시각들 | 진행 관리 |

권한(넓히지 않음):

- authenticated: 작업공간 owner(`private.app_is_workspace_owner`)만 **읽기**. 넣기·고치기·지우기 없음 → 화면이 브리핑 결과를 직접 쓸 수 없고, 인용 대조를 건너뛴 글이 저장되지 않는다.
- service_role(Edge `ai-assist` 브리핑 길만): 읽기 + 정한 칸 넣기·고치기. 지우기 없음.
- anon·PUBLIC 없음. 같은 자료에 진행 중 작업은 하나(부분 유일 색인).
- 함수·트리거·예약 실행·기존 표 변경 없음.

## 4. 서버 길 (Edge `ai-assist`, PR ②)

kind 3개. 모두 로그인 토큰으로 사용자·작업공간을 확인하고, 자료는 **로그인 토큰으로 읽어** owner RLS가 남의 작업공간 자료를 막는다(화면이 보낸 작업공간 id를 믿지 않음).

- `brief_start {document_id}`: 자료 확인 → **사람별 월 한도 판정**(`_shared/ai-user-cap.mjs`, 한도 이상이면 429 `ai_monthly_cap`, 숫자를 못 읽으면 멈춤) → 행 1개(queued) → 바로 이어서 돌리기.
- `brief_step {brief_id}`: 화면이 열려 있을 때 멈춘 작업을 이어 달라고 부른다(lease가 지난 작업만 잡음). 같은 한도 판정을 다시 거친다.
- `brief_read {brief_id}`: 필요 없음 — 화면은 표를 owner RLS로 직접 읽는다.

돌리기(한 번 부를 때 `EdgeRuntime.waitUntil`로 응답 뒤에도 이어 감, meeting-transcribe와 같은 방식):

1. `read`: Drive 파일을 끝까지 읽는다(`createDocumentText`의 자르지 않는 모드, 상한 60만 자). 글자가 300자 미만이면 `failed`/`no_text`("글자를 읽을 수 없는 파일이에요"). AI 비용 없음.
2. `chunk`: 글을 쪽 경계 우선으로 약 12,000자 조각으로 나눈다(`splitChunks`). 조각마다 AI 한 번 → 메모(다섯 칸 후보 + 원문 인용 후보와 쪽). 한 번 부를 때 조각 2~3개씩, 조각마다 한도 판정·사용 기록(`app_ai_daily_usage` 기존 표).
3. `merge`: 메모를 모아 AI 한 번 → 다섯 칸. 내 담당조직·사업영역 이름 목록(짧은 참조만)을 함께 보낸다.
4. 서버 검사(`verifyBrief`): 칸마다 줄 수·글자 수·제어 문자·꺾쇠 검사, '꼭 읽을 대목'은 **원문 대조**(공백·줄바꿈만 무시하고 원문에 그대로 있는 문장만 남김, 쪽 번호는 서버가 찾은 위치로 다시 매김 — AI가 준 쪽 번호를 믿지 않는다). 남은 대목이 없으면 그 칸은 빈 칸.
5. `done`: `brief` 저장, `source_text` 비우기, 자료실 자료 맨 위·목록 한 줄은 이 행의 `brief.lead`를 읽는다.

비용: [추정] 100쪽(약 20만 자, 조각 15~17개) 한 건에 입력 약 10만 토큰 → 기본 모델 단가로 50~100원. 한도(기본 월 3,000원) 안에서 30~60건.

## 5. 폴더 (PR ④)

- 자료실 '브리핑 요청함' 폴더는 기능이 스스로 만든다('회의 녹음' 폴더 #2485와 같은 방식: 최상위에 같은 이름 폴더가 없으면 owner RLS로 만든다).
- 브리핑 룸 [자료 넣기]·끌어 놓기 = 자료실 올리기와 같은 길(`library-upload`)로 올리고 이 폴더에 넣는다. 자료 원본은 자료실 한 곳, 브리핑 룸은 그 폴더를 보는 화면이다(새 저장소 없음).
- 자료실의 다른 자료도 자료 ⋯ 메뉴 [브리핑 받기]로 받을 수 있다(자료를 옮기지 않음).

## 6. 화면 (PR ③)

- 메뉴 판에 '브리핑 룸'.
- 목록: [자료 넣기]·놓기 칸, 자료 줄(형식 꼬리표·이름·상태). 상태는 [브리핑 받기] / "만드는 중 7/12" / 한 줄 요지 / "글자를 읽을 수 없는 파일이에요".
- 보기: 다섯 칸. ①~④는 짧은 줄, ⑤는 원문 그대로 + "31쪽 · 소제목" + 왜(한 줄). 쪽 번호는 원문 그 쪽으로 가는 링크.
- 폴드 펼침·PC(760 이상)는 왼쪽 목록·오른쪽 보기 두 칸.
- 다 되면 브리핑 룸 화면에 있을 때만 아래에 잠깐 알림(폰 알림 없음).
- 진행은 표를 몇 초 간격으로 다시 읽는다(화면이 떠 있을 때만). 오래 멈춘 작업은 화면이 `brief_step`으로 이어 달라고 한다.

## 8. 보안 확인

- 인증·RLS·권한 넓히기 없음. 새 표는 owner 읽기만, 쓰기는 서버 키의 정한 칸만.
- 자료 읽기·Drive 읽기는 로그인 사용자 것만. 남의 작업공간 자료 id를 보내도 owner RLS에서 0행 → 404.
- AI 답은 믿지 않는 입력: 모양·길이 검사, 인용은 원문 대조, 쪽 번호는 서버가 다시 매김.
- 원문 글(`source_text`)은 작업이 끝나면 비운다. 로그·오류에는 글 내용을 싣지 않는다(고정 오류 코드만).

## 9. 남은 위험

- [추정] PDF → Google 문서 변환이 쪽 나눔(`\f`)을 남기는지 실제 파일로 확인 필요. 남지 않으면 쪽 번호 대신 [원문 열기]만 보인다(거짓 쪽 번호는 만들지 않음).
- Drive 변환 상한(50MB)·내보내기 상한(지금 1MB)을 브리핑 길에서는 4MB로 둔다. 그보다 큰 자료는 "너무 큰 파일이에요" 한 줄.
- Edge 한 번 실행 시간 안에 조각을 다 못 끝내면 다음 부름(화면 또는 다음 조각 예약)에서 잇는다. 화면을 닫고 오래 두면 멈춘 채 남을 수 있다 → 브리핑 룸을 다시 열면 이어진다.
