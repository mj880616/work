# PROFILE-화면정리 설계 (시안만, 앱 코드·DB 변경 없음)

시안: `docs/design/mockups/profile-screen-tidy.html` (가 폰 지금 / 나 폰 바뀜 / 다 PC 바뀜). 2026-10-23 사용자 결정 6가지(00:09)를 화면에 옮긴 설계다. 구현은 별도 PR.

## 1. 현재 화면 구성 (사실, `app/profile-settings.js`·`profile-settings.css`)

- 열기: [계정 ▾] → [내 프로필] (`KPTURouter.go('profile')`, `?view=profile`). 화면 `#profileView`는 `view-loader.js`가 처음 열 때 불러온다.
- 위 줄: 제목 "내 프로필" + 안내문 + 채운 큰 버튼 [프로필 저장](`#psSaveProfile`, 이름·직책만 `app_profiles` PATCH).
- 기본 정보: 이름·직책 두 칸 (`two-col`).
- 담당 사업장: 안내문 + [추가][삭제][저장] + 조직 알약(가나다순 `localeCompare('ko')`) + 검색 고르기 + 아래 안내문. 알약을 누르면 조직 정보·현황이 열린다. [삭제] 모드에서만 ×가 보인다. 저장은 바뀐 것만: 추가는 `app_suborganization_assignees` POST → `app_profile_workplaces` POST/PATCH(두 번째가 실패하면 첫 번째를 되돌림), 삭제는 거울 행 DELETE → 담당 행 DELETE(실패하면 거울 행 복원). 끝나면 `kptu:profile-updated`·`kptu:suborganization-updated` 알림.
- 연결 전 옛 담당 사업장(`organization_id` 없는 거울 행)은 "기존 담당사업장 정보" 칩으로 읽기만 한다.
- 맡은 프로젝트: 안내문 + 줄마다 이름·설명·[저장][삭제] + 입력 두 칸 + [+ 프로젝트] (`app_profile_report_projects`).
- 계정: [내 공간](허용된 사람만) · [원장](`data-goto="ledger"`) · [로그아웃].
- 칸 제목은 `<h3>`인데 칸마다 안내문 유무·간격이 달라 크기가 들쭉날쭉하다. 저장 버튼은 세 군데(+프로젝트 줄마다 둘).
- 조직 묶음 순서의 정의: `app/organization-order.js`(`KPTUOrganizationOrder.groups/groupName/sort`: 철도 · 지하철 · 민자철도 · 민간도시철도 · 그 외). `기록할 곳 선택` 창은 `update-places.js`의 `placeSheetHtml`·`orgGroupRows`로 같은 순서를 그린다(묶음 이름은 작은 소제목, 조직은 한 줄에 하나·작은 체크 칸, `choice-sheet.css`의 `.home-choice-check`).

## 3. ④ 조사 결과와 이전안 (사실)

- `app_profile_report_projects`를 읽거나 쓰는 앱 코드는 `app/profile-settings.js` 하나뿐이다(`grep` 전체: app·scripts·supabase/functions에서 이 파일만). 나머지는 DB 정책(`20260925084844_task12a_sole_owner_db.sql`의 owner RLS)·롤백·스냅샷·테스트 fixture·E2E뿐이다.
- 주간보고(`journal-weekly.js`, `weekly-hwpx/*`)의 사업요약표는 이 표를 쓰지 않는다. 사업영역 → 세부 과제 → 진행 상황은 `project-catalog.js`의 앱 프로젝트 트리(`app_spaces`)에서 만든다(`app/ARCHITECTURE.md` 업무일지 절). 화면 안내문 "주간보고의 사업요약표에 보고되는"은 현재 사실이 아니다.
- 이 표에는 기록이 붙지 않고 이름·설명·정렬만 있다. `docs/design/weekly-report-hub.md` 3절도 같은 사실을 적고 큰 프로젝트를 쓰는 편이 맞다고 했다.
- 2026-09-25 조사(`docs/web2-bundle-a-investigation.md`)에서 0행이었다. 지금 행 수는 이 세션에서 production을 조회하지 못해 확인하지 않았다(구현 PR의 로컬 세션이 읽기 전용으로 확인).

이전안(추천 A): 합칠 곳이 없다. **화면·경로만 제거하고 표와 데이터는 그대로 둔다**(기능 삭제 원칙). 프로젝트 메뉴에는 옮기지 않는다(주간보고가 앱 프로젝트를 이미 쓰고, 두 목록을 합치는 일은 WEEKLY-자동화 소관). 구현 PR에서 production 읽기 전용으로 행 수를 확인해 0이 아니면 내용만 사용자에게 보여 주고, 그때 프로젝트 화면으로 옮길지 따로 묻는다. 표 삭제는 DB 정리 때 별도 작업.

## 4. 저장 버튼 하나: 저장 범위와 실패 처리

저장 범위(바뀐 것만 보냄, 새 표·함수 없음):
1. 이름·직책: 바뀌었으면 `app_profiles` PATCH 한 번(기존 `saveProfile`). 이름이 비면 저장하지 않고 이름 칸에 안내.
2. 담당 사업장: 체크가 바뀐 조직만 기존 `addOrg`/`removeOrg` 호출(기존 되돌림 로직 유지).
3. 프로젝트는 화면에서 빠지므로 범위 밖.

순서와 실패 처리:
- 순서: 프로필 → 사업장 추가 → 사업장 삭제. 하나의 큰 거래가 아니라 단계별이다(지금과 같은 방식이고 서버는 바꾸지 않는다).
- 단계가 실패하면 거기서 멈추고, 이미 성공한 것은 그대로 두며, 실패한 것부터 아래는 화면에 체크·입력을 **남겨 둔다**(지금은 실패하면 선택을 지우고 다시 읽음 — 사용자가 다시 골라야 해서 바꾼다). 알림 한 줄에 어디까지 저장되고 어디가 실패했는지(예: "프로필은 저장했고 담당 사업장 1곳은 저장하지 못했어요"), 저장 버튼은 다시 켜져 같은 변경을 다시 시도할 수 있다.
- 저장 중에는 버튼 잠금 + 입력 잠금, 끝나면 서버 값을 다시 읽어 화면을 맞춘다(지금 `load()`).
- 다른 기기가 그사이 바꾼 경우: 추가는 이미 있으면 PATCH, 삭제는 이미 없으면 통과(기존 코드가 현재 행을 다시 읽고 처리)하므로 동작 변경 없음.
- 화면을 떠날 때 저장 안 된 변경이 있으면 확인 한 번(공용 확인창)을 둔다. 브라우저 저장소 사용 없음.

## 5. PR 나눔

화면 PR 하나가 적당하다: `profile-settings.js`·`.css` 한 곳에서 ②~⑥이 서로 얽혀(저장 버튼 하나는 체크 목록과 프로필 칸을 함께 알아야 함) 나누면 중간 상태 화면이 어색하다. DB·Edge 변경 없음, 테스트(`tests/app-e2e/profile-workplaces-fixture.html` 등)는 같이 고친다. ①은 LEDGER-자동기록 설계의 사이드바 항목이 먼저 있어야 하므로 구현 순서는: (a) 원장 사이드바 메뉴(LEDGER 쪽 PR) → (b) 이 화면 PR(원장 버튼 제거 포함). 사이드바가 늦어지면 (b)에서 원장 버튼만 남기고 나머지를 먼저 낼 수 있다.

## 6. 명진 질문 (추천안 먼저)

1. 조직 이름 누르면 정보 열기: 체크 목록에서 이름은 체크 전용, 열기는 줄 끝 `›`로 — 추천. (대안: 이름 누르면 열고 체크 칸만 따로.)
2. 맡은 프로젝트: 화면만 제거, 데이터는 보존(추천 A). 구현 때 행이 있으면 알려 드리고 그때 다시 묻기.
3. 원장을 사이드바에 두는 순서: 사이드바 PR을 먼저 내고 이 화면 PR을 뒤에(추천), 또는 한 번에.
4. 저장하지 않은 채 다른 화면으로 가려 할 때 확인창 한 번(추천), 또는 묻지 않고 버림.
5. "그 외"(묶음에 없는 조직)도 목록 맨 아래에 가나다순으로 보임(추천), 또는 숨김.
