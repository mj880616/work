- **투쟁 중으로 봄**: 단계마다 켜고 끌 수 있는 표시. 켠 단계에 있는 조직이 주간보고 투쟁 사업장 표 자동 채움 대상이다. 기본은 쟁의발생결의~쟁의행위 켬.

## 3. 담당조직 화면

- 위치: 조직 상세 맨 위 이름 줄 바로 아래 한 줄(`쟁의 단계 [쟁의발생결의 ▾] [10.20]`). 목록 줄에는 투쟁 중인 조직에만 단계 이름을 작은 글씨로 덧붙인다(평시 조직은 아무것도 안 붙임 — 줄이 길어지지 않게).
- 입력: 단계는 한 줄 선택 칸(`select`, 폰에서 기본 선택창) 하나. 고르면 오른쪽에 날짜 칸(달력 입력, 기본값 오늘)이 나타난다. [저장] 버튼은 그 줄 끝 작은 기본 버튼 하나. 담당조직 추가·수정 창에는 넣지 않는다(상세에서만 — 창이 길어지지 않게).
- '없음'으로 되돌릴 때는 날짜 칸을 숨긴다. 같은 단계를 다시 저장하면 날짜만 고친 것으로 본다.
- 한 줄 요약 아래에 접힘 '단계 이력'(평소 닫힘)에 날짜·단계 목록 3~5줄.
- 단계 고르는 칸의 선택지는 명진이 관리하는 단계 목록(2절)이다. 목록 줄 표시는 '투쟁 중으로 봄' 켠 단계와 이번 주 '끝남' 단계(타결)에만 붙는다.
- 단계 관리: 담당조직 화면 오른쪽 위 ⋯ 메뉴의 '쟁의 단계 관리'(추천, 질문 3) 한 곳. 줄마다 이름·투쟁 중 켬/끔·⋯(이름 바꾸기·지우기)·끌어 순서 바꾸기, 맨 아래 작은 [+ 단계]. 끝남 표시를 단계별로 켜게 하면(질문 1) 줄의 ⋯ 안에 둔다. 시안 (다).
- 크고 굵은 버튼·카드·안내문 없음. 색은 기존 `--kptu-*`·`--ds-kind-*` 토큰 중 톤다운 색만(투쟁 중 = 기존 '챙길 것' 주황 계열 연한 바탕).

## 4. 변경 이력

남긴다(추천). 이유: 주간보고에서 "언제부터 이 단계인지"를 매주 쓰고, 단계가 잘못 눌렸을 때 되돌릴 근거가 필요하다. 별도 이력 표 하나를 **유일한 원본**으로 하고, 현재 단계 = 그 조직의 가장 나중 줄(단계 날짜 → 입력 시각 순)로 읽는다. 조직 표에 '현재 단계' 칸을 따로 두면 저장이 두 곳이라 어긋날 수 있어 두지 않는다. 잘못 넣은 줄은 이력에서 지우면 이전 단계로 돌아간다(데이터 삭제는 그 줄 하나뿐).

이력 줄은 **단계 id와 그때의 이름 사본**을 같이 저장한다. 나중에 단계 이름을 바꾸거나 단계를 지워도 지난 이력 글자는 그대로 남는다. 현재 단계의 투쟁 중·끝남 판정은 단계 id로 목록 표를 찾아 읽고, 단계가 지워져 id가 비어 있으면(이력에만 쓰였던 단계) 투쟁 중 아님·끝남 아님으로 읽는다.

## 5. 주간보고 투쟁 사업장 표 자동 채움 규칙

1. 대상: `my-organizations.js`의 내 담당 조직 중 현재 단계가 **'투쟁 중으로 봄' 켬**인 조직만(기본: 쟁의발생결의·조정신청·조정종료·찬반투표·쟁의행위).
2. 표 줄: 조직명 칸은 조직 이름(보고서 표기 규칙은 기존 그대로), 현황 칸 첫 줄에 `- {단계 이름}({M.D})`. 그 아래는 직전 확정본의 그 조직 현황 줄을 그대로 이어 사람이 고친다(기존 동작 유지, 앱이 현황 문장을 지어내지 않음).
3. 투쟁 중이 아닌데 직전 확정본에 줄이 있던 조직: 초안에서 줄을 지우자고 제안(기존 `remove` 고침 항목)하고, 화면 '고칠 목록'에서 명진이 확인한다. 자동으로 말없이 지우지 않는다.
4. 현재 단계가 '끝남' 켬이고 그 단계 날짜가 이번 보고 주간 안이면 그 주 한 번만 `- 타결(M.D)`(단계 이름)로 보여 주고 다음 주부터 뺀다. 끝남 표시가 켜진 단계가 목록에 하나도 없으면 이 규칙은 없는 것으로 읽는다.
5. 단계가 안 정해진 조직(이력 없음) = 없음 = 표에 안 나옴. 조회 실패 시 기존처럼 직전 확정본 줄을 그대로 쓰고 화면에만 "단계를 불러오지 못했어요" 한 줄.
6. 외부 행동 없음: 읽기만 하고, 보고서는 지금처럼 명진이 확인 후 받는다.

## 6. DB 변경안 (설계만 — 이 PR에서는 만들지 않음)

새 표 두 개, 기존 표는 건드리지 않는다.

```
app_dispute_stages                       -- 단계 목록(소유자별)
  id            uuid pk default gen_random_uuid()
  owner_id      uuid not null            -- 소유자 칸: 기존 소유자 정책(task12a_owner_all)이 쓰는 칸·방식과 같게 구현 때 확인해 맞춤
  name          text not null check (char_length(btrim(name)) between 1 and 20)
  sort_order    integer not null         -- 목록 순서(끌어 바꾸면 다시 매김)
  is_struggle   boolean not null default false   -- 투쟁 중으로 봄
  is_ending     boolean not null default false   -- 끝남
  created_at    timestamptz not null default now()
  check (not (is_struggle and is_ending))
  unique (owner_id, name)

app_suborganization_dispute_stages       -- 이력(유일한 원본)
  id              uuid pk default gen_random_uuid()
  organization_id uuid not null references app_suborganizations(id) on delete cascade
  stage_id        uuid references app_dispute_stages(id) on delete set null   -- 단계가 지워지면 비움
  stage_name      text not null          -- 저장 당시 이름 사본(이름을 바꾸거나 지워도 남음)
  stage_date      date not null          -- 그 단계가 된 날(달력 입력, 기본 오늘)
  created_by      uuid references auth.users(id) default auth.uid()
  created_at      timestamptz not null default now()
  index (organization_id, stage_date desc, created_at desc)
```

- RLS: 두 표 모두 켠다. 단계 목록은 기존 소유자 정책과 같은 조건(소유자만, `for all to authenticated`, using/with check 동일)으로, 이력은 `app_suborganization_updates`처럼 `private.app_is_owner_organization(organization_id)`로. 이력 저장 때 `stage_id`가 같은 소유자의 단계인지 검사를 더한다(남의 단계 id를 끼워 넣는 것 방지 — 서버 쪽에서 막고 화면 제한에만 기대지 않음). anon·공개 읽기 없음, 권한 확대 없음. 공유 페이지·Edge는 이 표들을 읽지 않는다(조직 이름이 공개 저장소·공개 화면으로 나가지 않게).
- 삭제 막기(지금 어느 조직이 그 단계에 있으면 지우기 불가)는 화면 안내와 별도로 서버(DB) 쪽에서도 거절한다 — 화면 제한만으로는 보호가 안 된다는 AGENTS.md §3 2번. 구현 방식(삭제 전 확인 함수 또는 트리거)은 DB PR에서 정하고 check SQL로 검증한다.
- 이름 사본 칸은 단계 이름 길이 제한과 같게 자른다. 메모(자유 글) 칸은 두지 않는다(저장소 공개·민감 내용 방지).
- 기본 목록 채움은 migration이 아니라 소유자가 처음 열 때 앱이 소유자 권한으로 넣는다(production 데이터를 migration이 건드리지 않음). 단계 목록이 비어 있으면 화면은 기본 목록 8개를 한 번에 넣을지 묻지 않고 채운다.
- 적용: `docs/design/sql` 방식의 `.check.sql`·`.rollback.sql`(표 두 개 삭제)을 함께 둔 migration 파일 하나. 운영 적용은 AGENTS.md §7·승인형 DB workflow대로 DB PR merge 뒤 사용자 승인 단계에서 정지. 되돌리기 = rollback SQL로 두 표 삭제(이 표들의 데이터만 사라지고 다른 표에는 영향 없음).
- production 데이터 변경 없음(빈 표 생성). 기존 조직은 모두 '이력 없음 = 없음'.

## 7. PR 순서

1. DB PR: migration + check + rollback + RLS(위 두 표). 정지 지점: 운영 적용 직전(사용자 승인형 workflow). 코드 변경 없음.
2. 화면 PR(DB 적용 후): 단계 목록 읽기·기본 목록 채움, `workplace-detail.js`에 쟁의 단계 줄·접힘 이력, 목록 줄 표시(투쟁 중·끝남만), '쟁의 단계 관리' 화면(추가·이름 바꾸기·지우기·끌어 순서·투쟁 중 켬/끔), 읽기·저장 REST, 테스트. `app/ARCHITECTURE.md`에 유일 정의 모듈(예: `org-dispute-stage.js`: 단계 목록·투쟁 중 판정·현재 단계 읽기) 한 줄. 판정은 이 모듈 한 곳에만 두고 주간보고가 같은 것을 쓴다. 화면이 커지면 관리 화면을 별도 PR로 나눈다.
3. 주간보고 PR(화면 후): `delta.mjs`/`draft.mjs`의 투쟁 사업장 초안에 5절 규칙 반영, 화면 '3. 2) 투쟁 사업장 현황' 설명 갱신, `docs/design/weekly-hwpx-draft.md` 해당 줄 갱신, 테스트.

## 9. 명진에게 남은 질문 (추천안 포함)

1. '끝남' 표시도 단계마다 켜고 끌 수 있게 할까요? **추천: 예**(기본은 타결만 켬, 다른 끝 단계를 직접 만들 때 필요). 대안: 끝남은 '타결' 하나에만 고정.
2. 지금 어느 조직이 있는 단계는 지우기를 막고 이유 한 줄을 보여 주는 방식이 맞나요? **추천: 예**(이력에만 쓰인 단계는 지울 수 있고 이력 글자는 이름 사본으로 남음). 대안: 조직을 '없음'으로 자동 이동하며 삭제.
3. 단계 관리 화면 위치를 담당조직 화면 ⋯ 메뉴의 '쟁의 단계 관리'로 할까요? **추천: 예.** 시안 (다)를 보고 정해 주세요.
4. '없음' 단계도 이름 바꾸기·지우기를 허용할까요? **추천: 이름 바꾸기만 허용, 지우기는 막음**(이력 없는 조직의 기준이라서).
5. 변경 이력을 남길까요? **추천: 예**(4절 방식, 이력 표 1개).
6. 입력은 조직 상세에서만 할까요(추가·수정 창에는 안 넣음)? **추천: 상세에서만.**
7. 표 현황 칸 첫 줄 모양 `- 쟁의발생결의(10.20)`로 괜찮은가요? 시안 (나)를 보고 정해 주세요.
