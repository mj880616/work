# ORG-쟁의단계 설계 — 담당조직 '쟁의 단계' 칸과 주간보고 투쟁 사업장 표 자동 채움

상태: 설계·시안만(앱 코드·DB 변경 없음). 시안: `docs/design/mockups/org-dispute-stage.html`(혼자 열리는 정적 HTML, 가짜 조직 이름).
기준: 2026-10-23 16:28 명진 결정 — 담당조직마다 '쟁의 단계' 칸을 둔다. 주간보고 투쟁 사업장 표는 쟁의발생결의를 한 곳 중 지금 투쟁 중인 곳만 자동으로 채운다. 시안을 먼저 보고 정한다.

## 1. 지금 상태 (확인한 것)

- 담당조직 원본은 `app_suborganizations`(이름·다른 이름·조직유형·설명·`active`). 담당조직 추가·수정 창은 `app/suborganizations.js`, 상세는 `app/workplace-detail.js`. 단계·투쟁 여부를 담는 칸은 없다.
- 권한: `app_suborganizations`는 작업공간 소유자만(`task12a_owner_all`), 조직 딸린 표(`app_suborganization_updates` 등)는 `private.app_is_owner_organization(organization_id)`로 소유자만.
- 한글 주간보고 `3. 투쟁 사업 › 2) 투쟁 사업장 현황`(2열: 조직명|현황)은 지금 **직전 주 확정본의 내 담당 조직 줄을 그대로 가져와** 사람이 고친다(`app/weekly-hwpx/delta.mjs`의 `keepOrgRows(team.sites, myOrgs)`, 설계는 `docs/design/weekly-hwpx-draft.md` 표). 어느 조직이 투쟁 중인지 앱이 아는 곳이 없다.
- "내 담당 조직"의 유일한 정의는 `app/my-organizations.js`. 표 채움도 이 정의를 쓴다.

## 2. 단계 목록 (제안)

노동쟁의 절차 순서대로, 화면에는 일상어로 쓴다. 코드값은 영어 소문자(DB 저장용).

| 순서 | 화면 이름 | 코드 | 투쟁 중? | 뜻 |
| --- | --- | --- | --- | --- |
| 0 | 없음 | `none` | 아니오 | 쟁의 단계가 아님(평시·기본값) |
| 1 | 교섭 중 | `bargaining` | 아니오 | 임단협 교섭 진행 |
| 2 | 쟁의발생결의 | `dispute_resolved` | **예** | 교섭 결렬 선언·쟁의발생 결의를 한 상태 |
| 3 | 조정신청 | `mediation_filed` | **예** | 노동위원회에 조정 신청 |
| 4 | 조정종료 | `mediation_ended` | **예** | 조정이 끝남(중지·불성립 포함) — 쟁의행위 가능 상태 |

| 6 | 쟁의행위 | `action` | **예** | 파업·태업·집회 등 쟁의행위 중 |

- '타결'과 '종료'를 나눈 이유: 보고서에서 읽는 뜻이 다르다. 합치고 싶으면 질문 3.
- 단계는 순서대로만 가지 않는다(조정종료 후 바로 쟁의행위 없이 타결 등). 입력 때 아무 단계나 고를 수 있게 하고 순서를 강제하지 않는다.
- '쟁의발생결의를 한 곳'이라는 결정은 단계 2 이후를 뜻하는 것으로 읽었다(질문 1에서 확인).

## 3. 담당조직 화면

- 위치: 조직 상세 맨 위 이름 줄 바로 아래 한 줄(`쟁의 단계 [쟁의발생결의 ▾] [10.20]`). 목록 줄에는 투쟁 중인 조직에만 단계 이름을 작은 글씨로 덧붙인다(평시 조직은 아무것도 안 붙임 — 줄이 길어지지 않게).
- 입력: 단계는 한 줄 선택 칸(`select`, 폰에서 기본 선택창) 하나. 고르면 오른쪽에 날짜 칸(달력 입력, 기본값 오늘)이 나타난다. [저장] 버튼은 그 줄 끝 작은 기본 버튼 하나. 담당조직 추가·수정 창에는 넣지 않는다(상세에서만 — 창이 길어지지 않게).
- '없음'으로 되돌릴 때는 날짜 칸을 숨긴다. 같은 단계를 다시 저장하면 날짜만 고친 것으로 본다.
- 한 줄 요약 아래에 접힘 '단계 이력'(평소 닫힘)에 날짜·단계 목록 3~5줄.
- 크고 굵은 버튼·카드·안내문 없음. 색은 기존 `--kptu-*`·`--ds-kind-*` 토큰 중 톤다운 색만(투쟁 중 = 기존 '챙길 것' 주황 계열 연한 바탕).

## 4. 변경 이력

남긴다(추천). 이유: 주간보고에서 "언제부터 이 단계인지"를 매주 쓰고, 단계가 잘못 눌렸을 때 되돌릴 근거가 필요하다. 별도 이력 표 하나를 **유일한 원본**으로 하고, 현재 단계 = 그 조직의 가장 나중 줄(단계 날짜 → 입력 시각 순)로 읽는다. 조직 표에 '현재 단계' 칸을 따로 두면 저장이 두 곳이라 어긋날 수 있어 두지 않는다. 잘못 넣은 줄은 이력에서 지우면 이전 단계로 돌아간다(데이터 삭제는 그 줄 하나뿐).

## 5. 주간보고 투쟁 사업장 표 자동 채움 규칙

1. 대상: `my-organizations.js`의 내 담당 조직 중 현재 단계가 쟁의발생결의·조정신청·조정종료·찬반투표·쟁의행위(= 투쟁 중)인 조직만.
2. 표 줄: 조직명 칸은 조직 이름(보고서 표기 규칙은 기존 그대로), 현황 칸 첫 줄에 `- {단계 이름}({M.D})`. 그 아래는 직전 확정본의 그 조직 현황 줄을 그대로 이어 사람이 고친다(기존 동작 유지, 앱이 현황 문장을 지어내지 않음).
3. 투쟁 중이 아닌데 직전 확정본에 줄이 있던 조직: 초안에서 줄을 지우자고 제안(기존 `remove` 고침 항목)하고, 화면 '고칠 목록'에서 명진이 확인한다. 자동으로 말없이 지우지 않는다.
4. 타결·종료로 바뀐 주에는 그 주 한 번만 `- 타결(M.D)`로 보여 주고 다음 주부터 뺀다(추천, 질문 4).
5. 단계가 안 정해진 조직(이력 없음) = 없음 = 표에 안 나옴. 조회 실패 시 기존처럼 직전 확정본 줄을 그대로 쓰고 화면에만 "단계를 불러오지 못했어요" 한 줄.
6. 외부 행동 없음: 읽기만 하고, 보고서는 지금처럼 명진이 확인 후 받는다.

## 6. DB 변경안 (설계만 — 이 PR에서는 만들지 않음)

새 표 하나, 기존 표는 건드리지 않는다.

```
app_suborganization_dispute_stages
  id            uuid pk default gen_random_uuid()
  organization_id uuid not null references app_suborganizations(id) on delete cascade
  stage         text not null check (stage in ('none','bargaining','dispute_resolved','mediation_filed','mediation_ended','strike_vote','action','settled','closed'))
  stage_date    date not null            -- 그 단계가 된 날(달력 입력, 기본 오늘)
  created_by    uuid references auth.users(id) default auth.uid()
  created_at    timestamptz not null default now()
  index (organization_id, stage_date desc, created_at desc)
```

- RLS: 켠다. 정책 하나 `task12a_owner_all` 방식 그대로 — `for all to authenticated using (private.app_is_owner_organization(organization_id)) with check (private.app_is_owner_organization(organization_id))` (`app_suborganization_updates`와 같음). anon·공개 읽기 없음, 권한 확대 없음. 공유 페이지·Edge는 이 표를 읽지 않는다(조직 이름이 공개 저장소·공개 화면으로 나가지 않게).
- 메모(자유 글) 칸은 두지 않는다(저장소 공개·민감 내용 방지, 한 줄 선택으로 충분).
- 적용: `docs/design/sql` 방식의 `.check.sql`·`.rollback.sql`(표 삭제)을 함께 둔 migration 파일 하나. 운영 적용은 AGENTS.md §7·승인형 DB workflow대로 DB PR merge 뒤 사용자 승인 단계에서 정지. 되돌리기 = rollback SQL로 표 삭제(이 표 데이터만 사라지고 다른 표에는 영향 없음).
- production 데이터 변경 없음(빈 표 생성). 기존 조직은 모두 '이력 없음 = 없음'.

## 7. PR 순서

1. DB PR: migration + check + rollback + RLS(위 표). 정지 지점: 운영 적용 직전(사용자 승인형 workflow). 코드 변경 없음.
2. 화면 PR(DB 적용 후): `workplace-detail.js`에 쟁의 단계 줄·접힘 이력, 목록 줄 표시(투쟁 중만), 읽기·저장 REST, 테스트. `app/ARCHITECTURE.md`에 유일 정의 모듈(예: `org-dispute-stage.js`: 단계 목록·투쟁 중 판정·현재 단계 읽기) 한 줄. 단계 목록·판정은 이 모듈 한 곳에만 두고 주간보고가 같은 것을 쓴다.
3. 주간보고 PR(화면 후): `delta.mjs`/`draft.mjs`의 투쟁 사업장 초안에 5절 규칙 반영, 화면 '3. 2) 투쟁 사업장 현황' 설명 갱신, `docs/design/weekly-hwpx-draft.md` 해당 줄 갱신, 테스트.
