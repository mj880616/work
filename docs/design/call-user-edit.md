# 통화 손고치기 설계 (CALL-손고치기)

통화 목록·상세에서 제목, 조직, 상대 이름·직함, 핵심내용(AI 요약)을 사람이 직접 고치는 기능이다. 실제 이름, 번호, 통화 내용은 이 문서에 없다.

- 작성: 2026-10-26, Claude Code 웹. 근거: 명진 10/26 00:11·01:46·01:47 요청. 단계별 PR: ① DB(`20261026120000_call_user_edit`, 적용 대기) ② Edge `ai-assist`(원장 재료, 배포 안 함) ③ 화면.
- 앞 설계: [call-personal.md](call-personal.md)(업무·개인 두 통화함, 옮기기), [call-telegram-feed.md](call-telegram-feed.md), [call-context.md](call-context.md)(맥락 문서).

## 1. 명진용 요약

- **고치는 곳 네 군데**: 제목(줄 안에서 바로, F2), 조직·이름(상세의 상대 글자를 누르거나 메뉴), 핵심내용(상세 연필 또는 메뉴 [요약 고치기]), 확인할 통화의 [업무 · 개인] 버튼은 작은 글자로.
- **고친 값은 서버에 따로 저장**한다. AI가 채운 값은 한 글자도 안 바뀌고, 화면은 고친 값이 있으면 그것을 보여 준다. 그래서 AI가 나중에 같은 칸을 다시 써도(업무로 옮길 때 다시 채우기, 다시 분석) 고친 값이 덮이지 않는다. 고칠 때마다 이전 값이 이력에 남는다.
- **되돌리기 두 가지**: 방금 고친 것은 알림 줄의 [되돌리기], 오래된 것은 조직·이름 박스와 핵심내용 박스의 [AI 값으로].
- **요약 복사·원장 재료는 고친 값**을 쓴다. 이미 원장에 들어간 기록은 손대지 않고, 고친 통화가 이미 원장에 읽혔으면 "원장은 그대로예요" 한 줄만 보인다.

## 2. 저장 구조 (사실: 이번 DB PR)

| 대상 | 내용 |
| --- | --- |
| 새 표 `app_call_edits` | 통화 한 건당 한 줄. `call_id`(통화 ID), `vals`(jsonb: `title`·`counterpart`·`organization_id`·`points` 중 사용자가 고친 칸만). 키가 있으면 사용자 값, 없으면 AI 값. 소유자 읽기 전용 정책 1개 |
| 새 표 `app_call_edit_history` | 칸마다 이전 값·새 값 한 줄씩 더하기만 한다(AI 원래 값이 첫 줄에 남는다). 소유자 읽기 전용 |
| 새 함수 `app_call_edit(p_id, p_patch)` | 쓰는 길은 이것 하나. SECURITY DEFINER, 빈 search_path, authenticated만 실행, 안에서 소유자 확인. 제목 1~80자, 상대 100자, 핵심내용 8줄·줄당 150자, 조직은 같은 작업공간만, 개인 통화는 조직 불가, `reset`으로 AI 값 복귀, 같은 값이면 이력 안 씀 |
| 기존 표 | `app_feed_items`·`app_call_personal`의 칸·권한·정책·트리거, `app_call_move`·`app_call_work_info`는 바꾸지 않는다 |

- 왜 칸을 늘리지 않고 새 표인가: 통화 ID는 업무 통화함 ⇄ 개인 통화함으로 옮겨도 같아서 한 표로 양쪽을 덮는다. 기존 통화 표의 권한(로그인 본인은 제목·핵심내용 쓰기 불가)을 넓히지 않아도 된다. AI(`collector-feed`는 넣기만, `call_refill`은 기존 DB 함수)가 쓰는 길이 사용자 값 표와 달라서 서로 덮을 수 없다.
- 권한: anon·PUBLIC·service_role 권한 없음, 로그인 본인은 읽기만. 쓰기 함수는 소유자만. RLS 약화·권한 확대 없음.
- 우선순위: 사용자 값 > AI 값. 사용자 값은 지우지 않으면 계속 이긴다. 업무 통화의 조직은 기존 [조직 연결] 박스도 있으므로, 조직을 손으로 고친 통화에서 [조직 연결]을 저장하면 같은 조직으로 사용자 값도 함께 맞춘다.

## 3. 화면 (3단계 PR)

- **제목 바꾸기**: 메뉴 맨 위 [제목 바꾸기](PC 오른쪽 클릭·⋯, 폰 길게 누르기·⋯, PC는 F2). 창 없이 줄 안 제목이 입력칸으로 바뀌고 전체 선택. Enter 저장, Esc 취소, 바깥 누르면 저장, 비우면 그대로 둔다. 저장하면 "제목을 바꿨어요 · 되돌리기" 한 줄. 폰은 상세 제목이 입력칸이다. 고친 제목은 그대로 보인다(AI 제목에만 조직·사람 머리 떼기 규칙).
- **조직·이름 고치기**: 상세 날짜·시간 옆 상대 글자를 누르거나 메뉴 [조직·이름 고치기] → 상세 맨 위에 작은 박스(조직은 기존 담당조직 선택 창, 이름·직함은 직접, [AI 값으로][취소][저장]). 개인 통화에는 조직 칸이 없다.
- **핵심내용 고치기**: 상세 제목 줄 연필 또는 메뉴 [요약 고치기] → 줄마다 고치기·지우기, [+ 줄 더하기](8줄·줄당 150자), [AI 값으로][취소][저장]. 줄 안 `[확정]` 같은 머리말도 글자 그대로 둔다.
- **업무 · 개인**: 확인할 통화 줄과 상세 위 줄 둘 다 큰 버튼을 없애고 작은 글자 버튼(`feed-text-btn`)으로.
- 고친 값 표가 아직 없으면(DB 적용 전) 고치기 항목만 없고 나머지는 그대로다. 읽기가 실패하면 "AI 값이 보일 수 있어요" 한 줄을 목록 위에 보인다.

## 4. 원장·복사·다른 쓰임

- 요약 복사: 화면 줄에 사용자 값이 덧씌워져 있어 고친 값이 복사된다.
- 원장 자동 기록(`ai-assist`): 통화 재료의 제목·핵심내용·조직을 사용자 값이 있으면 그 값으로 읽는다(2단계 PR, 읽기만). 상대 이름은 지금처럼 재료에 쓰지 않는다. 이미 읽힌 통화는 처리 표의 본 시각(`seen_updated_at`)이 그대로라 다시 읽히지 않는다 = 이미 들어간 원장 기록은 손대지 않는다.
- 업무일지·주간보고: 지금 통화를 재료로 읽지 않는다(`call-personal.md` 4절). 나중에 읽을 때는 `app_feed_items`와 `app_call_edits`를 함께 읽어 `applyCallEdit`과 같은 규칙(사용자 값 우선)을 써야 한다.

## 5. 단계·정지 지점·되돌리기

| # | 단계 | 정지 지점 | 되돌리기 |
| --- | --- | --- | --- |
| 1 | DB PR: migration + 짝 파일 5개 | DB migration(승인형 DB workflow 확장 규칙 또는 SQL Editor) | 짝 rollback(SQL Editor). 고친 값이 한 줄이라도 있으면 멈춤 |
| 2 | Edge `ai-assist`(원장 재료 읽기만) | Edge 배포(DB 적용 뒤) | 이전 소스 SHA 재배포. 표가 없으면 AI 값 그대로 읽어 DB보다 먼저 배포해도 안전 |
| 3 | 화면 | 없음(앱만) | 화면 경로 제거. DB가 없으면 고치기 항목만 숨김 |

권장 순서: 1 → 3 → 2. 3은 DB가 없어도 열리고, 2는 표가 없으면 AI 값을 쓴다.

## 6. 다른 AI 요약·제목에도 같은 방식이 필요한가 (목록)

| 대상 | 저장 위치 | AI가 다시 쓰는가 | 판단 |
| --- | --- | --- | --- |
| 텔레그램 소식 요약·제목 | `app_feed_items`(source=telegram) 같은 표 | 수집이 새 줄을 넣기만 하고 기존 줄은 안 고침 | 필요 시 같은 방식(`app_call_edits`는 통화 ID 기준이라 소식 ID를 같은 표에 둘 수 있으나 함수가 통화만 받으니 확장 필요). 명진 요청이 있을 때 후속 |
| 개인 텔레그램 하루 요약(적용 대기 표) | 하루 한 줄, 서버 AI가 재생성 | 예(재생성) | 생길 때 같은 "사용자 값 따로 + 이력" 규칙으로 |
| 원장 자동 기록 | 원장 표 | 더하기만, 고치기는 이미 '원장 수정 요청' 흐름 | 추가 불필요 |
| 업무로 옮길 때 다시 채우기(`call_refill`) | 통화 줄(`app_call_work_info`로 한 번) | 예(옮긴 직후 한 번) | 이번 구조로 해결: 화면이 사용자 값을 앞세움 |
| 자료실 AI 이름·분류, 일정 제목 정리 등 | 각 표의 칸 | 요청할 때만 | 해당 없음(바로 고칠 수 있는 칸) |

## 7. 제안: 고친 사람-조직 연결을 다음 통화부터 AI도 쓰게 하기 (설계만, CALL-맥락문서와 함께)

- 재료: `app_call_edit_history`(조직·상대 칸의 새 값)와 `app_call_edits.vals`. 사람 이름·직함과 조직 이름 쌍만 쓴다(전화번호·내용 없음).
- 방법 A(추천): CALL-맥락문서(`collector-feed` `action=context`)의 응답에 "사람-조직" 목록을 더한다. 값은 로그인 본인의 최근 사용자 고침에서 (조직 이름, 이름, 직함)을 중복 없이 뽑은 이름 문자열 최대 N쌍. 갱신 스크립트가 맥락 문서 자동 구간에 적어 통화 분석 때 Gemini가 읽는다. 사용자 값이 AI 추측보다 앞선다.
- 필요한 권한 변경: `collector-feed`는 service_role이라 새 표를 읽을 수 없다. 읽기 전용 DB 함수(이름 문자열만 반환, service_role 실행) 하나를 새 migration으로 더해야 하며 이는 권한 확대에 해당하므로 **별도 승인 사항**이다. 대안 B: 화면(로그인 본인)이 "맥락 보내기"를 눌러 같은 목록을 보내게 하는 방식(권한 변경 없음, 손이 한 번 더 간다).
- 오류 방지: 이름이 같은 다른 사람, 조직이 바뀐 사람은 "최근 고침 우선, 같은 이름에 조직이 둘이면 목록에 넣지 않음". 개인 통화(조직 없음)는 제외.
- 이 PR들은 이 제안을 구현하지 않는다.
