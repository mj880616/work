# 읽생기 글 → Web2 노트 옮기기 SQL 설계 (RTW-노트일원화 ④ 초안)

📱 폰 경로 C — 이 문서와 SQL 파일은 설계·초안이다. 이 작업에서 운영 DB·Edge·Cloudflare에 접근하거나 SQL을 실행하지 않았고, workflow도 실행하지 않았다. 실행은 커맨드센터 승인 뒤 명진이 Supabase SQL Editor에서 직접 한다(DB 승인 버튼은 `rtw_`가 들어간 SQL을 거절한다).

상위 설계: [rtw-note-unify-investigation.md](rtw-note-unify-investigation.md) (결정 D1~D12는 7.1절 추천안 그대로, 옮기기 순서는 5절).

## 명진용 요약

1. 읽생기 명진 글 49개(읽기 글 38, 독립 메모 8, 질문 1, 글쓰기 기록 1, 훈련 기준 1)를 Web2 노트 49개로 옮긴다. 글에 붙은 메모 9개와 책갈피 6개는 그 글 노트 안에 들어간다.
2. 먼저 "해 보기만"(SQL 파일 1)을 돌린다. 실제처럼 노트를 넣어 보고 개수·제목 길이를 표로 보여 준 뒤 맨 끝에서 전부 취소하므로 아무것도 안 바뀐다.
3. 표의 판정이 모두 OK이면 "실제 실행"(SQL 파일 2)을 돌린다. 한 번에 전부 들어가거나 하나라도 이상하면 아무것도 안 들어간다.
4. 같은 SQL을 다시 돌려도 같은 글이 두 번 들어가지 않는다(5겹 장치, 아래 4절). 마음에 안 들면 "옮겨 온 노트만 지우기"(SQL 파일 4) 한 번으로 되돌린다. 옮긴 뒤 노트를 고쳤으면 지우지 않고 멈춘다.
5. 읽생기 원본은 읽기만 하고 그대로 둔다. 읽생기 표·권한·정책은 건드리지 않는다.

### 일상어 3줄 (AGENTS §7)

- 무엇이 바뀌나: Web2 노트 목록에 읽생기 글이 노트로 한꺼번에 들어온다. 날짜는 읽생기에서 쓴 날 그대로라 최근 노트가 위에 남는다. 읽생기 글과 바구니 메모는 그대로다.
- 잘못되면: SQL이 앞뒤 확인에서 멈추면 아무것도 안 바뀐다. 다 들어간 뒤 모양이 마음에 안 들면 노트 목록에 옛 글이 많이 보일 뿐 남에게는 안 보인다.
- 되돌리는 법: SQL 파일 4(옮겨 온 노트만 지우기) 한 번. 읽생기 원본이 남아 있어 다시 옮길 수 있다.

## 1. 파일

| 순서 | 파일 (`docs/design/sql/`) | 하는 일 | 끝 줄 |
| --- | --- | --- | --- |
| 1 | `rtw-note-copy-1-dry-run.sql` | 해 보기만. 실제와 같은 본문으로 넣어 본 뒤 결과표를 보이고 취소 | `rollback;` |
| 2 | `rtw-note-copy-2-apply.sql` | 실제 실행. 1번과 본문이 글자 하나까지 같고 끝만 다름(시험이 같은지 비교함) | `commit;` |
| 3 | `rtw-note-copy-3-check.sql` | 옮긴 뒤 종류별 개수를 읽생기 원본과 대조하는 읽기 전용 표 하나 | (select 한 문장) |
| 4 | `rtw-note-copy-4-revert.sql` | 되돌리기. 옮겨 온 노트만 삭제, 바뀐 노트가 있으면 멈춤 | `commit;` |

- `supabase/migrations/` 아래에 두지 않는다. 표 구조가 안 바뀌는 데이터 옮기기라 DB 변경 기록표(`schema_migrations`)에도 한 줄 남기지 않는다(D12 추천안). 파일 이름에 버전 숫자를 붙이지 않은 이유다.
- 붙여 넣기는 새 쿼리 창(+)에 파일 전체를 한 번에 한다. 1·2번 파일은 약 2.4만~3만 바이트, 3·4번은 약 5천 바이트다. 중간에서 잘리면 `commit;`이 없어 저장되지 않거나 문법 오류로 아무것도 실행되지 않는다(전부 아니면 전무).
- 해 보기와 실제 실행은 한 거래(트랜잭션) 하나다. AGENTS 폰 경로 C의 "길면 조각으로 나눔"은 이번에는 쓰지 않는다. 조각으로 나누면 중간에 멈췄을 때 일부만 들어가기 때문이다.

### 0단계 읽기 전용 확인 (select만)

```sql
-- 노트 종류 열이 운영에 있는지(MEMO-노트 DB 변경이 적용됐는지). 기대: cols 3 / migration_row 1
select
  (select count(*) from pg_attribute where attrelid = 'public.app_notes'::regclass and not attisdropped
     and attname in ('kind', 'title', 'metadata')) as cols,
  (select count(*) from supabase_migrations.schema_migrations where version = '20261017052234') as migration_row;
```

`docs/migration-history.md`에는 `20261017052234_journal_memo_notes_kind.sql`이 "준비중·운영 미적용"으로 적혀 있다(원장 MEMO-노트 행은 완료). 적용 전이면 SQL 파일 1·2는 `RTW_COPY_STOP-05`에서 아무것도 하지 않고 멈춘다.

## 4. 한 줄도 두 번 안 들어가는 방법

1. 노트마다 `metadata.rtw = {table, id, migrated_at, src_updated_at}`를 남긴다(`table`·`id`가 읽생기 행 하나를 가리킨다).
2. 시작 전 확인 4번: `metadata.rtw`가 있는 노트가 하나라도 있으면 `RTW_COPY_STOP-04`로 멈춘다. 실제 실행을 두 번 돌려도 두 번째는 0건 추가다.
3. 안전망: 넣을 때도 "같은 `table`·`id`가 이미 있으면 넣지 않는다"를 건다. 2번 확인이 사라져도 중복이 들어가지 않는다.
4. 넣은 뒤 확인: 이번에 들어간 수가 계산한 수와 같고(`STOP-21`), 전체 노트 수가 시작 전 + 계산한 수이며(`STOP-22`), 종류별 수가 원본과 같은지(`STOP-24`) 본다. 다르면 전체 취소.
5. 노트 표에 쓰기 잠금(`share row exclusive`)을 걸어, 창 두 개에서 동시에 돌려도 한쪽은 기다린 뒤 2번에서 멈추거나(5초 안에 끝나지 않으면 잠금 시간 초과 오류로 멈춤) 한다. 동시 실행 시험으로 확인했다.

"옮긴 뒤 읽생기에 새로 쓴 글만 더 옮기기"는 지금 SQL에 없다(D11로 읽생기에 더 쓰지 않기로 했기 때문). 필요해지면 되돌린 뒤 처음부터 다시 옮기거나, 별도 작업으로 "이어서 옮기기" 판을 만든다(결정 N2).

## 5. 만들어지는 노트의 모양

모두 `app_notes`의 `kind='note'` 행이다. 날짜는 원본 그대로(`created_at`, `updated_at`), `occurred_at` = `created_at`이다. 바구니·AI 복사·Drive 요약은 `kind=basket`만 읽으므로 섞이지 않는다.

| 원본 | 제목 | 본문 |
| --- | --- | --- |
| 읽기 글 1개 | 글 제목(한 줄, 200자까지. 비면 원문 제목, 그래도 없으면 "(제목 없음)") | `> 원문: [원문 제목](주소) · 저자 · 출처 · 발표 날짜 · 책갈피 표시`(있는 것만) → 본문 그대로 → `## 나의 메모`(`- [유형] 날짜` + 들여쓴 본문) → `## 책갈피`(`> 문장` + `메모: …`) → 끝 줄 `주제: A, B · 질문: …` |
| 독립 메모 1개 | Web2 `noteTitleFromText` 규칙(첫 줄, 앞의 `#` 표시 제거, 200자). 본문이 비면 "(제목 없는 메모)" | 메모 전체 → 끝 줄 `유형: … · 주제: … · 질문: …` |
| 질문 1개 | 질문(공백을 합친 한 줄, 200자) | 질문 전문 → `## 현재 생각` → `상태: 열림/닫힘` |
| 글쓰기 기록 1개 | 기록 제목(비면 "(제목 없는 글쓰기 기록)") | `## A 처음 쓴 글`, `## B 피드백`, `## C 고친 글`, `## 배운 것`(있는 것만) → 끝 줄 `종류: … · 태그: … · 원본 글: 제목` |
| 훈련 기준 1개 | 글쓰기 훈련 기준 | 기준 글 그대로(비어 있으면 만들지 않음) |

세부 규칙(모두 시험으로 확인):

- 원문 주소는 `http://`·`https://`만 링크로 만든다. 다른 모양(`ftp://` 등)은 링크 없이 글자로만 적는다. 주소의 공백·괄호는 `%20`·`%28`·`%29`로 바꾸고, 제목 속 `[ ]`는 `\[ \]`로 막는다.
- 글에 붙은 메모는 쓴 날(서울 시간) 순, 책갈피는 문장 위치 순이다. 글 전체 책갈피는 머리말에 "책갈피 표시"만 붙이고 메모가 있을 때만 `## 책갈피`에 한 줄 더 적는다.
- 글에 붙은 메모에서 나간 주제·질문 연결은 그 메모가 붙은 글 노트의 끝 줄에 합친다. 질문은 앞 60자만 적는다.
- 본문 끝의 공백·빈 줄은 지운다(글 내용은 그대로).
- `ai_export_allowed`는 노트 기본값(true)이고 첨부·보관·`journal_day`는 비어 있다. 주제 요약이 모두 비어 있어 주제 노트는 만들지 않는다(D5).
- 옮기지 않는 것: 피드백, 초대 명단, AI 사용량, 소유자 설정, 메모 유형 목록. 지인 계정의 글은 `owner_id` 조건으로 제외한다(`rtw_personal_mode` 소유자만).

예시(가짜 글로 시험한 결과):

```
> 원문: [원문 제목](https://example.test/a) · 저자 갑 · 출처 을 · 발표 2026-09-18 · 책갈피 표시

본문 첫 줄

## 나의 메모

- [생각] 2026-09-06

  첫 메모 첫 줄

## 책갈피

> 앞쪽 문장

주제: 주제 둘, 주제 하나 · 질문: 열린 질문입니다
```

## 6. 되돌리는 법

SQL 파일 4가 한다. 순서와 안전장치:

1. 먼저 지워질지만 보려면 마지막 줄 `commit;`을 `rollback;`으로 바꿔 실행한다(오류 없이 끝나면 지울 수 있다는 뜻이고 실제로는 안 지워진다).
2. 지우는 대상은 `metadata.rtw`가 있는 노트뿐이다. 읽생기 원본, 바구니, 업무일지, 일기, 직접 쓴 노트는 건드리지 않는다.
3. 아래 중 하나라도 있으면 아무것도 지우지 않고 멈춘다(`RTW_REVERT_STOP-05`, 오류 문구에 종류별 개수가 나온다). 고친 내용을 지워서 통과시키지 않는다.
   - 옮긴 뒤 고친 노트: `updated_at`이 옮길 때 값(`metadata.rtw.src_updated_at`)과 다름
   - 종류가 `note`가 아니게 바뀐 노트(바구니로 되돌린 노트 등)
   - 첨부가 붙었거나 보관 처리된 노트
   - AI 내보내기 설정이나 `metadata`의 다른 칸을 바꾼 노트
   - 프로젝트·조직·회의·자료 연결(`app_record_links`)이 붙은 노트
4. `metadata.rtw`가 예상 모양이 아니거나(`STOP-03`), `app_notes`를 가리키는 다른 표가 새로 생겼거나(`STOP-04`), 지울 노트가 0개이면(`STOP-02`) 멈춘다.
5. 멈춘 노트는 따로 판단한다(예: 그 노트만 남기고 나머지를 직접 지우거나, 고친 내용을 복사해 둔 뒤 되돌리기). 다 지운 뒤에는 SQL 파일 2를 다시 돌리면 처음부터 다시 옮겨진다.

## 7. 이 SQL이 하지 않는 것

- 읽생기 표(`rtw_*`)는 select만 한다. 표 구조·권한·정책·RLS·함수를 바꾸지 않는다(시험에서 `rtw_*`에 select 권한만 가진 역할로 실행해 통과, 실행 전후 정책·권한·함수 목록 비교 동일).
- `GRANT`·`REVOKE`·정책 변경·`SECURITY DEFINER`·새 함수·새 표(임시 표 제외)·`schema_migrations` 기록이 없다. 임시 표(`rtw_ctx`, `rtw_rel`, `rtw_plan`, `rtw_report`)는 거래가 끝나면 사라진다.
- Edge·Cloudflare·workflow·비밀값과 무관하다.
- 읽생기 원본을 지우지 않는다(D9: 지인 시험 끝날 때까지 둠).

## 8. 점검 필요

운영 DB를 읽지 않았으므로 아래는 저장소 migration 파일과 조사 문서, 명진이 조회해 준 결과로만 확인했다. SQL이 실행 때 스스로 다시 확인하는 것은 "실행 때 확인" 칸에 적었다.

### 8.1 `app_notes` 열·제약과 맞는지

근거: `supabase/migrations/20261010120000_basket1_notes_links.sql`(attachments, archived_at, ai_export_allowed, metadata), `20261013034836_basket_photo_ocr_db.sql`(attachments 검사), `20261017052234_journal_memo_notes_kind.sql`(kind, title, journal_day). 이 마지막 것이 운영에 적용됐는지가 선행 조건이다(위 2절 0단계).

| 열 | 이 SQL이 넣는 값 | 맞춰야 할 제약 | 실행 때 확인 |
| --- | --- | --- | --- |
| `workspace_id` | `kptu-work` 작업공간 id (표에서 slug로 찾음, 정확히 1개) | 외래 키, 정책 `notes_owner_all` | STOP-02·03 |
| `kind` | `'note'` | `app_notes_kind_check` | STOP-05 |
| `title` | 한 줄 1~200자 | `app_notes_title_check`(노트는 title 필수, 1~200자, 줄바꿈 없음) | STOP-05·14, 해 보기에서 실제 insert |
| `raw_text` | 최대 10만 자 | `app_notes_raw_text_check`(노트는 0~10만 자) | STOP-05·13, 해 보기에서 실제 insert |
| `occurred_at`, `created_at`, `updated_at` | 원본 날짜 | 시간 열(트리거 없음 전제) | STOP-05(트리거 없음) |
| `attachments` | 기본 `[]` | `app_notes_attachments_check` | 넣은 뒤 STOP-23 |
| `archived_at`, `journal_day` | 비움 | `journal_day`는 노트에서 null이어야 함 | STOP-23 |
| `ai_export_allowed` | 기본 true | 일기만 false 강제 | — |
| `metadata` | `{"rtw": {…}}` | `app_notes_metadata_check`(객체) | STOP-05 |

- 해 보기는 실제로 `insert`를 한 뒤 취소하므로 위 검사 조건을 운영 DB 자체가 한 번 확인해 준다.
- 사전 확인 STOP-05는 열 11개, 검사 조건 4개(검증 완료), 제목 조건에 `<= 200`, 본문 조건에 `100000`, RLS 켜짐, 정책 `notes_owner_all` 존재, 사용자 트리거 0개를 본다. 하나라도 다르면 멈춘다.

### 8.2 작업공간(`workspace_id`) 얻기

- `app_workspaces.slug = 'kptu-work'`로 찾는다(조사 문서 3.2절, `private.app_is_workspace_owner`의 Web2 입장 기준). 정확히 1개여야 하고(STOP-02), 그 작업공간의 `role='owner'` 구성원이 정확히 1명이며 읽생기 소유자(`rtw_personal_mode`의 `id='owner'`)와 같은 사람이어야 한다(STOP-03). 화면·클라이언트가 준 값은 쓰지 않는다.
- 확인 못 한 것: 운영의 slug 값이 정말 `kptu-work`인지, 작업공간이 1개뿐인지는 실행 전까지 가정이다. 다르면 STOP-02로 멈추므로 잘못된 곳에 들어가지 않는다.

### 8.3 트리거·정책·실행 주체

- 정책 `notes_owner_all`은 `authenticated`용(`private.app_is_workspace_owner(workspace_id)`)이다. SQL Editor는 표 소유자(RLS를 거치지 않는 역할)로 실행하므로 이 정책이 막지도 열지도 않고, 이 SQL은 정책을 바꾸지 않는다. 대신 대상 작업공간·종류를 SQL 안에서 고정하고 앞뒤 확인을 둔다.
- 트리거: `app_notes`에는 사용자 트리거가 없다는 것이 이전 migration의 전제다. 트리거가 있으면 날짜(`created_at`·`updated_at`)가 바뀔 수 있어 STOP-05로 멈춘다.
- 로그인한 `authenticated` 역할로 실행하는 경로는 쓰지 않는다. 읽생기 표의 정책(소유자 + 초대 확인 restrictive)을 거쳐야 해서 SQL Editor 소유자 권한을 전제로 만들었다.
- 시험은 `rtw_*`에 select만 가능하고 RLS를 건너뛰는 역할로 실행한다. 쓰기 권한이 없는 역할로는 `42501`로 막힘도 확인했다.

### 8.4 읽지 못한 운영 부분 (가정)

- rtw 표의 열 이름은 명진이 확인해 준 목록과 조사 문서 2.1절을 따른다. SQL이 읽는 열이 하나라도 없으면 STOP-06으로 멈춘다. 열 형식(`id`가 uuid인지, `rtw_personal_mode.id`가 글자인지, `tags`가 배열인지, `published_on`이 날짜인지)은 가정이다. 비교는 `::text`로 맞추지만 `rtw_personal_mode.id = 'owner'`와 `tags`의 배열 형식은 그대로 쓴다.
- 값의 가정: 책갈피 종류 `passage`·`resource`(다른 값이면 STOP-12), 연결 `source_type` `resource`·`note`와 `target_type` `topic`·`question`, 질문 `status` `open`(그 외 `closed`는 "닫힘", 다른 값은 값 그대로 적음), 글 소유 칸 `visibility`는 읽지 않음.
- rtw 표의 정책·트리거·함수(`rtw_is_personal_owner()` 본문 포함)는 읽지 않았다. 이 SQL은 select만 하고 소유자 권한으로 실행하므로 영향이 없다고 본다.
- 연결 42개가 모두 글자 줄로 남는지는 실행 전 알 수 없다. 대상 글이 없거나 `resource`·`note`가 아닌 출발점은 글자로 옮기지 못하며, 해 보기 표의 "연결" 줄이 `확인 필요`로 보인다. 이 경우 실행은 막지 않았다(글자가 사라지는 것은 메모·책갈피만 막음: STOP-11·12). 판단은 명진이 한다(결정 N4).
- 운영 PostgreSQL 버전: 시험은 PostgreSQL 17에서 했다. `string_to_table`(14 이상)·`regexp_replace` 플래그를 쓴다.

## 10. 명진이 정할 것 (추천안 포함)

- N1. 독립 메모가 인용(`> `)으로 시작할 때 제목: ① Web2 `noteTitleFromText`와 똑같이 첫 줄 그대로(제목이 `> 인용 문장`이 됨) **(추천: 글 쓸 때와 같은 규칙)** ② 인용 다음 첫 줄을 제목으로. 조사 문서 2.3절은 ②처럼 적었지만 실제 함수는 ①이라 ①로 만들었다. 해 보기 결과표의 "인용(>)으로 시작해 제목이 인용문인 독립 메모" 줄이 영향 개수를 알려 준다(0이면 신경 쓸 필요 없음). ②를 원하면 SQL 4-2의 제목 계산만 바꾸면 된다.
- N2. 옮긴 뒤 읽생기에 쓴 글을 나중에 이어서 옮길 판이 필요한지: ① 필요 없음(읽생기에 더 안 쓰기, D11) **(추천)** ② 별도 작업으로 "이어서 옮기기" SQL.
- N3. 옮긴 노트의 AI 내보내기: ① 노트 기본값(허용) 그대로 **(추천: 바구니·AI 복사 경로는 `kind=basket`만 읽어 섞이지 않음)** ② 옮긴 노트는 허용 끔.
- N4. 해 보기의 "연결" 줄이 `확인 필요`일 때: 어느 연결이 글자로 못 남는지 보고 ① 그대로 진행(주제·질문 이름만 줄로 남는 것이 원래 계획) **(추천)** ② 멈추고 원인 확인.

## 11. 시험 (로컬 PostgreSQL, 가짜 글)

`tests/auth-handoff/rtw-note-copy.test.mjs`, 가짜 표·데이터는 `rtw-note-copy-fixture.mjs`. 기존 `tests/auth-handoff` 관례대로 내장 PostgreSQL을 격리 환경에서 띄우고(운영·Supabase·Google 접속 없음) migration 파일을 순서대로 적용한 뒤 시험한다. CI 워크플로(`authz-security-check.yml`의 `auth-handoff-postgres`)가 `npm test`로 함께 실행한다.

- 정적: 4개 SQL에 `GRANT`·정책·함수·표 변경·`rtw_*` 쓰기·`schema_migrations`·이메일·키가 없음, 1·2번 본문 글자 단위 동일, 시작·끝 줄 확인, `supabase/migrations` 밖.
- 해 보기: 결과표 값, 실행 뒤 남는 노트 0, 실행 전후 `rtw_*`·정책·권한·함수·기존 노트 해시 동일, 대안(`yes`) 경로.
- 사전 조건 8가지 각각 위반 시 해당 오류로 멈추고 아무것도 안 바뀜.
- 실제 실행: 노트 13개(가짜), 날짜·`metadata`·노트 모양(읽기 글 4종, 독립 메모, 질문, 기록, 훈련 기준) 글자 단위 비교, 지인 행 제외, 길이 규칙.
