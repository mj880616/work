# 텔레그램 소식 보낸 사람 이름 설계 (TG-발언자이름)

이 문서는 설계와 시안만 다룬다. 앱 코드, DB, Edge, Apps Script, 수집기, workflow는 바꾸지 않는다.

- 작성: 2026-10-26, Claude Code 웹. production과 Google Drive를 직접 읽지 않았다. "사실"은 저장소 파일(커밋 `f61242c` 기준)이고, "추정"·"확인 필요"는 확인하지 못한 것이다. 공개 저장소이므로 실제 이름, 번호, 방 이름은 이 문서에 없다. 예시는 모두 지어낸 이름이다.
- 원장 행: TG-발언자이름. 이 PR은 `docs/roadmap.md`를 고치지 않는다.
- 시안: [mockups/telegram-sender-names.html](mockups/telegram-sender-names.html)
- 관련 문서: [통화·텔레그램 한 흐름](call-telegram-feed.md), [통화 요약용 맥락](call-context.md), [통화 손고치기](call-user-edit.md), [저장소 규칙](../../AGENTS.md).

## 0. 명진용 요약

**문제.** 원문 보기에서 말한 사람이 A, B로만 나온다.

**원인 (사실).**
1. 회사 PC 수집기가 Drive에 남기는 메시지 파일에는 `sender_id`(숫자)만 있고 이름 칸이 없다(`call-telegram-feed.md` 1.1절).
2. 앱 스크립트 `tgFeedAssignSenders`(`docs/ops/collector-feed.gs`)가 그 숫자를 **방·날짜마다 새로** 처음 나온 순서대로 A, B, C로 바꿔 서버에 보낸다. 실제 숫자는 서버로 가지 않는다.
3. 서버는 원문 줄을 `HH:MM A: 글` 모양으로 `app_feed_items.raw_text`에 저장한다. 그래서 같은 사람이 어제는 A, 오늘은 B일 수 있고, Web2에는 A가 누구인지 알려 주는 정보가 **어디에도 없다.**

**명진 결정(10/26 20:30): "3".** 수집기가 이름도 적게 고치고(자동), Web2에서 A·B 옆 [이름 붙이기]로 손으로도 붙인다(수동). 새 메시지는 자동, 빠진 사람만 손으로.

**추천하는 모양.**
- Web2에 **사람 이름표** 표 하나를 새로 둔다. 같은 목적의 기존 표가 없다(2절).
- 앱 스크립트가 숫자를 **비밀 열쇠 섞은 고정 해시**로 바꿔 보낸다. 같은 사람이면 방·날짜가 달라도 같은 값이 되므로 한 번 붙인 이름이 모든 날·모든 방에 따라간다. 원래 숫자는 여전히 서버로 가지 않는다.
- 서버는 "방·날짜·A → 어느 사람"을 **따로 한 표**에 기록한다. 원문 줄(`A:`)은 그대로 둔다. 그래서 지난 소식 글을 고치지 않고도 이름이 붙는다.
- 지난 소식은 두 가지로 이름이 붙는다. ① 명진이 A를 눌러 그 방·그 날에 이름을 붙임(바로 가능, 그 하루에만 적용). ② 앱 스크립트 "소급 보내기"가 Drive에 남은 지난 메시지에서 방·날짜별 A→해시 연결만 다시 보냄(한 번 붙인 이름이 모든 날에 적용됨, 3.3절).
- AI 요약에는 **이번 단계에서 이름을 넘기지 않는다**(A·B 그대로). 넘길지는 명진 결정(Q3).

**순서.** ① DB → ② 서버(collector-feed) → ③ 앱 스크립트(+수집기, 저장소 밖) → ④ 화면. ①과 ②는 멈춤 지점이다(7절). 수집기 고치기(`sender_name`)는 ③과 따로 아무 때나 해도 안전하다(칸이 없으면 지금처럼 동작).

**결정 질문은 5개다(PR 본문 맨 위, 9절).**

## 1. 조사한 사실

### 1.1 지금 데이터가 흐르는 길

```
수집기(회사 PC) json: sender_id(숫자), 이름 칸 없음
   ▼
앱 스크립트 tgFeedAssignSenders: 숫자 → 방·날짜별 A, B, C   (숫자는 여기서 버려짐)
   ▼  POST ?action=telegram  {day, room_key, room_label, total, messages:[{ref, at, sender:"A", text, ...}]}
서버 collector-feed: sender는 /^[A-Z]{1,3}$/만 받음 → AI(임시 이름 A,B로 읽음) → 소식 묶음마다 app_feed_items 한 줄
   raw_text = "16:31 A: 글\n16:33 B: 글 …"   (rawLines)
   ▼
화면 telegram-feed.js: feed-model.mjs telegramLines()가 줄을 {시각, A, 글}로 쪼개 그림
```

- 같은 날 같은 방의 A는 한 사람이다. 라벨은 하루치 전체 메시지(분할 전)에서 처음 나온 순서로 정해지므로 묶음(part)이 나뉘어도 같다(`tgFeedAssignSenders`는 분할 `tgFeedSplit` 앞에서 돈다). 이 성질이 소급의 열쇠다.
- 서버는 소식 항목이 어느 메시지 묶음에서 나왔는지 `source_ref = tg:<해시>:<번호>`로만 남긴다. 해시는 `방|날짜|메시지 ref들`의 SHA-256이라 거꾸로 메시지를 찾을 수 없다. 그래서 **저장된 항목에서 "이 A가 누구인지"를 알아낼 방법은 없다.**
- 원문 전문(`raw_text`)은 명진이 화면에서 비울 수 있다. 비운 항목은 이름을 붙일 줄이 없다(그대로 둔다).

### 1.2 이미 있는 비슷한 것 (재사용 가능성 조사)

| 후보 | 실제 모양 | 재사용? |
| --- | --- | --- |
| 통화 손고치기 `app_call_edits` (`20261026120000_call_user_edit`) | 통화 한 건당 한 줄(`call_id` 기본키). `vals` 안 키는 `title`·`counterpart`·`organization_id`·`points` 네 개만 허용(CHECK) | 아니오. **통화 한 건**의 상대 글을 고치는 표라 사람 목록이 아니고 키 제한이 걸려 있다 |
| 통화 맥락 사람 `app_call_context_people()` (`20261026160000_call_context_people`) | 표가 아니라 **읽기 전용 함수**. 업무 통화의 상대 글(`조직 이름 직함`)과 고친 값을 모아 문서용 한 줄씩 돌려줌 | 아니오. 사람 표가 아님. 나중에 텔레그램 이름을 맥락 문서에 넣을지는 별도 결정(8절) |
| 담당조직 `app_suborganizations` | 조직당 대표자 이름 칸 하나(`representative_name`)와 연락처 칸 하나(`contact`)뿐. 사람 목록 아님 | 아니오. 연락처(전화번호)가 섞인 칸이라 이름표로 재사용하면 안 된다 |
| 담당조직 기록 / 업데이트 | 글 기록. 사람 단위 구조 없음 | 아니오 |
| 이름을 보관하는 다른 표 | migration 전체를 조사했으나 **외부 사람 목록 표는 없다**(사실, 이 저장소 기준. production은 확인하지 못함) | - |

결론: 재사용할 기존 사람 표가 없다. 새 표 하나가 필요하다. 다만 통화 화면의 "이름 고치기"(`feed-whoname`, 점선 밑줄 글자를 누르면 입력)와 같은 누르는 방식·말투를 화면에서 재사용한다.

### 1.3 AI가 읽는 것 (사실)

- 텔레그램 AI 재료는 `m1 16:31 A (m3에 답): 글` 모양이고 지시문은 "보낸 이(A, B 같은 임시 이름)"라고 못 박는다(`telegram.ts`). 실제 이름은 어디에서도 AI에 가지 않는다.
- 통화는 반대다. 분석 파일의 상대 이름·직책이 요약·제목에 들어가고, `counterpart`는 화면·원장 재료로 쓰인다(`call-telegram-feed.md` 4.5절).

## 2. 데이터 설계

### 2.1 새 표 2개 (추천)

**`app_tg_senders` — 사람 이름표.** 한 사람이 한 줄.

| 칸 | 내용 |
| --- | --- |
| `id` uuid | 기본키 |
| `workspace_id` | 작업공간(서버가 정함. 요청 값 신뢰 안 함) |
| `sender_key` text null | 앱 스크립트가 만든 고정 해시(16~32자 소문자 16진수). 손으로만 만든 사람은 비어 있다. 작업공간 안에서 값이 있으면 유일 |
| `name` text null | 명진이 붙인 이름(1~40자, 제어문자 없음). **있으면 이것이 이긴다** |
| `auto_name` text null | 수집기가 보낸 이름(같은 제한). `name`이 없을 때만 보인다 |
| `created_at`, `updated_at` | 시각 |

표시 이름 = `name` → `auto_name` → 없으면 A·B 그대로. 수집기가 나중에 이름을 바꿔도 명진이 붙인 이름은 덮이지 않는다(통화 손고치기와 같은 원칙: 자동 값과 사용자 값을 다른 칸에 둔다).

**`app_tg_day_senders` — 방·날짜별 A가 누구인지.**

| 칸 | 내용 |
| --- | --- |
| `workspace_id`, `room_key`, `day`, `label`(A~ZZZ) | 기본키 4칸 |
| `sender_id` uuid | `app_tg_senders.id` (사람 삭제 시 이 줄도 같이 지움) |

- `raw_text`는 **한 글자도 바꾸지 않는다.** 화면이 줄의 A를 `(room_key, day, label)`로 찾아 이름을 입힌다. 이렇게 하면 지난 소식 전부에 대해 데이터 이전 작업이 필요 없고, 이름을 고쳐도 소식 글이 변하지 않는다.
- 표는 둘 다 소유자 전용 RLS, anon·PUBLIC 권한 없음. 로그인한 본인은 **읽기만** 하고(두 표), 쓰기는 아래 함수로만 한다(`app_call_edit` 방식).

### 2.2 함수 (DB 단계에서 같이 만든다)

| 함수 | 부르는 쪽 | 하는 일 |
| --- | --- | --- |
| `app_tg_senders_upsert(p_workspace, p_room_key, p_day, p_senders jsonb)` | 서버 입구(service_role만) | `[{label, key, name?}]`를 받아 사람을 키로 찾거나 만들고, `auto_name`은 `name`이 없을 때만 채우며, 방·날짜·라벨 연결을 더한다. 이미 있는 연결은 바꾸지 않는다(명진이 손으로 붙인 선택이 이긴다). 충돌 건수를 돌려준다 |
| `app_tg_sender_set_name(p_room_key, p_day, p_label, p_name)` | 화면(authenticated, 안에서 소유자 확인) | 그 방·날짜·라벨의 사람에게 `name`을 붙인다. 연결이 없으면(지난 소식) **키 없는 새 사람**을 만들고 연결한다. `p_name`이 빈 글이면 `name`을 지운다 |
| `app_tg_sender_merge(p_from, p_to)` | 화면(소유자만) | 같은 사람인데 둘로 갈라졌을 때 합친다(연결을 `p_to`로 옮기고, 키 있는 쪽의 키를 살린다). 합치기는 되돌릴 수 없으므로 화면에서 한 번 더 묻는다 |
| `app_tg_sender_forget(p_id)` | 화면(소유자만) | 사람 한 줄과 연결을 지운다. 소식 글은 영향 없다. 다시 자동 수집이 오면 `auto_name`만 다시 생길 수 있다 |

- 모두 SECURITY DEFINER + 빈 search_path, 실행 권한은 필요한 역할 하나씩만(PUBLIC·anon 없음). 소유자 확인은 기존 `private.app_is_workspace_owner`를 쓴다.
- 입력 검사(이름 길이·제어문자, 키 모양, 라벨 `^[A-Z]{1,3}$`, room_key 모양)는 DB 함수 안에서 한 번 더 한다(AGENTS.md 3절 5번).
- 이름을 지울 때 이전 값 기록은 남기지 않는다(작은 메모일 뿐이고 원문은 Drive에 있다). 필요하면 통화 손고치기처럼 이력 표를 나중에 더할 수 있다.

### 2.3 `sender_id`를 서버로 안전하게 보내기

세 가지를 비교했다.

| | 가. 원래 숫자 그대로 | 나. 숫자의 단순 해시 | 다. **열쇠 섞은 해시(추천)** |
| --- | --- | --- | --- |
| 서버·DB에 남는 것 | 텔레그램 사용자 번호 | 해시 | 해시 |
| 번호를 거꾸로 알아낼 위험 | 번호가 그대로 있음 | **있다.** 번호는 10자리 안팎 숫자라 모든 경우를 해시해 맞춰 보면 풀린다 | 열쇠를 모르면 풀 수 없다. 열쇠는 앱 스크립트 속성에만 있고 서버·저장소에 없다 |
| 같은 사람이 방·날짜가 달라도 같은 값? | 예 | 예 | 예 |
| 비고 | 개인 식별번호라 공개 저장소·로그·화면에 새면 안 되는 값을 서버 쪽에 늘린다 | 안전해 보이지만 사실상 가명일 뿐 | `HMAC-SHA256(열쇠, 번호)`의 앞 32자리. 앱 스크립트는 `Utilities.computeHmacSha256Signature`로 만든다 |

**추천: 다.** 새 앱 스크립트 속성 `TG_FEED_SENDER_KEY`(임의 긴 글, 저장소·채팅에 쓰지 않는다)가 필요하다. **이 열쇠를 바꾸면 모든 사람의 해시가 달라져** 같은 사람이 새 사람으로 생긴다. 그래서 한 번 정하면 바꾸지 않고, 속성 값은 명진이 따로 메모해 둔다. 잃어버리면 이름표를 처음부터 다시 붙여야 하는 정도의 피해이며 보안 사고는 아니다.

- 번호가 비어 있는 메시지(예: 채널 글, 익명 관리자)는 지금처럼 `?` 한 사람으로 묶이는데 이 경우 키를 만들지 않는다. 화면은 그 라벨에 이름을 붙일 수 있지만(그 방·날짜에만 적용) 다른 날로 따라가지 않는다.
- 서버는 해시만 받으므로 "이 키가 어느 번호인지"를 알 수 없다. 이름은 화면에서 보는 별명이다.

## 3. 흐름

### 3.1 자동: 새 메시지

```
수집기 json: sender_id + sender_name(새 칸)
   ▼
앱 스크립트: 방·날짜마다 A,B,C 정하기(지금과 같음) + 라벨마다 {label, key=HMAC(번호), name=sender_name}
   ▼ POST ?action=telegram  (messages는 그대로 + 새 칸 senders:[{label,key,name?}])
서버: ① 기존 검사·AI·저장은 그대로 ② app_tg_senders_upsert로 이름표·연결 기록
   ▼
화면: raw_text의 A를 (방,날짜,A)로 찾아 이름 표시, 이름이 없으면 A + [이름 붙이기]
```

- 서버가 `senders`를 못 받아도(예: 옛 앱 스크립트) 소식 저장은 지금과 똑같이 된다. `senders` 처리 실패는 소식 저장을 막지 않는다(로그 코드만 남긴다). 이름은 화면 편의 정보일 뿐이라 소식 저장보다 앞서 실패시키지 않는다.
- 묶음(part)이 나뉘면 각 묶음이 같은 `senders`를 다시 보낸다(작은 목록이고 upsert라 중복해도 같다).
- 한 방·하루의 `senders`는 40명 이하, 이름 40자 이하. 서버 입구 몸통 상한(200 KB)에 영향 없다.

### 3.2 수동: A 옆 [이름 붙이기]

1. 원문 줄에서 이름 없는 라벨의 **그 방·그 날 첫 줄**에만 [이름 붙이기]를 보인다(다른 줄에는 조용히 A만).
2. 누르면 작은 입력 창. 이미 있는 사람 이름이 칩으로 나와서 고르거나, 새로 입력한다.
3. 저장하면 `app_tg_sender_set_name`이 사람(없으면 새로 만들고)에 이름을 붙인다.
   - 그 라벨이 키 있는 사람이면: **그 사람의 모든 날·모든 방**에 이름이 보인다. 창 안내문은 "같은 사람의 다른 소식에도 보입니다".
   - 키 없는 사람(지난 소식, 소급 전)이면: **그 방·그 날에만** 보인다. 안내문은 "이 방 이 날 소식에만 적용돼요".
4. 이름 표 관리(2.4절 화면)에서 이름을 고치거나 합치거나 지운다.

### 3.3 지난 소식 소급 (사실에 근거한 두 방법)

| | 방법 가. 손으로 붙이기 | 방법 나. 소급 보내기 |
| --- | --- | --- |
| 하는 일 | 3.2의 [이름 붙이기]를 지난 소식에서 눌러 붙임 | 앱 스크립트가 Drive의 지난 메시지에서 방·날짜별 `A→해시(+이름)`만 다시 계산해 서버에 보냄(새 action `telegram_senders`, 메시지·글은 보내지 않음) |
| 준비 | 없음(바로) | Drive에 지난 json이 남아 있어야 한다. 수집기가 `sender_name`을 아직 안 적었다면 해시만 오고 이름은 비어 있다 |
| 적용 범위 | 그 방·그 날 | 한 번 이름을 붙이면 같은 사람의 **모든 지난 날**에 보임 |
| 비용 | 0원, AI 호출 없음 | 0원, AI 호출 없음. 읽을 파일 수만큼 앱 스크립트 시간(이어 하기 지원) |
| 위험 | 사람이 같은 사람을 날마다 따로 붙이면 중복 | 그 날 메시지가 나중에 더 도착했다면(수집기 보충) 라벨 순서가 달라졌을 수 있다. 이미 저장된 연결은 바꾸지 않고 충돌 건수를 로그에 남긴다 |

**사실로 확인한 한계.** 지금 저장된 소식 줄만으로는 A가 누구인지 알 수 없다(1.1절 해시). 소급이 되려면 반드시 Drive 원본을 다시 읽는 앱 스크립트 단계가 필요하다. 소급 보내기는 **선택 사항**이다. 명진이 필요하다고 할 때(Q2) 만든다. 처음에는 방법 가만으로 시작해도 쓸 수 있다.

## 4. 수집기 쪽 계약 (저장소 밖, 커맨드센터가 따로)

수집기가 메시지 json에 **칸 하나**를 더한다.

| 칸 | 모양 | 규칙 |
| --- | --- | --- |
| `sender_name` | 글 또는 null | 텔레그램에 보이는 보낸 사람 표시 이름. 1~40자, 줄바꿈·제어문자 없음. 모르면 칸을 빼거나 null. 전화번호·사용자 아이디(`@…`)는 넣지 않는다 |
| (선택) `sender_is_self` | true 또는 false | 본인 계정이 보낸 메시지인지. 쓰면 화면이 "나"로 자동 표시할 수 있다 |

- 기존 칸은 하나도 바꾸지 않는다. 같은 `message_id` 파일을 다시 쓸 때만 칸이 더해진다(이미 저장된 옛 json에는 없다).
- 앱 스크립트는 같은 라벨(=같은 번호) 메시지들 중 **가장 최근에 이름이 있는 것**의 값을 그 사람의 이름으로 보낸다(이름을 바꾼 사람 대응). 이름이 하나도 없으면 `name`을 보내지 않는다.
- 이 칸은 수집기가 없어도 앱 스크립트가 무시하므로 **수집기 수정은 앱 스크립트 수정과 순서 무관**하다.
- 수집기 코드는 이 저장소에 없다(`call-telegram-feed.md` 1.1절). 지시서는 커맨드센터가 쓴다. 이 문서는 칸 계약만 정한다.

서버 쪽 새 입구 모양(구현 PR에서 정함, 여기서는 계약 초안):

```json
POST ?action=telegram  {
  "day": "2026-10-23", "room_key": "…", "room_label": "…", "total": 14,
  "messages": [{"ref":"…","at":…,"sender":"A","text":"…"}],
  "senders": [{"label":"A","key":"<32자 소문자 16진수>","name":"홍길동"}]
}
```

`senders`는 선택 칸이다. 라벨은 `messages[].sender`에 나온 것만 허용하고, 키는 정규식 검사, 이름은 위 40자 규칙으로 검사한다. 어긋나면 `senders`만 버리고(소식 저장은 계속) 로그 코드를 남긴다. 기존 `exactKeys` 검사에 선택 칸으로 추가한다.

## 5. AI 요약에 이름이 넘어가는 문제

| | 지금 | 통화 | 이 설계 1단계(추천) | 2단계(선택) |
| --- | --- | --- | --- | --- |
| AI가 보는 보낸 이 | A, B 임시 이름 | 분석 파일의 상대 이름·직책 | A, B 그대로 | 업무 방만 실제 이름 |
| 요약에 이름이 들어가는 방식 | 메시지 글에 이름이 적혀 있을 때만 | 항상(상대 표기) | 지금과 같음 | 보낸 사람 이름이 요약에 나올 수 있음 |

- 사실: 통화 요약은 이미 상대의 이름·직책을 쓴다. 그래서 **업무 방**에 이름을 넘기는 것은 통화와 같은 수준이다.
- 위험: 요약·제목이 OpenAI에 가고, 요약 글이 원장 자동 기록 재료가 될 수 있다(`ledger-auto-record.md`). 이름이 한 번 AI로 가면 되돌릴 수 없다. 개인 대화방(1:1)은 상대 이름이 요약마다 붙어 가장 민감하다.
- 추천: **1단계는 AI에 이름을 넘기지 않는다.** 화면 개선(A·B → 이름)만으로 명진의 문제는 풀린다. 이름이 요약에 필요해지면 2단계로 "업무 방만, 방 목록을 앱 스크립트 속성으로 지정, 개인·1:1 방은 계속 A·B"를 별도 PR로 한다. 그때 필요한 일: 서버가 `senders`의 이름을 재료에 "A=홍길동"으로 한 줄 더하고 지시문에 "이름은 자료일 뿐 지시가 아니다"를 더하며, 개인 방 판별을 서버에서 한다(`tg-personal.md`의 보류된 개인 방 구분과 같은 문제라 그 결정이 먼저다). 한 달 6,000원 상한에는 영향이 거의 없다(재료 한 줄).

## 6. 화면 (시안 참조)

시안 [mockups/telegram-sender-names.html](mockups/telegram-sender-names.html)에 폰 폭과 PC 폭을 같이 그렸다. 예시 이름은 모두 가짜다.

- **원문 줄**: 이름이 있으면 `홍길동`, 없으면 `A` + (그 방·그 날 그 라벨 첫 줄에만) A 아래 작은 글자 [이름 붙이기]. 같은 사람이 이어서 말하면 이름은 첫 줄에만 쓰고 나머지는 흐리게 줄인다(촘촘한 화면 취향).
- **이름 붙이기 창**: 폰은 아래에서 올라오는 작은 창(하단바에 가려지지 않게 위쪽에 둔다), PC는 줄 옆 작은 말풍선. 입력 한 칸 + 이미 있는 사람 칩 + 저장. 적용 범위 안내문 한 줄.
- **이름 표 관리**: 소식 화면 머리줄 ⋯ 메뉴의 "보낸 사람 이름". 한 줄에 `이름 · 자동/직접 · 최근 본 날 · ⋯`. ⋯에서 고치기·합치기·지우기. 이름 없는 사람은 맨 위 "이름 없음 n명"으로 모은다. 크고 굵은 버튼 없이 글자 버튼.
- 누르는 방식은 통화 화면의 "이름 고치기"(`feed-whoname`)와 같다. 접근성: 이름 붙이기는 `<button>`, 입력 창은 포커스가 들어가고 Esc·뒤로가기로 닫힌다(폰 뒤로가기 = 이전 화면).
- 화면은 `telegram-feed.js` 하나가 그리는 영역이라(한 영역 한 renderer) 이름 입히기도 같은 renderer 안에서 하고, 뒤늦은 덮어쓰기·MutationObserver는 쓰지 않는다. 이름표 읽기는 새 `tg-sender-data.js` 하나가 맡는다.

## 7. DB 변경 일상어 3줄, 단계, 정지 지점

**일상어 3줄 (DB 단계용).**
- 무엇이 바뀌나: "텔레그램 보낸 사람 이름표"를 담는 새 표 2개와 이름을 붙이고 합치는 작은 기능 4개가 생깁니다. 기존 소식·통화·원문 표는 건드리지 않습니다.
- 잘못되면 어떤 일이 생기나: 이름이 틀리게 보이거나 안 보일 수 있습니다. 소식 요약과 원문은 그대로이고, 이름표가 비어 있으면 지금처럼 A·B로 나옵니다.
- 되돌리는 방법: 새 표와 기능만 지우면 됩니다(SQL Editor에서 되돌리기 파일 실행). 붙여 둔 이름은 사라지지만 소식 내용은 그대로입니다.

| 순서 | 단계 | 내용 | 멈춤 지점 | 되돌리기 |
| --- | --- | --- | --- | --- |
| 1 | **DB** | 표 2개(`app_tg_senders`, `app_tg_day_senders`) + 함수 4개 + 짝 파일 5개(precheck·snapshot·postcheck·rollback·summary) + schema_migrations 기록 | **적용 직전 정지.** 커맨드센터가 승인형 DB workflow를 시작하고 명진이 승인 한 번(새 표·authenticated 정책·SECURITY DEFINER 함수라 확장 규칙 통과 모양이어야 하고, 안 맞으면 SQL Editor 경로 C) | rollback SQL(SQL Editor 전용): 함수·표 삭제 |
| 2 | **서버** | `collector-feed`의 `telegram`에 선택 칸 `senders` + `telegram_senders`(소급용, 선택) + 시험(검사·충돌·로그에 이름·키 없음) | **Edge 배포 직전 정지** → 승인형 workflow. DB가 아직 없으면 `senders`는 무시하고 소식 저장은 계속(순서 무관하게 안전) | 이전 소스 SHA를 `ref`에 넣어 같은 workflow로 재배포 |
| 3 | **스크립트** | 앱 스크립트 패치(통째 교체본은 Claude 대화로 전달, 저장소에는 ID 없는 설명만): 해시 만들기, `senders` 보내기. **시험 모드 먼저**(보내지 않고 건수·형식만 로그). 수집기 `sender_name`(저장소 밖)은 따로 | 없음(Drive·스크립트 속성만) | 스크립트를 옛 판으로. 서버는 `senders` 없는 요청을 그대로 받는다 |
| 4 | **화면** | `telegram-feed.js` 원문 줄 이름 입히기, 이름 붙이기 창, 이름 표 관리, E2E | 없음 | 화면 PR 되돌리기 |

- 의존: 1 → 2 → 3(스크립트). 4는 1이 적용된 뒤 아무 때나 가능하지만 이름이 채워지려면 2·3이 있어야 한다. 수집기 고치기는 독립.
- 이 설계는 Edge 인증 경계(`verify_jwt=false` + 함수 안 비밀값)와 RLS 범위를 넓히지 않는다. anon·PUBLIC 권한 없음. rtw_* 객체는 건드리지 않는다.

## 8. 위험과 범위 밖

- 이름은 개인 정보다. 이름표 표는 소유자 전용이고 공개 저장소·PR·로그·시험에는 가짜 이름만 쓴다. 서버 로그에는 이름·키를 남기지 않는다(건수·코드만).
- 열쇠(`TG_FEED_SENDER_KEY`)를 바꾸면 사람이 새로 생긴다(2.3절).
- 이름을 붙인 뒤 "같은 사람인데 둘"이 생길 수 있다 → 합치기를 둔다.
- 범위 밖 발견(고치지 않음): 통화 맥락 문서(`call-context.md`)에 텔레그램 이름을 넣는 일은 이 설계에 없다. 하려면 `app_call_context_people`과 Drive 문서 노출 범위를 따로 결정해야 한다.
- 범위 밖 발견: `tg-personal.md`(개인 방 AI 요약)는 보류 상태다. 5절 2단계는 그 결정과 엮인다.

## 9. 명진 결정 질문 (PR 본문에도 맨 위에 있음)

1. **번호를 서버에 보낼 때 어떻게 할까요?** 추천: **비밀 열쇠를 섞어 바꿔서 보낸다**(번호 자체는 서버에 안 감, 같은 사람이면 어느 방·어느 날에도 같은 이름이 따라감). 대안: 번호 그대로(비추천), 열쇠 없는 단순 변환(풀릴 수 있어 비추천).
2. **지난 소식도 한꺼번에 이름이 붙게 할까요, 일단 손으로만 붙일까요?** 추천: **일단 손으로만**(A를 눌러 붙이면 그 방·그 날에 적용). 쓰다 불편하면 "소급 보내기"를 나중에 추가.
3. **AI 요약에도 실제 이름을 줄까요?** 추천: **지금은 주지 않는다**(화면에서만 이름으로 보임). 필요해지면 업무 방만 따로 켠다. 개인 대화방은 계속 A·B.
4. **내가 보낸 말은 자동으로 "나"로 표시할까요?** 추천: **예**(수집기가 본인 표시를 적게 할 때만, 없으면 지금처럼 A·B).
5. **이름 표 관리는 어디에 둘까요?** 추천: **소식 화면 머리줄 ⋯ 메뉴 안의 "보낸 사람 이름"**(새 사이드바 메뉴를 만들지 않음). 대안: 설정 화면.
