# PERF-첫로딩 — Web2 첫 화면 로딩 줄이기 설계

상태: 설계(코드 변경 없음). 근거 main `2787ca5`(지시서 점검 기준은 `156a4f5`). 작업 세션 S47-53.

## 한 줄 요약

홈 한 화면을 보이기 전에 프로그램 파일 약 195개(2.2MB)를 **줄줄이(앞 파일을 받아야 다음 파일을 알 수 있는 순서로) 약 32단계에 걸쳐** 받는다. 느린 이유는 파일 "개수"보다 이 **줄 서기 깊이**와 **첫 화면에 필요 없는 기능까지 미리 받는 양**이다. 그래서 ② 자주 쓰는 화면만 먼저 불러오기(필요 없는 것 뒤로 미루기 + 줄 서기 펴기)를 먼저 하고, 다시 재서 목표에 못 미치면 ① 빌드 묶기를 더하는 순서(③의 단계적 진행)를 추천한다.

## 1. 지금 구조 (사실)

- 진입: `index.html` → `app.js`(일반 스크립트) → `import('./loader-v2.js')` → 공용 코어 → `view-loader.js` → 화면 모듈(`app/ARCHITECTURE.md` 1절).
- `loader-v2.js`는 시작 순서 규칙(세션 확인 → 경로 → 모듈 → 한 번에 보이기)을 지키려고 `await import(...)`를 차례로 건다: 런타임 → 로그인 보조 → 인증 → 세션 확인 → 공용 10개 → 상단·조직(`team.js` 75KB + 조직 자료 기다림) → 보기 설정 → `drive-summary.js`(await) → `wait-state.js` → `view-loader.js` → `area-window.js` → 화면 모듈.
- 화면 모듈 안에서도 정적 `import`가 깊다. 홈(`journal.js`)은 정적 import가 9단 깊이이고, 주간 보고·한글(HWPX) 내보내기·다음 주 시트 같은 기능 모듈 23개(약 475KB, `journal-hwpx.js` 122KB, `journal-weekly.js` 92KB 등)를 맨 위에서 정적으로 불러온다.
- `view-loader.js`의 `module(path)`는 `import(path)`처럼 **변수 경로**로 불러온다. 묶기 도구(esbuild 등)는 변수 경로를 따라가지 못한다(3절 ① 위험 참고).
- 캐시: Pages 빌드(`scripts/build-pages.mjs`)가 파일마다 내용 해시를 `?v=`로 붙이고, Cloudflare 라우터가 manifest와 바이트가 맞는 `?v=` 파일만 `max-age=31536000, immutable`로 내보낸다. 한 파일이 바뀌면 그 파일과 부모 사슬(`view-loader.js` → `loader-v2.js` → `app.js` → `index.html`)만 새로 받는다.
- 폰 앱은 같은 주소를 WebView(`LOAD_DEFAULT`, 일반 HTTP 캐시)로 연다. 서비스 워커(`sw.js`)는 요청을 가로채지 않는다(빈 fetch 처리기).
- 실기기 측정 도구가 이미 있다: 주소에 `?startup-debug=1`을 붙이면 오른쪽 아래 [로딩 기록 복사] 버튼이 생기고, 단계별 시각(`marks`)과 서버 요청 시간(`requests`)을 복사한다(`app/app.js`).

### 2-1. 방법

- 스크립트: `scripts/perf/first-load.spec.mjs`(Playwright, CI에서 돌지 않음), 운영 캐시 머리말 흉내 서버 `scripts/perf/serve-built.mjs`. 실행법은 스크립트 머리 주석.
- 대상: `git archive HEAD`를 `scripts/build-pages.mjs`로 빌드한 결과(운영과 같은 `?v=`). 로그인은 E2E 도우미(`tests/app-e2e/helpers/home-entry.mjs`)의 흉내 Supabase로 하고, 로그인 뒤 `/app/?view=<화면>`을 새로 연다.
- 잰 값: `#appView`에 `kptu-ui-ready`가 붙는 시각(화면 보임), 그 전까지 받은 같은 출처 JS 파일 수·풀린 크기(KB), 요청 시작 시각 묶음 수(100ms 넘게 쉬면 새 단계로 셈 = 줄 서기 깊이 근사). 조건마다 3번 재서 가운데 값.
- 조건
  - `local`: PC 화면, 네트워크 지연 없음 → "받기"를 뺀 실행 비용.
  - `phone`: 412×915, 왕복 150ms·내려받기 9Mbps(4G 흉내), CPU 4배 느리게, 캐시 없음 → 새 폰·캐시 빈 첫 방문.
  - `phone-warm`: `phone`과 같되 한 번 연 뒤 다시 엶. `?v=` 파일은 받은 내용 그대로 즉시 돌려줘 immutable 캐시 적중을 흉내 낸다(실기기의 디스크 읽기·V8 코드 캐시 이득은 빠짐).
- 한계(중요)
  - 자료(Supabase) 요청은 흉내 서버가 즉시 답한다. 숫자는 **프로그램 파일을 받고 실행하는 시간만**이다. 실제 홈은 여기에 자료 요청 시간이 더해진다(실기기는 `?startup-debug=1`로 함께 본다).
  - 로컬 서버는 HTTP/1.1(한 주소에 동시 6개)이다. 운영(Cloudflare)은 HTTP/2·3으로 한 연결에서 여러 파일을 받으므로, `phone` 숫자는 파일 수 때문에 생기는 손해를 **부풀려** 보여 줄 수 있다(추정).

## 3. 안 비교

### ① 빌드에서 화면별 묶기 (`scripts/build-pages.mjs`에 esbuild 등)

- 하는 일: 빌드 때 공용 바탕 하나 + 화면별 묶음으로 합치고, 공백·이름 줄이기. 저장소 소스는 그대로(번호 없는 경로, `?v=` 금지 유지). 묶음 파일도 기존 빌드가 내용 해시 `?v=`를 붙이고 manifest에 넣어 Cloudflare immutable 규칙을 그대로 쓴다.
- 효과(추정): E2 기준 크기 −30%, 첫 방문 −13% 안팎. 묶음 단위를 굵게(화면당 1개) 하면 더 줄 수 있으나 그만큼 ②의 "필요 없는 것 미루기"와 겹친다.
- 위험
  - `view-loader.js`의 변수 경로 `import(path)`를 글자 경로로 바꿔야 한다(안 하면 모듈 두 벌, E2-a). `${…}` 동적 경로·`import.meta.url`·`document.currentScript`를 쓰는 곳 전수 확인 필요.
  - **E2E 시험은 저장소 소스(묶기 전)를 띄운다.** 운영 코드와 시험 코드가 달라진다 → 빌드 결과로 도는 시험 묶음을 새로 둬야 한다.
  - **업데이트 때 다시 받는 양이 커진다.** 지금은 기능 파일 하나가 바뀌면 그 파일과 부모 사슬 몇십 KB만 새로 받는다. 묶으면 그 파일이 든 묶음 전체(공용 바탕이면 1MB 가까이)를 새로 받는다. 하루 여러 번 배포하는 지금은 폰 앱(WebView)·폰 브라우저 모두 "캐시 있음" 상태가 자주 깨진다.
  - 시작 순서(세션 확인 → 경로 → 모듈 → 한 번에 보이기)·화면 소유권: 묶어도 `await` 순서는 그대로라 규칙은 유지되지만, 정적 import 실행 순서가 바뀌는 곳(부작용 있는 모듈)을 확인해야 한다.
  - 업데이트 안내(`version-notice.js`)는 `index.html`의 `app.js` 해시로 새 판을 안다 → 영향 없음. `release-notes.json`은 그대로.
- 되돌리기: 빌드 옵션 한 줄(묶기 끔)로 지금 방식 빌드로 돌아가게 만든다. 소스가 그대로라 Pages 재배포만 하면 된다.
- 시험: 빌드 결과를 띄운 E2E 핵심 묶음(로그인·홈·사업영역·원장·화면 전환), `check-pages-build.mjs`에 "같은 모듈이 두 번 실리지 않음" 검사, 위 측정 스크립트.

### ② 자주 쓰는 화면만 먼저 불러오기 (지연 import + modulepreload)

- 하는 일
  1. 홈 첫 화면에 그리지 않는 기능(주간 보고 표·한글 내보내기·다음 주 시트·학습 패널 등)을 `journal.js` 맨 위 정적 import에서 빼고, 그 칸을 펼치거나 버튼을 누를 때 `import()`로 부른다. 후보 23개·약 475KB(실제로 첫 화면에서 쓰는지는 구현 PR에서 하나씩 확인). 사업영역(`team.js` 계열)·바탕(`global-search.js` 42KB, `topbar-actions.js` 41KB 등)도 같은 기준으로 본다.
  2. `loader-v2.js`의 차례 `await` 중 서로 기다릴 필요가 없는 것(예: `drive-summary.js` 불러오기, 화면 표시와 무관한 모듈)을 같은 단계 안에서 함께 부르거나 보인 뒤로 미룬다. **세션 확인 전에는 아무 기능 모듈도 부르지 않는다**는 규칙은 그대로다(모듈 단계 안에서만 펼침).
  3. 바탕의 핵심 파일(세션 확인 직후 반드시 받는 것 20~40개)만 빌드가 `index.html`에 `modulepreload`로 적는다. 손으로 쓰지 않고 `build-pages.mjs`가 정적 import 사슬로 계산해 `?v=`까지 붙인다(손 `?v=` 금지 규칙 유지). E1에서 보듯 전부 넣지 않는다.
- 효과(추정): 홈 보이기 전 파일 195 → 120개 안팎, 크기 2.2MB → 1.5MB 안팎, 단계 32 → 20 안팎. phone 첫 방문 8.8초 → 6초 안팎, phone-warm 2.1초 → 1.5초 안팎.
- 위험
  - 미룬 기능을 처음 누를 때 잠깐 기다림이 생긴다 → 기존 `wait-state.js` 표시를 쓰고, 기존 "쉬는 틈 미리 받기"(`view-loader.js`의 `warm`)에 그 모듈을 더해 거의 안 보이게 한다.
  - 시작 순서 규칙: `loader-v2.js`를 건드리므로 `app-initial-paint.spec.mjs`·`web2-anonymous-auth-gate.test.mjs`·`router-ready` 시험이 지켜 준다. 화면 소유권은 바뀌지 않는다(같은 renderer가 늦게 불릴 뿐).
  - 캐시·업데이트: 파일 단위 해시를 그대로 쓰므로 배포 때 다시 받는 양은 지금과 같다. 폰 앱 WebView도 그대로.
- 되돌리기: PR 단위 revert. 데이터·서버 영향 없음.
- 시험: 기존 E2E 전부(소스 = 운영 코드), 미룬 기능을 처음 누르는 시험 추가, 측정 스크립트 전후 비교.

### ③ 둘 다

- ②로 받는 양과 단계를 줄인 뒤 ①로 남은 바탕을 묶으면 효과는 가장 크다(추정 phone 첫 방문 5초 안팎).
- 위험은 ①의 위험을 그대로 더한다(시험 대상 분리, 배포마다 큰 묶음 재다운로드).

## 4. 추천

**③을 단계로: ② 먼저, 다시 잰 뒤 ①은 조건부.**

- 이유: 느림의 주된 원인이 줄 서기 깊이와 첫 화면에 필요 없는 양이라, 묶기(①)만으로는 13% 안팎에 그쳤다(E2). ②는 소스가 곧 운영 코드라 기존 시험이 그대로 지켜 주고, 배포 때 다시 받는 양도 늘지 않는다.
- ①은 ② 뒤에도 목표에 못 미칠 때만, 그리고 "배포마다 묶음 전체 재다운로드" 손해를 실기기 기록으로 따져 본 뒤 한다.

### 7-3. 같은 조건 3번 재기 — 흩어짐

- 전체 121칸 중 119칸이 한도 안. **파일 수·크기 칸은 모두 10% 안**(대부분 0~1%, 쉬는 틈 미리 받기와 겹치는 원장·사업영역 phone-warm이 3~6%).

### 7-4. 숫자로 본 것 (P2·P3·P5에 넘김)
