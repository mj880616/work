## 0. 명진용 요약

**만드는 것.** 이미 Drive에 있는 **통화 분석 파일**(앱 스크립트가 Gemini로 통화마다 만드는 `검토__…md`)과 **텔레그램 메시지 파일**에서 업무에 쓸 것만 골라 Web2 메뉴 두 개로 보여 준다. 두 메뉴는 사이드바 **맨 아래**에 둔다(명진 결정).

- **통화**: 업무 통화마다 제목 한 줄과 핵심내용을 보여 준다. **새 AI 판정을 만들지 않는다.** 제목, 핵심내용, 상대(조직)는 기존 통화 분석 결과에서 가져온다. 개인 통화는 Web2로 옮기지 않고 몇 건이었는지만 보여 준다.
- **텔레그램 소식**: 하루치 메시지를 방별로 묶어 중요한 것만 골라 말풍선 요약으로 보여 준다. 잡담은 거른다. 이쪽은 분석 파일이 없어서 Web2 서버의 AI가 한 번 판정한다.

**한 흐름.** 길은 하나다. 명진 님 계정의 앱 스크립트가 Drive에서 새 것만 읽어 Web2 서버로 보내고, 서버가 Web2 표에 저장한다. 두 메뉴와 바구니 쪽 AI는 모두 이 표를 읽는다.

**가장 큰 제약 (사실).** Web2가 받은 Drive 권한은 `drive.file` 하나라 수집기와 전사 스크립트가 만든 파일은 못 읽는다. 권한은 넓히지 않는다. 그래서 Drive 전체를 볼 수 있는 앱 스크립트가 **보내 준다**.

**이번에 확인된 사실이 바꾼 것.**
1. 통화는 이미 분석 파일이 있다(제목은 없고 핵심요약·약속 후보·결정 후보가 있다). 그래서 통화용 AI 판정을 Web2에 새로 만들지 않고 **분석 파일을 재료로** 쓴다. 비용이 줄어든다.
2. 분석에 "업무/개인/애매" 구분이 없으면 그 한 줄만 분석 안내문에 추가한다. 제목 한 줄도 같이 추가하자고 제안한다(명진 님이 앱 스크립트에 붙여 넣는다. 위치는 3.4절).
3. 전사본은 **줄바꿈 없는 한 문단이고 나/상대 구분이 없다.** 전문은 지금은 한 문단 그대로 보이고, 화자 구분은 전사 안내문을 고친 뒤 **새 통화부터** 생긴다. 상대를 특정할 수 있으면 '상대' 대신 소속조직·이름·직책으로 적는다(Q11, 4.5절).
4. 텔레그램은 **메시지 1개 = 파일 1개**다. 하루 800개면 파일 800개를 읽는다. 앱 스크립트가 날짜별·방별로 묶어 보내고, 시간 제한에 걸리면 다음 실행으로 이어 간다(6절).
5. 수집 폴더에 있던 `검토후보` 폴더와 AI 검토 상태 파일은 확인 결과(10/24) 새 흐름과 겹치지 않는다. 둘 다 그대로 둔다(Q9, 12.2절).

**개인 통화를 막는 장치.** 세 겹이다.
1. 명진 님이 정한 개인 번호·연락처 이름 목록은 앱 스크립트 단계에서 **전사 파일 이름**과 대조해 바로 거른다. 이 통화는 Web2로 가지 않는다(3.3절).
2. 통화 분석의 "업무/개인/애매" 구분이 업무인 것만 저장한다. 개인·애매·구분 없음은 개수만 센다.
3. 읽거나 해석하다 실패하면 아무것도 저장하지 않고 다음 실행 때 다시 시도한다.

**비용 (추정, 5절).** 통화는 Web2 AI를 쓰지 않아 **0원**이다(분석은 기존 Gemini가 이미 한다). 텔레그램만 하루 약 36원, 한 달 약 1,100원이고, 많은 날이 이어져도 한 달 3,000원 안팎이다. 이 기능 한 달 상한은 6,000원으로 결정되었다.

**순서.** ① DB(표) → ② 서버 함수 → ③ 앱 스크립트(통화부터, 그다음 텔레그램) → ④ 두 메뉴 화면 → ⑤ 바구니 AI·주간보고. ①과 ②는 멈춤 지점이라 각각 승인을 받는다(9절).

**결정은 모두 끝났다(Q1~Q8 10/23, Q9~Q13 10/24).** 결정 표는 12.1·12.2절에 있다.

## 1. 현재 수집 흐름 (사실)

아래 1.1~1.3은 커맨드센터가 Drive에서 확인한 **구조**다(이름·번호·내용은 쓰지 않았다). 이 세션이 직접 확인한 것이 아니다.

### 1.1 텔레그램 수집 저장 구조

| 항목 | 내용 |
| --- | --- |
| 만드는 곳 | 회사 PC 텔레그램 수집 프로그램(본인 계정 로그인). 이 저장소 밖에 있다. 업무방은 매일 07:30 한 번(`docs/ops/collector-heartbeat.md`) |
| 위치 | 수집 폴더 아래 `원문/<대화방 숫자 id>_<방 표시 이름>/messages/<YYYY-MM>/<message_id>.json` |
| 단위 | **메시지 1개 = JSON 파일 1개**. 한 파일은 약 0.5~0.8KB |
| 칸 | `attachment_path`, `attachment_pending`, `backfill`, `chat_entity_id`, `chat_name`, `chat_peer_id`, `date_kst`, `date_utc`, `edit_date_utc`, `file_extension`, `forwarded`, `grouped_id`, `media_type`, `message_id`, `original_filename`, `reply_to_message_id`, `sender_id`, `service_action`, `text` |
| 대화방 종류 | 단체방과 업무 관계자 1:1 대화(2026-10-20 명진 결정으로 수집) |
| 같은 수집 폴더의 다른 것 | `검토후보` 폴더, AI 검토 상태 파일(`telegram_ai_review_state_v2.json`, 약 550KB, 10/20까지 갱신), 수집 상태 파일(`telegram_drive_state.json`) |

- 이 구조에서 읽어낸 것: 하루 건수는 `date_kst`로 센다. 글 없이 첨부만 있는 메시지(`media_type`만 있고 `text` 없음)와 시스템 메시지(`service_action`)는 AI에 보내지 않고 개수에만 더한다. `forwarded`는 "전달된 글" 표시로 쓴다. `reply_to_message_id`는 묶음 안에서 답글 관계를 AI에 알려 주는 데 쓴다. `sender_id`는 실제 값을 보내지 않고 방·날짜마다 A, B, C로 바꿔 보낸다(시안의 원문 보기와 같다). `edit_date_utc`가 있는 수정 메시지는 처음 보낸 것을 유지한다(같은 `message_id`는 한 번만 저장).
- **`검토후보`와 AI 검토 상태 파일 (2026-10-24 확인, Q9).** `검토후보`는 텔레그램 수집 프로그램이 30분마다 AI 없이 규칙(문서 첨부 또는 핵심 단어)으로 만든다. 파일은 본문 없이 메시지를 가리키는 표다. `telegram_ai_review_state_v2`는 옛 ChatGPT 정기 검토(원장 후보 흐름)가 쓰던 것이고 10/20 이후 멈췄다(10/21 ChatGPT 예약 삭제). 둘 다 그대로 둔다(끄기·지우기 없음). 새 텔레그램 보내기(3-나)는 원문 메시지 파일을 직접 읽으므로 겹치지 않는다.

### 1.2 통화 전사

| 항목 | 내용 |
| --- | --- |
| 만드는 곳 | 폰 녹음을 클라우드 앱이 Drive에 올리고, 명진 님 Google 앱 스크립트가 Gemini API(무료 등급)로 전사한다. 10분 간격(사용자 진술). 저장소에는 그 코드가 없다 |
| 전사본 | 텍스트 파일 `통화 <상대 번호 또는 연락처 이름>_<YYMMDD>_<HHMMSS>.txt` |
| 내용 모양 | **줄바꿈 없는 한 문단이고 나/상대 구분 표시가 없다** |
| 녹음 원본 | m4a, 같은 이름 규칙 |

### 1.3 통화 분석 (이미 있음)

명진 님의 기존 Google 앱 스크립트가 Gemini로 통화마다 분석 파일을 만든다.

| 항목 | 내용 |
| --- | --- |
| 이름 | `검토__<원본 전사 이름>__SRC_<전사 파일 id>.md` |
| 앞머리(frontmatter) | `analysis_version`(현재 3.1), `status`(예: 검토대기), `source_type`(통화녹음), `source_txt_id`, `source_txt_name`, `source_txt_url`, `transcript_created_at`, `recording_datetime`, `analysis_model`, `analysis_at`, `has_candidates` |
| 본문 절 | 원본·자료유형·녹음일시 / 상대 이름·직책 / 주체 확인 / 판단 메모 / 핵심요약 / 약속 후보 / 결정 후보 / 후속확인 필요사항 / 중요 원문 / 애매하여 등록하지 않은 표현 / AI 메모 |
| 그 밖 | Drive 파일 설명(description)에도 `analysis_status=pending` 등이 들어간다 |

- 분석 파일에는 **제목 한 줄, 업무/개인 구분, 통화 길이**가 없다(위 목록에 없다). 제목은 핵심요약 첫 문장으로 대신하거나 안내문에 한 줄 추가하고(3.4절), 업무/개인 구분은 한 줄 추가한다. 통화 길이는 어디에도 없어서 화면에서 뺀다(시안 수정).
- `약속 후보`는 화면의 "예정", `결정 후보`는 "확정" 표시에 대응시킨다. 날짜·숫자는 분석 글을 그대로 옮긴다.

### 1.4 Web2 쪽 사실 (저장소 기준)

| 출처 | 만드는 곳 | 주기 | 근거 |
| --- | --- | --- | --- |
| 수집 점검 신호 | 별도 앱 스크립트 `Web2 수집 점검`(코드는 `docs/ops/collector-heartbeat.gs`). 시각과 건수만 보낸다 | 1시간마다 | `drive-summary` `POST ?action=heartbeat` |

- 작업지시 배경에는 "회사 PC 수집기가 두 가지를 모두 저장한다"고 되어 있었다. 저장소 문서에서는 **텔레그램만 회사 PC**이고 **통화 전사는 앱 스크립트**다. 이 문서는 저장소 문서와 커맨드센터 확인 사실을 기준으로 한다.
- Web2가 이 파일들을 읽는 경로는 지금 **없다**. 홈 화면 "마지막 수집 시각" 칸이 받는 것은 시각과 건수뿐이다(`drive-summary` `?action=status`의 `collectors`).
- Web2의 Drive 권한은 `drive.file` 하나다(`docs/design/drive-tree-permission-check.md` 1절). 바깥 프로그램이 만든 파일은 못 읽는다. BASKET-수집연동 행(2026-10-20 #796 조사)과 OPS-수집점검 행에서도 같은 판단이었다.
- 바구니 AI의 현재 모습: `ai-assist`(OpenAI Responses, 기본 모델 `gpt-6-luna`(단일 출처 `_shared/ai-model.ts`), 비밀값 `WEB2_OPENAI_API_KEY`)가 사용자 로그인 토큰으로 동작한다. 연결 요약, 챙길 것, 원장 후보, 자료실 채우기, 조직 요약, 일정 제목 다듬기를 처리한다. 비용 장치는 한 달 상한 `MONTHLY_LIMIT_KRW = 15000`과 `app_ai_daily_usage` 기록이다. 챙길 것 찾기는 이미 회의 `transcript_text`를 재료로 읽는다.
- 원장의 BASKET-수집연동 원래 요청(10/14)은 "둘 다 바구니 미분류로, 원문은 Drive, 바구니에는 출처·날짜·상대·원문 링크"였다. 이 문서는 그 요청을 **두 메뉴 + 바구니 AI 재료**로 바꾼다. 명진 님이 Q1 추천안으로 확정했다.
- OPS-텔레그램상태파일: 원장에는 아직 행이 없다. 2026-10-23 사용자 결정은 A안(회사 PC 수집기가 실행마다 상태를 남김)이다. Drive에 수집 상태 파일이 이미 있으니 건수는 거기서도 얻을 수 있다(8절).

## 2. 한 흐름 구조

```
[Drive 원본]
  텔레그램: 원문/<방>/messages/<월>/<message_id>.json  (메시지 1개 = 파일 1개)
  통화:     전사 txt (한 문단)  +  분석 md "검토__…__SRC_<전사 id>.md" (이미 있음)
      │  (Web2는 못 읽음 — drive.file)
      ▼
[앱 스크립트 "Web2 수집 보내기"]  명진 계정, Drive 전체 읽기
  · 허용 목록의 업무방만, 개인 번호·연락처 목록은 전사 파일 이름으로 대조해 거름(개수만)
  · 텔레그램: 날짜별·방별로 메시지 파일을 모아 묶음으로 보냄 (매일 08:10)
  · 통화: 새 분석 md를 읽어 앞머리·절을 그대로 보냄 + 전사 txt (1시간마다)
  · 어디까지 보냈는지 표시(스크립트 속성) → 새로 생긴 것만
      │  POST (전용 비밀값 헤더)
      ▼
[서버 함수 collector-feed]  (새 Edge, verify_jwt=false + 함수 안 비밀값 검사)
  · 통화: AI 호출 없음. 분석 md의 앞머리·절을 읽어 업무면 저장, 개인·애매·구분 없음은 개수만
  · 텔레그램: 묶음마다 AI 한 번(중요한 것 고르기 + 요약 + 조직 추천)
  · 같은 원본 키는 다시 저장 안 함
      ▼
[Web2 표]  app_feed_items(소식·통화 한 줄씩) · app_feed_days(하루 개수)   — 소유자 전용 RLS
      ├─▶ 통화 메뉴  (source=call)       — 사이드바 맨 아래
      ├─▶ 텔레그램 소식 메뉴 (source=telegram)  — 사이드바 맨 아래, 고정·지우기는 같은 표의 칸
      └─▶ 바구니 쪽 AI 재료: 챙길 것·원장 후보·주간보고
```

**왜 이 모양인가**

- **권한을 넓히지 않는다.** Drive를 읽는 쪽은 원래 Drive를 다 볼 수 있는 명진 님 앱 스크립트다. Web2는 받기만 한다. 수집 점검 신호(#906)에서 이미 쓰고 있는 방향이다.
- **통화는 새 AI 판정을 또 만들지 않는다.** 이미 통화마다 분석이 돌고 있다. 같은 일을 Web2 AI로 한 번 더 하면 돈이 들고, 두 분석이 다른 말을 하는 문제가 생긴다. 그래서 분석 파일을 **재료로 읽기만** 한다. 분석 파일은 고치거나 상태(`status`)를 바꾸지 않는다.
- **텔레그램은 AI가 한 곳에서 돈다.** 분석 파일이 없으므로 판정·요약은 Web2 서버 한 곳에서 한다. 판정 기준, 비용 상한, 사용 기록이 한 곳에 모인다. 기존 `검토후보`·AI 검토 상태 파일과는 겹치지 않는다(Q9).
- **바구니 메모로 복사하지 않는다.** 하루 수십 건이 바구니에 쌓이면 묻힌다. 대신 바구니 쪽 AI가 새 표를 **재료로 읽는다**(Q1 결정).
- **앱 화면은 서버 함수를 거치지 않는다.** 목록 읽기와 고정·지우기는 기존 화면처럼 로그인 토큰과 REST로 처리하고, 권한은 소유자 RLS가 막는다.

### 2.1 하루 흐름 예시 (가짜)

| 시각 | 일 |
| --- | --- |
| 07:30 | 회사 PC가 업무방 메시지를 Drive에 저장한다(기존, 메시지마다 파일 하나) |
| 08:10 | 앱 스크립트가 방별 폴더에서 어제 이후 새 파일을 모아 날짜·방별 묶음으로 보낸다. 서버는 묶음마다 AI를 한 번 부르고 중요한 것만 저장한다. `app_feed_days`에 "오늘 n개 중 m개 · 방 k곳"이 기록된다 |
| 매시 | 앱 스크립트가 새 통화 분석 파일을 찾아 한 건씩 보낸다. 개인 번호·연락처면 보내지 않고 개수만 센다. 서버는 분석의 업무 구분이 업무면 저장하고, 개인이나 애매면 개수만 센다 |
| 언제든 | 명진 님이 통화 메뉴와 텔레그램 소식 메뉴를 연다. 고정하거나 지우면 서버 표의 칸이 바뀐다 |

## 3. 개인 판정

### 3.1 판정 기준 (통화는 분석 안내문에 한 줄 추가, 텔레그램은 서버 AI 지시문 초안, 일상어)

| 판정 | 기준 | 예 (가짜) |
| --- | --- | --- |
| 업무 | 노조, 산하 조직, 기관, 교섭, 투쟁, 회의, 일정, 자료, 정책, 인사, 언론 중 하나라도 **구체적인 내용**이 있다 | "○○지부 교섭 다음 주 화요일로 미뤄짐", "자료 금요일까지 보내기로" |
| 개인 | 가족, 친구, 병원, 택배, 쇼핑, 광고·스팸, 사적 약속, 안부만 | "저녁 뭐 먹을까", 카드사 안내 |
| 애매함 | 업무 관계자와 나눈 안부만 있다. 너무 짧다. 전사가 깨져서 내용을 알 수 없다. 판단 근거가 없다 | 30초 미만 통화, "네네 나중에 다시 걸게요" |

- **업무와 개인이 섞인 통화**는 업무로 옮긴다. 핵심내용에는 업무 부분만 쓴다. 다만 전문에는 개인 부분도 들어간다(질문 Q3).
- 통화의 "업무/개인/애매"는 **기존 분석 결과의 한 줄**이다(3.4절). 서버가 새로 판정하지 않는다. 위 표는 그 한 줄을 만드는 분석 안내문에 넣을 기준이기도 하다.
- 텔레그램은 방 단위로 이미 업무방만 보낸다. 그래서 AI가 하는 일은 메시지 묶음 중 **중요한 소식만 고르는 것**이다. 잡담, 인사, 이모티콘, 단순 "확인했습니다"는 버린다. 버린 메시지는 Web2에 저장하지 않는다.

### 3.2 실패할 때 안전한 쪽 (제안)

| 상황 | 처리 | 화면 |
| --- | --- | --- |
| 개인 번호·연락처 목록에 있음 | 앱 스크립트가 보내지 않는다. 서버는 개수만 받는다 | "개인 통화 n건 걸러짐" |
| 분석의 업무 구분이 개인 또는 애매, 또는 구분 줄이 없음(분석 안내문 수정 전 파일) | 저장하지 않는다. 개수만 센다(개인과 애매함을 따로 센다. 구분 없음은 애매로 센다) | 같은 줄. 누르면 "개인 n · 애매 m"과 안내 한 줄만 보인다 |
| 통화 분석 파일 모양이 다름(버전이 3.x가 아님, 절 이름이 없음) | 저장하지 않는다. "판정 실패"로 센다. 분석 안내문이 바뀌면 서버 해석을 맞춰야 한다 | 머리줄 끝에 "판정 실패 n" |
| 텔레그램 AI 오류, 시간 초과, 답 형식 틀림 | **아무것도 저장하지 않는다.** 앱 스크립트는 그 건을 "안 보냄"으로 두고 다음 실행에서 다시 보낸다. 3번 실패하면 넘기고 "판정 실패" 개수에 더한다 | 머리줄 끝에 "판정 실패 n" (있을 때만) |
| 한 달 AI 상한 도달 | 저장하지 않고 다음 달까지 기다린다. 앱 스크립트는 "안 보냄"을 유지한다 | 같은 줄에 "AI 한도" |
| 분석 파일이 아직 없거나 전사본이 비어 있음 | 보내지 않고 다음 실행에서 다시 찾는다. 분석이 끝나야 보낸다 | 없음 |
| 텔레그램 묶음에 글 없는 메시지(첨부만, 시스템)만 있음 | AI에 보내지 않고 건수에만 더한다(비용 절약) | 오늘 n개 숫자에 포함 |
| 비밀값이 새어 가짜 내용이 들어옴 | 서버는 형식, 크기, 하루 상한만 막을 수 있다. 비밀값을 지우면 그 즉시 입구가 닫힌다 | 해당 없음 |

**원칙: 애매하면 옮기지 않는다.** 업무 통화를 놓칠 위험은 남는다. 대신 Drive 원본은 그대로 있으니 나중에 명진 님이 Drive에서 찾을 수 있다. 개인 통화가 업무로 잘못 옮겨지는 반대 방향의 실수가 더 나쁘다고 본다.

### 3.3 개인 번호 목록 대조 (1단계)

- 전사 파일 이름에 **상대 번호 또는 연락처 이름**이 들어 있다(`통화 <번호 또는 이름>_<날짜>_<시각>.txt`). 그래서 앱 스크립트가 전사 파일 이름의 그 부분을 명진 님의 개인 목록과 **이름으로 대조**할 수 있다. 번호는 하이픈과 공백을 지운 숫자만 비교한다. 연락처 이름은 글자 그대로 비교한다.
- 목록에 있으면 그 통화는 분석 파일을 읽지도, 보내지도 않는다. 개수만 센다.
- 목록은 앱 스크립트 안에만 둔다. 저장소, 채팅, PR에 쓰지 않는다. 목록에 없는 개인 통화는 2단계(분석의 업무/개인 구분)가 맡는다.
- 한계: 업무 관계자가 개인 일로 걸거나, 모르는 번호로 온 개인 통화는 1단계로 못 거른다.

### 3.4 통화 분석 안내문에 추가할 한 줄 (명진 님이 앱 스크립트에 붙여 넣음)

> **2026-10-24 명진 결정:** 통화 전사·분석 앱 스크립트는 요청함 밖 Claude 대화에서만 고친다. 그 대화에서 분석 v3.2(`is_work_related`·`call_title`·`related_organizations`, 개인은 `status: "개인"`)를 이미 적용했으므로 #1111의 3.3 수정안(`docs/ops/call-prompts-patch.md`)은 쓰지 않고, Web2 서버·보내기 스크립트가 v3.2를 그대로 읽는다. 구분: `is_work_related` 참 → 업무, 거짓 또는 `status: "개인"` → 개인(개수만), 칸 없음·비어 있음(옛 3.1 포함) → 구분 없음(개수만).

기존 통화 분석 앱 스크립트(Gemini 분석 안내문이 들어 있는 것)를 고친다. 이 세션은 그 코드를 읽지 못했다. 그래서 정확한 줄 번호는 3번 PR에서 코드를 받아 확정하고, 여기에는 **위치와 문구**만 적는다.

| 어디에 | 무엇을 | 문구(안) |
| --- | --- | --- |
| 분석 안내문의 "출력 형식" 중 앞머리(frontmatter) 항목 목록 맨 끝 | 칸 두 개 추가 | `work_class:` (업무 / 개인 / 애매 중 하나), `call_title:` (통화 제목 한 줄, 40자 안쪽, 날짜·숫자는 통화에 나온 그대로) |
| 같은 안내문의 "판단 메모" 절 지시 바로 위 | 판정 기준 한 문단 | 3.1절 표의 업무·개인·애매 기준을 그대로 옮긴다. 업무와 개인이 섞이면 업무로 하고 핵심요약에는 업무 부분만 쓴다 |
| 안내문 속 `analysis_version` 값 | 3.1 → 3.2로 올림 | 서버가 "구분 줄이 있는 버전"을 알아보는 표시 |

- 지금 파일에 이미 업무/개인을 가리키는 칸이 있으면 그것을 쓰고 새 칸은 만들지 않는다. 3번 PR에서 코드를 보고 정한다.
- 이 수정은 Gemini 호출 횟수를 늘리지 않는다(같은 호출에 칸 두 개 추가). 기존 `status`, Drive 설명의 `analysis_status`는 그대로 둔다.
- 서버는 `call_title`이 없으면 핵심요약 첫 문장(80자까지)을 제목으로 쓴다. `work_class`가 없으면 애매로 센다.

### 3.5 "개인 통화 n건 걸러짐 ›"을 누르면

- **결정 (Q2-①): 개수와 안내만 보여 준다.** "개인 n건 · 애매 m건 · 원본은 Drive 통화 녹음/전사 폴더에 있습니다." Web2에는 그 통화의 시각, 길이, 상대가 남지 않는다.
- 채택하지 않은 안 (Q2-②): 살리기를 허용한다. 서버가 걸러진 건의 **불투명 번호**(내용·이름·시각 없음)만 저장한다. 명진 님이 [이 날 걸러진 것 다시 보기]를 누르면 앱 스크립트가 다음 실행에서 해당 건을 "업무로 보기" 표시와 함께 다시 보낸다. 살리기 목록 화면에 시각과 길이 정도는 보여야 고를 수 있어서 결국 Web2에 흔적이 남는다. 또 앱 스크립트가 서버에서 "다시 보낼 목록"을 읽어 와야 해서 길이 하나 더 생긴다.

## 4. 저장 구조와 DB 변경안

### 4.1 원문을 어디에 둘까 (비교)

| | A. 원문은 Drive에만 | **B. 업무로 판정된 것만 Web2에 사본 (추천)** |
| --- | --- | --- |
| 통화 "전문 펼치기" | Web2에서 못 보여 준다. Drive 파일 링크만 연다(앱 스크립트가 파일 링크를 함께 보내야 함) | 바로 펼쳐진다. 지금 전사본은 한 문단 그대로(4.5절) |
| 텔레그램 "원문 보기" | 메시지마다 파일이 따로라 한 묶음의 원문을 한 번에 열 링크가 없다 | 그 소식의 원문 n개만 보인다 |
| 개인정보 | Web2에는 요약만 남는다 | 업무 원문이 Web2 DB에 남는다(소유자 전용 RLS). 개인·애매함은 B안에서도 남지 않는다 |
| 바구니 AI 재료 | 요약만 쓸 수 있다 | 원문도 쓸 수 있다(챙길 것 찾기의 정확도가 올라감) |
| 용량 | 거의 없음 | 하루 수십 KB 수준(추정), 한 해 수십 MB 이하 |

명진 님이 승인한 화면(전문 펼치기, 짧게 눌러 원문)은 B안이어야 그대로 나온다. 그래서 **B안을 추천**한다. Drive 원본은 지우지 않고, Drive 링크는 함께 저장한다.

### 4.2 표 (DB PR `20261024140000_call_tg_feed`에서 만듦)

**`app_feed_items`**: 통화 한 건 또는 텔레그램 소식 한 묶음이 한 줄이다.

| 칸 | 뜻 |
| --- | --- |
| `id` uuid, `workspace_id` uuid | 기존 표와 같다. 업무공간은 서버가 `kptu-work`로 정한다 |
| `source` text check in (`call`, `telegram`) | 출처 |
| `day` date (한국 날짜), `occurred_at` timestamptz | 날짜 구분과 시각 |
| `room_key` text, `room_label` text | 텔레그램 방 구분값과 표시 이름. 통화는 비운다 |
| `title` text (≤ 80자) | 통화 제목 한 줄(분석의 `call_title`, 없으면 핵심요약 첫 문장). 텔레그램은 비워 두거나 요약 첫 줄을 쓴다 |
| `summary` text (≤ 400자) | 텔레그램 말풍선의 한두 줄 |
| `points` jsonb (문자열 배열, ≤ 8개) | 통화 핵심내용 점 목록. 날짜·숫자·"예정/확정"을 그대로 둔다 |
| `counterpart` text null (≤ 100자) | 통화 상대 표기. 재료는 전사 파일 이름의 연락처 이름과 분석의 "상대 이름·직책" 절이고, 소속은 Web2 담당조직 이름과 확실히 맞을 때만 붙인다(`소속조직 이름 직책` 모양, Q11). 모르면 비운다. 통화만. 개인 연락처가 아니라 업무 상대라서 저장하지만, 공개 문서에는 쓰지 않는다 |
| `speaker_split` boolean | 전문이 화자별 줄인지. 줄 머리는 `나:`와 상대 표기(`counterpart`와 같은 글), 모르면 `상대:`, 헷갈리면 `화자1:`/`화자2:`. 옛 전사본은 false(4.5절) |
| `raw_text` text (≤ 200 KB) | 업무로 판정된 원문 사본(4.1 B안). 통화는 전사본(옛 것은 한 문단, 새 통화부터 화자별 줄: 4.5절), 텔레그램은 메시지 n개 |
| `raw_count` int | 텔레그램 원문 개수 |
| `organization_id` uuid null | 조직 연결(Q4). 통화는 상대 글과 담당조직 이름 대조, 텔레그램은 서버 AI 추천. 명진 님이 바꿀 수 있다 |
| `suggested_project_id` uuid null | 서버 AI가 추천한 프로젝트(서버만 쓴다) |
| `project_id` uuid null | 명진 님이 상세에서 확정한 프로젝트(화면만 쓴다, Q4) |
| `source_ref` text | 원본을 가리키는 불투명 키. 통화는 전사 파일 id(`source_txt_id`), 텔레그램은 방 폴더와 날짜의 해시. 중복 방지에 쓴다 |
| `drive_url` text null | Drive 원본 링크 |
| `pinned_at`, `hidden_at` timestamptz null | 고정과 지우기 |
| `model`, `judged_at`, `created_at`, `updated_at` | 기록. 통화는 `model`에 분석 모델 이름(`analysis_model`), `judged_at`에 `analysis_at`을 쓴다 |
| unique (`workspace_id`, `source`, `source_ref`) | 같은 원본은 한 번만 저장한다. "요약은 한 번만"을 DB가 보장한다 |

**`app_feed_days`**: 하루·출처마다 한 줄이다(머리줄 숫자).

| 칸 | 뜻 |
| --- | --- |
| `workspace_id`, `day`, `source` (기본 키) | |
| `total_count` | 텔레그램은 그날 받은 메시지 수, 통화는 전사본 수 |
| `kept_count` | 저장한 소식·통화 수 |
| `room_count` | 텔레그램 방 수 |

| `updated_at` | |

- 분석 파일의 "애매하여 등록하지 않은 표현", "AI 메모", 판단 메모는 Web2로 가져오지 않는다(개인 내용이 섞일 수 있어 필요한 절만 가져온다). 가져오는 절은 상대, 핵심요약, 약속 후보, 결정 후보, 후속확인 필요사항, 그리고 필요하면 중요 원문뿐이다.

방 색은 저장하지 않는다. 화면이 `room_key`로 톤다운 색 6개 중 하나를 정해서 늘 같은 방이 같은 색으로 보이게 한다. 방별 태그는 Q6 결정 뒤에 정한다.

### 4.3 권한 (기존 소유자 정책과 같게)

- 두 표 모두 `enable row level security`. `revoke all … from public, anon, authenticated, service_role` 뒤에 필요한 것만 다시 준다(`20261023140000_weekly_exec_requests.sql`과 같은 형식).
- authenticated(로그인한 본인): 두 표 `select`, 그리고 `app_feed_items`의 `update (pinned_at, hidden_at, raw_text, organization_id, project_id, updated_at)` **칸만**. `raw_text`는 비우기(전문 지우기, Q3)만 되고 트리거가 다른 값으로 바꾸기를 막는다. 연결한 조직·프로젝트는 같은 업무공간인지 트리거가 모든 역할에 똑같이 검사한다. insert와 delete는 주지 않는다. 정책은 표마다 하나다: `for all to authenticated using/with check (private.app_is_workspace_owner(workspace_id))`.
- 서버 함수: `collector-feed`에는 사용자 로그인이 없다(앱 스크립트가 부름). 그래서 저장은 service role로 한다. service role에도 **`app_feed_items`는 칸별 insert(고정·지우기·확정 프로젝트 칸 제외)와 중복 확인 세 칸(`workspace_id`, `source`, `source_ref`) 읽기만, `app_feed_days`는 읽기·insert·숫자 칸 update만** 준다. 소식 줄 고치기·지우기와 원문 읽기는 없다. 모든 요청에 `workspace_id`를 서버가 정해 넣는다. drive-summary `text_backfill`이 `app_documents` 글자 칸에 쓰는 방식과 같은 선례다. anon·PUBLIC 권한, 공개 정책, RLS 끄기, 기존 정책 교체는 없다(확장 규칙 거절 대상이 아님). 새 표에 대한 grant라서 기존 권한을 넓히는 것이 아니다.
- AI 사용 기록: `ai-assist`처럼 `app_ai_daily_usage`에 더해서 한 달 상한을 함께 쓴다. 이 표에 service role이 쓰는 권한이 지금 있는지는 **확인 필요**다. 없으면 DB PR에 그 표의 service role insert/update를 넣을지, 별도 사용 기록 칸을 `app_feed_days`에 둘지를 정해야 한다. 추천은 **후자**다. 기존 표의 권한을 건드리지 않는다. (DB PR에서 후자로 만들었다: `app_feed_days.ai_*`.)
- `room_label`, `raw_text`, `points`는 화면에 그릴 때 글자로만 넣는다(HTML 해석 금지). 바깥에서 들어온 글이기 때문이다.

### 4.4 서버 함수 `collector-feed` (Edge PR에서 만들 것, 지금은 제안)

- `verify_jwt=false`. 대신 함수 안에서 `x-collector-feed-secret`을 새 비밀값 `COLLECTOR_FEED_SECRET`과 비교한다(heartbeat와 같은 SHA-256 고정 길이 비교). **heartbeat 비밀값과 따로 둔다**: heartbeat 비밀값은 시각만 쓸 수 있고, 이 비밀값은 내용을 넣을 수 있어 힘이 더 크다. 사용자 JWT, 예약 비밀값, heartbeat 비밀값은 이 함수에서 모두 401이다.
- `POST ?action=call`: 본문 `{ref, analysis_md, transcript, drive_url}`, 합계 200 KB 이하. `analysis_md`는 분석 파일 전체 글이고 `transcript`는 전사 txt 글이다. **AI를 부르지 않는다.** 서버가 앞머리(`analysis_version`, `work_class`, `call_title`, `recording_datetime`)와 정해진 절(상대, 핵심요약, 약속 후보, 결정 후보, 후속확인)을 읽어 업무면 저장하고 개인·애매·구분 없음이면 개수만 센다. 상대 글이 Web2 조직 이름과 글자로 맞으면 조직을 연결하고, 맞지 않으면 비워 둔다(Q4 결정은 텔레그램에서 AI 추천, 통화는 글자 대조만).
- `POST ?action=call_skip`: `{day, personal:n, short:n}`. 앱 스크립트가 개인 번호로 거른 수만 보낸다.
- `POST ?action=telegram`: 본문 `{day, room_key, room_label, total, messages:[{ref, at, sender, text, reply_to, forwarded}]}`, 방 하나의 하루치(`date_kst` 기준), 200 KB 이하. `sender`는 A, B, C 같은 방·날짜별 임시 이름이다. 크면 앱 스크립트가 같은 방을 여러 묶음으로 나눈다. AI는 묶음마다 한 번만 부른다.
- 응답은 `{ok, kept, personal, unsure}` 같은 개수와 단계 코드뿐이다. 원문, 요약, 오류 원문은 응답과 로그에 넣지 않는다.
- 하루 상한: 통화 50건, 텔레그램 묶음 80개(넘으면 429). 비밀값이 새었을 때 비용 폭주를 막는다.
- 텔레그램 AI 모델과 열쇠는 `ai-assist`와 같은 `WEB2_OPENAI_API_KEY`·`WEB2_AI_MODEL`을 쓴다. 판정·요약 답은 엄격한 JSON 형식으로 받고, 형식이 틀리면 저장하지 않는다.

### 4.5 통화 전문의 화자 구분 (나/상대)

> **2026-10-24 명진 결정:** 화자 구분은 전사 앱 스크립트를 고치는 요청함 밖 Claude 대화로 요청한다(Web2 보내기 스크립트는 전사를 고치지 않고 그대로 보낸다). 그 전까지 전사는 한 문단(`speaker_split=false`)이다. 상대 표기는 분석 머리의 상대 이름·직책과 `call_title`에서 확실할 때만 쓴다.

- 지금 전사본은 **줄바꿈 없는 한 문단이고 나/상대 표시가 없다.** Web2가 나중에 나누려면 AI가 문단을 다시 써야 하고(하루 약 20원 추가, 틀릴 수 있음) 원문과 달라질 위험이 있다.
- **결정 (가), 2026-10-24 (Q11): 전사 안내문(Gemini 전사 앱 스크립트)에 화자 구분을 넣게 고친다.** 새 통화부터 화자별 줄로 나뉜다. 옛 전사본은 그대로 한 문단이다(Q12).
- **상대 표기 (명진 보완).** 상대를 특정할 수 있으면 `상대:` 대신 소속조직·이름·직책으로 적는다(예: `가상노조 홍길동 위원장:`). 재료는 전사 파일 이름의 연락처 이름과 분석의 "상대 이름·직책" 절이다. 소속은 Web2 담당조직 이름과 확실히 맞을 때만 붙이고, 아니면 이름·직책만 쓴다. 누군지 모르면 `상대:`, 누가 "나"인지 헷갈리면 `화자1:`/`화자2:`로 적는다. 새 AI 호출은 없다(기존 전사·분석에서 나온 글을 쓴다).
- 같은 표기를 `counterpart` 칸에도 넣는다. 고친 뒤 통화 몇 건으로 먼저 맞는지 본다. 수정 위치는 전사 앱 스크립트의 전사 안내문이며, 분석 안내문(3.4절)과 같은 작업(3-가)에서 코드를 받아 문구를 정한다.
- (나안, 채택 안 함) 한 문단 그대로 보여 주기.
- 화면은 `speaker_split`이 false이면 한 문단으로, true이면 줄 단위로 보인다(줄 머리는 위 표기 그대로). 시안(가)(다)에 두 모양을 모두 넣었다. 한 문단 모양에는 "화자 구분은 전사 수정 뒤" 표시가 붙는다.
- 핵심내용·제목은 분석 파일이 만들기 때문에 화자 구분과 상관없이 먼저 나온다.

## 5. AI 비용 추정 (2판: 통화는 Web2 AI 없음)

통화는 기존 분석 파일을 읽기만 하므로 **Web2 서버 AI 비용이 0원**이다. 분석 안내문에 칸 두 개를 더하는 것은 같은 Gemini 호출 안에서 처리되어 호출 수가 늘지 않는다(Gemini 무료 등급 안, 추정). 전문 화자 구분을 전사 안내문에 넣어도 같은 호출이다.

텔레그램만 Web2 AI(OpenAI)를 쓴다. 가정은 이렇다(추정). 업무방 메시지 하루 800개, 개당 약 60자로 48,000자다. 글 없는 메시지(첨부, 시스템)는 AI에 보내지 않으므로 실제는 더 적다. 한글은 대략 글자 1개가 토큰 1개 안팎이다. 가격은 저장소 기본값(입력 100만 토큰당 350원, 출력 100만 토큰당 2,800원, `ai-assist` 기본 설정)을 쓴다. 실제 가격은 운영 설정값에 따라 다를 수 있다.

| | 들어가는 글(토큰) | 나오는 글(토큰) | 하루 비용 |
| --- | --- | --- | --- |
| 통화 5건(분석 파일 읽기) | 없음 | 없음 | **0원** (1판 약 14원) |
| 텔레그램 800개(방별 묶음, 중요한 것 고르기 + 요약) | 약 5만 + 지시문 0.5만 | 약 0.6만 | 약 36원 |
| **합계** | | | **약 36원/일, 한 달 약 1,100원** (1판 약 1,500원) |

- 많은 날(메시지 2,500개)이 매일 이어지면 하루 약 100원, 한 달 3,000원 안팎이다(1판 4,500원).
- 이 기능 한 달 상한은 **6,000원 따로**로 결정되었다(Q7). 위 추정은 그 절반 이하다. 더 줄일 수 있지만 결정은 바꾸지 않고 둔다.
- 서버 쪽 저장 비용은 따로 없다(표 몇 줄).
- 통화 전문을 Web2 AI가 "나/상대"로 다시 써 주는 안은 하루 약 20원이 더 들고 틀릴 수 있어서 쓰지 않는다(4.5절).

## 6. 예약 실행 방식

| 무엇 | 누가 | 언제 | 이유 |
| --- | --- | --- | --- |
| 텔레그램 하루치 보내기 | 새 앱 스크립트 `Web2 수집 보내기`의 시간 트리거 | 매일 08:10 (07:30 수집 뒤) | "하루 한 번 묶어서" 결정. 수집 시각이 바뀌면 이 시각도 바꾼다 |
| 새 통화 분석 보내기 | 같은 스크립트 | 1시간마다 | 전사(10분 간격) 뒤 분석이 끝나면 1~2시간 안에 보인다. 건마다 한 번만 보낸다 |
| 어디까지 보냈는지 | 스크립트 속성("마지막으로 본 시각" + 실패 건 목록) | | Drive 파일을 고치지 않는다. 분석 파일의 `status`도 건드리지 않는다 |
| 점검 | 기존 홈 "마지막 수집 시각" 칸에 줄 하나 추가 제안: "소식·통화 정리" 마지막 성공 시각 | | 조용히 멈추는 것을 알아채기(OPS-수집점검과 같은 목적) |

**텔레그램을 하루 묶음으로 보내는 방법 (메시지 파일 1개 = 1메시지 구조에 맞춤)**

1. 허용 목록에 있는 방 폴더만 하나씩 연다. 방마다 `messages/<이번 달>/`(월이 바뀌는 날은 전달도)에서 **마지막으로 본 시각 이후 만들어진 파일**만 Drive 검색(수정 시각 조건)으로 찾는다. 폴더 전체를 매번 열지 않는다.
2. 찾은 파일을 읽어 `date_kst`가 같은 것끼리, 방별로 묶는다. `message_id` 순서로 정렬한다.
3. 글 없는 메시지와 시스템 메시지는 빼고 건수에만 더한다. `service_action`이 있으면 건너뛴다.
4. 한 묶음이 200 KB를 넘으면 쪼개서 여러 번 보낸다. 묶음마다 서버가 AI를 한 번 부른다.
5. 하루 800개면 파일 800개를 읽는다. 파일 한 개 읽기에 0.1~0.3초라고 보면 2~4분이다(추정, **시험 필요**). 앱 스크립트 한 번 실행은 6분을 넘을 수 없어서, 실행마다 5분 안에서 멈추고 못 한 방은 다음 실행(10분 뒤 보조 트리거)이 이어서 한다.
6. 어제 이후 새로 쓰인 파일이 없는 방은 건너뛴다. `backfill` 표시가 있는 메시지는 `date_kst`가 오래된 날이어도 그 날짜 묶음으로 보낸다(처음 연결할 때 과거분이 몰려오지 않게 "시작일"을 정해 그 이전은 가져오지 않는다. 시작일은 3번 PR에서 정한다).

- GitHub Actions 예약은 쓰지 않는다. Web2 서버는 Drive 원본을 못 읽으므로, 원본을 읽을 수 있는 쪽(앱 스크립트)이 시작해야 한다.
- 앱 스크립트는 기존 `Web2 수집 점검`과 **따로** 만든다. 점검 신호는 내용을 보내지 않는 작은 스크립트로 남긴다. 비밀값도 다르다.
- AI 응답 시간 때문에 앱 스크립트의 외부 호출 대기 한도에 걸리는지는 **시험 필요**다(묶음을 작게 해서 피한다).
- **수집 대상에서 빼는 것**: 개인 용도로 따로 수집하는 대화(업무 밖 수집분)는 이 흐름에 절대 들어오지 않게 한다. 앱 스크립트는 **허용 목록에 적힌 업무방 폴더/방만** 읽는다. 허용 목록은 스크립트 안에만 두고 저장소에는 쓰지 않는다. 업무 관계자 1:1 대화방은 허용 목록에 넣을지 방마다 명진 님이 정한다.
- **`검토후보` 폴더와 AI 검토 상태 파일**은 이 앱 스크립트가 읽거나 고치지 않는다. 원문 메시지 파일을 직접 읽으므로 겹치지 않는다(Q9 결정, 둘 다 그대로 둔다). 검토되지 않은 옛 후보는 처리하지 않는다.

## 7. 바구니 수집연동과 어떻게 합치나

- BASKET-수집연동의 원래 목표는 "가치 있는 것을 놓치지 않고 Web2로"였다. 그 목표는 두 메뉴가 받는다. 바구니 미분류 메모로는 복사하지 않는다(2절 이유).
- 바구니 쪽 AI 연결(⑤단계, Q1·Q5 결정 뒤):
  - **챙길 것 찾기**(`todo_radar`): 지금처럼 메모와 회의 전사본을 읽고, 여기에 `app_feed_items`(지우지 않은 것) 최근분을 재료로 더한다. 통화에서 나온 "금요일까지 자료"가 할 일 후보가 된다.
  - **원장 후보**(`ledger_candidates`): 같은 방식으로 재료에 더한다. 원장 행은 지금처럼 명진 님이 [확정]해야 생긴다.
  - **주간보고**: 고정된 소식과 업무 통화 핵심내용을 주간보고 재료 목록에 넣을지는 Q5다.
- DRIVE-바구니원문제외와의 관계: Drive 읽기용 사본에는 이 표의 원문이나 요약을 **싣지 않는다**. 같은 결정의 연장선이다. 바깥 AI에 원문을 내보내지 않는다.

### 12.3 필요한 정보 (질문이 아니라 정보)

- 개인 번호·연락처 이름 목록: 전사 파일 이름에 번호나 연락처 이름이 들어 있으니 이름으로 대조할 수 있다(3.3절). 목록은 앱 스크립트 안에만 두고 저장소나 채팅에는 쓰지 않는다. 설치(3-가) 때 명진 님이 직접 붙여 넣는다.
- 업무 관계자 1:1 대화방 중 어느 방을 허용 목록에 넣을지(설치 때, 방 이름은 스크립트 안에만).
- 통화 분석 앱 스크립트와 전사 앱 스크립트의 코드 중 **안내문 부분** (3-가에서 받는다. 비밀값이 있으면 빼고 준다).

## 부록. 통화 분석 v3.3 대응 (CALL-통화v3.3대응)

- 기준 형식이 v3.3(2026-10-24 19:30 적용)이다. 3.1·3.2 파일은 새 칸 없이 그대로 읽는다(`KNOWN_VERSION`은 3.x 전부).
- `speaker_labels`(한 줄 JSON): 서버가 전사 줄 머리 `화자N:`을 값으로 바꿔 `raw_text`에 저장한다. 값이 비었거나 칸이 없으면 `화자N` 그대로. `speaker_split` 판정은 바꾸기 전 전사로 한다. DB 칸 추가 없음.
- `counterparty_name`·`counterparty_title`·`counterparty_organization`: 상대 표시(`counterpart`)의 첫째 재료. 소속이 담당조직 이름과 딱 하나 맞을 때만 `organization_id` 연결 후보(기존 글자 대조 방식 그대로, 명진 님이 상세에서 바꿀 수 있음). 자동 연결을 새로 만들지 않았다.
- 애매한 통화(`is_work_related: ""`, `status: "애매"`): 업무로 읽지 않고 `unsure_count`로 개수만 센다.
- Drive 설명 `analysis_status=ambiguous`: 앱 스크립트·서버는 설명을 읽지 않으므로 영향 없음.
