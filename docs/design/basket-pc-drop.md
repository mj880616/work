## 0. 명진용 요약 (쉬운 말)

**무엇을 만드나.** 윈도우 PC에서 글·사진·파일을 휴지통에 버리듯 던지면 Web2 바구니에 쌓이는 작은 프로그램 하나. 웹페이지나 브라우저 확장이 아니라 PC에 깔아 쓰는 프로그램이다.

**이미 정해진 것 (다시 묻지 않음, 2026-10-15 사용자 결정).**

1. 형태: 윈도우 전용 프로그램 하나. 이 PR은 문서만이고 만드는 일은 PC에서 한다.
2. 입구: ① 기본은 화면 구석에 마우스를 대면 던지기 영역이 나타남(파일을 끌고 오는 동작을 알아채는 것은 보조). ② Win+D를 눌러도 늘 보이게 할지는 시험판을 써 본 뒤 정함. ③ 보조 입구: 파일 우클릭 [보내기], 작업 표시줄 아이콘, 클립보드 단축키(기본 Ctrl+`(숫자 1 왼쪽 키), 트레이 메뉴에서 Ctrl+Q·Ctrl+Space로 바꿈. 2026-10-20 결정: 복사해 둔 글·사진을 바로 보내고 작은 알림. Win+Shift+S로 캡처한 뒤 바로 보내기와 이어짐), 붙여넣기 창(Ctrl+V로 글·사진 미리보기 → 메모 한 줄 → Ctrl+Enter로 보내기). ④ 클립보드는 단축키를 누르거나 붙여넣을 때만 읽는다. 늘 감시하지 않는다.
3. 저장: 지금 바구니와 같은 길. 글은 바구니 메모, 파일·사진은 Drive 첨부(사진 글자 읽기는 기존대로). 새 저장소나 새 서버 통로는 만들지 않고 기존 바구니 업로드를 그대로 쓴다. 안 되는 부분은 제안으로만 적는다.
4. 로그인: Windows 자격 증명 관리자(윈도우가 비밀번호를 맡아 두는 금고)에 보관하고, Web2 화면에 "이 PC 로그아웃"(이 PC의 접속 끊기) 버튼을 둔다. 로그인·바구니 권한은 지금 그대로이고 우회·확대는 없다.
5. 아직 안 정함(결정 목록에 남김): 코드 서명(설치 때 윈도우 경고 없애기, 비용 가능), Win+D 상시 표시.

**조사 결과 한눈에.**

- 글과 파일을 바구니에 넣는 길은 이미 있고, 서버를 새로 만들 필요는 없어 보인다(3절). 파일은 `basket-files`, 글만 있는 메모는 `app_notes`에 바로 저장하는 기존 방식이다. 그래서 이 프로그램은 "웹 바구니가 하는 호출을 PC에서 똑같이 하는 손"이다.
- 가장 어려운 것은 **로그인**이다(4절). 웹은 브라우저 안에 로그인 정보를 둔다. PC 프로그램은 같은 방식을 쓸 수 없다. 안전한 정석은 "평소 쓰는 브라우저에서 로그인 → 프로그램이 결과만 받기"인데, 이 방법은 Supabase 로그인 설정(허용 주소 목록)에 한 줄을 더해야 하고, 이 설정은 읽생기와 같이 쓴다. 설정 변경은 멈춤 지점이라 승인 뒤에만 한다.
- 만드는 도구는 **.NET(윈도우 기본 개발 도구)** 를 추천한다(5절). 이 저장소에 이미 윈도우 빌드 환경이 있고, 단축키·끌어다 놓기·클립보드·자격 증명 관리자가 모두 기본 기능이다.
- **1차 시험판**은 붙여넣기 창 + 단축키 + 우클릭 [보내기] + 작업 표시줄 아이콘으로 한다. 구석에 마우스를 대면 나타나는 영역과 늘 떠 있는 위젯은 3단계다(9절). 가장 눈에 띄는 입구가 마지막인 이유는, 만들기 어려워서가 아니라 "보내는 길과 로그인"이 먼저 단단해야 하기 때문이다.
- 서버를 안 건드리고도 되지만, 큰 파일·여러 파일을 보내다 연결이 끊기면 "저장됐는지 모르는" 상태가 생긴다. 지금 서버에는 같은 요청을 알아보는 장치가 없어서 프로그램이 대기열과 확인 화면으로 막아야 한다(7절).

## 2. 조사 방법과 기준

`app/`·`supabase/functions/`·`supabase/migrations/`·`windows-app/`·`.github/workflows/`와 위 관련 문서를 읽었다. 읽은 파일은 부록에 모았다. 과거 대화보다 저장소를 따랐다.

## 3. 기존 바구니 업로드 경로 (사실)

### 3.1 웹 화면이 지금 하는 일

| 입력 | 화면 코드 | 부르는 곳 | 비고 |
| --- | --- | --- | --- |
| 글만 | `app/home-quick.js`의 `save()` → `app/basket-data.js`의 `createNote` | REST `POST /rest/v1/app_notes`, 본문 `{workspace_id, raw_text, [ai_export_allowed]}` | 로그인 사용자의 토큰으로 호출하고 접근은 DB의 소유자 권한(RLS)이 막는다. `kind`는 기본값 `basket`이다. 글은 1~20,000자(글자 수), 공백·줄바꿈 보존 |
| 파일(+글) | `app/basket-upload.js`의 `uploadBatch` → `uploadBasketFile` | `POST {Supabase 주소}/functions/v1/basket-files`, `multipart/form-data` | 파일마다 한 요청. 첫 요청에 `raw_text`, 이후 요청은 직전 응답의 `note_id`를 붙여 같은 메모에 이어 붙임 |
| 글 붙여넣기 | `home-quick.js` | 입력칸 `paste` 이벤트 | 웹에는 **클립보드 사진을 바로 첨부하는 코드는 없다**(사실: `app/`에서 `clipboardData`는 완전한 HTML 문서 붙여넣기와 노트 복사에만 쓰임). 설계 문서(`basket-design.md` 2절)에는 사진 붙여넣기가 있으나 아직 구현이 확인되지 않았다 |

`workspace_id`는 로그인한 사용자의 `app_workspace_members`를 REST로 읽어 얻는다(`app/loader-v2.js`가 시작할 때 읽어 `KPTURuntime.context`에 둠). 이 프로그램도 같은 읽기를 하면 된다.

### 3.2 `basket-files` 요청·응답·인증·제한

| 항목 | 내용 (출처: `handler.ts`, README) |
| --- | --- |
| verify_jwt | **false** (`docs/web2-env6b-edge-source.md` 5절 32번, v5, 2026-10-18). 대신 함수 안에서 `Authorization: Bearer <로그인 토큰>`을 Supabase Auth `getUser`로 검증하고, 서버가 `app_workspace_members`에서 `role=owner`인 업무 공간을 찾는다. 소유자가 아니면 403 |
| 필요한 요청 머리 | `Authorization: Bearer <access_token>`, `apikey: <공개용 키>`(웹과 같은 값은 `app/runtime-client.js`의 `config`에 있다. 비밀이 아니라 공개 키이며 서버 전용 키는 절대 프로그램에 넣지 않는다) |
| Origin 검사 | **없음**. CORS는 `*`. 브라우저가 아닌 프로그램도 같은 방식으로 부를 수 있다 |
| 본문 | `file`(같은 키로 1~20개, 실제 사용은 1개씩), `raw_text`(새 메모에만, 20,000자), `note_id`(UUID, 기존 메모에 추가) |
| 크기·개수 | 파일당 100 MiB(104,857,600 bytes), 빈 파일 거절, 메모당 첨부 20개, 파일명 1~255자, MIME은 `종류/세부` 모양만 검사 |
| 허용 형식 | **형식 제한 없음**. MIME 모양만 검사하며 확장자·내용 검사는 없다. (실행 파일도 막지 않는다. 본인 전용이라 문제 없으나 이 프로그램이 자체 제한을 둘지는 결정 거리) |
| 성공 응답 | `200 {ok:true, note_id, attachments:[{drive_file_id,file_name,mime_type,size_bytes}]}` |
| 실패 응답 | `{error, code, stage, retryable:false}`. 401 `session_required`, 403 `forbidden`, 400 `file_missing/file_empty/file_metadata_invalid/too_many_attachments/raw_text_too_long`, 413 `file_too_large`, 404/409 `note_not_found/note_changed/duplicate_attachment`, 409 `drive_folder_*`, 424 `drive_not_connected/drive_auth_expired`, 503 `*_failed/auth_unavailable/note_save_result_unknown` |
| 저장 위치 | 서버가 가진 Drive 연결로 내 Drive 최상위 "Web2 바구니" 폴더에 올린다. **프로그램은 구글 Drive 인증이 필요 없다**(Drive 로그인 정보는 서버 안에만 있음) |
| 하지 않는 일 | 자료실 등록·AI 제목·자동분류·프로젝트 연결 없음 |
| 서버 메모리 | `req.formData()`는 요청 전체를 메모리에 읽는다(README). 그래서 파일은 하나씩 보낸다. 100 MiB 근처 파일의 실제 운영 성공은 보장되지 않는다고 README가 적고 있다 |

웹은 파일 크기에 따라 응답 대기 시간을 `90초 + 올림 MiB × 4초`(최대 10분)로 둔다. 시간이 지나면 "저장 결과를 확인하지 못함"으로 보고 **자동으로 다시 보내지 않는다**(`basket-upload.js`).

### 3.3 사진 글자 읽기(OCR)

JPEG·PNG 첨부는 업로드가 성공한 뒤 웹 화면이 별도 요청으로 글자 읽기를 부른다(`basket-ocr-runtime.js`, 기능이 켜진 경우만). 업로드와 분리되어 있어 OCR이 실패해도 업로드는 취소되지 않는다. 이 프로그램은 1차에서 글자 읽기를 **부르지 않고**, 사진은 업로드만 한다. 나중에 바구니 화면에서 읽을 수 있다(OCR 요청은 `note_updated_at`·`expected_attachment`가 필요한 별도 계약이라 프로그램이 따라 하면 복잡해진다. 사용자 결정 0절 3의 "OCR 기존대로"는 "바구니에서 기존 방식으로 읽는다"로 해석했다. 보내자마자 자동으로 읽기를 원하면 알려 주면 된다. D11 참고).

## 4. 인증 설계 (보안 설계: 결론은 추천안 + 위험 + 검토 필요 이유)

### 4.1 현재 사실

- 로그인 화면(`app/login/`)은 **이메일·비밀번호**(`POST /auth/v1/token?grant_type=password`, `auth-service.js`)와 **구글**(`/auth/v1/authorize?provider=google&redirect_to=…`)을 둘 다 제공한다. 명진이 실제로 쓰는 쪽은 이 세션에서 확인하지 못했다(D10).
- 웹은 로그인 결과 전체(접근 토큰·새로고침 토큰 포함)를 브라우저 `localStorage`의 `kptu_collab_session_v1`에 둔다. 브라우저 안에서는 그렇게 하지만, PC 프로그램이 같은 방식으로 파일에 두면 안 된다.
- 이전 윈도우 래퍼(`windows-app/`, 개발 중단·보관)와 안드로이드 앱은 `native-callback.html` → `auth-handoff` 함수 → `kptuwork://` 방식으로 로그인 정보를 앱에 넘겼다. 이 함수는 허용 Origin이 브라우저 주소 3개뿐이고 `Origin` 머리가 없는 프로그램 요청은 403이다(`auth-handoff/index.ts`). 이 방식을 PC 프로그램에 되살리는 것은 **추천하지 않는다**: 중단된 구조를 되살리지 않는 규칙(AGENTS §4)과, 새로 고침 토큰이 주소줄을 거치는 문제, `auth-handoff` 수정이 필요한 점 때문이다.
- Supabase 프로젝트와 로그인(Auth)은 **읽생기(RTW)와 공유**한다(AGENTS §5). 허용 주소 목록(Redirect URLs)은 프로젝트 전체 설정이다(`docs/bokdoong-domain.md`).
- Edge 쪽 권한 확인은 서버가 맡는다: 토큰 검증 + `app_workspace_members.role=owner`. 프로그램이 보내는 사용자·업무 공간 값은 믿지 않는다. 그래서 프로그램에서 새로운 권한 경로는 생기지 않는다.

### 4.2 후보 비교

| --- | --- | --- | --- | --- |
| **A. 시스템 브라우저 로그인 + 루프백 돌려받기 + PKCE** (정석, RFC 8252, 추천) | 프로그램이 일회용 비밀(code_verifier)을 만들고 평소 브라우저로 구글/비밀번호 로그인 화면을 연다. 로그인 후 브라우저가 `http://127.0.0.1:<임의 포트>/…`로 돌아오면 프로그램이 잠깐 열어 둔 수신기가 일회용 코드(code)를 받아 Supabase에 verifier와 함께 내고 토큰을 받는다 | 비밀번호·구글 계정이 프로그램을 거치지 않는다. 구글·비밀번호 계정 모두 가능. 코드는 verifier 없이는 쓸 수 없다 | 허용 주소 목록에 루프백 주소 추가가 필요. 같은 PC의 다른 프로그램이 같은 포트를 먼저 잡아 코드를 가로챌 수 있으나 verifier가 없어 토큰으로 못 바꾼다. 수신기는 127.0.0.1에서만 열고, state 값 확인, 1회 수신 후 닫기, 2분 제한이 필요 | **Supabase Auth 설정 변경(멈춤 지점)**. 포트가 매번 달라도 되는 패턴을 허용할지, 고정 포트 몇 개만 등록할지 선택 필요(확인 필요: 이 프로젝트의 와일드카드 규칙) |
| B. 프로그램 안 이메일·비밀번호 | 프로그램의 로그인 창에서 비밀번호를 받아 `grant_type=password` 호출 후 비밀번호는 버림 | 설정·서버 변경 없음. 지금 바로 가능 | 구글로만 들어가는 계정이면 불가(비밀번호가 없음). 비밀번호를 프로그램이 직접 다룸. 이메일 확인·추가 인증(MFA)이 있으면 막힘(확인 필요) | 없음 |

| E. 기존 `auth-handoff` 재사용 | 4.1 | — | 위 이유 | 채택 안 함 |

### 4.3 추천안

**정식은 A. 시험용은 B가 가능하면 B로 먼저 만들고 A로 바꾼다.** 이유: B는 설정 변경 없이 보내는 길을 먼저 검증하게 해 주고, A로 바꿀 때 바뀌는 부분은 "토큰을 얻는 부분"뿐이도록 만든다(토큰 얻기와 보내기를 분리). 단, D10의 답이 "구글로만 들어간다"이면 B는 쓸 수 없고 시험판도 A의 허용 주소 승인을 기다려야 한다.

A를 쓸 때 정해야 할 것 (모두 "확인 필요"):
1. 허용할 루프백 주소의 모양(포트 고정/범위). 추천: 고정 주소 2~3개 후보 중 비어 있는 것을 쓰고 목록에는 정확한 경로까지 등록(넓은 와일드카드 지양).
2. Supabase PKCE 코드 교환의 정확한 호출 모양과 코드 유효 시간 — 구현 때 공식 문서와 시험 프로젝트가 아닌 **읽기만 하는 확인**으로 점검. 시험은 본인 계정으로 한다.
3. 구글 쪽 설정은 바뀌지 않는다는 추정: 구글이 돌아오는 주소는 Supabase 자신의 주소이고, 루프백은 그 다음 단계의 Supabase→프로그램 이동이기 때문이다.

### 4.4 토큰 보관·원칙

- **프로그램이 저장하는 것은 새로고침 토큰 하나뿐**. 접근 토큰은 메모리에만 두고 만료 전에 갱신한다. 보관 위치는 Windows 자격 증명 관리자(0절 결정). 대안으로 윈도우 데이터 보호(DPAPI)로 암호화한 파일이 있으나 결정에 따라 자격 증명 관리자를 쓴다. 두 방법 모두 **같은 윈도우 계정으로 실행되는 다른 프로그램(악성코드 포함)은 막지 못한다**. 이 점은 위험으로 인정한다.
- 새로고침 토큰은 쓸 때마다 새 것으로 바뀌는 방식일 가능성이 높다(추정, Supabase 기본). 두 프로세스가 동시에 갱신하면 세션이 끊길 수 있으므로 **토큰을 만지는 프로세스는 하나**로 한다. 우클릭 [보내기]로 새로 뜬 프로그램은 실행 중인 본체에 파일 경로만 넘기고 끝낸다(기존 `windows-app/Program.cs`의 단일 실행 + 이름 있는 파이프 방식과 같은 패턴).
- 토큰·인증 코드·로그인 주소가 **파일, 로그, 화면, 명령줄 인자, 충돌 보고서, 대기열 폴더**에 남지 않게 한다(AGENTS §3 토큰 취급). 우클릭 [보내기]가 넘기는 것은 파일 경로뿐이다. 로그에는 고정 오류 코드와 개수만 쓰고 응답 본문·파일 내용·메모 글은 쓰지 않는다. 파일 이름은 개인정보일 수 있어 기본 로그에 쓰지 않는다.
- 서버 전용 키(service role)는 프로그램에 없다. 공개용 키만 쓰며 이는 이미 공개 저장소에 있는 값이다. 인증 우회·권한 확대·RLS 약화는 없다.
- 인증서 검증을 끄지 않는다. Supabase 요청은 HTTPS만.

### 4.5 새로고침·폐기·"이 PC 로그아웃"

- 프로그램 안 [로그아웃]: Supabase 로그아웃을 이 세션 범위로 호출하고(`scope=local`) 자격 증명을 지우고 대기열을 어떻게 할지 묻는다. 이 동작은 서버 변경이 필요 없다.
- 0절 4의 **Web2 화면의 "이 PC 로그아웃" 버튼**은 두 가지 방법이 있다.
  - 기본 로그아웃 기능의 `scope=others`는 "지금 화면의 세션 말고 **다른 모든 세션**"을 끊는다. 이것은 이 PC만 끊는 것이 아니라 폰·다른 브라우저·읽생기 세션까지 끊을 수 있다(같은 로그인 사용자를 공유하므로, 추정). **그대로 쓰면 의도와 다르다.**
  - 이 PC만 끊으려면 세션별 폐기가 필요한데, 서버 함수 또는 DB 변경이 따른다(제안 P3). 그 전까지는 "전부 로그아웃(다른 기기 모두)" 버튼으로 약속하거나, 프로그램 안 [로그아웃]만 제공하는 선택이 있다. **D12로 결정 필요.**
- Supabase의 세션 만료·미사용 만료 설정은 이 세션에서 확인하지 못했다(확인 필요).

### 4.6 Opus 검토가 필요한 이유

이 절은 보안 설계이고 되돌리기 어려운 부분이 있다. ① 읽생기와 공유하는 로그인 설정을 바꾸는 제안이다. ② 토큰을 PC에 두는 새 경로가 생긴다. ③ PKCE 검증(state, verifier, 1회성), 새로고침 토큰 경합, 로그아웃 범위는 틀리면 조용히 약점이 된다. ④ AGENTS §3은 협상 불가 항목이다. 구현 전에 독립된 검토(Opus)로 위 내용과 구현 PR을 확인하고, 허용 주소 변경은 사용자 승인 뒤에 한다(9절 멈춤 지점).

**추천: .NET 데스크톱 프로그램(WinForms로 시작).** 이유: ① 이 프로그램의 핵심이 모두 윈도우 기본 기능(단축키, 끌어다 놓기, 클립보드 사진, 자격 증명 관리자, 구석 감지, 항상 위 창)이고 .NET이 가장 직접 쓴다. ② 이 저장소에 이미 윈도우 러너 빌드 경험과 단일 실행 + 파이프 전달 코드가 있다(참고용으로만 보며 보관 폴더 `windows-app/`는 되살리지 않고 새 폴더에 만든다). ③ 웹뷰가 필요 없다. 화면은 작은 창뿐이다.

주의: 기존 프로젝트는 .NET 8을 쓴다. 일반 지식으로 .NET 8의 지원 종료가 2026년 11월로 알려져 있어(확인 필요) 새 프로그램은 **더 최신의 장기 지원 버전**으로 시작하는 것이 안전하다. GitHub Actions `setup-dotnet`이 그 버전을 지원하는지 구현 때 확인한다.

서명 없는 경고: 인터넷에서 받은 서명 없는 exe는 윈도우 SmartScreen이 "PC를 보호했습니다"를 띄울 수 있다(추정, 일반적). 브라우저로 받은 압축 파일에 "인터넷에서 받음" 표시가 붙기 때문이다. 시험판 방법: 압축 파일 속성에서 "차단 해제" 후 풀거나 "추가 정보 → 실행". 코드 서명(D7)은 이를 줄이지만 비용이 든다. 일부 보안 프로그램은 "마우스 위치를 계속 읽거나 전역 단축키를 쓰는 서명 없는 프로그램"을 의심할 수 있다(추정).

## 7. 전송 실패·대기열·중복·결과 표시

**원칙: 놓치지 않기 > 한 번만 저장하기 > 빨리 저장하기**, 그리고 "저장됐는지 모르는 상태"를 숨기지 않는다.

### 7.1 상태

| 상태 | 뜻 | 화면 표시 | 자동 재시도 |
| --- | --- | --- | --- |
| 대기 | PC에 있고 아직 안 보냄 | 대기 중 | 예 |
| 보내는 중 | 요청 진행 | 진행 표시 | — |
| 완료 | 응답 `ok:true`, `note_id` 확인 | 완료 + [바구니에서 열기] | — |
| 실패(확실) | 서버 거절 4xx 중 고칠 수 있는 것: 413 너무 큼, 400 빈 파일 등 | 이유 한 줄 + [다시 보내기]/[버리기] | 아니오 |
| 연결 전 실패 | 서버에 닿지 않음(인터넷 없음, 이름 확인 실패, 연결 거부) | 오프라인 대기 | 예(간격을 늘려가며) |
| **결과 불명** | 요청을 보낸 뒤 응답이 없거나 `note_save_result_unknown`, 시간 초과, 5xx | **"저장됐는지 확인이 필요해요"** + [바구니 열기] [그래도 다시 보내기] | **절대 아니오**(웹과 같은 규칙) |
| 로그인 필요 | 401/갱신 실패 | 로그인 요청 | 로그인 후 대기 상태로 복귀 |

중복 방지: 서버에는 같은 요청을 알아보는 장치가 없다(제안 P1). 그래서 프로그램이 지킨다. ① 결과 불명은 자동 재전송 금지. ② PC 안에 "보낸 기록"(파일 지문(해시)·크기·시각·`note_id`, 파일 내용은 저장하지 않음)을 두고 같은 파일을 다시 놓으면 "이미 보낸 파일이에요, 또 보낼까요?"를 묻는다. ③ 글만 있는 메모는 프로그램이 `id`를 미리 만들어 REST로 저장하면 같은 `id`의 재전송이 충돌로 거절되어 중복이 생기지 않는다(추정: 표에 `id`를 넣을 권한이 막혀 있지 않음 — 테이블 단위 insert 권한이며 열 단위 제한은 migration에서 찾지 못함. 구현 전 확인 필요).

### 7.2 대기열

- PC 안 전용 폴더(사용자 계정의 앱 데이터)에 원본 사본을 두고 목록 파일을 둔다. 원본이 지워지거나 USB가 빠져도 보낼 수 있게 한다. 토큰은 여기에 없다.
- 상한: 전체 용량 상한(예 2GB), 성공하면 즉시 삭제, 7일 넘은 대기 항목은 "버릴까요?" 확인. 사용자가 모르게 용량이 쌓이지 않게 한다.
- 순차 전송: 한 번에 파일 하나(웹과 같음). 한 메모로 묶인 여러 파일은 첫 성공의 `note_id`에 이어 붙이고(서버는 메모당 20개), 20개를 넘으면 다음 메모로 나눈다. 중간 파일이 실패하면 나머지는 멈추고 이유를 표시한다.
- 프로그램 종료·재부팅 중이던 "보내는 중" 항목은 **결과 불명**으로 되돌린다(자동 재전송 금지).

### 7.3 크기·형식 제한을 기존과 맞추기

사전 확인은 웹과 같은 값으로 한다: 파일당 100 MiB, 빈 파일 거절, 한 메모 20개, 글 20,000자, 파일명 255자. 서버가 다시 확인한다(두 곳). 형식은 서버가 제한하지 않으므로 프로그램도 기본은 제한하지 않되, 실행 파일(.exe 등) 전송은 확인 한 번을 거치는 것을 제안한다(D13, 선택). 100 MiB 근처 파일은 서버 메모리 때문에 실패할 수 있어 대용량 시험은 단계 ②에서 따로 한다.

### 7.4 결과 표시

보내기 직후 작은 알림(성공 "바구니에 담았어요 · 파일 N개", 실패 "보내지 못했어요 · 다시 보내기"). 트레이 아이콘 메뉴에 "최근 10건 · 대기 N건 · 확인 필요 N건". 소리·깜빡임은 없다. 알림에 파일 이름·글 내용을 넣을지는 설정(기본: 개수만)으로 한다.

## 8. 놓을 때 분류 vs 바구니에서 분류

**추천: 놓을 때는 분류하지 않는다.**

- 기존 설계([basket-design.md](../basket-design.md))는 "분류 없이 담고, 나중에 AI·사용자 분류"이다. 홈 빠른 입력도 같다(바구니 모드는 조직·프로젝트 선택이 없음, `home-quick.js`). PC 입구만 다르게 하면 두 기준이 생긴다.
- 놓는 순간에 목적지를 고르게 하면 던지기의 가벼움이 사라지고, 목록 전체(프로젝트·담당조직)를 프로그램이 읽어야 해서 권한 읽기 범위도 넓어진다.
- 입력 항목은 **메모 한 줄(선택)** 하나뿐. 붙여넣기 창에서 이 줄은 `raw_text`가 된다. 파일만 보내면 글 없는 메모가 된다(서버가 허용).
- AI 전달: 새 메모의 `ai_export_allowed`는 서버·DB 기본값(true)을 따른다. 프로그램에 "AI 제외" 체크를 둘지는 열려 있다(D14, 기본: 두지 않음 — 바구니 화면에서 바꾸면 됨).

## 10. 범위 밖 발견사항 (고치지 않고 기록만)

1. `docs/web2-env6b-edge-source.md` 4절 3번은 "`auth-handoff` 봉인 토큰은 1회용 확인이 없다"고 적지만, 현재 `supabase/functions/auth-handoff/index.ts`는 일회용 소비(`app_consume_auth_handoff`)를 구현했다(커밋 `2b14a5b9`, SEC-1). 문서 설명과 코드가 다르다. 운영 배포 상태(5절 표는 v3, 09-12)와 코드의 일치 여부는 확인하지 못했다.
2. `docs/basket-design.md` 2절은 "사진 붙여넣기"를 확정 동작으로 적지만 현재 웹 코드에는 클립보드 사진을 첨부로 받는 처리가 보이지 않는다(`app/`에서 `clipboardData`는 HTML 문서 붙여넣기만 처리). 원장에서 해당 행의 완료 여부를 확인할 필요가 있다.
3. `basket-files/README.md` 첫 문단에 "배포 대기·운영 DB/Edge 적용 전에는 화면에서 호출하지 않는다"가 남아 있으나 실제로는 v5까지 배포되어 있다(Edge 표 32번). 문서 정리 대상.
4. `windows-app/`(.NET 8, WebView2 래퍼)는 개발 중단 상태로 보관 중이다. `windows-app` 빌드 workflow는 수동 실행 전용이다. 이 설계의 새 프로그램과는 별개로 두며 이번에 건드리지 않았다.
5. `basket-files`는 형식(확장자·내용) 제한이 없고 CORS가 `*`다. 본인 전용 로그인·소유자 확인이 있어 당장 문제는 아니지만, 서버 쪽 형식·요청 출처 정책은 보안 정리 때 검토할 수 있다.
