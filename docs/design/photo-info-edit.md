## 1. 왜 둘을 함께 고치나

직전 PHOTO-찍은시각EXIF(취소)에서 확인한 것: 파일 EXIF만 고치면 폰 사진첩 목록(MediaStore `DATE_TAKEN`)이 옛 값이라
삼성 갤러리·웹2 폰 사진 순서가 그대로다. 웹2가 고칠 때는 앱이 **파일 EXIF와 사진첩 목록 칸을 한 번에** 고친다.

## 2. 화면

- 사진을 꾹 눌러(PC는 클릭) 고른 뒤 사진 ⋯(PC 우클릭) → **[정보 고치기…]**. 한 장만 고르면 그 한 장. 폰 앱 0.4.15+에서만 보인다.
- 창 위쪽: 고른 장수 + 카메라·렌즈(보기만, 여러 종류면 "여러 가지").
- 고치는 방법(한 번에 하나만 고른다):
  - **시각 밀기**: `모두 [+|−] n시간 n분 밀기` (소니 시계가 틀린 경우처럼 한꺼번에 몇 시간 어긋난 경우).
  - **이 날짜로**: `모두 이 날짜·시각으로`(달력 입력). 여러 장이면 원래 순서·간격은 지키고 첫 장을 그 시각에 맞춘다.
  - **이 장소로**: `모두 이 장소로`(위도·경도 입력, 지도에서 고르기는 [지도 열기]로 확인) 또는 `위치 지우기`.
- 저장 전 **앞 → 뒤 미리 보기 표**(한 줄에 한 장: 이름 · 앞 시각 → 뒤 시각 · 위치). 못 고치는 사진(HEIC·동영상·옛 앱)은 표에 "못 고침"으로 보이고 빠진다.
- [저장] → 안드로이드 수정 허락 창 **한 번**(여러 장은 묶어서 한 번, '미디어 관리 허용'이 켜져 있으면 창 없음).
- 끝나면 알림 `12장 고쳤어요 · [되돌리기]`. 나중에도 이 창 맨 아래 `지난번 고친 12장 · [되돌리기]`로 묶음 통째 되돌린다.
- 한 번에 최대 200장. 자동 변경 없음(명진이 고른 사진만).

## 3. 폰 앱(0.4.15, versionCode 55)

다리 메시지(앱 상태 `photos:state`에 `meta:true`):

| 웹 → 앱 | 앱 → 웹 |
| --- | --- |
| `photos:meta:read:[번호…]` | `photos:meta:{ok, items:[{id, taken, lat, lon, make, model, lens, can}], error}` |
| `photos:meta:write:{items:[{id, taken?, loc?}]}` | `photos:metadone:{ok, count, failed:[번호], error}` |

- 읽기: `MediaStore.setRequireOriginal` + `ACCESS_MEDIA_LOCATION`(위치 칸이 가려지지 않게, 대화창 없이 사진 권한에 딸린 허락)로 원본 EXIF를 읽는다.
- 쓰기: `MediaStore.createWriteRequest`(허락 창 한 번) → 장마다 `rw`로 열어 androidx `ExifInterface`로
  `DateTimeOriginal`·`DateTimeDigitized`·`DateTime`·`OffsetTime*`(폰 시간대) 또는 GPS 칸만 다시 쓴다(사진 화질·그림 바이트는 그대로) →
  닫은 뒤 `DATE_TAKEN`을 같은 시각으로 고친다(사진첩이 다시 읽어도 같은 값).
- 고칠 수 있는 종류: JPEG·PNG·WebP. HEIC·동영상은 `can:false`(읽기만).
- 로그에 사진 이름·시각·위치를 쓰지 않는다(실패 종류·예외 클래스 이름만). 서버로 사진·EXIF를 보내지 않는다.
- 규칙(메시지 해석·시각 글자 만들기·한도)은 `PhotoMetaRules.kt`, 단위 시험 `PhotoMetaRulesTest.kt`.

## 4. 되돌리기 기록(서버)

새 표 `public.app_photo_info_edits`(DB `20261103140000_photo_info_edits`): 한 줄 = 고친 사진 한 장.
`batch_id`, `source`('phone'), `item_key`('ms:<번호>'), 앞 시각·위치, 뒤 시각·위치, `undone_at`.
- 작업공간 주인만 읽기·넣기·`undone_at` 고치기(owner RLS 정책 하나, anon·PUBLIC·service_role 없음). 지우기 없음.
- 위치는 민감하므로 이 표는 화면 주인만 읽는다. 사진 이름·내용은 넣지 않는다.
- [되돌리기] = 그 묶음의 앞 값으로 다시 쓰기(같은 다리 `photos:meta:write`) → 성공한 줄에 `undone_at`.
- 표가 아직 없으면(DB 적용 전) 고치기는 하되 되돌리기 기록 없이 "이번 화면에서만 되돌릴 수 있어요"로 알린다.

## 5. 원드라이브·구글 드라이브 사진 (② 설계, S50-28)

### 5-1. 출처별로 할 수 있는 것과 한계

| 출처 | 웹2가 찍은 시각을 어디서 읽나 | "정보 칸만" 고치는 길 | 원본 파일을 고치는 길 | 한계 |
| --- | --- | --- | --- | --- |
| 폰 사진 | 파일 EXIF 먼저(#1883), 없으면 사진첩 목록 | 없음(사진첩 목록만 고치면 갤러리 상세와 어긋남) | 앱이 그 자리에서 EXIF + 사진첩 목록 함께 고침(①, 완료) | 폰 앱에서만. HEIC·동영상 못 고침 |
| 원드라이브 | Graph `photo.takenDateTime`(EXIF에서 뽑은 값, 읽기 전용) | **없음** — Graph가 이 칸을 고치게 해 주지 않음 | 원본을 받아 EXIF만 다시 써서 **같은 파일의 새 판**으로 올림. 원드라이브 판 기록에 옛 판이 남음 | 판 기록 보관 기간·개수는 원드라이브 설정에 따름. 올린 뒤 원드라이브가 찍은 시각을 다시 뽑는지 실기기로 확인 |
| 구글 드라이브 | Drive `imageMediaMetadata.time`(EXIF에서 뽑은 값, 읽기 전용) | **없음** — 이 칸은 읽기 전용 | 원본을 받아 EXIF만 다시 써서 같은 파일의 새 판(revision)으로 올림 | Drive는 옛 판을 기본 30일·100개까지 보관(그 뒤 자동 삭제될 수 있음). 시각 다시 뽑기 확인 필요 |
| 구글 포토 | 웹2가 읽지 않음(PHOTO-출처구글드라이브 2절) | — | — | 대상 아님 |

- 원드라이브·구글 드라이브 모두 **서비스 쪽 "찍은 시각" 칸은 고칠 수 없다.** 그래서 고르는 길은 둘뿐이다:
  - **(가) 원본 파일을 고친다** — 사진 그림은 그대로, EXIF 칸만 다시 써서 새 판으로 올린다. 원드라이브 앱·구글 드라이브 앱·다른 기기에서도 고친 시각으로 보이고, 웹2 색인은 다음 갱신 때 서비스가 다시 뽑은 값을 그대로 받는다(색인 규칙 그대로, 새 칸 없음).
  - **(나) 원본은 그대로, 웹2 기록만 고친다** — 웹2에 "이 사진은 이 시각으로 본다"를 따로 적고 화면·순서·날짜 묶음에서 그 값을 먼저 쓴다. 다른 앱에서는 옛 시각 그대로다. 색인 갱신(원드라이브 delta·드라이브 다시 읽기)이 `taken_at`을 다시 덮으므로 색인 칸이 아닌 **따로 둔 고친 값**이 필요하다(DB 변경).
- 폰 사진은 이미 (가)로 했다(E2). 같은 원칙이면 클라우드 사진도 (가)가 자연스럽다. 추천은 7절 E3.

### 5-2. (가) 원본 고치기 — 어떻게

- 어디서 고치나: Edge 함수가 원본을 **메모리로만** 받아 EXIF 칸(찍은 시각 3칸·시간대 칸 또는 GPS 칸)만 바꾸고 곧바로 같은 파일 새 판으로 올린다. 디스크·Storage·DB에 사진을 두지 않는다(지금 크게 보기 원본 중계와 같은 원칙: 지나가기만 함).
  - 원드라이브: `onedrive-photos`에 새 동작 `photos-meta-write`. 받기 `GET /items/{id}/content` → 다시 쓰기 → `PUT /items/{id}/content`에 `If-Match: <받을 때 eTag>`(그 사이 누가 바꿨으면 412로 멈춤, 덮어쓰지 않음). 권한은 지금 `Files.ReadWrite` 그대로, 고른 폴더 안 사진만(기존 폴더 나무 이중 확인 재사용).
  - 구글 드라이브: `gdrive-photos`에 새 동작 `photos-meta-write`. 받기 `files.get alt=media` → 다시 쓰기 → `files.update uploadType=media`. 받기 전 `headRevisionId`·`md5Checksum`을 적고 올리기 직전 다시 확인(바뀌었으면 멈춤). 권한은 G1 결정의 `drive` 그대로, 운영자 작업공간만(기존 4중 확인 그대로).
- EXIF 다시 쓰기 부품: `supabase/functions/_shared/`에 JPEG 전용 작은 부품 하나(외부 라이브러리를 쓰면 판 고정 + 저장소 안에 복사, 시험 포함). **JPEG만** 처음 판 대상. PNG·WebP·HEIC·동영상은 "못 고침"(미리 보기 표에 표시, 빠짐).
- 한도: 한 장 30MB 이하(넘으면 못 고침), 한 번 부를 때 최대 10장, 화면이 200장까지 나눠 부름. 사진 이름·시각·위치를 로그에 쓰지 않음(실패 종류만).
- 확인 한 번: 요청에 `confirm: true`가 없으면 서버가 거절(기존 지우기·옮기기 규칙과 같음). 자동 변경 없음.
- 화면: 지금 [정보 고치기…] 창 그대로. 섞인 선택(폰 + 원드라이브 + 드라이브)도 한 창에서 미리 보기 표 한 장으로 보이고, 저장 때 출처별로 나눠 보낸다(폰 = 앱 다리, 클라우드 = Edge). PC에서도 클라우드 사진만 고를 때 메뉴가 보인다(E4).
- 다 고친 뒤: 색인을 그 사진만 바로 다시 읽어(원드라이브 item 한 장, 드라이브 file 한 장) 화면 순서·날짜 묶음을 맞춘다. 서비스가 찍은 시각을 바로 다시 뽑지 않으면(지연) 몇 분 동안 옛 값이 보일 수 있다 — 실기기 확인 항목.

### 5-3. 되돌리기

- 지금 표 `app_photo_info_edits`를 그대로 쓴다. `source` 칸 허용 값에 `'onedrive'`·`'gdrive'`를 더하고, `item_key`는 `od:<item id>`·`gd:<file id>`(DB 변경 1건, 짝 파일 5개 — 허용 값 넓히기만, 권한·정책은 그대로).
- [되돌리기] = 그 묶음의 앞 값으로 **같은 길로 다시 쓰기**(또 하나의 새 판). 서비스의 옛 판 되살리기는 쓰지 않는다(그 사이 다른 판이 생겼을 때 덮어쓸 위험). 대신 사람이 원드라이브·드라이브 "판 기록"에서 옛 판을 직접 되살릴 수 있다는 안내를 창 맨 아래 한 줄로.
- 폰 사진과 같은 묶음 단위·같은 알림(`12장 고쳤어요 · [되돌리기]`).

### 5-4. (나) 웹2 기록만 고치기 — 고를 경우

- 새 칸 또는 새 표(사진 열쇠 → 고친 시각·위치), 화면·정렬·날짜 묶음·일기 사진 줄·연월 보기가 모두 이 값을 먼저 읽게 바꿔야 한다(읽는 곳이 많아 범위가 크다). 원드라이브·드라이브 정렬은 서버 색인 표에서 하므로 서버 정렬에도 넣어야 한다.
- 원본이 안 바뀌어 안전하지만, 다른 앱·다른 기기와 시각이 어긋난 채 남는다. 폰 사진(E2 = 원본 고침)과 규칙이 달라져 "어디서는 바뀌고 어디서는 안 바뀌는" 혼란이 생긴다.

## 7. 명진 결정 (② 원드라이브·구글 드라이브)

- **E3 원드라이브·구글 드라이브 사진은 어떻게 고치나** — (가) 원본 파일을 고침(사진 그림은 그대로, 정보 칸만. 원드라이브·드라이브 앱에서도 고친 시각. 옛 판은 서비스 판 기록에 남음) / (나) 원본은 그대로 두고 웹2 화면에서만 고친 시각으로 보임. **추천 (가)** — 폰 사진과 같은 규칙이고, 고칠 곳이 적다.
- **E4 PC에서도 고치나** — 예: PC 웹2에서 원드라이브·드라이브 사진을 골라 고칠 수 있음(폰 사진은 지금처럼 폰 앱에서만). **추천 예.**
- **E5 처음 판은 JPEG만** — 아이폰 HEIC·PNG·동영상은 "못 고침"으로 빼도 되나. **추천 예**(소니·삼성 사진은 대부분 JPEG).

## 8. ② 구현 순서 (E3=(가) 기준, 줄 세움)

2. Edge `onedrive-photos` `photos-meta-write` + `_shared` JPEG EXIF 부품·시험(verify_jwt keep, 되돌리기 ref 기록).
3. Edge `gdrive-photos` `photos-meta-write`(같은 부품).
4. 화면 `photo-info-edit.js`: 섞인 선택·출처별 보내기·PC 메뉴, E2E.

### 8-1. 1~3 구현(S50-31 첫 PR)

- 부품 `supabase/functions/_shared/jpeg-exif.ts`(외부 라이브러리 없음, 시험 `tests/security/jpeg-exif.test.mjs`): EXIF 조각(APP1) 안에서 값만 그 자리에서 덮어쓰고,
  칸을 더하거나 빼야 할 때만 그 칸 목록(IFD)을 EXIF 끝에 새로 적고 가리키는 곳 하나만 고친다(제조사 메모·썸네일 자리는 그대로). 그림 바이트는 한 바이트도 안 바뀐다.
  시각은 서울 벽시계로 적고, 시간대 칸이 있으면 "+09:00"으로 맞춘다. 위치 지우기는 GPS 칸 목록과 값을 0으로 덮는다(옛 위치가 파일에 남지 않음).
  XMP에도 위치가 있으면 위치는 못 고침(`xmp_location`). 고친 뒤 다시 읽어 같지 않으면 올리지 않는다(`verify_failed`).
- 서버 동작(두 함수 같은 모양):
  - `photos-meta-read` `{ids:[≤10]}` → `{items:[{id, can, taken, lat, lon, make, model} | {id, can:false, why}]}`. 파일 앞 256KB만 받는다.
  - `photos-meta-write` `{confirm:true, items:[{id, taken?, loc?:{lat,lon}|null}] ≤10}` → `{done:[{id, before:{taken,lat,lon}, after:{…}}], failed:{id: 이유}}`.
    이유: `missing`·`outside`·`trashed`·`not_jpeg`·`too_big`·`no_exif`·`xmp_location`·`changed`(그 사이 바뀜 — 덮어쓰지 않음)·`throttled`·`unavailable` 등.
  - 되돌리기 기록(`app_photo_info_edits`)은 서버가 쓰지 않는다. 화면이 `done`의 앞·뒤 값으로 사용자 로그인 그대로 넣는다(주인만, 지금 정책 그대로).
- 서비스가 찍은 시각을 바로 다시 뽑지 않으면 색인에 옛 시각이 잠깐 남을 수 있다(8절 5 실기기 확인).
