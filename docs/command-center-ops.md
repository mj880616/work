# 커맨드센터 운영 규칙 (V30부터, 후속 방 V31·V32…에 그대로 인계)

2026-10-21 사용자 결정. 이 문서가 커맨드센터(CC) 채팅방의 운영 기준이다. 새 방은 시작할 때 이 문서와 `docs/roadmap.md` 맨 위 상태 줄을 먼저 읽는다. 과거 채팅보다 이 문서·원장·실제 GitHub 상태가 우선한다. (2026-10-22 사용자 결정)

## 0. 가장 중요한 원칙 — 사용자 손이 덜 가게 (2026-10-31 사용자 결정)

- 목적은 업무 편의다. 사용자가 직접 눌러야 하는 일을 최대한 없애고 CC가 처음부터 끝까지 한다.
- 새 방은 첫 메시지로 이 허락 문장을 받는다(받은 허락은 다음 인계서 첫 허락 문장에 그대로 넣는다):
  > 이 방에서 CC는 저장소 연결(add_repo push), PR merge, Edge 배포, DB 적용(승인형 workflow), 예약 작업 추가·수정·삭제, 폰 앱·바구니 PC 릴리스(GitHub 공개 릴리스·태그 만들기)를 내 추가 승인 없이 진행한다. 보안 책임은 내가 진다.
  > 동시 작업 세션 수는 제한 없다. 예약 작업과 브라우저 일(사이트 열기·허용·로그인된 화면 조작)은 묻지 않고 한다. 작업 세션도 DB 시험 적용·실제 적용까지 직접 하고, 검사 실패는 4번까지 고친다. 같은 파일 작업은 한 세션이 연달아 처리하고, 점검은 10분 간격으로 한다. 요청함 방은 요청함 문서만 고친다(요청 정리·접수 줄). CC가 요청함을 10분 점검 때마다 확인하고, 새 요청을 직접 작업 세션으로 띄운다.
- (2026-11-01 00:15·00:16 사용자 결정) 위 둘째 문단은 속도를 위한 추가 허락이다. 보안 규칙(AGENTS.md 3절, DB 시험 적용 먼저·실패하면 멈춤, 비밀값·개인정보 기록 금지)은 그대로다. 사용량이 한도에 닿아도 세션 수를 줄이지 않는다(1절 '사용량과 동시 세션' 참고).
- CC가 묻지 않고 하는 일: 세션 띄우기·점검 예약(예약 작업 추가·수정·삭제), PR 검토·merge(세션이 멈추면 이어받아 고침), DB merge → dry-run → apply → 결과 확인(사용자에게 승인 버튼을 누르라고 하지 않음), Edge 배포(merge sha를 ref로, 되돌리기 ref 기록), 폰 앱·바구니 PC 릴리스, 브라우저가 연결돼 있으면 대시보드 일(SQL 포함).
- 사용자에게 남기는 일: 로그인·2단계 인증, 실기기 확인, 화면 결정(시안), 되돌릴 수 없는 일의 결정.
- 막히면(자동 판정·도구 없음) "무엇이 막혔고 허락 문장 한 줄이면 된다"를 일상어로 한 번만 묻는다.
- 편의는 누가 버튼을 누르느냐를 줄이는 것이지 보호 장치를 낮추는 것이 아니다. 인증 우회·RLS 약화·권한 확대·비밀값 노출·서버 검사 생략은 그대로 금지(AGENTS.md 3절). DB는 늘 시험 적용 먼저, 실패하면 멈춤.
- DB 적용 결과는 check-run 주석으로 API에서 읽는다(`docs/ops-db-workflow.md` 'CC가 결과 읽는 법').
- 인계서(다음 방이든 다른 계정으로 옮기는 전체 경과 인계서든) 맨 앞 서두에 이 0절과 첫 허락 문장을 둔다.

## 1. 작업 세션

- 커맨드센터가 작업 세션을 **직접 띄운다**. 사용자에게 지시서를 넘겨 다른 세션에 붙여넣게 하지 않는다.
- **시작·끝 절차와 PR 양식은 `docs/ops/session-brief.md`·`.github/pull_request_template.md` 한 곳**(2026-11-26 사용자 결정, OPS-작업양식). 지시서는 그 문서를 가리키고 과제·영역·완료 기준만 적는다. merge 전 점검은 `node scripts/cc/merge-check.mjs <PR 번호>`(OPS-넣기점검, 쓰기 없음).
- **사용량과 동시 세션**(2026-11-02 13:07 사용자 결정, 아래 옛 '사용량 절약 규칙'의 세션 수 줄이기를 대체):
- **세션 공통 지시: 커밋 작성자 메일은 GitHub noreply 주소만 쓴다**(SEC-공개저장소청소 ②, 2026-11-26 사용자 결정, `AGENTS.md` 3절). 지시서·PR 글에도 실제 사람·단체 이름을 쓰지 않는다(CI `public-words-check`).
  - 전체 일의 양이 같으면 쓰는 사용량도 거의 같다. 동시 세션을 줄이면 사용량이 아껴지는 게 아니라 끝나는 때만 늦어진다. 그러므로 목표는 **남은 사용량 안에서 최대한 빨리 끝내기**다.
  - 동시 세션 수는 사용량으로 정하지 않는다. **같은 파일을 만지는 일이 겹치지 않는 만큼** 모두 띄우고, 하나가 끝나면 대기 줄 다음 과제로 바로 채운다.
  - 한도에 닿으면 세션을 줄이지 않고, 풀리는 즉시 이어서 돌린다(끊긴 세션은 아래 '멈춤' 규칙대로 이어 하기).
  - 진짜 낭비는 같은 파일을 두 세션이 동시에 고쳐 다시 하는 일, 끝난 세션을 다시 불러 기억을 다시 읽히는 일, 같은 확인 반복이다. 이것을 줄인다.
  - 인계서·보고에서 '사용량 때문에 세션을 줄인다'는 판단을 쓰지 않는다.
- 같은 파일을 고치는 과제는 한 세션으로 묶거나 순서를 둔다(충돌 방지).
- 모델: 쉬운 작업은 Sonnet, 원인 조사·여러 파일·보안·DB·Edge는 Opus.
- 프로젝트에 붙은 CC 방에서 띄우는 세션은 저장소 `.claude/settings.json` 모델 설정이 안 먹을 수 있으므로 CC가 세션마다 모델을 직접 지정한다.
  - **지정하는 방법**(2026-11-08 V54 확인, 사용자 "오래전부터 시킨 지시, 인계서에 계속 남겨"): 예약 작업 세션(`create_trigger`)은 모델을 고르는 칸이 없어 **Opus로 돈다**. 그래서 쉬운 일은 CC 방 안 작업자(Agent 도구 `model: "sonnet"`, 백그라운드, 필요하면 `isolation: "worktree"`)로 돌리고, Opus가 필요한 일(설계·원인 모를 버그·보안 판단·DB·권한)만 예약 작업 세션으로 띄운다. CC 방 안 작업자는 방이 닫히면 같이 멈추므로 2시간 넘게 걸리거나 방을 넘길 일은 세션으로 하고, 방을 닫기 전 돌고 있는 작업자의 브랜치·PR 상태를 인계서에 적는다. 이 기준은 인계서 맨 앞(0절 바로 아래)에 늘 옮겨 적는다.
- 세션 지시 공통: 최신 main에서 새 폴더 clone, 10분 안에 첫 push, 전용 포트·`pkill` 금지(자기 PID만), rebase·force push 금지(main이 앞서면 merge), PR 본문 끝 "원장 반영" 절, CI 확인까지, merge 금지(merge는 CC가), 범위 밖 발견은 보고만.
  - 완료 기준 공통 줄(2026-11-10 사용자 결정, UI-위쪽줄흰띠·여백): **화면이 바뀌는 PR은 PC(1280)·폰(412) 화면 사진(고치기 전·후, 가짜 데이터만)을 PR에 붙인다.** 사진이 없으면 완료가 아니다.
  - **완료 기준에 통과할 자동 시험을 적는다**(2026-11-25 사용자 결정, OPS-완료기준시험): 지시서 '완료 기준'에는 "어떤 자동 시험이 통과해야 하는지"를 시험 파일·시험 이름(또는 새로 만들 시험의 파일 이름과 검사 내용)으로 반드시 적는다. "CI 통과"만 적은 지시서는 완료 기준이 없는 것으로 본다. 요구를 지키는 시험이 아직 없으면 **시험부터 추가**하게 한다(고치기 전 main에서 실패하고, 고친 뒤 통과하는 시험). CC는 merge 전에 그 시험이 PR에 있고 CI에서 통과했는지 확인한다.
- **전수 검사와 PR 나누기**(2026-11-25 사용자 결정, OPS-전수검사별도PR): 지적받은 문제와 같은 종류를 전수 검사하는 것은 그대로 한다. 다만 전수 검사에서 **다른 곳의 같은 종류 문제를 찾으면 지금 PR에 섞지 않는다.** 지금 PR은 지시서 범위만 끝내고, 찾은 곳은 PR 본문 '범위 밖 발견사항'에 위치(파일·화면)와 함께 목록으로 적는다. CC는 그 목록으로 별도 지시서를 만들어 지금 PR **뒤에 줄 세운다**(같은 파일이면 앞 PR merge 뒤 시작, 2절 줄 세우기). 이 규칙은 '같은 종류 함께 고치기'로 PR이 커지고 서로 충돌하는 것을 막기 위한 것이다.
- **한 번 정리는 CC가 직접**(2026-11-25 사용자 결정, OPS-일회용기능금지): 지시서를 쓰기 전에 그 일이 '한 번 정리'인지 본다. 그렇다면 작업 세션에 화면 기능을 맡기지 않고 CC가 직접 한다(AGENTS.md 4절). 세션이 정리 버튼을 만들어 오면 merge 전에 되돌려 보낸다. 예외로 둔 정리 버튼은 원장에 '지울 때'와 함께 올리고, 그때가 되면 지우는 작업을 띄운다.
- **동시 작업 수**(2026-11-25 사용자 결정, OPS-시험줄): 작업 세션은 한 번에 10개 안팎만 띄운다. 열린 PR의 시험 대기 줄이 길면(대기 run 30개 이상) 새 세션을 띄우지 않고 받은 요청은 줄에 적어 두었다가 줄이 줄면 띄운다. DB 적용·Edge 배포·main 시험 깨짐 고침은 줄 맨 앞(다른 PR보다 먼저 merge·실행). 지난 버전 결과물의 대기·진행 중 시험은 CC가 취소한다(사용자 11/25 허락).
- 세션이 "멈춤"으로 끝나면 같은 사본 위에서 이어서 다시 띄운다(재구현 금지, push 상태부터 확인).
- 작업 세션이 멈추면(사용자 메시지로 CC 답이 끊긴 경우 포함) **사용자에게 묻지 않고** 멈춘 자리에서 바로 이어서 다시 띄운다(2026-10-22 사용자 결정).
  - 재구현하지 않는다. 사본·브랜치·push 상태부터 확인하고, 미커밋 변경은 살린다.
- 세션 지시에 "의미 있는 진행마다 커밋·push"를 넣는다(중단 대비).
- CC는 답을 짧게 끝내고, 긴 대기(검사·배포 결과)는 뒤에서 돌린다. CC 답 도중 사용자 메시지가 오면 그때 돌던 세션이 멈출 수 있기 때문이다.
- 세션은 가능하면 CC 답 끊김과 분리된 방식(원격 실행)으로 띄운다.
- 보고는 PR 번호 대신 작업 내용(무엇을 하는 작업인지)으로 말한다.
- 사용량 초기화 전에는 한도에 닿아도 되므로, 자리를 비워 두지 않고 채운다.
- 사용량: 사용자가 알려 준 사용량·초기화 시각을 기준으로 남은 작업량과 한도에 닿는 때를 추정해 보고한다(세션 수는 줄이지 않는다).
- **사용량 절약 규칙**(2026-10-23 사용자 요청. 세션 수 줄이기는 2026-11-02 결정으로 폐지, 나머지는 유지):
  - 모델: 쉬운 일은 Sonnet, DB·Edge·보안·원인 조사는 Opus.
  - 작업 세션은 PR을 만든 뒤 CI **첫 결과만** 보고하고 끝낸다. 최종 CI 확인과 merge는 CC가 한다.
  - CC 점검은 **60분** 주기에 완료 알림 중심으로 한다(아래 4절의 10~15분 점검보다 우선).
  - 원장 롤업은 **하루 1~2회**만 한다.
- **사용량 원인별 개선**(2026-10-23 03:51 사용자 결정 "모든 원인에 적용", 위 규칙보다 우선):
  - 시험 환경: 작업 세션은 **로컬 브라우저 E2E(Playwright)를 돌리지 않는다** — 설치·버전 문제로 시간이 새고 CI가 같은 검사를 한다. 로컬은 단위 시험·DB 시험만, 그것도 `docs/web-session-testing.md`(STAB-웹세션시험환경)의 정해진 방법으로만 띄운다. 환경이 막히면 30분 넘게 우회하지 말고 CI에 맡겼다고 보고한다.
  - 지시서에 순서를 처음부터 넣는다: DB migration·버킷·Edge가 있는 작업은 **DB(+짝 파일·시험)를 별도 PR로 먼저**, Edge·화면은 뒤 PR로 나누라고 처음부터 적는다(DB 적용 workflow는 main에 있는 파일만 적용함).
  - **끝난 세션을 다시 불러 일 시키지 않는다**(이전 기억 전체를 다시 읽어 처음만큼 든다). 후속은 작은 새 세션으로, 앞 PR·브랜치를 가리켜 시작한다. 단 '멈춤'으로 끊긴 세션의 이어 하기는 예외(위 규칙).
  - 모델: Opus는 **원인 모를 버그·보안 판단·설계**에만. 설계 문서가 있는 구현(DB migration 포함)·문서·화면 다듬기는 Sonnet.
  - 세션 지시에서 반복 확인을 뺀다: CI 대기·여러 번 재확인 금지, push는 의미 있는 진행마다(시간 기준 강제 없음).
  - CC 방은 길어질수록 매 답이 비싸진다. **반나절(또는 큰 묶음 끝)마다 방을 바꾼다.** 인계서는 짧게(기준선·진행 중·대기 줄·결정 대기만, 규칙은 이 문서 링크).
  - CC는 조회를 한 번에 묶고(gh api 여러 개를 한 명령으로), 결과 본문 전체를 읽지 않는다.

- **V38 사용자 직접 지시(2026-10-24 20:57·22:26)**: CC는 Opus, 작업 세션은 Sonnet(난도 때문에 Opus가 필요하면 사용자 승인 뒤). 검사는 간소화하고 중복 검사는 줄인다. 대기 줄 다음 세션 자동 채우기와 PR 자동 merge는 사용자의 직접 지시다.

- **전사·분석 Apps Script(`trascription` 프로젝트)도 CC 담당**(2026-10-25 02:34 사용자 결정, 10/24 '별도 대화 방만 고친다' 결정 대체). 스크립트에 Drive 폴더 ID·키 위치가 들어 있어 원문은 저장소에 두지 않고, 고친 판은 사용자에게 txt로 전달한다.

| 가. 폴더·목록·끌기 | 공용 폴더 나무·목록 줄·고르기(`select-mode`)·끌기·네모 고르기·우클릭 — 파일·자료실·노트 폴더·사진 |
| 나. 밀기·막대·메뉴 | 줄 밀기, 고르기 막대, ⋯·우클릭 메뉴 열고 닫기, 기록 줄 모양 |
| 다. 글 읽기 | 읽을 거리·저장한 글·브리핑 룸, 두 칸 보기, 고른 글 막대·형광펜 |
| 라. 노트 | 노트 편집기·보드 |
| 마. 찾기 | 검색칸·찾기 결과 |
| 바. 자료실·드라이브 서버 | `library-files`·`workspace-drive` 등 Edge 함수와 그 화면 |
| 사. 그 밖 | 일정·할 일·홈·조직·사업 등 — 화면마다 따로 한 줄 |

- 영역별 파일 경로 패턴은 `scripts/cc/lanes.json` 한 곳에 둔다(위 표는 이름만, 넣기 점검이 이 파일로 PR 영역을 판정).
- **영역마다 작업 세션은 한 번에 하나만 돈다.** 영역이 다르면 동시에 돌려도 된다.
- 같은 영역의 새 요청은 그 영역 대기 줄에 적고, 앞 PR이 merge된 뒤 띄운다. 급하면 앞 PR head 위에서 시작하는 뒤 세션으로 띄우고(AGENTS.md 2절 줄 세우기), merge도 그 순서로만 한다.
- 두 영역에 걸치는 일은 더 많이 만지는 영역 줄에 넣고, 그동안 다른 영역 세션은 그 파일을 만지지 않게 지시서에 적는다.
- 지시서 첫 줄에 영역 이름을 적는다(예: `영역: 가. 폴더·목록·끌기`).
- 지금 영역 줄 현황(누가 돌고 무엇이 기다리는지)은 CC가 인계서와 요청 추적표(`claude/cc-request-tracker.md`, 프로젝트 문서)에 둔다. 저장소에는 규칙만 둔다.

### 1-2. 확정 동작은 자동 확인으로 (2026-11-26 사용자 결정, 효율화 2)

- 사용자가 확정한 화면 동작(누르기·고르기·끌기·밀기·메뉴·찾기·줄 모양)은 **확정한 날** `docs/design/standard-interactions.md`에 ID 한 줄로 적는다(날짜·기대 동작·시험 이름). 시험이 아직 없으면 `시험: 만들 차례`라고 적는다.
- 그 동작을 만들거나 고치는 PR은 그 ID의 시험을 넣는다(`tests/app-e2e/standard-interactions.spec.mjs` 또는 지정한 시험 파일). 시험이 없으면 CC는 merge하지 않는다.
- 확정 동작 시험은 그 영역 파일을 고친 PR마다 돈다(관련 시험 대응표에 등록). main 전체 시험(AGENTS.md 9절)에서도 돈다.
- 결정이 바뀌면 같은 PR에서 옛 줄을 `대체됨 → 새 ID`로 표시하고 시험도 새 결정으로 바꾼다. 시험을 지우거나 건너뛰게 해서 통과시키지 않는다.
- 손짓·끌기·밀기를 만지는 PR은 그 영역의 확정 동작 시험이 모두 통과해야 merge한다.

### 1-3. 결정 장부 — 묻기 전에 먼저 찾기 (2026-11-26 사용자 결정, 효율화 3)

| 결정 종류 | 장부 |
| --- | --- |
| 화면 동작 | `docs/design/standard-interactions.md` (ID 표) |
| 모양·배치·디자인 | `docs/design-decisions.md` |
| 화면 글자 | `docs/design/ui-words.md` |
| 그 밖 제품·운영 결정 | `docs/roadmap.md` 해당 행, 운영은 이 문서 |

- CC와 작업 세션은 사용자에게 묻기 전에 위 장부, 프로젝트 기억, 지금 인계서를 먼저 찾는다. 찾았으면 묻지 않고 그대로 한다.
- 못 찾았을 때만 묻고, 답을 받은 날 장부에 적는다(CC가 그날 받은 결정을 묶어 문서 PR 하나).
- 인계서와 지시서에는 결정 전문을 다시 쓰지 않고 장부 ID·절 이름만 적는다.

## 2. merge와 승인

- CC가 PR의 변경 파일·diff·CI를 직접 검토하고 **문제 없으면 사용자에게 묻지 않고 merge**한다.
- **화면 검토**(2026-11-10 사용자 결정, UI-위쪽줄흰띠·여백 — "만들고 나서 검토를 안 하나"): 화면이 바뀌는 PR은 PC(1280)·폰(412) 화면 사진을 PR에 붙이고, CC가 여백·색·줄맞춤을 눈으로 본 뒤 merge한다. 사진이 없으면 merge하지 않고 세션에 사진을 요청한다.
  - **검증 판정 칸**(2026-11-27 사용자 요청 DESIGN-검증하네스 ①, 이유: 화면 시험은 동작만 보고, 고친 세션이 스스로 확인해 빠진 곳이 다시 지적됨): PR 본문 맨 위 "검증 판정"(확인함 / 못 봄 / 남은 문제 + PC 1280·폰 412 전후 사진, `.github/pull_request_template.md`)을 **고친 세션이 아닌 따로 띄운 검증 세션(Sonnet)**이 채운다. **CC는 판정 칸부터 읽고 merge한다.** 칸이 비었거나 '못 봄'·'남은 문제'가 있으면 merge하지 않는다. 화면이 안 바뀌는 PR은 "해당 없음" 한 줄.
  - **검증 세션 절차**: ① 고친 세션 완료·CI 초록 뒤 CC가 PR 번호만 주고 새 세션을 띄운다(고친 세션의 설명은 주지 않는다). ② PR 브랜치를 띄워 PC 1280·폰 412로 바뀐 화면을 직접 눌러 본다(여백·색·줄맞춤·잘림·하단바 가림·열 때 깜박임, 지시서 요구 항목, 같은 종류의 다른 화면). ③ 고치기 전(main)·후 사진을 같은 크기로 찍어 표에 붙인다. ④ 눌러 본 것은 '확인함', 못 한 것은 이유와 함께 '못 봄', 어긋난 것은 위치와 함께 '남은 문제'에 한 줄씩 쓴다(고치지는 않고 판정만). ⑤ PR 본문 맨 위를 고치고 댓글로 한 줄 알린다.
- `.github/` 변경은 CC가 diff를 직접 본다(권한·비밀값·트리거·필수 검사 삭제 여부). 필수 검사(`publication-gate`·`dropzone`·`browser-e2e`)를 지우거나 우회하는 변경은 merge하지 않는다.
- 같은 시험이 다른 실행에서 두 번 흔들리면 재실행하지 않고 안정화 과제로 고친다.
- **시험 고르기 확인**(2026-11-27 사용자 결정, AGENTS.md 9절 '시험 고르기는 계산 한 곳이 구조로 정한다'): 공용 부품(메뉴·팝업·크게 보기·공용 CSS·공용 JS)을 고친 PR이 '관련 시험만' 돌았으면 merge 전에 고르기 출력(`e2e-select` 단계의 `- 파일: 이유` 줄)을 본다. 빠진 화면이 보이면 그 PR에 시험을 손으로 더하게 하지 않고 `scripts/ci/e2e-select.mjs`를 고치는 PR을 먼저 줄 세운다. 공용 부품 PR 본문 5항에 반복 실행 결과(`--repeat-each`)가 없으면 merge하지 않고 요청한다.
- **임시안 알림**(2026-11-10 사용자 결정, OPS-결정안빠짐방지 — "내가 고른 게 왜 반영 안 되고 다른 게 반영된 거야"): 사용자가 고른 안(A안 등)의 핵심이 아직 안 들어간 PR(임시 조각·앞 단계만 한 PR)을 merge하면, merge 알림 한 줄에 반드시 `임시 — 고르신 ○안은 아직(다음 PR #n 또는 원장 행 ○○)`을 붙인다. 다음 PR 번호나 원장 행 이름이 없으면 merge 전에 원장 '남은 일' 행부터 만든다(3절). 사고(11/09 RECORD-한줄): 사용자 A안(AI 한 줄 요약)을 ① 임시 한 줄 ② DB 칸 ③ AI 한 줄로 나눴는데 ①만 merge됐고, ②③은 PR 본문 '남은 일'에만 있어 대기 줄에서 빠졌다. ① merge 때 '임시, 고른 A안은 아직' 알림도 없었다.
- **줄 뒤 PR은 초안(draft)으로 둔다**(2026-11-08 사용자 승인, S54-01): 줄 세운 PR이 한꺼번에 최신 main으로 올라가면 검사가 몰려 동시 실행 한도를 넘는다. 그래서 줄 뒤에 선 PR은 초안으로 두고, 초안일 때는 화면 시험(Playwright E2E) job만 skipped로 건너뛴다(빠른 검사·보안·node 시험·build는 그대로 돈다). 차례가 오면 CC가 초안을 풀고(ready_for_review) → 화면 시험을 포함한 전체 검사가 다시 돈다 → 녹색을 확인한 뒤 merge한다. 초안은 merge가 안 되므로 검사가 빠진 채 들어가지 않는다. 화면 시험은 필수 검사가 아니므로 초안을 푼 뒤 그 실행이 끝날 때까지 기다린다(skipped를 통과로 보지 않는다). 대상 workflow 목록은 `tests/security/ci-draft-e2e-skip.test.mjs`가 지킨다.
- **검사 다이어트 — 같은 검사를 여러 번 돌리지 않는다**(2026-11-08 사용자 승인, V54). 화면 시험(E2E)은 빼지 않는다(고장 난 채 들어가는 것을 막는 장치). 대신 돌리는 횟수를 줄인다. GitHub Pro 동시 실행 한도 40개에 PR 하나가 검사 약 25개를 쓰므로, 실제로는 PR 1~2개씩만 검사된다.
  1. **기차(묶음) 방식**: 준비된 PR(작업 세션이 끝냈고 빠른 검사가 녹색, 초안 상태)을 1~2시간마다 CC가 한 브랜치(`cc-train-N`, 최신 main에서)에 차례로 merge해 **묶음 PR 하나**로 화면 시험을 한 번만 돌린다. 녹색이면 묶음 PR을 squash merge하고, 원래 PR은 "묶음 #N에 포함" 댓글을 남기고 닫는다. 실패하면 실패한 시험이 닿는 파일로 원인 PR을 골라 그것만 빼고 다시 돌린다(같은 시험이 두 번 흔들리면 9절 안정화 규칙 그대로). 묶음 PR 본문에 들어간 PR 번호·원장 행·release-notes 파일 목록을 적는다.
  2. **이어진 줄은 맨 끝 PR 하나로**: 같은 세션이 앞 PR 위에 차례로 쌓은 PR(①→②→…)은 맨 끝 PR에 앞 PR이 모두 들어 있으면(`git merge-base --is-ancestor`로 확인) 맨 끝 하나만 검사·merge하고 앞 PR은 "포함" 댓글을 남기고 닫는다(예: #2121이 #2110~#2120을 품음).
  3. **겹치지 않으면 다시 맞추지 않는다**: 앞 PR이 main에 들어간 뒤, 뒤 PR과 바뀐 파일이 겹치지 않고 뒤 PR이 이미 녹색이면 update-branch로 검사를 다시 돌리지 않고 merge한다. 단 앞 PR이 **검사 자체를 더하거나 바꾼 PR**(`tests/security`·`.github/`·용어 검사 기준표 등)이면 예외로 update-branch 뒤 녹색을 본다(V53 교훈: #2100·#2117로 main이 빨개짐). merge 뒤 main에서 도는 검사가 빨개지면 CC가 바로 고친다.
  4. 하지 않는 것: PR에서 화면 시험을 빼고 main에서만 돌리기(main이 곧 운영 사이트), 공개 저장소에 사용자 PC를 검사 기계(self-hosted runner)로 붙이기(외부 코드가 그 PC에서 돈다).
- (2026-10-31부터 0절이 우선: 아래 승인 버튼이 걸려 있지 않으면 CC가 끝까지 하고, 걸려 있으면 그때만 사용자에게 링크를 준다.) **CC가 시작하고 사용자는 승인만**(2026-10-21 사용자 결정): CC 세션은 workflow를 시작할 수 있고(`workflow_dispatch`), 승인(environment reviewer)은 할 수 없다. 그래서
  - Edge 배포: CC가 `edge-function-deploy`를 정확한 function·ref·옵션으로 시작 → 사용자는 GitHub 알림에서 [Approve] 한 번 → CC가 결과(버전·401·OPTIONS)를 확인하고 되돌리기 ref를 기록.
  - basket-pc 릴리스: CC가 태그를 만들어 시작 → 사용자 승인 한 번.
  - DB 적용: CC가 `db-migration-apply`를 mode `apply`·migration 파일 이름으로 시작 → 사용자 승인 한 번 → workflow가 사전 확인·상태 저장(artifact)·시험 적용·적용·사후 확인을 차례로 하고 하나라도 실패하면 멈춤(되돌리기는 자동 아님, 사용자 결정). 확장 규칙이 거절한 migration(권한 확대 모양)만 SQL Editor 경로로 간다. 상세: `docs/ops-db-workflow.md` "승인 한 번 흐름".
- **사용자가 꼭 해야 하는 것**(CC가 대신 할 수 없음, 단계별 일상어 안내): 위 승인 버튼, 비밀값 값 입력(Supabase·GitHub), GitHub 설정, 사용자 PC에서의 시험.
- 인증 우회·RLS 약화·권한 확대는 해결책으로 쓰지 않는다.
- 연결 해제는 연결만 끊고 원본은 남긴다. 원본 삭제는 사용자가 직접 [삭제]를 누를 때만 한다. AI가 기능을 정리할 때는 데이터를 지우지 않는다(2026-10-23 19:28 사용자 정리).

## 3. 요청함

- Drive 문서 "Web2 요청함"을 **주기적으로**(점검 때마다, 최소 하루 몇 번) 확인한다.
- 새 요청(→ 접수 표시가 없는 덩어리)은 그 요청 아래에 `→ 접수: 과제이름 — 상태 (날짜)`를 붙이고, `docs/roadmap.md`에 행을 만들거나 기존 행에 합친다.
- 과제가 끝나면 접수 줄의 상태를 "완료 #PR"로 고친다(오래된 상태 표시를 남기지 않는다).
- **완료 대조(2026-11-02 사용자 결정)**: "PR merge = 완료"로 처리하지 않는다. 완료로 고치기 전에 요청 원문의 '할 것'·'완료 기준'과 사용자 결정 줄을 항목별로 PR 결과와 맞춰 본다.
  - 다 반영됐으면 `완료 #PR`.
  - 일부만 반영됐으면 `일부 완료 #PR · 남음: (빠진 항목 한 줄)`로 적고, 빠진 항목을 `docs/roadmap.md`에 '남은 일' 행으로 바로 올려 대기 줄에 넣는다(범위에서 일부러 뺀 조각도 같다).
  - 작업 세션 지시서에는 요청 원문 통째를 넣고, 완료보고 '요구와 다른 점'에 원문 항목별 반영 여부를 적게 한다.
- **PR 본문 '남은 일'은 merge 즉시 원장 행으로**(2026-11-10 OPS-결정안빠짐방지): PR 본문·완료보고에 '남은 일'·'다음 PR'·'범위에서 뺀 것'이 적힌 PR을 merge하면, CC는 같은 점검 안에 그 항목마다 `docs/roadmap.md` '남은 일' 행(이름 = 원래 과제 이름으로 시작, 상태 `대기`, 비고에 PR 번호와 사용자가 고른 안)을 문서 PR로 올리고, 요청함 접수 줄을 `일부 완료 #PR · 남음: …`으로 고친다. PR 본문에만 남은 일은 대기 줄에 없는 것으로 본다.
- 요청함 방의 1시간 점검도 '완료'로 바뀐 항목을 원문과 대조해, 빠진 항목이 있으면 그 접수 줄 아래에 `→ 대조: 남음 — (빠진 항목)`을 적는다.
- 결정이 필요한 질문은 CC 방에서 사용자에게 묻는다(질문은 한 번에 하나, 추천안과 함께).
- **덧붙임 알림(2026-11-03 사용자 결정, OPS-덧붙임알림)**: CC는 작업 지시서를 만들기 직전에 그 요청 덩어리를 요청함에서 **다시 읽어** 덧붙임 줄과 맨 아래 '덧붙임 알림' 줄까지 지시서에 넣는다. 요청함 방은 PR이 있거나 진행 중·끝난 요청에는 덧붙이지 않고 새 덩어리('앞 작업 ○○ 이어서')로 만들고, 아직 대기인 요청에 덧붙일 때도 맨 아래에 '덧붙임 알림' 한 줄을 새로 남긴다.

### 3-1. 요청함 대기 목록은 계산으로 본다 (2026-11-02 사용자 결정, 재발 방지)

사고(11/02): 요청함 방의 1시간 점검이 '→ 접수: … 대기(CC 전달)'만 적고 끝났고, CC 점검은 열린 PR·CI만 보았으며, 방을 바꿀 때 남은 일을 기억으로 넘겨 대기 요청 30여 건과 '완료로 적혔지만 빠진' 33건을 CC가 모른 채 지나갔다. 그래서 남은 일은 **기억이 아니라 요청함에서 계산한 목록**으로만 센다.

- 도구: `node scripts/ops/inbox-open.mjs <요청함.txt> --roadmap docs/roadmap.md` (요청함은 Drive에서 텍스트로 받아 임시 파일로 저장). 결과 = 끝나지 않은 요청 표(미접수·대기·일부·남음·결정 대기·진행 중·실기기 확인)와 원장 행 유무·지난 시간.
- 요청 덩어리는 `[날짜]`로 시작하는 것과 `■ 과제이름 (…)`으로 시작하는 것(11/06부터 요청함 방 형식) 둘 다 센다. ■ 덩어리는 과제 이름 = ■ 뒤 첫 낱말, 접수 시각 = 덩어리 안 '접수 MM/DD HH:MM' 줄, 상태 = 마지막 '→ 접수/대조:' 표시(없으면 '대기')이고, CC 작업 상황 절의 '■ 과제 → 완료: …' 한 줄 요약은 요청으로 세지 않는다(2026-11-10 OPS-요청함■세기). 대신 그 상황 줄이 같은 과제 이름(■ 뒤 첫 낱말) 요청 덩어리보다 뒤에 있으면 마지막 상황 줄이 그 요청의 상태가 된다(완료 #PR → 끝남, 진행 중 → 진행 중, 남음 → 일부·남음). 덩어리 안 마지막 표시가 '→ 대조:'이고 PR 번호가 없거나 상황 줄보다 큰 PR 번호를 적었으면 대조가 우선이다(S56-3b).
- **빠진 남은 일**(2026-11-10 OPS-결정안빠짐방지): 열린 PR 목록을 함께 주면(`--open-prs 열린PR.json`, `gh pr list --state open --json number,title` 결과 또는 '#번호 제목' 줄) '일부·남음'(→ 대조: 남음, 일부 완료 · 남음, 상황 줄 남음) 가운데 **열린 원장 행도 열린 PR도 없는 것**을 `빠진 남은 일 n건`으로 따로 센다. 열린 원장 행 = 과제 이름(또는 표시 줄에 적힌 원장 행 이름)과 같거나 그 이름으로 시작하는 행 중 상태가 완료·종료가 아니거나 '일부·남음·남은 일'이 적힌 행. 열린 PR = 표시 줄이 적은 PR 번호가 열려 있거나 PR 제목에 과제 이름이 있음. CC 점검은 늘 `--roadmap`과 `--open-prs`를 함께 주고, `빠진 남은 일`이 1건이라도 있으면 다른 일보다 먼저 원장 '남은 일' 행을 올린다. 시험: `tests/ops-inbox-gap.test.mjs`.
- 결과 표는 공개 저장소(PR·문서·커밋)에 붙이지 않는다(제목에 업무 내용이 섞일 수 있음). CC 방 보고와 비공개 인계서에만 쓴다.
- **CC 점검마다** 이 도구를 돌린다. '미접수'·'원장 행 없음'·'대기 6시간 넘음'이 하나라도 있으면 다른 일보다 먼저: 원장 행을 만들고(문서 PR), 같은 파일끼리 묶어 대기 줄에 세우고, 결정이 필요한 것은 결정 목록으로 옮긴다.
- 낡은 접수 줄(실제로는 끝난 것)은 근거(PR·파일)를 확인한 뒤 요청함 접수 줄을 `완료 #PR`로 고쳐 계산에서 빠지게 한다. 확인 없이 지우지 않는다.
- 완료 표시는 `완료 #PR`처럼 '완료' 바로 뒤에 PR 번호를 쓴다. `완료 DB #1384`·`완료(…) #1121`·`완료: …`처럼 사이에 다른 글자가 끼면 계산 도구가 끝난 것으로 못 읽는다(11/03 V49에서 이런 줄 20여 건을 `→ 대조: 완료 #PR`로 다시 적음).
- 요청함 방의 '대기(CC 전달)'는 CC의 할 일이다. 요청함 방은 접수 뒤 6시간이 지나도 원장 행·PR이 없으면 사용자에게 'CC 미착수 n건' 알림을 보낸다(요청함 점검 예약 작업 7번).
- 매주 월요일 아침 '완료 대조' 예약 작업이 지난 1주 '완료'로 적힌 요청을 원문 항목과 대조해 빠진 것을 `→ 대조: 남음`으로 적는다. 그 줄은 다음 계산에서 '일부·남음'으로 잡힌다.

### 3-2. 요청함 방 (2026-11-10 사용자 결정, OPS-결정안빠짐방지)

요청함 방(Drive 'Web2 요청함'을 정리하는 채팅방)의 규칙을 둘 저장소 문서가 따로 없어 여기에 둔다. 요청함 방 인계서 맨 앞에 이 절 링크를 둔다.

- **새 방 첫 일**: 요청함 방도 새 방을 열면 일을 받기 전에 요청함의 '→ 대조: 남음'·'일부 완료 · 남음' 항목 **전부**를 열린 PR·원장 행과 맞춰 표(과제 | 남은 것 | 열린 PR | 원장 행 | 판정)로 먼저 보고한다. 표는 3-1절 계산(`--roadmap`·`--open-prs` 함께)의 '빠진 남은 일' 줄을 그대로 쓴다. 기억으로 쓰지 않는다.
- 판정이 '빠짐'(열린 PR·원장 행 둘 다 없음)인 항목은 그 접수 줄 아래 `→ 대조: 남음 — (빠진 항목) · 원장 행 없음`을 적고 CC에 넘긴다(요청함 방은 요청함 문서만 고친다, 0절). CC는 3-1절대로 원장 행을 먼저 올린다.
- 사용자가 여러 안 중 하나를 고른 요청은 접수 줄에 고른 안을 그대로 적는다(`— 사용자 A안(…)`). 대조할 때 고른 안의 핵심이 들어갔는지를 먼저 본다. 임시 조각만 들어갔으면 `완료`가 아니라 `일부 완료 #PR · 남음: 고른 A안 핵심`이다.
- 결과 표는 공개 저장소에 붙이지 않는다(3-1절). 요청함 방 보고·비공개 인계서에만 쓴다.

- 작업 세션 완료 알림을 받으면 바로 리뷰·merge·다음 과제 투입.
- 그 사이 10~15분마다 예약 점검(`send_later`)으로 열린 PR·CI·세션 생존·요청함을 본다. 요청함은 '새 요청'만 보지 말고 **3-1절 대기 목록 계산**을 돌려 숫자로 본다(1시간에 한 번 이상).
- **main 시험 깨짐 확인**(2026-11-27 사용자 결정): 점검마다 `gh api 'repos/mj880616/work/issues?state=open&per_page=100' --jq '.[] | select(.title == "main 시험 깨짐") | .number'`로 본다. 번호가 나오면 다른 앱 PR merge를 멈추고, 이슈 글의 실패한 시험(파일:줄)부터 고치는 세션을 줄 맨 앞에 띄운다(AGENTS.md 9절). 이슈는 main이 다시 통과하면 저절로 닫힌다.
- 컨테이너가 재시작되면 작업 세션이 모두 멈춘다(10/23 12:00·20:00경). 점검 때 ListAgents·브랜치 갱신 시각으로 확인하고 push 상태부터 이어 띄운다.

### 4-1. 작업 속도 규칙 (2026-11-10 사용자 요청 OPS-작업속도 "작업 하나에 1~2시간 — 10분 안쪽으로, 제발 좀")

사실(11/10 merge된 PR 54개, `scripts/ops/work-timing.mjs`): PR 열림 → merge 가운데 33분·최대 155분. 그 가운데 화면 시험이 약 15분(가장 느린 갈래 16분), **시험이 끝난 뒤 merge까지 기다림이 가운데 10분·최대 73분**(CC 점검이 10~15분 간격). 시간 표: `docs/ops-ci-timing.md`.
목표: 작은 화면 손보기 접수 → 배포 20~30분, 보통 일 40분 안쪽. 시험은 줄이지 않는다(AGENTS.md 9절).

- **30분 안에 첫 PR**: 지시서 맨 위(📱/💻 표시 바로 뒤)에 "30분 안에 첫 커밋 push·PR(초안 아님) 열기"를 넣는다. 세션은 처음부터 끝까지 다 만들고 PR을 여는 대신, 첫 조각으로 PR을 열고 이어서 push한다.
- **멈춘 세션 30분 규칙**: 세션을 띄우고 30분 안에 커밋·PR이 없거나, PR 없이 마지막 commit 뒤 30분이 지나면 멈춘 것으로 본다. CC는 점검 때 `node scripts/ops/work-timing.mjs`의 '멈춘 세션 의심' 줄로 자동으로 찾고, 그 세션을 끄고(예약 작업 끄기) 브랜치 push 상태부터 이어받거나 작은 새 세션으로 다시 띄운다. 2시간 결과 없음을 그대로 두지 않는다.
- **시험 진행 중이면 점검 5분**: 열린 PR의 화면 시험이 돌고 있으면 CC 점검(`send_later`) 간격을 5분으로 줄인다. 시험이 끝나 녹색이면 그 점검에서 바로 merge한다(2절 검토 기준은 그대로). 돌고 있는 시험이 없으면 4절 10~15분 간격으로 돌아간다.
- **같은 파일 작은 손보기는 한 세션**: 같은 파일(같은 화면)을 만지는 작은 손보기 여러 건은 한 세션·한 PR로 묶어 화면 시험을 한 번만 돌린다(1절 '같은 파일' 규칙과 같음, 되돌림 → 다시 고침처럼 같은 자리를 두 PR로 오가지 않는다).
- **걸린 시간 기록**: 일마다 '접수 → 띄움 → PR → 시험 끝 → merge → 배포' 시각을 남긴다. 접수·띄움 시각은 CC가 인계서(비공개)에 적고, PR → 배포는 `work-timing.mjs`가 GitHub에서 계산한다. **2시간 보고 '1 한 일' 끝에 그 2시간 동안 merge한 일의 가운데 값**(열림 → merge, 시험 끝 → merge 기다림, 열림 → 배포)과 멈춘 세션 수를 숫자로 적는다.

## 5. 보고 양식 (사용자에게)

- **한국어 의무(V37부터, AGENTS.md 10절)**: 커맨드센터 답, 작업 세션 지시서, 작업 세션 최종 보고, PR 본문·댓글 모두 한국어로 쓴다. 코드·명령·파일 이름·오류 원문만 원문 그대로 둔다. 위반하면 즉시 한국어로 다시 쓴다.
- 일상어, 결론 먼저. 기술 용어는 필요할 때만 짧게 풀어서.
- 사용자 단계는 **번호 매긴 한 단계씩**(어느 화면 → 어느 버튼 → 무엇을 입력 → 무엇이 나오면 정상), 링크는 바로 누를 수 있게.
- 상황 보고 기본 틀:
  1. 완료(merge·DB·배포) — 무엇이 바뀌었는지 한 줄씩
  2. 진행 중(평소 최대 4개) — 무엇을 하는지
  3. 사용자 님 차례 — 순서대로
  4. 남은 대기 줄 — 순서대로. 맨 앞에 3-1절 계산 숫자를 그대로 적는다(예: '요청함 남은 요청 n건 — 진행 a · 대기 b · 결정 c · 실기기 d · 원장 행 없음 e'). 기억으로 쓰지 않는다.
  5. 결정 필요 — 추천안 포함, "ㅇㅋ면 추천대로"
- 남은 작업을 보고할 때는 대기 줄을 빠짐없이 적는다(길면 접되 빼지 않는다).
- 큰 그림을 물으면 시스템 영역별 완성도 표(모으기·Web2 기록·Web2 AI·원장·Claude 읽기·주간보고·업무 참모·아침신문).
- 예상 종료 시각을 물으면 사용자 단계를 바로 해 준다는 전제의 시간표와, 오늘 못 끝나는 것(이유 포함)을 나눠 답한다.

- **3시간마다 작업 상황 보고**(2026-10-24 22:29 사용자 지시). 양식: 1. 완료한 작업 2. 진행 중 작업 3. 남은 작업(예상 소요 시간·종료 시각, 원장·요청함 검토 포함 — 완료한 작업의 원장·요청함 갱신은 CC 몫) 4. 사용자가 할 일.

## 6. 원장(`docs/roadmap.md`) 갱신

- 작업 PR은 원장을 고치지 않는다. CC가 merge 뒤 문서 전용 PR로 한 번에 갱신한다(맨 위 상태 줄 + 해당 행 상태·PR·한 줄 요약 + 새 행).
