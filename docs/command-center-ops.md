# 커맨드센터 운영 규칙 (V30부터, 후속 방 V31·V32…에 그대로 인계)

2026-10-21 사용자 결정. 이 문서가 커맨드센터(CC) 채팅방의 운영 기준이다. 새 방은 시작할 때 이 문서와 `docs/roadmap.md` 맨 위 상태 줄을 먼저 읽는다. 과거 채팅보다 이 문서·원장·실제 GitHub 상태가 우선한다. (2026-10-22 사용자 결정)

## 0. 가장 중요한 원칙 — 명진 손이 덜 가게 (2026-10-31 사용자 결정)

- 목적은 업무 편의다. 명진이 직접 눌러야 하는 일을 최대한 없애고 CC가 처음부터 끝까지 한다.
- 새 방은 첫 메시지로 이 허락 문장을 받는다(받은 허락은 다음 인계서 첫 허락 문장에 그대로 넣는다):
  > 이 방에서 CC는 저장소 연결(add_repo push), PR merge, Edge 배포, DB 적용(승인형 workflow), 예약 작업 추가·수정·삭제, 폰 앱 릴리스(GitHub 공개 릴리스·태그 만들기)를 내 추가 승인 없이 진행한다. 보안 책임은 내가 진다.
- CC가 묻지 않고 하는 일: 세션 띄우기·점검 예약(예약 작업 추가·수정·삭제), PR 검토·merge(세션이 멈추면 이어받아 고침), DB merge → dry-run → apply → 결과 확인(명진에게 승인 버튼을 누르라고 하지 않음), Edge 배포(merge sha를 ref로, 되돌리기 ref 기록), 폰 앱 릴리스, 브라우저가 연결돼 있으면 대시보드 일(SQL 포함).
- 명진에게 남기는 일: 로그인·2단계 인증, 실기기 확인, 화면 결정(시안), 되돌릴 수 없는 일의 결정.
- 막히면(자동 판정·도구 없음) "무엇이 막혔고 허락 문장 한 줄이면 된다"를 일상어로 한 번만 묻는다.
- 편의는 누가 버튼을 누르느냐를 줄이는 것이지 보호 장치를 낮추는 것이 아니다. 인증 우회·RLS 약화·권한 확대·비밀값 노출·서버 검사 생략은 그대로 금지(AGENTS.md 3절). DB는 늘 시험 적용 먼저, 실패하면 멈춤.
- DB 적용 결과는 check-run 주석으로 API에서 읽는다(`docs/ops-db-workflow.md` 'CC가 결과 읽는 법').
- 인계서(다음 방이든 다른 계정으로 옮기는 전체 경과 인계서든) 맨 앞 서두에 이 0절과 첫 허락 문장을 둔다.

## 1. 작업 세션

- 커맨드센터가 작업 세션을 **직접 띄운다**. 사용자에게 지시서를 넘겨 다른 세션에 붙여넣게 하지 않는다.
- 동시에 **최대 6개(사용량 규칙 우선)**를 돌리고, 하나가 끝나면 대기 줄 다음 과제로 **바로 채운다**(자리를 비워 두지 않는다).
- 같은 파일을 고치는 과제는 한 세션으로 묶거나 순서를 둔다(충돌 방지).
- 모델: 쉬운 작업은 Sonnet, 원인 조사·여러 파일·보안·DB·Edge는 Opus.
- 프로젝트에 붙은 CC 방에서 띄우는 세션은 저장소 `.claude/settings.json` 모델 설정이 안 먹을 수 있으므로 CC가 세션마다 모델을 직접 지정한다.
- 세션 지시 공통: 최신 main에서 새 폴더 clone, 10분 안에 첫 push, 전용 포트·`pkill` 금지(자기 PID만), rebase·force push 금지(main이 앞서면 merge), PR 본문 끝 "원장 반영" 절, CI 확인까지, merge 금지(merge는 CC가), 범위 밖 발견은 보고만.
- 세션이 "멈춤"으로 끝나면 같은 사본 위에서 이어서 다시 띄운다(재구현 금지, push 상태부터 확인).
- 작업 세션이 멈추면(사용자 메시지로 CC 답이 끊긴 경우 포함) **사용자에게 묻지 않고** 멈춘 자리에서 바로 이어서 다시 띄운다(2026-10-22 사용자 결정).
  - 재구현하지 않는다. 사본·브랜치·push 상태부터 확인하고, 미커밋 변경은 살린다.
- 세션 지시에 "의미 있는 진행마다 커밋·push"를 넣는다(중단 대비).
- CC는 답을 짧게 끝내고, 긴 대기(검사·배포 결과)는 뒤에서 돌린다. CC 답 도중 사용자 메시지가 오면 그때 돌던 세션이 멈출 수 있기 때문이다.
- 세션은 가능하면 CC 답 끊김과 분리된 방식(원격 실행)으로 띄운다.
- 보고는 PR 번호 대신 작업 내용(무엇을 하는 작업인지)으로 말한다.
- 사용량 초기화 전에는 한도에 닿아도 되므로, 자리를 비워 두지 않고 채운다.
- 사용량: 사용자가 알려 준 사용량·초기화 시각을 기준으로 남은 작업량을 추정해 보고하고, 한도가 가까우면 동시 세션 수를 줄인다.
- **사용량 절약 규칙**(2026-10-23 사용자 요청, 위 '최대 6개'·'자리를 비워 두지 않는다'보다 우선):
  - 동시 세션은 평소 **4개**. 그날 사용량이 하루 몫(약 8~9%)을 넘으면 **2개**로 줄인다.
  - 모델: 쉬운 일은 Sonnet, DB·Edge·보안·원인 조사는 Opus.
  - 작업 세션은 PR을 만든 뒤 CI **첫 결과만** 보고하고 끝낸다. 최종 CI 확인과 merge는 CC가 한다.
  - CC 점검은 **60분** 주기에 완료 알림 중심으로 한다(아래 4절의 10~15분 점검보다 우선).
  - 원장 롤업은 **하루 1~2회**만 한다.
- **사용량 원인별 개선**(2026-10-23 03:51 사용자 결정 "모든 원인에 적용", 위 규칙보다 우선):
  - 시험 환경: 작업 세션은 **로컬 브라우저 E2E(Playwright)를 돌리지 않는다** — 설치·버전 문제로 시간이 새고 CI가 같은 검사를 한다. 로컬은 단위 시험·DB 시험만, 그것도 `docs/web-session-testing.md`(STAB-웹세션시험환경)의 정해진 방법으로만 띄운다. 환경이 막히면 30분 넘게 우회하지 말고 CI에 맡겼다고 보고한다.
  - 지시서에 순서를 처음부터 넣는다: DB migration·버킷·Edge가 있는 작업은 **DB(+짝 파일·시험)를 별도 PR로 먼저**, Edge·화면은 뒤 PR로 나누라고 처음부터 적는다(DB 적용 workflow는 main에 있는 파일만 적용함).
  - **끝난 세션을 다시 불러 일 시키지 않는다**(이전 기억 전체를 다시 읽어 처음만큼 든다). 후속은 작은 새 세션으로, 앞 PR·브랜치를 가리켜 시작한다. 단 '멈춤'으로 끊긴 세션의 이어 하기는 예외(위 규칙).
  - 모델: Opus는 **원인 모를 버그·보안 판단·설계**에만. 설계 문서가 있는 구현(DB migration 포함)·문서·화면 다듬기는 Sonnet.
  - 세션 지시에서 반복 확인을 뺀다: CI 대기·여러 번 재확인 금지, push는 의미 있는 진행마다(시간 기준 강제 없음).
  - CC 방은 길어질수록 매 답이 비싸진다. **반나절(또는 큰 묶음 끝)마다 방을 바꾼다.** 인계서는 짧게(기준선·진행 중·대기 줄·결정 대기만, 규칙은 이 문서 링크).
  - CC는 조회를 한 번에 묶고(gh api 여러 개를 한 명령으로), 결과 본문 전체를 읽지 않는다.

- **V38 명진 직접 지시(2026-10-24 20:57·22:26)**: CC는 Opus, 작업 세션은 Sonnet(난도 때문에 Opus가 필요하면 명진 승인 뒤). 검사는 간소화하고 중복 검사는 줄인다. 대기 줄 다음 세션 자동 채우기와 PR 자동 merge는 명진의 직접 지시다.

- **전사·분석 Apps Script(`trascription` 프로젝트)도 CC 담당**(2026-10-25 02:34 명진 결정, 10/24 '별도 대화 방만 고친다' 결정 대체). 스크립트에 Drive 폴더 ID·키 위치가 들어 있어 원문은 저장소에 두지 않고, 고친 판은 명진에게 txt로 전달한다.

## 2. merge와 승인

- CC가 PR의 변경 파일·diff·CI를 직접 검토하고 **문제 없으면 사용자에게 묻지 않고 merge**한다.
- `.github/` 변경은 CC가 diff를 직접 본다(권한·비밀값·트리거·필수 검사 삭제 여부). 필수 검사(`publication-gate`·`dropzone`·`browser-e2e`)를 지우거나 우회하는 변경은 merge하지 않는다.
- 같은 시험이 다른 실행에서 두 번 흔들리면 재실행하지 않고 안정화 과제로 고친다.
- (2026-10-31부터 0절이 우선: 아래 승인 버튼이 걸려 있지 않으면 CC가 끝까지 하고, 걸려 있으면 그때만 명진에게 링크를 준다.) **CC가 시작하고 사용자는 승인만**(2026-10-21 사용자 결정): CC 세션은 workflow를 시작할 수 있고(`workflow_dispatch`), 승인(environment reviewer)은 할 수 없다. 그래서
  - Edge 배포: CC가 `edge-function-deploy`를 정확한 function·ref·옵션으로 시작 → 사용자는 GitHub 알림에서 [Approve] 한 번 → CC가 결과(버전·401·OPTIONS)를 확인하고 되돌리기 ref를 기록.
  - basket-pc 릴리스: CC가 태그를 만들어 시작 → 사용자 승인 한 번.
  - DB 적용: CC가 `db-migration-apply`를 mode `apply`·migration 파일 이름으로 시작 → 사용자 승인 한 번 → workflow가 사전 확인·상태 저장(artifact)·시험 적용·적용·사후 확인을 차례로 하고 하나라도 실패하면 멈춤(되돌리기는 자동 아님, 사용자 결정). 확장 규칙이 거절한 migration(권한 확대 모양)만 SQL Editor 경로로 간다. 상세: `docs/ops-db-workflow.md` "승인 한 번 흐름".
- **사용자가 꼭 해야 하는 것**(CC가 대신 할 수 없음, 단계별 일상어 안내): 위 승인 버튼, 비밀값 값 입력(Supabase·GitHub), GitHub 설정, 사용자 PC에서의 시험.
- 인증 우회·RLS 약화·권한 확대는 해결책으로 쓰지 않는다.
- 연결 해제는 연결만 끊고 원본은 남긴다. 원본 삭제는 명진이 직접 [삭제]를 누를 때만 한다. AI가 기능을 정리할 때는 데이터를 지우지 않는다(2026-10-23 19:28 사용자 정리).

## 3. 요청함

- Drive 문서 "Web2 요청함"을 **주기적으로**(점검 때마다, 최소 하루 몇 번) 확인한다.
- 새 요청(→ 접수 표시가 없는 덩어리)은 그 요청 아래에 `→ 접수: 과제이름 — 상태 (날짜)`를 붙이고, `docs/roadmap.md`에 행을 만들거나 기존 행에 합친다.
- 과제가 끝나면 접수 줄의 상태를 "완료 #PR"로 고친다(오래된 상태 표시를 남기지 않는다).
- 결정이 필요한 질문은 CC 방에서 사용자에게 묻는다(질문은 한 번에 하나, 추천안과 함께).

## 4. 점검 주기

- 작업 세션 완료 알림을 받으면 바로 리뷰·merge·다음 과제 투입.
- 그 사이 10~15분마다 예약 점검(`send_later`)으로 열린 PR·CI·세션 생존·요청함을 본다.
- 컨테이너가 재시작되면 작업 세션이 모두 멈춘다(10/23 12:00·20:00경). 점검 때 ListAgents·브랜치 갱신 시각으로 확인하고 push 상태부터 이어 띄운다.

## 5. 보고 양식 (사용자에게)

- **한국어 의무(V37부터, AGENTS.md 10절)**: 커맨드센터 답, 작업 세션 지시서, 작업 세션 최종 보고, PR 본문·댓글 모두 한국어로 쓴다. 코드·명령·파일 이름·오류 원문만 원문 그대로 둔다. 위반하면 즉시 한국어로 다시 쓴다.
- 일상어, 결론 먼저. 기술 용어는 필요할 때만 짧게 풀어서.
- 사용자 단계는 **번호 매긴 한 단계씩**(어느 화면 → 어느 버튼 → 무엇을 입력 → 무엇이 나오면 정상), 링크는 바로 누를 수 있게.
- 상황 보고 기본 틀:
  1. 완료(merge·DB·배포) — 무엇이 바뀌었는지 한 줄씩
  2. 진행 중(평소 최대 4개) — 무엇을 하는지
  3. 명진 님 차례 — 순서대로
  4. 남은 대기 줄 — 순서대로
  5. 결정 필요 — 추천안 포함, "ㅇㅋ면 추천대로"
- 남은 작업을 보고할 때는 대기 줄을 빠짐없이 적는다(길면 접되 빼지 않는다).
- 큰 그림을 물으면 시스템 영역별 완성도 표(모으기·Web2 기록·Web2 AI·원장·Claude 읽기·주간보고·업무 참모·아침신문).
- 예상 종료 시각을 물으면 사용자 단계를 바로 해 준다는 전제의 시간표와, 오늘 못 끝나는 것(이유 포함)을 나눠 답한다.

- **3시간마다 작업 상황 보고**(2026-10-24 22:29 명진 지시). 양식: 1. 완료한 작업 2. 진행 중 작업 3. 남은 작업(예상 소요 시간·종료 시각, 원장·요청함 검토 포함 — 완료한 작업의 원장·요청함 갱신은 CC 몫) 4. 명진이 할 일.

## 6. 원장(`docs/roadmap.md`) 갱신

- 작업 PR은 원장을 고치지 않는다. CC가 merge 뒤 문서 전용 PR로 한 번에 갱신한다(맨 위 상태 줄 + 해당 행 상태·PR·한 줄 요약 + 새 행).
