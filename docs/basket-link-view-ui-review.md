## 화면과 공통 처리

- `basket-link-records.js`가 같은 업무공간 confirmed note→조직/프로젝트 조회, 기존 100행 페이지 방식, summary 검증, CAS 수정 RPC, 읽기용 행과 메모리 편집기를 공유한다. 링크/메모 업무공간을 함께 제한하며 Google 할 일·suggested 링크를 섞지 않는다. 보관/AI 제외는 상세 읽기 제외 사유가 아니다. 조회 실패를 빈 목록으로 바꾸지 않는다.
- 연결 미리보기의 조직·프로젝트마다 기록 요약을 고친다. 기본값은 옛 AI 답 reason이며, reason/schema_version:1/5종 파서 호환은 유지한다. 새 RPC 호출은 승인한 summary를 명시하고 기존 summary 미지정 호출도 유지한다. 선택/검증 오류/일부 성공 후 미처리 초안을 보존한다. Unicode 공백(NEL/BOM 포함)·2,000 code point를 DB와 같은 기준으로 검사하며 양끝 공백을 자르지 않는다. 중복 탭을 잠그고 불명 응답은 현재 연결 확인을 요구하며 자동 재전송하지 않는다. 동시에 이미 연결된 목적지가 있으면 실제 서버 요약을 재조회한다.
- 조직은 기존 기록과 메모 날짜 순으로 섞고, 기존 삭제는 기존 조직 기록에만 붙인다. 프로젝트는 진행기록 안의 접힌 native details 목록에 날짜·요약·원문·수정을 표시한다. 상위 링크·하위 목록·⋯ 메뉴 분리는 유지한다.
- 홈 이번 주 조직 기록은 활성+내 담당 조직만 읽는다. 두 종류를 함께 메모/기록 occurred_at 기준으로 정렬한 뒤 최신5개를 선택한다. KST 범위·미세초·안정적인 ID/종류 추가 정렬을 사용한다. 새 저장소 없이 기존 소유자/업무공간 캐시에 승인 요약 최대80 code point·종류·원문 경로용 메모 ID만 저장한다. 옛 캐시 형식과 정리 규칙은 유지한다. NULL은 요약 없음이며 원문 발췌를 요약으로 저장하지 않는다.
- 요약 수정은 읽었던 정확한 문자열/NULL을 p_expected_summary로 보낸다. RPC 성공 뒤 서버 값을 다시 읽는다. 충돌/통신 결과 불명은 초안을 보존하고 최신 요약 확인을 요구한다. 최신 확인 후에도 사용자가 저장을 다시 눌러야 한다. 없음·권한 없음·기능 미준비·입력 오류·통신 불명은 서로 다른 일상어로 표시한다.
- 닫기/뒤로가기/화면·세션 전환과 늦은 조회/저장을 보호한다. 원래 편집기 DOM은 버린 뒤 응답으로 복원하지 않으며 같은 로그인/업무공간의 늦은 저장은 새 화면의 기록을 다시 조회하게 한다. 다른 세션의 응답은 적용하지 않는다. 명시적으로 비운 runtime 문맥은 예전 boot 문맥/이전 담당조직 사용자로 대체하지 않으며, 읽기 메서드가 없는 기존 runtime에만 인증된 기존 fallback을 사용한다. 이 경우를 RED→GREEN으로 검증했다. AI 답/편집 초안/복사 전문을 새 브라우저 저장소에 저장하지 않는다. #504 복사/대체 상자/닫기/전환 비움은 유지한다.
- HTML·스크립트 같은 글은 텍스트로 이스케이프한다. 기능 모듈은 업무 원문·요약·토큰을 로그에 남기지 않는다. 공개 fixture·문서·캡처는 합성 데이터만 사용한다.

## AI 안내

reason의 의미는 기록 요약이다. 한 줄에 원문 날짜·요일·시간·장소·주체·대상·숫자·상태를 보존하고, 없는 사실을 만들지 않는다. 합성 원문과 좋은/나쁜 예를 포함하며 날짜/시간 등을 빠뜨린 일반 문장만 쓰지 않게 안내한다. 브라우저 복사 글과 배포 내부 Edge 안내는 전문 동일성 검사를 통과한다. Edge import는 supabase/functions 내부에만 있다. 원문·상한·담당조직 필터·프로젝트 목적지·AI 제외/보관 제외·메모 지시 무시는 유지한다. [합성 예](basket-record-summary-example.txt).

## Drive 조직 문서 최근4주 연결 요약 조사 · 구현 없음

현재 `drive-summary/core.mjs`는 조직 문서에서 기존 app_suborganization_updates만 최근4주 occurred_at으로 출력한다. noteLinks는 id/note_id/status만 읽으며 원문 notes는 보관 제외·ai_export_allowed=true로 읽는다. 조직 연결 summary는 현재 조직 문서에 출력하지 않는다.

후속 제안: 기존 두 문서와 같은 ID를 유지하고, 추가 읽기 전용 조회로 같은 업무공간 confirmed note→organization의 summary/메모 occurred_at을 가져와 조직별 기존 업데이트와 합쳐 시간순으로 출력한다. 날짜는 연결/수정 시각이 아닌 메모 시각이며 기존 KST 4주 도구를 재사용한다. NULL은 요약 없음+로그인 필요 원문 링크만 쓰고 원문 일부를 자동 요약으로 채택하지 않는다. 외부 AI용 사본은 현재 AI 포함 허용/보관 제외를 유지하는 방안을 권장한다(UI 읽기 정책과 구분). 조직 문서에도 별도 크기/행 상한과 초과 실패 표시를 설계해야 한다. 현재 1MiB 상한은 프로젝트 문서의 바구니 절만 보호하므로 조직 출력에 그대로 있다고 가정하면 안 된다. 이 후속 조회/출력·이관/요약 자동 갱신은 이번 PR에 구현하지 않았다.

## 운영 순서 · 이번에는 PR/자동 CI 확인 뒤 정지

현재 운영 drive-summary **v6**, source **`e1d74835f62a4a15e8c35905475c6869ebb4c973`**(#502). 시작 시 원장과 Edge 표5절을 대조하고 git으로 전체 SHA를 확인했다. 운영 접속으로 재확인한 값은 아니다. 실제 배포 직전 CC가 운영 소스 전체 SHA를 다시 대조하고 그 값을 되돌리기 ref로 고정한다. 운영 버전 표를 미리 올리지 않았다.

1. CC 검토 → 사용자 “머지” → 화면 PR squash merge.
   무엇이 바뀌나: 승인 요약 편집/연결 기록 표시 화면이 바뀐다.
   잘못되면: 기록을 읽거나 연결/요약을 고치는 화면이 불편하거나 실패할 수 있다.
   되돌리는 방법: 화면 PR revert로 이전 화면을 복원한다. UI 문제로 DB summary 칸이나 저장된 요약을 삭제하지 않는다.
2. 사용자가 drive-summary 승인 버튼으로 재배포.
   무엇이 바뀌나: 다음 Drive 사본 갱신부터 바구니 안내가 기록 요약 기준이 된다.
   잘못되면: 사본 갱신/안내가 잘못되거나 배포 후 검증이 실패할 수 있다.
   되돌리는 방법: 직전 운영 소스 전체 SHA(현재 기준 위 e1d74835… 전체)를 ref로 같은 승인 절차로 재배포한다.
   입력: function=drive-summary, ref=화면 PR merge 뒤 main의 고정 SHA, verify_jwt=keep, first_deploy=false, expect_unauth_401=true.
   성공 기준: version 증가·JWT 기존 false 유지·비로그인 POST401·OPTIONS200/204. workflow 실패가 이미 수행한 배포를 자동 취소하지 않으므로 결과를 CC가 확인한다.
3. 사용자 폰 확인.
   무엇이 바뀌나: 폰에서 실제 승인 요약/표시/원문 열기를 확인한다.
   잘못되면: 오류 위치를 기록하고 추가 연결/수정을 멈춘다.
   되돌리는 방법: CC가 UI PR revert 또는 위 Edge 소스 복원 중 해당 부분을 검토한다. DB가 필요하면 별도 검토한다.
   순서: **AI 결과 넣기 → 요약 고치기 → 연결하기 → 담당조직 상세·프로젝트 상세·홈 확인 → 요약 수정 → 원문 열기**. NULL 기존 연결·보관 원문도 확인한다.
4. CC가 운영 버전·소스·폰 확인을 문서 PR로 기록.
   무엇이 바뀌나: 실제 확인한 배포/폰 결과가 원장과 Edge 표에 남는다.
   잘못되면: 기록 오류를 바로잡는 문서 PR을 만든다.
   되돌리는 방법: 문서 PR 수정/revert이며 운영 화면이나 저장된 요약을 지우지 않는다.

DB 복구가 꼭 필요하면 CC가 기존 요약 보존·전체 행 대조·원자적 SQL Editor 복구를 별도로 검토한다. 현 정책상 이번 DB rollback 버튼은 사용할 수 없다. DB 재적용/수정·운영 접속·Edge 배포·workflow 수동 실행/재실행·승인·merge를 이번 세션에서 수행하지 않는다. 전체 작업 상태는 배포/폰 확인 전까지 진행중이다.
