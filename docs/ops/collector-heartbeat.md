# 수집 점검 신호 설정 안내 (OPS-수집점검 2단계)

Web2 홈 "마지막 수집 시각" 칸의 **텔레그램 수집**·**통화 녹음 전사** 두 줄을 보이게 하는 설정이다.

## 왜 이렇게 하나

- Web2는 자기가 만든 Drive 파일만 볼 수 있다(권한 `drive.file`). 텔레그램 수집 프로그램·전사 스크립트가 만든 파일은 못 본다. 권한을 넓히지 않는다.
- 그래서 반대로, 명진 님 Google 계정의 **앱 스크립트**(Drive를 다 볼 수 있음)가 1시간마다 **시각과 건수만** Web2에 알려 준다.
  - 텔레그램: `messages` 폴더 안 월별 폴더(예: `2026-10`)에서 가장 최근 메시지 파일 시각 + 최근 24시간에 생긴 파일 수
    - 이번 달·지난달 폴더 두 개와 그 안의 한 단계 아래 폴더까지 본다(달이 바뀌는 날도 맞게).
  - 통화 전사: `통화 녹음 → 전사` 폴더에서 가장 최근 txt 파일 시각 + 최근 24시간에 생긴 txt 수
  - 먼저 최근 7일 안에 바뀐 파일만 찾아서 빠르게 끝낸다. 7일 안에 하나도 없을 때만 폴더 전체를 훑는다(앱 스크립트 6분 제한 전에 멈춤).
- 파일 이름·내용·ID는 보내지 않는다. 회사 PC 텔레그램 프로그램은 건드리지 않는다.

## 홈 칸에서 보이는 것

| 줄 | 정상 | 주의 |
| --- | --- | --- |
| 텔레그램 수집 | `마지막 10. 21. 07:30` | 26시간 넘게 안 바뀌면 **조용함**(경고 아님. 업무방 수집이 매일 07:30 한 번이라 하루 + 여유 2시간, 메시지 없는 날이 있어서 — #999) |
| 통화 녹음 전사 | `마지막 10. 21. 08:05 · 24시간 3건` | 72시간 넘게 새 파일이 없으면 **조용함**(경고 아님. 통화 없는 주말은 넘기도록 72시간 — #999) |
| 두 줄 공통 | | 앱 스크립트 신호가 3시간 넘게 안 오면 **주의 · 점검 신호 끊김**(스크립트·트리거 문제). 두 줄의 유일한 경고 |
| 두 줄 공통 | | 아직 한 번도 신호가 없으면 `점검 신호 없음` |

홈 칸은 한 탭에서 10분에 한 번만 다시 읽는다. 바로 보고 싶으면 새로고침한다.

## 순서 (꼭 이 순서로)

먼저 커맨드센터가 **Web2 함수(`drive-summary`) 새 판 배포**를 마쳐야 한다(PR 본문의 1~2단계). 그 뒤에 아래를 한다.

### 1단계 — 새 앱 스크립트 프로젝트 만들기

1. 컴퓨터 브라우저에서 https://script.google.com 을 연다(통화 전사 스크립트와 **같은 Google 계정**).
2. 왼쪽 위 **[+ 새 프로젝트]**를 누른다.
3. 왼쪽 위 "제목 없는 프로젝트"를 눌러 이름을 `Web2 수집 점검 신호`로 바꾼다.
   - 기존 전사 스크립트에 섞지 않고 따로 두는 것을 추천한다(전사 쪽을 건드리지 않음).

### 2단계 — 코드 붙여넣기와 폴더 주소 두 칸 채우기

1. 저장소의 `docs/ops/collector-heartbeat.gs` 내용을 전부 복사한다.
2. 편집기의 `Code.gs`(또는 `코드.gs`) 안 내용을 모두 지우고 붙여 넣는다.
   - 예전 판을 이미 붙여 넣었다면 **전체를 새 코드로 바꾸고** 아래 두 칸만 다시 채운다. 비밀값(3단계)·트리거(6단계)는 그대로 두면 된다.
3. 맨 위 두 칸을 채운다. 넣을 글자는 커맨드센터가 채팅으로 알려 준다(직접 찾을 때 방법은 아래).
   - **① 텔레그램 메시지 폴더** — `'여기에_텔레그램_messages_폴더_주소_끝부분'` 자리.
     Drive에서 텔레그램 수집의 `messages` 폴더(안에 `2026-09`, `2026-10` 같은 월별 폴더가 있는 폴더)를 연다 → 주소창 `https://drive.google.com/drive/folders/` **뒤 글자**를 복사한다(`?` 뒤는 빼기).
   - **② 통화 전사 폴더** — `'여기에_통화_전사_폴더_주소_끝부분'` 자리.
     Drive에서 `통화 녹음` → `전사` 폴더를 연다 → 같은 방법으로 주소 뒤 글자를 복사한다.
   - 따옴표(`'`)는 그대로 두고 안쪽 글자만 바꾼다.
   - 이 글자는 저장소·문서에는 쓰지 않는다(이 스크립트 안에만).
4. 위쪽 **저장(디스크 모양)** 버튼을 누른다.

### 3단계 — 비밀값 만들기 (스크립트 속성)

1. 편집기 위쪽 함수 고르는 칸에서 `web2Heartbeat_makeSecret`을 고른다 → **[실행]**.
2. 처음이면 "승인 필요" 창이 뜬다 → **[권한 검토]** → 내 계정 선택 → "Google에서 확인하지 않은 앱" 화면이면 **[고급]** → **[Web2 수집 점검 신호(으)로 이동]** → **[허용]**.
   - 내가 만든 스크립트라 이 경고는 정상이다. Drive 보기·외부 주소 호출 권한을 묻는다.
3. 아래 실행 로그에 `비밀값을 만들어 스크립트 속성에 저장했습니다`가 나오면 정상.
4. 왼쪽 **톱니바퀴(프로젝트 설정)** → 맨 아래 **스크립트 속성**에 `COLLECTOR_HEARTBEAT_SECRET` 줄이 생겼는지 본다. 값은 다음 단계에서 한 번 복사한다. **이 값은 채팅·문서·저장소 어디에도 붙여 넣지 않는다.**

### 4단계 — Supabase에 같은 비밀값 등록

1. https://supabase.com/dashboard 에서 Web2 프로젝트를 연다.
2. 왼쪽 **Edge Functions** → **Secrets**(또는 "Manage secrets")로 간다.
3. **[Add new secret]**: 이름 `COLLECTOR_HEARTBEAT_SECRET`, 값은 3단계 스크립트 속성 값을 그대로 붙여 넣는다 → **[Save]**.
   - 함수를 다시 배포할 필요는 없다. 다음 신호부터 적용된다.

### 5단계 — 한 번 시험

1. 앱 스크립트 편집기로 돌아가 함수 칸에서 `web2Heartbeat_send`를 고른다 → **[실행]**.
2. 실행 로그에 아래 두 줄이 나오면 정상이다.
   ```
   transcript: 정상(200)
   telegram: 정상(200)
   ```
3. 다른 글이 나오면:
   - `비밀값 불일치(401)` → 3단계 값과 4단계 값이 같은지 다시 본다(앞뒤 빈칸 주의).
   - `칸을 코드 맨 위에 채우세요` → 2단계 3번.
   - `월별 폴더가 없습니다` → ① 칸에 `messages` 폴더가 아닌 다른 폴더(예: 그 위·아래 폴더)를 넣은 것. `2026-10` 같은 폴더가 바로 안에 보이는 폴더로 바꾼다.
   - `정상(200) (시간 제한으로 일부만 확인)` → 정상 동작. 폴더가 커서 6분 안에 다 못 본 것이니 커맨드센터에 알리면 된다.
   - `받는 입구 미배포(405)` → Web2 함수 새 판 배포가 아직이다. 커맨드센터에 알린다.
   - `Web2 읽기용 사본 폴더 없음(409)` → 커맨드센터에 알린다.
   - `읽기 실패 — ...` → 폴더 주소 글자가 맞는지, 이 계정이 그 폴더를 볼 수 있는지 본다.
4. Web2 홈을 새로고침하면 두 줄에 시각이 보인다.

### 6단계 — 1시간마다 자동 실행 켜기

1. 함수 칸에서 `web2Heartbeat_installHourlyTrigger`를 고른다 → **[실행]**.
2. 로그에 `1시간 트리거를 만들었습니다`가 나오면 끝.
3. 확인: 왼쪽 **시계 모양(트리거)** 메뉴에 `web2Heartbeat_send` · 시간 기반 · 1시간마다 한 줄이 있으면 정상.

## 멈추기·되돌리기

- **신호만 멈추기**: 함수 칸에서 `web2Heartbeat_removeTrigger` 실행(또는 트리거 메뉴에서 그 줄 삭제). 3시간 뒤 홈 칸에 "점검 신호 끊김"이 보인다.
- **입구 닫기**: Supabase Secrets에서 `COLLECTOR_HEARTBEAT_SECRET` 삭제 → 그 즉시 모든 신호가 거절된다(401). 다른 Web2 기능은 영향 없음.
- **비밀값 바꾸기**(새었다고 의심될 때): 스크립트 속성에서 `COLLECTOR_HEARTBEAT_SECRET` 줄 삭제 → 3단계 다시 → 4단계에서 같은 이름으로 새 값 저장.
- 프로젝트 자체가 필요 없으면 script.google.com 에서 `Web2 수집 점검 신호` 프로젝트를 휴지통으로 보낸다(전사 스크립트와 무관).

## 하는 일·하지 않는 일

- 하는 일: Drive 두 폴더에서 **가장 최근 시각과 24시간 개수**만 읽어 Web2에 보내기, 1시간마다.
- 하지 않는 일: 파일 내용·이름·ID 보내기, 파일 고치기·지우기, 텔레그램 프로그램·전사 스크립트 고치기.
- Web2 쪽은 받은 시각을 "Web2 읽기용 사본" 폴더의 숨은 속성에만 남긴다(데이터베이스·문서 내용은 바뀌지 않음).

## 점검 기록 2026-10-23 (OPS-수집점검원본맞추기) — 조사·제안만, 코드 변경 없음

### 1. 저장소 코드와 실제 Apps Script 맞춤 — 아직 못 함

- Drive에서 `Web2 수집 점검`(Apps Script 파일)은 찾았으나, Drive 연결 도구가 Apps Script 형식을 읽지 못한다(읽기 불가 응답, 내려받기 오류). **실제 코드는 읽지 못했다.** 추측으로 `collector-heartbeat.gs`를 고치지 않았다.
- 필요한 것: 사용자가 Apps Script 화면의 코드를 복사해 전달(폴더 주소·비밀값 자리는 `여기에_…` 그대로 두거나 지우고). 받은 뒤 저장소 `.gs`와 줄 단위로 비교해 다른 점을 맞춘다.
- 참고: 이 문서 1단계는 프로젝트 이름을 `Web2 수집 점검 신호`로 안내하지만 Drive에는 `Web2 수집 점검`으로 올라 있다. 이름만 다른지 별도 프로젝트인지도 복사본을 받을 때 함께 본다.

### 2. 텔레그램 `count`의 뜻과 제안

- 현재: `count`는 월별 폴더(이번 달·지난달, 한 단계 아래 포함)에서 **최근 24시간에 새로 생긴 파일 수**다. 텔레그램 메시지 수가 아니다(한 파일에 여러 메시지가 들어가거나 첨부·보조 파일이 생기면 다르다).
- 화면은 지금 텔레그램 건수를 그리지 않는다(`app/collection-status.js`의 `COUNT_KEYS`는 `call`만). 서버는 `count`를 받아 저장한다. **확인 전이므로 `COUNT_KEYS`에 `telegram`을 넣지 않는다.**
- 제안(수집기 쪽): 회사 PC 수집기가 실행 끝에 작은 상태 파일(예: `messages/collector-status.json`, 내용은 `run_at`·`message_count`·`ok`만, 메시지 내용·이름 없음)을 덮어쓴다. 앱 스크립트는 파일 수 대신 이 값을 읽어 보낸다.
  - 이렇게 하면 건수가 "그날 수집한 메시지 수"가 되고, 메시지가 0건인 날도 "수집기가 돌았다"는 기록이 남는다.
  - 수집기 코드는 이 저장소 밖(회사 PC)이라 사용자 판단이 필요하다. 건수를 화면에 보일지도 확인 후에 정한다.

### 3. 홈 화면 텔레그램 줄이 보는 신호

- 텔레그램 줄 = 앱 스크립트가 보낸 `telegram` 신호 하나(`last_at` = 월별 폴더 안 가장 최근 파일 시각, `reported_at` = Web2가 신호를 받은 시각).
  - `reported_at`이 3시간 넘게 오래됨 → **주의 · 점검 신호 끊김**(유일한 경고).
  - `last_at`이 26시간 넘게 오래됨 → **조용함**(경고 아님, 2026-10-22 사용자 결정, #999).
  - 텔레그램 폴더를 못 읽는 등 앱 스크립트의 텔레그램 읽기가 실패하면 그 신호는 안 보내지므로 3시간 뒤 "점검 신호 끊김"이 된다(통화 전사 줄과 따로 판단).

### 4. 남은 위험(#999)과 막는 방법 제안

- 위험: 텔레그램 수집기만 죽어도 앱 스크립트는 **예전 파일 시각**을 계속 보고하므로 `reported_at`은 신선하다 → 화면에는 "조용함"만 뜨고 경고가 없다. 메시지가 원래 없는 날과 구분이 안 된다.
- 제안 A(권장): 위 2번의 수집기 상태 파일을 쓰고, 앱 스크립트가 `last_at` 자리에 **수집기가 마지막으로 돌았던 시각**(`run_at`)을 보낸다. 수집기는 메시지가 0건이어도 매일 돈다 → `run_at`이 26시간 넘게 오래되면 진짜 수집기 문제이므로 그때만 경고로 올릴 수 있다. 메시지가 없는 날의 "조용함"은 그대로 유지된다(결정과 충돌 없음). 화면은 텔레그램 줄만 `run_at` 기준 경고로 바꾸면 되고, Edge 함수의 신호 형식은 그대로 쓴다.
- 제안 B(수집기 수정 없이): 경고 기준이 아닌 **참고 표시**로, 텔레그램 `last_at`이 예컨대 3일 넘게 안 바뀌면 "조용함 · 3일째"처럼 기간만 보여 준다. 경고는 아니지만 길게 멈춘 것을 알아챌 수 있다. 정확도는 A보다 낮다.
- 제안 C: 기준 변경 없이 사용자가 주 1회 홈의 텔레그램 마지막 시각만 눈으로 확인(운영 규칙).
- 결정 필요: A·B·C 중 무엇으로 갈지(A는 회사 PC 수집기 수정 필요). 정하기 전에는 코드를 바꾸지 않는다.

### 26시간 등 기준을 줄이는 제안 (적용하지 않음)

- 텔레그램 26시간 → 줄이지 않기를 권장. 이 기준은 `정상`과 `조용함` 표시만 가르고 경고에 쓰이지 않는다. 줄여도 경고는 늘지 않고 `조용함`만 더 자주 뜬다. 메시지가 없는 날(주말)이 있고 파일 시각은 마지막 메시지 시각이므로 정확히 줄일 방법이 없다. 경고로 올리려면 A안(수집기가 돈 시각을 상태 파일로 남김)이 먼저다. A안 뒤에는 "마지막 수집기 실행 시각 기준 26시간 → 25시간"까지 줄일 수 있다(매일 07:30 간격 24시간 + 실행 지연 1시간).
- 통화 72시간 → 줄이지 않기를 권장(경고가 아니며, 금요일 저녁부터 월요일 저녁까지가 72시간).
- 점검 신호 끊김 3시간 → 유지 권장. 정상 최대 간격이 약 2시간이라 2.5시간 이하로 줄이면 정상인데도 경고가 뜰 수 있다.
- Drive 사본 24시간 → 유지 권장. 20시간으로 줄이면 06:17 갱신이 한 번 늦어진 날 오전 중에 잠깐 경고가 뜬다(가장 긴 정상 간격 17시간 + GitHub 예약 지연). 얻는 것이 적다.
