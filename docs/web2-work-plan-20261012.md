## 목표와 유지할 원칙

업무 바구니에서 미처리 메모와 읽기 상태를 알아보고, 승인한 기록이 조직·프로젝트에 일관되게 나타나야 한다. 홈은 입력·오늘 일정·할 일·회의 후속을 중심으로 유지하며 제거한 두 항목을 되살리지 않는다. 연결된 메모는 사용자가 전체 목록이나 원문 열기로 직접 선택할 때 본다. 새로고침 때문에 원하지 않는 상세를 다시 열지 않는다.

날짜는 기존 기록의 occurred_at과 연결 메모의 occurred_at으로 계산한다. 오래된 메모를 오늘 연결하거나 요약만 수정해도 기록 날짜를 임의로 오늘로 바꾸지 않는다. 실제 일시·장소·주체·숫자·확정 여부를 보존하고 AI가 없는 사실을 만들지 않게 한다.

기존 업무 구조·개인 소유자 인증·원문 한 번 저장·Drive 첨부·바깥 AI·목적지5종을 유지한다. 다른 담당 조직만 제외한다는 기존 사용자 정정을 보존한다. 내부 team-ai, 별도 업무 DB/관리 화면, 원장 직접쓰기, 옛 조직 기록 이중쓰기를 만들지 않는다.

### 1b. BASKET-바구니사용정리 — AI 대상과 목록 디자인 정리

기능 흐름과 안내를 함께 바꾼다. 시각 정리만 해서 동작의 혼란을 남기지 않는다.

- 목록: 첫 줄 강조 + 원문 미리보기2~3줄 + 날짜/첨부 상태. 사진·파일만 있어도 식별할 제목/이름을 표시한다. 이미지의 작은 미리보기는 기존 인증된 접근 경로로 가능한 범위만 구현하며 Drive 공개 공유나 새 저장소를 만들지 않는다.
- 상단: 반복 제목·간격을 줄이고 맡기기를 주 동작, 결과 넣기를 다음 동작으로 구분한다. 확인·연결 주 버튼은 오른쪽 아래에 두고 하단바·키보드와 겹치지 않게 기존 구성과 터치·키보드 접근성을 재사용한다.
- 유효하고 실제 처리 가능한 AI 연결은 기본 선택한다. 사용자는 요약과 대상을 고치거나 선택을 해제한 뒤 확정한다. 미리보기만으로 저장하거나 외부 할 일을 만들지 않으며 미지원·불명 대상은 선택할 수 없게 설명한다.
- 결과 미리보기와 조직·프로젝트 요약 편집창에서 원문 전체를 펼쳐 비교한다. 다른 창으로 이동을 강제하지 않고 수정 내용·선택 상태를 보존한다.
- 바구니에서 홈의 기존 입력 기능을 재사용해 직접 글·첨부를 넣는다. 성공한 입력만 비우고 실패·응답 불명은 보존한다. 중복 ‘홈에서 입력’ 버튼은 제거하고 하단 홈 버튼은 유지한다.
- 일괄 맡기기: 최근4주·미분류·AI 허용 기준을 유지하되 실제 전달 대상 수와 사진 글자 미인식 상태를 안내한다. 보관·AI 제외를 자동으로 풀지 않는다.
- 상세 맡기기: 사용자가 직접 연 현재 메모를 대상으로 한다. 연결된 메모도 명시적으로 다시 맡길 수 있다. 저장하지 않은 원문 변경을 묵살하거나 저장된 원문과 다른 초안을 조용히 보내지 않는다. 명시적 단일 메모 전달은 일괄 기간 필터와 구분해 설명한다.
- 다시 받은 결과: 새 목적지는 연결 후보, 기존 목적지는 요약 수정 후보로 구분한다. 이미 연결된 목적지를 confirm RPC로 재확정하면 요약은 갱신되지 않으므로 기존 summary 수정 RPC를 재사용한다. 기존 연결 ID·정확한 이전 문자열/NULL을 읽고 사용자 승인 후 CAS로 수정한다. 기존 연결 삭제·원문 덮어쓰기·자동 채택은 하지 않는다. 충돌·부분 성공·통신 결과 불명은 각각 표시하고 자동 재전송하지 않는다.
- 사진 읽기 전에는 AI가 사진을 읽었다고 표시하지 않는다. 원문 발췌·사진 인식 글·사용자 승인 요약을 구분한다.
- 주요 파일: app/basket.js/css, basket-ai-handoff.js, basket-classification.js, basket-classification-ui.js, basket-link-records.js, 관련 테스트/로더. 안내 공통 문구 변경으로 Edge 사본 안내도 수정할 경우에만 별도 재배포 필요성을 보고한다.
- DB 변경 없는 기존 계약 재사용을 우선한다. 원문 버전/권한을 기존 계약으로 지킬 수 없는 요구는 임의 구현하지 않고 CC에 제한·대안을 보고한다.
- 구현 반영: #519 병합·Pages 게시 완료. 직접 입력·원문 펼침·기본 선택 후 최종 확정·기존 요약 CAS·실제 대상 수·카드 식별을 새 독립 소스로 검증했다. 새 실기기 확인은 마지막 묶음에 남는다.

### 1c. 수정·저장과 전체 안내 문구 정리 — 최신 사용성 요구

- 할 일·프로젝트·일정 수정은 정상 저장이 확인되면 해당 편집창만 자동으로 닫는다. 실패·충돌·응답 불명·일부 저장은 입력과 다음 확인 동작을 남긴다.
- 정상 성공 시 닫기는 현재도 구현돼 있다. 실제 보완은 일부 연결 저장 실패 때 초안을 잃는 경우, 저장 중 다른 항목·세션으로 바뀐 뒤 옛 응답이 새 창을 닫는 경우, 일정 이동 일부 성공 뒤 입력을 서버 값으로 덮는 경우다. 기존 저장 경로와 창을 재사용해 고친다.
- 프로젝트 수정 버튼도 기존 공통 하단 구성을 재사용해 저장 오른쪽·삭제 왼쪽·상태 문구를 함께 보이게 한다. 모바일·PC·긴 내용·키보드를 확인한다.
- 실제 열리는 웹2 화면의 중복·긴 설명과 개발 용어를 줄인다. 현재 할 일·결과·확인 방법을 중심으로 쓰되 권한·출처·응답 불명 안내는 유지한다. 폐기된 프로필·내부 AI 화면을 되살리지 않고 AI 복사 형식·업무 원문을 문구 정리로 바꾸지 않는다.
- 바구니와 프로젝트 파일이 겹치므로1b 검토 뒤 같은 파일의 동시 구현 없이 진행한다. 새 DB·인증·원장 구조는 만들지 않는다.

### 2. BASKET-사진글자 — 사진 내용을 분류 가능한 글로 만들기

기존 사용자 승인 범위를 유지한다. 10/9의 “첨부 링크만” 원칙은 이 OCR 범위만 변경한다.

- basket-files의 기존 drive.file 범위에서 앱이 만든 사진의 변환·읽기·정리가 가능한지 먼저 확인한다. 불가능하면 권한 범위를 넓히지 말고 중단·보고한다.
- Google Drive OCR을 사용한다. 변환용 임시 문서→글 추출→임시 문서 삭제. 외부 AI 서비스나 새 수집기를 추가하지 않는다.
- 새 사진 업로드 성공 후 글자를 읽고, 실패해도 업로드 성공은 유지한다. 기존 사진은 “글자 읽기”로 실행한다.
- 기존 첨부 JSON 배열에 선택적 인식 글·상태·상한·시도/정리 추적을 추가한다. 새 첨부 표를 만들지 않는다. 원문과 섞지 않고 접힌 ‘사진 속 글자’로 표시한다. 텍스트 상한은16,384 Unicode 문자/65,536 UTF-8 bytes이며 초과를 몰래 자르지 않는다.
- 원문 버전·첨부·현재 시도가 맞는 경우만 인식 결과를 저장하고, AI가 읽는 글이 바뀌면 DB 기준 새 버전으로 진행시킨다. 읽는 중·정리만 바뀌는 경우와 구분한다. 임시 문서 생성/정리 결과 불명은 자동 재생성이나 임의 파일 삭제로 처리하지 않는다.
- 복사 글·Drive 사본에도 인식 글을 포함한다. 메모100건·1MiB 상한에 포함하며 읽기 전/읽는 중/완료/글자 없음/실패를 구분한다.
- 지원 이미지 형식을 검증하며 PDF와 글자 없는 사진의 시각적 의미 분석은 이번 범위 밖이다. 임시 문서 삭제 실패도 기록한다.
- 주요 대상: 기존 첨부 migration/rollback/snapshot, basket-files, drive-summary, basket-upload.js, basket.js, basket-ai-handoff.js와 테스트.
- 준비 순서는 호환 DB 파일·검사·PR→서버·사본·기본 비활성 화면 파일·검사·PR이다. 두 준비 단계는 실제 운영 적용 대기 때문에 멈추지 않는다. 검토 후 main에 병합한 SQL로 사용자 dry-run/apply→basket-files/drive-summary 배포→원본 보존·인식·임시 문서 정리 실사용 확인→활성화 PR 순서로 진행한다. DB workflow의 main 고정과 기존 화면 호환성을 지키며 운영 확인 전에는 새 실행을 비활성으로 둔다.
- 현재 운영 source를 단계마다 새로 확인해 rollback ref로 고정한다. 인계 시 drive-summary 기준은 v7의39f1dfec…이며 배포 직전에 실제 현재 상태·source를 다시 대조한다. v6 e1d7483을 관성적으로 쓰지 않는다.
- 완료: 새 사진·기존 사진의 글자가 표시되고 AI에게 줄 글에 포함되어 승인 연결까지 완료.

### 3. BASKET-4b — 목적지별 하나씩 구현

1. 4b-1 자료실: 자료 연결/등록 처리, 기존 파일 경로 재사용, 중복·부분 실패·결과 불명 표시.
2. 4b-2 쓰기요청 후보: 후보 표시·검토까지. 기존 원장 쓰기 권한과 제출 정책을 임의 변경하지 않는다.
3. 4b-3 Google 할 일: 사용자가 선택한 뒤 외부 생성·연결·실제 결과 확인. 결과 불명일 때 자동으로 같은 할 일을 다시 생성하지 않는다.

자료는 같은 Drive 파일 ID로 메타정보만 등록하고 재업로드하지 않는다. 바구니 원본을 참조하는 자료 삭제에는 파일 보존을 먼저 적용한다. 후보는 기존 metadata에 확인·수정 결과만 두고 실제 원장에 쓰지 않는다. Google 생성은 외부 POST 전에 영구 요청·승인 내용 기록을 확정하고 결과를 같은 기록에 보존해 중복 전송을 막는다. 결과 불명은 기존 할 일 확인으로 처리한다. 작은 신규 INVOKER 함수와 기존 서버를 재사용하며 적용 전 실제 schema·트리거·직전 운영 소스 SHA를 확인한다.

Google 실행 제목은 [공식 Tasks 규격](https://developers.google.com/workspace/tasks/reference/rest/v1/tasks)에 맞춰1,024자까지로 검증하고 초과 제안은 수정하도록 한다. 날짜는 Google가 처리하는 날짜만이며 기한 시각을 보장하지 않는다. 일반 파서·요약의 기존2,000자 상한은 유지한다. 요청 결과는 메모당 최대20개를 보존하고 미해결 생성이 있으면 추가 전송을 멈춘다.

각 PR에 해당 kind의 AI 안내를 준비하되 실제 서버·DB·화면이 활성화되기 전에는 사용 가능한 종류로 안내하지 않는다. 목적지5종은 유지하되 미구현 종류가 실제로 처리된 것처럼 보이지 않게 한다. docs/basket-design.md7.2·7.3을 구체 지시서 작성 때 대조한다. 연결 확정·요약 채택·프로젝트 진행기록/현재 상태 갱신을 구분한다.

### 4. OPS-DB버튼 보완

#513으로 안전한 실패 종류/HTTP 번호와 dry-run 후 ‘적용 전 상태 유지’ 판정을 반영했다. #506은 파일별 postcheck로 dry-run을 올바르게 처리했지만 모든 migration에 대한 일반 문제가 해결됐다고 보지 않는다. 기존 rollback 정책과 함수 복원 제한을 임의로 넓히지 않는다. 사진글자 등 다음 DB 작업은 착수 시 해당 자료의 dry-run/apply/rollback 호환을 먼저 확인한다.

### 5. 테스트 안정화·중복 CI 점검

#512는 스와이프 대상 DOM이 바뀐 뒤 늦은 검사 콜백이 옛 요소를 읽는 경쟁을 재현해 검사 대상 조회를 같은 실행 안에서 하도록 준비했다. 경계25/25·인접50/50 등은 통과했지만 전체CI의 별도 홈 화면 순서 검사1건이 실패했다. baseline/head 각각30회에서는 재현되지 않았고 실패 후 저장된 DOM은 올바른 순서여서 늦은 순서 변경 가능성이 있다. 원인은 확정하지 않고 최초 실패와 한 번의 같은 SHA CI 재확인1,293/1,293 통과를 구분해 기록했다. #512는 `ebd065c3`로 병합됐으며 재확인 성공을 해당 홈 검사의 영구 해결로 쓰지 않는다.

개별 browser job9개의 고유 app spec17개가 전체 suite에도 포함된다. 실행 집합의 겹침이며 paths·조건·빠른 gate·branch 요구가 같다는 뜻은 아니다. 검사 목적과 실제 같은 SHA 실행 시간을 대조해 정리안을 낸다.

기존 '밀기' 검사 main20회 중9회 실패 기록과 #507 로컬 스와이프 실패를 함께 조사한다. 같은 검사를 가리키는지 확인 전 동일 원인으로 단정하지 않는다. 요청 도착 전 단언·측정 시점·픽셀/글꼴 간헐 차이·전체 약1,300개 회귀시간·20여 CI칸의 중복을 조사한다. 전체 CI 통과와 로컬 잔여 실패를 분리하며 기존 검사를 삭제/제외하거나 한도를 낮추는 것으로 해결하지 않는다.

### 6. ENV-8 — 날짜 우선 예외

기본 기능 순서는 위와 같지만 10/19 전 CI 실행환경 전환 대응은 기한이 있는 별도 항목이다. 바구니 작업을 모두 마칠 때까지 기다리지 않고 먼저 영향 범위·필수 조치를 조사한다. 변경이 필요하면 기한 전에 다음 신규 기능보다 우선하는 별도 PR로 처리한다. 작업을 동시에 같은 바구니 파일에 적용하지 않는다.

#511은 Cloudflare 외32개 job을 Ubuntu24.04로 고정했다. 공식 전환 기간은10/19 시작~11/19 완료이며 OS 계열 고정 뒤에도 주간 이미지 갱신은 계속된다. Ubuntu26 지원 완료로 기록하지 않는다.

실제 Pages artifact에서 개발 폴더도 게시되는 것을 확인했다. 공개 업무 페이지와 앱의 의존성을 보존하는 제외 설정·실제 빌드 대조를 준비한다. 로더의 실제 android-app/windows-app 경로, 최소 workflow 권한, 죽은 저장소 예외, Actions Node24 런타임 호환 버전, smoke의 정확한 모듈·캐시 계약을 순차 보완한다. 애플리케이션 Node 버전과 Action 런타임은 구분한다.

Cloudflare workflow 수정은 병합 때 운영 배포를 유발하므로 별도 검토와 복구 자료가 필요하다. 옛 배포 점검 URL은 현재 동적 처리되어 중복 수정하지 않는다. Pages 중복 빌드 추정만으로 게시 workflow를 없애지 않는다.

### 7. 텔레그램 연계 1단계 — 기반 기능과 운영 점검 뒤 제안

1단계 개발 승인과 “기존 작업 보고를 먼저 기다릴 것”을 유지한다. 새 착수 위치는 바구니 사용/사진/4b 기반 및 운영·CI 정비 뒤로 제안한다. 별도 수집기 자료의 읽기 전용 조사는 대기 중 가능하다.

- 기존9방 수집 결과·원문 저장을 재사용한다. 저장 구조는 확인됐지만 수집 코드·실행환경·주기·연결 권한·AI 호출 체계는 추가 확인이 필요하다.
- AI 추출→기존 조직/프로젝트/할 일/일정/회의 대조→바구니 후보→사용자 승인→기존 데이터 반영.
- 신규/갱신/중복/충돌/제외를 구분한다. 논의/예정/확정 상태와 출처·원문을 보존하고 없는 날짜·담당자·결정을 만들지 않는다.
- 약칭을 고려하되 불명확한 조직·프로젝트를 자동 생성하지 않는다.

## 공통 검증·운영·완료 조건

각 작업은 별도 구현 세션에서 최신main→작업branch→PR→실제diff/독립 검토→최종SHA 검사 확인→사용자가 이미 맡긴 범위의 CC 병합 순서다. CC는 코드 수정하지 않는다. 바구니 파일을 공유하는1a·1b·사진글자·4b는 순차 진행하며 migration도 하나씩 적용한다. 이미 전달한1a 지시서의 구현이 시작됐다면 같은branch/PR에서 이어가고 중복 PR을 만들지 않는다.

- Node전체,390/1280px·키보드/터치·정상콘솔0, 직접기능과 인접회귀·최종SHA 자동CI·전체Chromium.
- DB 변경은 격리PostgreSQL migration/rollback/RLS·기존호환·snapshot·migration기록 검증.
- Edge 변경은 Deno check/lint·functions-only 격리bundle, 배포workflow가 함수폴더밖import를 필요로 하지 않음을 확인.
- 캐시 연쇄를index.html까지 맞추고 기대test·smoke를 갱신. 기존검사 삭제/약화 없음.
- 자동CI/로컬실행/clean main재현/사용자폰확인을 분리해12항목 PR댓글로 보고.
- 코드 구현 세션은 운영 접속·DB 적용·Edge 배포·workflow 수동 실행/승인·merge하지 않는다.
- DB/Edge 적용은 무엇이바뀌나·잘못되면·되돌리는방법3줄과 실제검토한복구자료를 준비한다. 현재 연결 도구에는 새 운영 workflow 실행·production 승인 기능이 없고 운영 키도 없으므로 실제 버튼은 마지막에 사용자에게 묶어 안내한다. 운영 토큰 등록·새 인증 우회는 제안하지 않는다. 승인형DBworkflow가main을checkout하므로 미병합migration PR을 먼저 적용하도록 안내하지 않는다.
- 폰확인과 운영결과는 문서PR로 기록하고 기존 위임 범위에서 검토 후 병합한다. 준비·코드 병합·운영 DB/Edge 적용·기능 활성화·실기기 확인은 따로 기록하며 완료를 추정하지 않는다.
