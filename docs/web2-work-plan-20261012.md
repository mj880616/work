## 목표와 유지할 원칙

업무 바구니에서 미처리 메모와 읽기 상태를 알아보고, 승인한 기록이 조직·프로젝트·홈에 일관되게 나타나야 한다. 연결된 메모는 사용자가 전체 목록이나 원문 열기로 직접 선택할 때 본다. 새로고침 때문에 원하지 않는 상세를 다시 열지 않는다.

날짜는 기존 기록의 occurred_at과 연결 메모의 occurred_at으로 계산한다. 오래된 메모를 오늘 연결하거나 요약만 수정해도 기록 날짜를 임의로 오늘로 바꾸지 않는다. 실제 일시·장소·주체·숫자·확정 여부를 보존하고 AI가 없는 사실을 만들지 않게 한다.

기존 업무 구조·개인 소유자 인증·원문 한 번 저장·Drive 첨부·바깥 AI·목적지5종을 유지한다. 다른 담당 조직만 제외한다는 기존 사용자 정정을 보존한다. 내부 team-ai, 별도 업무 DB/관리 화면, 원장 직접쓰기, 옛 조직 기록 이중쓰기를 만들지 않는다.

### 1b. BASKET-바구니사용정리 — AI 대상과 목록 디자인 정리

기능 흐름과 안내를 함께 바꾼다. 시각 정리만 해서 동작의 혼란을 남기지 않는다.

- 목록: 첫 줄 강조 + 원문 미리보기2~3줄 + 날짜/첨부 상태. 사진·파일만 있어도 식별할 제목/이름을 표시한다. 이미지의 작은 미리보기는 기존 인증된 접근 경로로 가능한 범위만 구현하며 Drive 공개 공유나 새 저장소를 만들지 않는다.
- 상단: 반복 제목·간격을 줄이고 맡기기를 주 동작, 결과 넣기를 다음 동작으로 구분한다. 터치·키보드 접근성과 기존 스타일을 재사용한다.
- 일괄 맡기기: 최근4주·미분류·AI 허용 기준을 유지하되 실제 전달 대상 수와 사진 글자 미인식 상태를 안내한다. 보관·AI 제외를 자동으로 풀지 않는다.
- 상세 맡기기: 사용자가 직접 연 현재 메모를 대상으로 한다. 연결된 메모도 명시적으로 다시 맡길 수 있다. 저장하지 않은 원문 변경을 묵살하거나 저장된 원문과 다른 초안을 조용히 보내지 않는다. 명시적 단일 메모 전달은 일괄 기간 필터와 구분해 설명한다.
- 다시 받은 결과: 새 목적지는 연결 후보, 기존 목적지는 요약 수정 후보로 구분한다. 이미 연결된 목적지를 confirm RPC로 재확정하면 요약은 갱신되지 않으므로 기존 summary 수정 RPC를 재사용한다. 기존 연결 ID·정확한 이전 문자열/NULL을 읽고 사용자 승인 후 CAS로 수정한다. 기존 연결 삭제·원문 덮어쓰기·자동 채택은 하지 않는다. 충돌·부분 성공·통신 결과 불명은 각각 표시하고 자동 재전송하지 않는다.
- 사진 읽기 전에는 AI가 사진을 읽었다고 표시하지 않는다. 원문 발췌·사진 인식 글·사용자 승인 요약을 구분한다.
- 주요 파일: app/basket.js/css, basket-ai-handoff.js, basket-classification.js, basket-classification-ui.js, basket-link-records.js, 관련 테스트/로더. 안내 공통 문구 변경으로 Edge 사본 안내도 수정할 경우에만 별도 재배포 필요성을 보고한다.
- DB 변경 없는 기존 계약 재사용을 우선한다. 원문 버전/권한을 기존 계약으로 지킬 수 없는 요구는 임의 구현하지 않고 CC에 제한·대안을 보고한다.
- 완료: 사용자가 대상과 사진 읽기 상태를 알고 맡기며, 연결된 메모의 재요약을 승인해 고칠 수 있음. 목록은 긴 글·사진·파일 메모를 빠르게 구분할 수 있음.

### 2. BASKET-사진글자 — 사진 내용을 분류 가능한 글로 만들기

기존 사용자 승인 범위를 유지한다. 10/9의 “첨부 링크만” 원칙은 이 OCR 범위만 변경한다.

- basket-files의 기존 drive.file 범위에서 앱이 만든 사진의 변환·읽기·정리가 가능한지 먼저 확인한다. 불가능하면 권한 범위를 넓히지 말고 중단·보고한다.
- Google Drive OCR을 사용한다. 변환용 임시 문서→글 추출→임시 문서 삭제. 외부 AI 서비스나 새 수집기를 추가하지 않는다.
- 새 사진 업로드 성공 후 글자를 읽고, 실패해도 업로드 성공은 유지한다. 기존 사진은 “글자 읽기”로 실행한다.
- 기존 첨부 구조에 인식 글·상태·상한을 추가한다. 메모 원문과 섞지 않고 접힌 “사진 속 글자”로 표시한다.
- 복사 글·Drive 사본에도 인식 글을 포함한다. 메모100건·1MiB 상한에 포함하며 읽기 전/읽는 중/완료/글자 없음/실패를 구분한다.
- 지원 이미지 형식을 검증하며 PDF와 글자 없는 사진의 시각적 의미 분석은 이번 범위 밖이다. 임시 문서 삭제 실패도 기록한다.
- 주요 대상: 기존 첨부 migration/rollback/snapshot, basket-files, drive-summary, basket-upload.js, basket.js, basket-ai-handoff.js와 테스트.
- 적용 순서는 PR 구성·DB workflow의 main 고정·기존 화면 호환성을 대조해 확정한다. 기본은 호환 DB 준비 PR merge→사용자 dry-run/apply→사용자 basket-files/drive-summary 배포→새 화면 반영/확인이다. 화면은 서버/DB 준비 전 새 기능을 사용하지 않게 분리한다.
- 현재 운영 source를 단계마다 새로 확인해 rollback ref로 고정한다. 다음 drive-summary 배포의 직전 소스는 현재 v7의39f1dfec…이며 v6 e1d7483을 관성적으로 쓰지 않는다.
- 완료: 새 사진·기존 사진의 글자가 표시되고 AI에게 줄 글에 포함되어 승인 연결까지 완료.

기본 기능 순서는 위와 같지만 10/19 전 CI 실행환경 전환 대응은 기한이 있는 별도 항목이다. 바구니 작업을 모두 마칠 때까지 기다리지 않고 먼저 영향 범위·필수 조치를 조사한다. 변경이 필요하면 기한 전에 다음 신규 기능보다 우선하는 별도 PR로 처리한다. 작업을 동시에 같은 바구니 파일에 적용하지 않는다.

원장 ENV-8의 공개 배포 범위·로더 제외 경로·workflow 읽기권한·Actions Node 경고·배포 도구 버전/옛 smoke 문자열·Pages 중복 빌드·없는 파일 예외·Ubuntu 실행환경을 대조한다. 원장의 경고를 최신 적용 상태로 추정하지 않고 실제 코드/CI 공지·결과로 확인한다.

### 7. 텔레그램 연계 1단계 — 기반 기능과 운영 점검 뒤 제안

1단계 개발 승인과 “기존 작업 보고를 먼저 기다릴 것”을 유지한다. 새 착수 위치는 바구니 사용/사진/4b 기반 및 운영·CI 정비 뒤로 제안한다. 별도 수집기 자료의 읽기 전용 조사는 대기 중 가능하다.

- 기존9방 수집 결과·원문 저장을 재사용한다. 저장 구조는 확인됐지만 수집 코드·실행환경·주기·연결 권한·AI 호출 체계는 추가 확인이 필요하다.
- AI 추출→기존 조직/프로젝트/할 일/일정/회의 대조→바구니 후보→사용자 승인→기존 데이터 반영.
- 신규/갱신/중복/충돌/제외를 구분한다. 논의/예정/확정 상태와 출처·원문을 보존하고 없는 날짜·담당자·결정을 만들지 않는다.
- 약칭을 고려하되 불명확한 조직·프로젝트를 자동 생성하지 않는다.
- 후보 수신 전용의 제한된 인증 경로를 설계한다. 외부 자동화에 불필요한 관리자·직접 DB 쓰기 권한을 주지 않는다.
- 메시지/수정판 중복과 사건 후속을 구분하고 반영 전후·결과·재시도/불명 상태를 추적한다.
- 기존 원장 writer·쓰기요청 정책을 유지한다. 새 업무 DB·관리 화면·인증·수집 프로그램을 중복 구축하지 않는다.
- 모델/전송 범위/보관정책/처리량을 확인해 월간 비용과 증가 시 비용을 산정한다. 미확인 수집환경을 임의 가정해 개발 완료를 약속하지 않는다.
- 자동 반영 2단계는 운영 정확성을 검증한 뒤 별도 승인한다. 최초에는 모든 실제 업무 반영을 사용자가 승인한다.

## 공통 검증·운영·완료 조건

각 작업은 별도 구현 세션에서 최신main→작업branch→PR→실제diff/독립 검토→사용자merge 승인 순서다. CC는 코드 수정하지 않는다. 바구니 파일을 공유하는1a·1b·사진글자·4b는 순차 진행하며 migration도 하나씩 적용한다. 이미 전달한1a 지시서의 구현이 시작됐다면 같은branch/PR에서 이어가고 중복 PR을 만들지 않는다.

- Node전체,390/1280px·키보드/터치·정상콘솔0, 직접기능과 인접회귀·최종SHA 자동CI·전체Chromium.
- DB 변경은 격리PostgreSQL migration/rollback/RLS·기존호환·snapshot·migration기록 검증.
- Edge 변경은 Deno check/lint·functions-only 격리bundle, 배포workflow가 함수폴더밖import를 필요로 하지 않음을 확인.
- 캐시 연쇄를index.html까지 맞추고 기대test·smoke를 갱신. 기존검사 삭제/약화 없음.
- 자동CI/로컬실행/clean main재현/사용자폰확인을 분리해12항목 PR댓글로 보고.
- 코드 구현 세션은 운영 접속·DB 적용·Edge 배포·workflow 수동 실행/승인·merge하지 않는다.
- DB/Edge 적용은 무엇이바뀌나·잘못되면·되돌리는방법3줄과 실제검토한복구자료를 제시한뒤 사용자만 실행/승인한다. 승인형DBworkflow가main을checkout하므로 미병합migration PR을 먼저 적용하도록 안내하지 않는다.
- 폰확인과 운영결과를 문서PR로 기록하고 사용자 별도“머지” 뒤 병합한다. 이번계획 제출을 코드 구현·배포·문서merge 완료로 취급하지 않는다.
